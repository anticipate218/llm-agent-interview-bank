# Agent 应用开发岗 · 模拟笔试卷 · 参考答案与解析

## 一、单选题（每题 2 分，共 30 分）

**1. D**

<sub>AGT-PROTO-004</sub>　**结论**：Host 管理多个 Client，每个 Client 只与一个 Server 通信（一对一）。

- Host 是用户直接使用的 AI 应用（桌面助手、IDE、自研 Agent），负责调用模型、汇总上下文、执行权限策略与用户授权；
- Client 是 Host 内部的连接器，只与一个 Server 通信：在每个请求中附带协议版本与客户端能力，收发消息、管理订阅，并守住不同 Server 之间的安全边界；
- Server 对外提供 Tools、Resources、Prompts，可以是本地子进程，也可以是远程服务。

逐项点评：
- A 错：把 Host 和 Client 混为一谈，这是面试中最常见的口误。
- B 错：Client 与 Server 是一对一的；要连多个 Server，Host 就创建多个 Client。
- C 错：驱动对话、调用模型的是 Host。Server 只对外提供能力，工具要不要用、怎么用，由 Host 交给模型决定。旧版规范中，Server 需要模型能力时可以通过 Sampling 请 Host 代为调用；2026-07-28 版已将 Sampling 标为弃用，建议这类 Server 直接对接模型提供商的 API，但那只是 Server 内部的实现细节，不改变「由 Host 侧的模型决定调用哪些工具」这一分工。

注意：2025-11-25 及更早的规范把 Client 与 Server 之间描述为一对一的「有状态会话」；2026-07-28 版改为无状态协议，移除了 initialize 握手和协议级会话，但 Host、Client、Server 的角色划分和一对一关系不变。

**2. A**

<sub>SEC-AGENT-021</sub>　**结论**：常用的四级划分与默认策略：
- **L0 只读、无副作用**（查天气、检索知识库）：自动执行；
- **L1 内部可逆写**（写草稿、建分支、写测试环境）：自动执行，记审计，可撤销；
- **L2 对外可见或难以撤回**（发邮件、发消息、合并 PR、改线上配置）：目标在白名单内自动执行，否则请用户确认；
- **L3 不可逆或涉及资金、权限**（转账、删库、改权限、生产发布）：人工审批，必要时双人复核并设限额。

A 属于 L2，策略正确。另外，不可信内容进入上下文之后，同一个动作还可以自动升一级。

- B 错：测试环境建分支是内部可逆写，每次都审批只会制造审批疲劳。
- C 错：改生产权限属于 L3，模型的自评置信度不是控制手段，必须人工审批。
- D 错：污点升级针对的是有副作用、能对外的动作；只读检索本身不该被拦下，真正需要把关的是之后的外发与写操作。

**3. A**

<sub>AGT-FW-044</sub>　**结论**：两者的出发点不同，但能力已经大量重叠。

LlamaIndex 官方文档把自己描述为「在你的数据之上构建 LLM 驱动的 Agent 的 Python 工具包」，最早以 RAG 闻名：数据连接器、索引与向量存储、查询引擎与聊天引擎是它的招牌抽象；如今也提供 Agent 与工具，以及支持分支、重试和人工审核的事件驱动 Workflows。LangChain 更偏通用：统一的模型接口、工具、Agent 循环与中间件，编排与持久化交给 LangGraph。

- B 错：LlamaIndex 早已支持 Agent 与工具。
- C 错：两者是不同团队维护的独立项目。
- D 错：二者可以组合，例如把 LlamaIndex 的查询引擎包装成一个工具，交给 LangChain 或 LangGraph 中的 Agent 调用。

选型建议：以「接数据、做检索与问答」为主的应用，LlamaIndex 的数据抽象更顺手；以复杂流程编排、长时间运行和人审为主的 Agent，LangGraph 更合适。两者都不必绑定：检索层与编排层可以各用所长。

**5. D**

<sub>RAG-EMB-020</sub>　**结论**：MRL（Kusupati 等, 2022）在训练时把多个前缀长度（如 64、128、256……）上的损失加在一起，迫使信息「由粗到细」地排在前面：前 64 维就能粗略表达语义，越往后补充越多细节。所以截取前缀仍然是一个好的低维表示。

- A 错：MRL 只约束前缀维度的检索效果，不约束范数。完整向量的范数为 1，但它前 256 维的平方和小于 1，且各向量截断后的范数各不相同；不重新归一化，内积就不等于余弦，排序会受范数影响。
- B 错：信息集中在前面，截取前缀才是正确用法。
- C 错：普通模型没有经过这种训练，信息分散在所有维度上，随意截断会显著掉点。

OpenAI text-embedding-3 系列的 `dimensions` 参数，就是这种截断思路的产品化。

<sub>SEC-INJ-033</sub>　**结论**：这种攻击利用的是「人看到的图」与「模型看到的图」不一致：攻击者针对具体的缩放算法（最近邻、双线性、双三次插值）精心构造像素，缩小之后才显现文字。

- D 错：文字是由重采样过程「合成」出来的，转成灰度不能消除。

**9. D**

<sub>ENG-PERF-005</sub>　**结论**：缓存只能命中「之前的请求在相同位置写入过」的前缀；断点放在每次都不同的内容之后，就只有写入、没有命中。

本例中，自动断点落在请求末尾，缓存键覆盖了「系统提示词 + 本次检索结果 + 本次问题」，下一个请求的这段内容必然不同，永远读不到；而所有请求共享的 6K 系统提示词上又没有断点，也无法命中。于是每个请求都为整段输入多付 25% 的写入溢价，这正是「自动缓存遇到唯一尾部」的典型症状：每个请求都有 `cache_creation_input_tokens`，`cache_read_input_tokens` 却始终为 0 或很小。

**改法**：在系统提示词的最后一个块上显式放置断点（共享部分），检索结果和问题放在断点之后；多轮对话则再在历史末尾加断点。改完后用 usage 字段确认：第二个请求起，约 6K token 应出现在命中字段中。

- A 错：命中价远低于基础价（约 0.1 倍），问题在于根本没有命中。
- B 错：6K token 远超最小可缓存长度（视模型从 512 到 4096 token 不等）；问题不在长度而在断点位置，把每次都不同的检索结果放进前缀只会更糟。
- C 错：Prompt Caching 缓存的是输入前缀，输出不会写入缓存，也不按写入价计费。

**10. C**

<sub>ENG-OBS-017</sub>　**结论**：「改标签即发布、移回标签即回滚」很方便，但生效时间受客户端缓存影响。

Langfuse 的 SDK 默认缓存提示词 60 秒，过期后采用「先返回旧值、后台刷新」的方式（stale-while-revalidate），不让业务请求等待网络。所以标签回滚后，每个实例大约要再过一个 TTL，并且在下一次取用触发后台刷新之后，才会真正切回；请求很少的实例可能更久。官方文档也提到，回滚大约在一个 TTL 内生效，需要更严格的时限时可以按次调小 TTL，或者自己提供主动刷新缓存的机制。

- A 错：忽略了客户端缓存：服务端的标签确实立即变了，但实例在缓存过期前不会去拉新版本。
- B 错：缓存会过期并在后台刷新，回滚会生效，只是有延迟，不需要重启服务。
- D 错：已经生成的回答（以及已经执行的操作）不会被撤回，需要另行处理。

**启示**：提示词变更同样要走评测门禁和灰度；事故时，除了回滚标签，还要有能秒级生效的降级或急停开关；每条 trace 要记录实际使用的提示词版本，才能确认回滚何时真正生效。

**11. B**

<sub>AGT-HARNESS-039</sub>　**结论**：钩子里运行的结构测试是在 Agent 行动之后检查（反馈），并且是确定性的程序（计算型）。Böckeler 文章中的例表正是这样归类的。

- A 错：编码约定在 Agent 动手之前提供引导，属于前馈；但它要靠模型理解和遵守，属于**推断型**。
- C 错：评审发生在改动之后，属于**反馈**；它依赖模型的判断，属于推断型。
- D 错：类型检查在修改之后报错，属于**反馈**；它是确定性的程序，属于**计算型**。

文章还指出两点：只有反馈，Agent 会反复犯同样的错误；只有前馈，你不知道规则到底有没有生效，所以两者都需要。计算型检查快、便宜、结果确定，可以在每次修改后都运行；推断型检查更慢、更贵、也不确定，但能做语义层面的判断。把修复建议写进 lint 报错信息，让 Agent 读到就能改，被称为一种「正面的提示注入」。

**12. B**

<sub>RAG-BASE-003</sub>　**结论**：资料量小、更新少、请求量低、又需要通读全文时，长上下文 + Prompt Caching 往往是更简单的起点。Anthropic 在介绍 Contextual Retrieval 的文章（2024）中给出的经验线是：知识库小于约 20 万 token（约 500 页）时，可以考虑直接整体放进提示词。

- 15 万 token 在不少长上下文模型（20 万 token 及以上窗口）的容量之内；Prompt Caching 让重复的手册前缀按较低价格计费、首 token 也更快；日均几十次请求，总成本可控。
- 问题需要跨章节综合，RAG 只取少数几块，容易漏掉分散在各章的信息。

逐项点评：
- A 错：日均几十次请求、又有 Prompt Caching 时，长上下文的总成本并不高；跨章节综合的问题上它也未必比 RAG 差。规模小、请求少时未必需要 RAG，应该用评测集说话，效果和成本都不达标时再上 RAG。
- C 错：继续预训练成本高，新知识学不牢，也无法给出出处。
- D 错：只取 3 段很难覆盖跨章节的信息，恰恰不适合综合类问题。

延伸：如果资料涨到几千页，或请求量涨到每天几十万次，长上下文的成本和延迟会很快变得不可接受，那时再上 RAG。

**13. A**

<sub>SEC-REL-003</sub>　**结论**：论文的直观结论是，预训练后的幻觉率至少约等于「只在训练数据中出现过一次的事实」所占的比例。例如若 20% 的生日事实在训练数据中只出现过一次，基础模型在这类问题上预计至少有约 20% 会出错。

**直觉**：只见过一次的事实，在统计上与从未见过的事实很难区分（这与估计「未见过的概率质量」的 Good-Turing 方法同源）。生成一个正确答案比判断一个答案对不对更难：如果模型连「是否有效」都分不清，生成时必然会产出一部分看似合理、实则错误的内容。

- B 错：论文特别强调，即使训练数据完全没有错误，这个下界依然存在；数据中的错误只会让情况更糟。
- C、D 错：与论文给出的下界无关。

论文的第二个论点是：后训练之后幻觉仍然顽固，是因为主流评测按「答对得分、答错与不答都不得分」计分，奖励的是猜测而不是承认不确定。

**14. D**

<sub>AGT-PROTO-015</sub>　**结论**：双方只能使用对方在握手时声明过的能力。Server 声明了 `resources`，但没有声明 `"subscribe": true`，说明它不支持订阅单个资源的变更，客户端就不应调用 `resources/subscribe`。

- A 合规：声明了 tools 能力，可以列工具。
- B 合规：声明了 `listChanged: true`，Server 会在工具增减时发通知，客户端收到后重新拉取列表是标准做法。
- C 合规：声明了 resources 能力，`resources/list` 与 `resources/read` 都可以用。

能力是逐项细分的：resources 下还有 `subscribe`（是否支持订阅）与 `listChanged`（是否发送列表变更通知）两个子能力。同理，Server 没声明 prompts 就不要调 `prompts/list`，否则通常会得到 -32601（方法不存在）。

**新版变化（2026-07-28）**：能力协商不再依赖 initialize 握手。Server 的能力通过 `server/discover` 的结果公布（客户端也可以不调用它，直接发请求）；客户端的能力随每个请求放在 `_meta` 的 `io.modelcontextprotocol/clientCapabilities` 中，处理某个请求需要客户端未声明的能力时，Server 返回 `MissingRequiredClientCapabilityError`。`resources/subscribe` 被 `subscriptions/listen` 取代：客户端在 `resourceSubscriptions` 中列出要关注的资源 URI，Server 在确认消息里只回显它同意支持的订阅类型，客户端应核对并妥善处理未被支持的部分。`resources` 下的 `subscribe` 与 `listChanged` 子能力仍然保留。

**15. C**

<sub>ENG-OBS-030</sub>　**结论**：长窗口保证「消耗的预算足够多、值得叫醒人」，短窗口保证「问题此刻仍在发生」，从而减少误报。

只用 1 小时窗口时，故障在 10 分钟内就修好了，但接下来的 50 分钟里，1 小时窗口的燃烧率仍然很高，告警会一直响。要求 5 分钟窗口也超标，故障一结束，短窗口的燃烧率很快回落，告警随之停止。SRE Workbook 给出的经验是短窗口取长窗口的 1/12 左右：1 小时配 5 分钟，6 小时配 30 分钟，3 天配 6 小时。

- A 错：触发速度主要由长窗口和阈值决定；短窗口虽然更快越过阈值，但「同时满足」的条件只会让触发不早于原来。
- B 错：多算一个窗口反而增加计算量。
- D 错：恰恰相反，要求两个窗口同时超标，短暂的尖峰（短窗口高、长窗口不高）不会触发告警。

## 二、多选题（每题 3 分，共 18 分）

**16. BCE**

<sub>AGT-MULTI-021</sub>　**结论**：一份合格的简报包括目标、边界、约束、输出格式、预算和已知信息。Anthropic 的经验是：早期只给子 Agent 一句简短指令，结果子 Agent 互相重复、理解跑偏；后来要求每个子 Agent 都有明确的目标、输出格式、可用工具与信息源的指引，以及清晰的任务边界。

- A 错：子 Agent 需要的是已确认的结论（写进「已知信息」），而不是别人的推理过程。
- B 对：缺了目标，子 Agent 只能猜意图；一句整体目标能帮它判断什么重要。
- C 对：写清「不负责什么」是防止重复劳动的第一道防线。
- D 错：把全部历史塞给子 Agent，成本翻倍、注意力被稀释，上下文隔离也白做了。
- E 对：没有格式，结果无法合并；没有预算，费用和时延会失控。

另外两项常被漏掉：全局约束（如「只用公开资料」）要原文写入；验收标准要在派活时就写进简报，而不是事后补。

**17. ABD**

<sub>ENG-PERF-016</sub>　**结论**：A、B、D 正确。判断标准只有一个：**有没有人在等结果**，与调用量大不大无关。

- A 对：历史文档的批量摘要是典型的离线任务。
- B 对：每晚的离线分类与标签抽取可以等几个小时，量大、对时延不敏感，改用批处理可以省下约一半的费用。
- C 错：代码补全要在几百毫秒内返回，调用量再大也不能走批处理。
- D 对：离线回归评测没有人在线等结果，正适合批处理，还可以叠加 Prompt Caching。
- E 错：用户在实时等待，批处理最长可能 24 小时才返回，完全不可用；在线场景的成本压力要靠缓存、路由、压缩输出等手段解决。

使用批处理的注意事项：
- 结果异步返回、顺序不固定，要用请求的自定义 ID 对应结果，并处理失败与过期的请求（重新提交）；

**32.** 显式；隐式

<sub>SEC-REL-028</sub>　- **显式标识**：例如在 AI 生成的文本开头或结尾加提示文字、在生成的音频里加语音提示、在图片和视频上加角标。
- **隐式标识**：例如在文件元数据中写入「生成合成内容」属性、服务提供者名称或编码、内容编号等信息，也可以使用数字水印。

办法由国家网信办、工信部、公安部、广电总局联合发布，配套的强制性国家标准《网络安全技术 人工智能生成合成内容标识方法》（GB 45438—2025）同步实施。传播平台要核验元数据中的隐式标识，并提醒用户主动声明发布的内容是否由 AI 生成。

对大模型应用的工程含义：生成内容的输出链路要能统一加上显式提示、写入元数据，并且这些标识不能在后续的格式转换、压缩、转发中被意外丢掉。

**33.** 目标竞争 / 竞争目标 / 目标冲突 / competing objectives；泛化不匹配 / 不匹配的泛化 / mismatched generalization

<sub>SEC-INJ-011</sub>　- **目标竞争**（competing objectives）：例如要求模型以肯定语开头、禁止使用拒绝措辞、扮演一个「没有限制」的角色。模型被训练成既要遵循指令又要安全，攻击者制造两者冲突的局面，让前者胜出。
- **泛化不匹配**（mismatched generalization）：例如 base64 编码、密码、低资源语言。预训练让模型具备了理解这些形式的能力，安全训练的数据却没有覆盖，安全行为没有泛化过去。

论文据此提出「安全能力要与模型能力相当」（safety-capability parity）：模型越强，能理解的输入形式越多，安全机制也要同样精细，单靠扩大规模解决不了这两类问题。

**34.** M^{-l} / M^(-l) / 1/M^l / $M^{-l}$ / M的-l次方；3906 / 约3906 / 3,906 / 3906.25

<sub>RAG-EMB-037</sub>　- 层号 $\ge l$ 等价于 $-\ln U\cdot m_L\ge l$，即 $-\ln U\ge l\ln M$，即 $U\le M^{-l}$，概率为 $M^{-l}$。
- $M=16$、$l=2$：$16^{-2}=1/256$，$10^6/256\approx3906$ 个。

**含义**：每往上一层，节点数约缩小为 $1/M$：第 1 层及以上约 62,500 个，第 2 层及以上约 3,906 个，第 3 层及以上约 244 个……总层数约为 $\log_M N$（本例约 5 层）。这种结构类似跳表：高层节点稀疏、边跨度大，查询先在高层快速逼近目标区域，再逐层下降，访问的节点数随规模近似对数增长。

## 五、代码输出题（每题 3 分，共 3 分）

**35.** 输出：

```text
notification: notifications/progress
export tool error
refund needs input: ['confirm']
search protocol error -32602
{}
```

<sub>AGT-PROTO-014</sub>　逐条分析：

1. 有 method、无 id → **通知**（进度通知），不需要回复；
2. 无 method、有 result → **响应**，按 id=2 匹配到 export。响应可以乱序到达，必须靠 id 而不是到达顺序来匹配。`isError: true` 表示**工具执行失败**（如下游 API 出错），这仍是一个正常的响应，内容应回填给模型，让它决定重试或换方案；
3. `resultType` 为 `input_required` → **多轮往返请求（MRTR）的中间结果**：Server 需要用户确认（`inputRequests` 中的 `elicitation/create`）。原请求 id=3 到此已经结束，所以同样从 `sent` 中删除；客户端向用户收集答案后，要用**新的** id 重发原请求，并附上 `inputResponses`（以及 Server 给出的 `requestState`）；
4. 带 error 的响应 → **协议错误**，-32602 表示参数无效，这里是工具名不存在。

三个请求都已收到响应，最后 `sent` 为空字典 `{}`。

要点：协议错误走 JSON-RPC 的 error，通常由 Host 处理；执行错误放在 result 里用 isError 标记，模型能看到并据此修正；`resultType` 决定如何解析 result，缺失时按 `"complete"` 处理，以兼容旧版 Server。2026-07-28 版中 Server 不再向客户端发送请求（旧版可能夹带 `sampling/createMessage` 这类「既有 method 又有 id」的反向请求），需要客户端补充信息时一律通过 `input_required` 结果表达；但客户端的读循环仍要能处理等待响应期间插进来的通知。

## 六、编程题（每题 12 分，共 12 分）

**36.** 参考实现：

```python
def compact(text, max_lines=6):
    if not text.strip():
        return "（命令执行成功，没有输出）"
    rows = []                                  # [内容, 连续出现次数]
    for line in text.splitlines():
        if rows and rows[-1][0] == line:
            rows[-1][1] += 1
        else:
            rows.append([line, 1])
    shown = [s + (f"  [×{n}]" if n > 1 else "") for s, n in rows]
    if len(rows) <= max_lines:
        return "\n".join(shown)
    h = max_lines // 2
    t = max_lines - h
    omitted = sum(n for _, n in rows[h:len(rows) - t])
    return "\n".join(shown[:h] + [f"…省略 {omitted} 行…"] + shown[len(rows) - t:])
```

<sub>AGT-HARNESS-032</sub>　**思路**：先逐行扫描，把连续相同的行合并成 `[内容, 次数]`；再判断是否需要截断；截断时保留头尾，中间写明省略了多少**原始**行。

**为什么这样设计**：

- 保留尾部：pytest、编译器都把最终统计和关键报错放在末尾，只保留开头是最常见也最糟糕的截断方式；
- 折叠重复行：大量重复的警告、进度条会挤占预算，折叠后既省 token 又保留了「重复了 50 次」这个信息；
- 写明省略量：模型要知道「还有东西没看到」，否则会把残缺的输出当成全部；
- 空输出给明确提示：避免模型分不清成功与没执行。

**生产中还要补上**：中段保留含 Error、Traceback、FAILED 的行并标出原始行号；超长的单行（压缩后的 JS、长列表）切断并注明剩余字符数；全文落盘，在观察里给出路径，方便模型按需取回。

## 七、简答题（每题 8 分，共 24 分）

**37.** 参考答案：

1. **定义**：Agent 是让大模型在循环中根据环境反馈、自主使用工具去完成目标的系统。常拆成五部分：LLM（决策）、工具（获取信息、执行动作）、记忆（短期为上下文中的轨迹，长期为外部存储）、规划（拆解、排序、重规划）、循环（加上终止条件把它们串起来）。
2. **三个本质区别**：
   - 多步：一个目标需要多轮「思考 → 行动 → 观察」；
   - 有副作用：会下单、改代码、发邮件，而不只是生成文本；
   - 自己决定下一步和何时停：控制流交给了模型。
3. **自主程度是光谱**：单次调用 → 增强型 LLM（带检索、工具，但只走一轮）→ 工作流（代码写死路径）→ 受限 Agent（在限定工具内自选下一步）→ 自主 Agent。区别在于谁决定下一步。
4. **工程含义**：一旦自主，就要处理终止条件、错误恢复、预算、权限与结果验证。这些都属于运行时，所以 Agent = 模型 + 运行时，而不是「更聪明的模型」。

评分要点：

- 给出「LLM 在循环中根据环境反馈使用工具」的定义，并说出主要组件及职责（3 分）
- 说清多步、副作用、自主决定何时停这三个区别（3 分）
- 用自主程度光谱说明增强型 LLM、工作流与 Agent 的差异（2 分）
- 指出终止、错误处理、预算、权限等运行时问题（2 分）

<sub>AGT-BASE-032</sub>　**常见失分点**：把 Agent 说成「更聪明的模型」或「接了插件的聊天机器人」；把只调用一次工具的问答也叫 Agent；只背组件名，说不出多步、副作用、自主停止带来的工程难点。追问「只调用一次工具的机器人算不算 Agent」时，要答出它是增强型 LLM，缺少观察后再决策的循环。

**38.** 参考答案：

**1. 为什么是配置包**：Agent 的行为由多项配置共同决定，只管代码或只管提示词，都无法完整复现和回滚。任何一项变化都应视为一次发布，走评测门禁和灰度。

**2. 包含什么**：模型（带日期的快照）与采样参数；系统提示词与各类模板；工具定义（名称、描述、参数 schema、工具实现的版本）；检索参数与索引版本；护栏策略与路由规则；必要时还有评审模型与评分细则的版本。打包后计算哈希作为不可变的版本号，内容只增不改。

**3. 如何配合**
- **trace**：每条 trace、每个模型调用 span 都记录配置包版本（以及提示词名与版本），排障时能精确知道当时用的是什么；
- **回放**：按版本号取回当时的配置，在相同条件下重跑出问题的那一步；
- **评测与灰度**：门禁和灰度都以配置包为单位，指标按版本切片对比；
- **回滚**：把「当前生效版本」的指针切回上一版，代码、提示词、工具、索引一起回，一步到位；
- **控制面与数据面分离**：配置中心（控制面）故障时，数据面继续使用最后一份有效配置。

**4. 进行中的长任务**：检查点里记录任务启动时的配置包版本。默认按旧版本跑完（新旧版本并存一段时间）；必须切换时，只在检查点处迁移，并确认新版本能理解旧版本留下的状态（状态格式带 schema 版本号，必要时写迁移逻辑）。

评分要点：

- 说明多项配置共同决定行为，只版本化代码或提示词不足以复现与回滚（2 分）
- 列出配置包的主要组成，并说明不可变、带版本号（2 分）
- 说明与 trace 记录版本、回放、按版本灰度与一键回滚的配合（3 分）
- 说明进行中的长任务的处理：记录版本、按旧版本跑完或在检查点迁移（2 分）
- 提到控制面故障时数据面使用最后一份有效配置（1 分）

<sub>ENG-OBS-019</sub>　**常见失分点**：只灰度代码、不灰度提示词；回滚只回了代码，没回提示词、工具版本或索引；trace 里不记录版本，出了问题说不清是哪个配置；忽略进行中的长任务，切换版本后状态不兼容导致任务失败。

**39.** 参考答案：

**1. 租约为什么不够**
- Worker A 可能「假死」：长时间 GC 停顿、虚拟机被挂起、网络分区，时间超过了租约；
- 租约过期后，任务被 Worker B 接手；A 醒来后并不知道自己已经失效，还会继续写状态、调用工具；
- 即使 A 在每次写之前检查租约，检查和写入之间也可能发生停顿，问题依旧。

**2. 围栏令牌**
- 每次授予租约时，任务的版本号（令牌）单调递增：A 拿到 33，B 接手时拿到 34；
- 每次写状态库（以及支持的话，写下游资源）都带上令牌，存储层只接受不小于当前最大值的令牌，用比较并交换（CAS）实现；
- A 醒来后带着 33 写入，被直接拒绝。关键在于由**存储方**来检查，而不是靠写入方自觉；
- 「谁持有租约」这类元数据要求强一致，通常放在 etcd、ZooKeeper 这类基于共识协议的存储里。

**3. 「副作用已执行、完成事件未写入」的窗口**
- 恢复后这一步一定会重新执行（至少一次），无法避免；只能让重复执行无害；
- 幂等键由「工作流 ID + 步骤名（+ 调用序号）」生成，重放时保持不变；下游按键去重，返回首次的结果；
- 下游不支持幂等键时：执行前先记意图，恢复后先用业务单号查询对方状态（对账），确认没做过再执行；能两阶段的先预留后确认（TCC）；
- 持久化执行引擎（如 Temporal）把这套机制做进了框架：工作流代码可确定性地重放，副作用放在活动（activity）里，活动有自己的超时与重试策略，但活动本身仍然要求幂等，因为它可能已经执行完、结果还没记下 Worker 就崩溃了。

评分要点：

- 讲清假死与租约过期导致双 Worker 并发写，检查租约无法避免（3 分）
- 讲清围栏令牌单调递增、由存储层拒绝旧令牌写入的机制（3 分）
- 指出崩溃窗口内的重复执行无法避免，只能靠稳定的幂等键或对账让其无害（3 分）
- 提到持久化执行引擎或租约元数据需要强一致存储（1 分）

<sub>ENG-STAB-027</sub>　**常见失分点**：以为「心跳续约」就能防止双写；让写入方自己检查租约；幂等键用随机数或时间戳，重放时变了；以为用了 Temporal 之类的框架，活动就不需要幂等。围栏令牌的核心是「把判断放到存储侧」，这一点讲清楚很加分。

## 八、场景分析题（每题 12 分，共 12 分）

**40.** 参考答案：

**问题诊断**：

1. **query**：名字和描述都没有信息量，模型不知道它查什么、何时该用；参数 `q`、`t` 不自解释，没有格式说明，也没有 required。
2. **order**：
   - 把只读与写操作、可逆与不可逆操作揉进一个工具，`op` 还是自由文本，没有 enum；
   - `user_id` 交给模型填写：模型可能填错，也可能被注入篡改，从而操作别人的订单；
   - `amount` 没有单位（元还是分），`date` 没有格式；没有 required，也没有 `additionalProperties: false`；
   - 创建、退款等写操作没有幂等保护，也没有标注需要用户确认。
3. **get_logs**：返回全部日志会撑爆上下文，没有时间范围、级别、关键词等过滤条件，也没有分页或截断。
4. **整体**：没有命名空间和统一的命名规范；描述里没有「何时不该用」；没有约定出错时返回什么。

**改进设计**：

1. 按任务和副作用拆分：`orders_search`（按状态、时间搜索当前用户的订单，返回摘要）、`orders_get`（按订单号查详情）为只读；`order_cancel`、`order_refund` 为写操作，标注为需要用户确认的破坏性操作。
2. 当前用户身份由程序从登录态注入，不出现在参数里；工具层按登录身份做权限校验。
3. 参数：`status` 用 enum；`amount` 写明单位（如「单位：元，最多两位小数」）；日期写明 YYYY-MM-DD 并给示例；列出 required，设 `additionalProperties: false`，必要时开启严格模式。
4. 写操作由运行时生成并注入幂等键（绑定会话、订单与动作），重试时复用；执行前由状态机要求用户确认金额与订单。
5. 日志工具改为 `logs_search(level, since, until, keyword, limit=50, cursor)`，默认只返回少量匹配行，结果过长时截断并给出下一页的游标。
6. 描述写清做什么、何时用、何时改用别的工具、返回哪些字段；错误信息可行动，例如「date 应为 YYYY-MM-DD，收到 11/20」。

评分要点：

- 指出 query 的名称、描述、参数缺乏信息量（2 分）
- 指出 order 混合读写、op 无 enum、user_id 由模型填写等问题（3 分）
- 指出 get_logs 返回过大、缺少过滤与分页（1 分）
- 给出按副作用拆分、身份由程序注入、幂等键与确认等改进（3 分）
- 给出参数规范与可行动的错误信息（1 分）

<sub>AGT-TOOL-042</sub>　**常见失分点**：只改描述文字，不改工具粒度；没发现 `user_id` 由模型填写带来的越权风险；忽视写操作的幂等与确认；对返回过大的工具只说「让模型少调用」。挑毛病时可以按「名字 → 描述 → 参数 → 返回 → 副作用 → 错误」的顺序逐项检查。

## 九、系统设计题（每题 15 分，共 15 分）

**41.** 参考答案：

**1. 选型**：知识量约 2.5 亿 token，远超上下文窗口；每天 500 份变更；要求出处和部门权限。这些都是知识问题，选 RAG。生成模型如需固定话术或格式，再考虑轻量微调。

**2. 离线链路**
- 解析：版面分析恢复阅读顺序，去掉页眉页脚；表格转 Markdown 或按行线性化；扫描件做 OCR，低置信度页标记复核；
- 切块：递归切分 + 按标题结构，256～512 token、10%～20% 重叠，块开头拼上标题路径；
- 元数据：来源、标题路径、页码、版本、生效时间、部门 ACL、内容哈希；
- 索引：稠密向量（HNSW）+ BM25 倒排；按内容哈希增量更新，删除走软删除。

**3. 在线链路**：多轮追问时用小模型改写 → 带 ACL 前过滤的稠密 + BM25 并行召回（各 top-50）→ RRF 融合 → Cross-Encoder 重排保留 top-5 → 分数低于阈值则拒答 → 资料编号、逐句引用生成 → 引用校验、记录日志与反馈。

**4. 容量估算**
- 语料 $5\times10^4\times5000=2.5\times10^8$ token；块 512、重叠 64（步长 448），约 $2.5\times10^8/448\approx5.6\times10^5$ 块；
- 1,024 维 float32 向量每个 4 KB，共约 2.3 GB；HNSW 邻接表（M = 32，底层 64 个 4 字节 id）约 0.14 GB；单机内存即可容纳；
- 每天 500 份变更，约 5,600 块需要重新向量化，离线开销很小；
- 日均 3 万次，按 8 小时工作时间集中、高峰系数 3 估算，峰值约 3 QPS，规模不大。

**5. 首字延迟预算（P95 < 2 s）**
- 改写（按需触发，小模型）约 200 ms；向量化 + ANN 与 BM25 并行，约 50 ms；RRF 约 1 ms；重排 50 个候选约 150 ms；
- 生成 TTFT：5 块 × 约 500 token ≈ 2.5K token 输入，约 300～500 ms；
- 合计约 0.7～0.9 s，为网络与排队留出余量。

**6. 风险与对策**
- 解析质量（扫描件、表格）决定下限：抽样检查解析结果，建立解析质量监控；
- 权限泄露：ACL 在检索阶段前过滤，缓存键也要包含权限维度；
- 新旧版本混用：版本元数据 + 默认只检索有效版本；
- 幻觉：阈值拒答 + 引用校验；
- 效果评估：建立分类型评测集（事实、多跳、无答案、权限），分段看 Recall@k、忠实度、拒答准确率，配合线上点踩与转人工的反馈闭环。

评分要点：

- 给出选 RAG 的理由，并与微调、长上下文对比（1 分）
- 离线链路完整：解析（含扫描件与表格）、切块、元数据、混合索引、增量更新（2 分）
- 在线链路完整：改写、带权限过滤的混合召回、融合、重排、拒答、引用生成与校验（2 分）
- 给出语料规模、块数、向量存储与 QPS 等量级估算（2 分）
- 给出合理的首字延迟预算，并说明并行、按需触发等手段（2 分）
- 指出权限、版本、解析质量、评测等主要风险与对策（1 分）

<sub>RAG-BASE-030</sub>　**常见失分点**：只画「切块 → 向量库 → LLM」三个框；不做任何量级估算；权限靠提示词控制或检索后再过滤；忽略扫描件与表格的解析；延迟预算只算生成、不算改写和重排；没有评测与反馈闭环，无法证明系统可用。
