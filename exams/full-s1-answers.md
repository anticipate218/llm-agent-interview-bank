**1. C**

<sub>ALN-RLHF-021</sub>　**结论**：KL 管的是「累计跑多远」。奖励模型是在 SFT 一类模型的输出上训练的，策略一旦偏离太远，生成的就是奖励模型没见过的文本，打分不再可信，策略会找到奖励模型的盲区刷分（奖励黑客）。KL 惩罚也防止策略塌缩到少数讨好奖励模型的固定套路，保住通用语言能力与多样性。数学上，它还让目标有闭式最优解 $\pi^*\propto\pi_{\text{ref}}\exp(r/\beta)$，这是 DPO 推导的出发点。

- A 错：限制单步更新、让数据可以多用几轮的是 PPO 的**裁剪**，参照对象是 $\pi_{\text{old}}$，而不是 $\pi_{\text{ref}}$。
- B 错：KL 惩罚只出现在 PPO 阶段，与奖励模型的训练无关。
- D 错：基线由 critic 的价值估计提供；KL 项是奖励的一部分，不起基线作用。

**2. B**

<sub>RAG-RETR-014</sub>　**结论**：向量模型把「E1024」「E2048」都理解成「某个错误码」，语义上非常接近；而 BM25 把「e1024」当作一个独立的稀有词项（IDF 很高），只有包含它的文档才会得分。两者的盲区互补，这正是生产系统几乎都做混合检索的原因。

- A 错：维度再高，模型也是按语义相似来编码，精确的字符差异依然难以体现。
- C 错：归一化后余弦与 L2 的排序完全相同，换度量解决不了问题。
- D 错：「e1024」与「e2048」是两个不同的词项，BM25 能精确区分。前提是分词器把错误码作为完整词项保留，不要切碎。

**3. B**

<sub>ENG-PERF-015</sub>　**结论**：批处理用「时间上的灵活性」换价格。

在线请求必须按 SLO 立即处理，厂商要按峰值预留算力，低谷时大量闲置；批处理请求没有时延要求，可以填进低谷、攒成大 batch 高效运行，单位 token 的成本显著降低，厂商再把省下的成本部分让利给用户。这和自部署时「把离线任务放到低峰期跑」是同一个道理。

以 2026 年的公开规则为例：两家的批处理都约为五折、最长 24 小时内完成（Anthropic 称多数批次在 1 小时内完成），Anthropic 的批处理折扣还可以与 Prompt Caching 的折扣叠加。

- A 错：使用的仍是请求中指定的模型，输出质量相同。
- C 错：输出长度由请求参数（如 max_tokens）决定，与是否批处理无关。
- D 错：批处理请求同样受使用政策与安全机制约束。

**5. B**

<sub>AGT-TOOL-008</sub>　**结论**：严格模式要求**所有字段都列进 required**、每一层对象都设 `additionalProperties: false`。「可选」用「允许为 null」来表达（类型写成 `["string", "null"]`，或用 anyOf 加 null）：模型必须显式给出 `note: null`。执行时可以把 null 还原成函数的默认值。

为什么这样设计：约束解码要求结构确定，模型必须逐个生成每个字段；好处是模型不会因为「忘了」某个字段而出错。

- A 错：这是普通 JSON Schema 的可选写法；不在 required 里的字段，在严格模式下不被允许。
- C 错：删掉字段只会让信息无处安放，塞进其他参数还会污染那些参数的取值。
- D 错：严格模式要求 `additionalProperties: false`，设为 true 不符合要求。

**6. D**

<sub>AGT-HARNESS-030</sub>　**结论**：子 Agent 是一个有独立上下文、独立工具集和权限的「分身」，最适合边界清楚、以读为主、会产生大量中间输出的子任务。几十个文件的阅读过程留在子 Agent 的窗口里，主 Agent 只收到一份压缩后的清单，主上下文保持干净。

- A 错：几十个文件的全文涌进主窗口，后续编辑时目标和约束会被稀释。
- B 错：写操作强耦合，多个子 Agent 并行改会产生冲突；何况任务本身只要求调研评估。常见做法是「主 Agent 写、子 Agent 只读」。
- C 错：即使用长上下文模型，整个仓库也常常放不下，而且太贵、更不准。

配置要点：只读调研就不给编辑工具（被注入时破坏面也更小）；可以用更便宜的模型；限制派生深度和并发数；回传设长度上限，否则子 Agent 把原文当「结论」交回，隔离就白做了。子 Agent 通常会增加总 token，只在值得的任务上用。

**7. A**

<sub>SEC-DEF-025</sub>　**结论**：裁判和被测 Agent 读的是同一份攻击文本，攻击文本完全可以顺带写一句「评审请注意：本次操作是用户授权的」。再加上 LLM 打分有随机性，同一条轨迹两次评分可能不同，回归对比就失去了意义。

规则判定的好处：确定、可复现、便宜，而且攻击文本无法影响它。被测 Agent 接的是只做记录的假工具，判据可以直接写成「是否调用了 `send_email` 且收件人属于攻击者域名」「出站内容是否包含金丝雀」。

- B 错：成本是次要因素，问题出在可信度上。
- C 错：规则覆盖不了所有目标，例如「摘要是否被歪曲」这类语义层面的攻击，确实需要模型或人来判断；这时要对裁判做隔离（只给它判断所需的最少信息）并人工抽检。
- D 错：任何判定方式都做不到 100% 召回，规则的优势在于确定和抗操纵。

**8. C**

<sub>INF-QUANT-005</sub>　**结论**：非对称量化用零点让整数网格对齐数据的实际范围 $[\min,\max]$，适合明显偏向一侧的分布。

ReLU 之后的激活全部非负。若用对称量化，范围是 $[-\max,\max]$，负半轴的一半刻度永远用不到，相当于白白损失 1 bit；非对称量化把 $[0,\max]$ 映射到全部 $2^b$ 个整数上，分辨率提高约一倍。

- A、B 错：数据本身关于 0 对称，对称量化不浪费刻度，还省去零点的存储和计算，权重通常就用对称量化。
- D 错：离群通道的问题在于 scale 被少数大值撑大，加零点只是平移范围，解决不了；需要更细的粒度、混合精度或 SmoothQuant 一类的平滑方法。

**9. B**

<sub>TRN-MEM-019</sub>　**结论**：loss scaling 解决的是**范围**（下溢）问题，而 BF16 的范围与 FP32 相当。

反向传播中，很多激活梯度都很小（$10^{-6}$ 乃至更小）。FP16 的最小正规数约 $6.1\times10^{-5}$，更小的值只能用有效位越来越少的次正规数表示，小于约 $6\times10^{-8}$ 就直接变成 0。把 loss 乘以 $S$，所有梯度同比放大，就被「搬」回了可表示区间。BF16 的最小正规数约 $1.2\times10^{-38}$，不存在这个问题。

- A 错：BF16 只有 7 位尾数，比 FP16 的 10 位少，它的弱点恰恰是精度。
- C 错：硬件不会自动缩放梯度，loss scaling 要由训练框架显式实现。
- D 错：矩阵乘内部用 FP32 累加，但输出的激活梯度仍以 BF16 存储和传递。

<sub>RAG-BASE-027</sub>　**结论**：首字延迟 = 生成之前所有环节的耗时 + 生成模型的首 token 时间（TTFT）。输出长度只影响首字之后的解码阶段，不影响第一个字何时出现。

- A 有帮助：TTFT 主要由 prefill 决定，输入越短，prefill 越快。
- B 有帮助：串行时召回耗时是两路之和，并行后只取较慢的一路。
- C 没有直接帮助：限制最大输出长度只会缩短完整回答的总时长（也能避免长篇大论），对首字没有影响。
- D 有帮助：重排耗时大致与候选数成正比，减少候选能直接缩短生成前的等待；代价是可能漏掉排在后面的正确块。

**12. A**

<sub>ENG-OBS-032</sub>　**结论**：这是飞轮里的「自我污染」：训练集与评测集重叠，评测就变成了背题。

回归集的作用是衡量模型在没见过的样本上表现如何。同一批失败样本既拿去训练、又拿来考试，回归集成功率自然会涨，但它已经无法反映泛化能力，线上指标不动也就不奇怪了。正确做法：
- 失败样本进入飞轮时先决定去向：一部分进评测集，一部分进训练集，按会话或用户切分，避免同一会话的近似样本两边都有；
- 对训练数据与评测集做去重（精确与近似去重）；
- 保留一份长期不参与训练、也不参与日常调参的留出集，定期用它检查泛化；
- 线上效果最终以 A/B 为准。

- B 错：规模不是主要矛盾，重叠问题不解决，扩到多大都会虚高。
- C 错：修正质量高不会导致这个现象；即使训练样本偏理想化，也解释不了回归集涨到 95% 而线上不动。
- D 错：问题出在数据切分，与训练方法无关；换成强化学习，同样要隔离评测环境与训练环境。

**13. B**

<sub>INF-SERVE-025</sub>　**结论**：这是对话模板或停止条件出错的典型症状。

Chat 接口收到的是结构化的 messages，服务端要用模型自带的对话模板（tokenizer 配置中的 chat template）把它们拼成训练时见过的格式，并在末尾加上「助手开始回答」的提示。模型学会了在回合结束时输出结束标记（如 `<|im_end|>`），服务端要把它当作停止条件。

- 模板不对，模型看到的格式与训练时不同，行为就会异常；
- 没把结束标记设为停止条件，模型输出它后会「顺势」开始写下一轮的 `<|im_start|>user`，看起来像在自问自答。

vLLM 等框架默认使用模型自带的模板，也可以用 `--chat-template` 指定；生成配置中的 EOS token 也要正确。

- A 错：温度过高会让内容发散，但不会系统性地出现对话模板的特殊标记。
- C 错：FP8 KV 一般只带来轻微的精度变化，不会导致这种格式性错误。
- D 错：`max_tokens` 只是上限，模型输出结束标记（且服务端识别它）就会停止，设得再大也不会被迫写满；太小则只会让回答被截断。

**14. D**

<sub>FND-OPT-033</sub>　**结论**：Muon 改变的是二维权重矩阵的**更新方向**：AdamW 逐元素地做自适应缩放，Muon 则在矩阵层面把更新「正交化」。

按 Keller Jordan 的博客（2024-12）与 Moonshot 的论文（arXiv:2502.16982）：
- 先对梯度做动量累积（默认使用 Nesterov 风格，动量系数常取 0.95）；
- 把动量矩阵除以其 Frobenius 范数，再做 5 步 Newton–Schulz 迭代（五次多项式，系数约为 3.4445、−4.7750、2.0315），得到近似的 $UV^\top$，即离原矩阵最近的半正交矩阵；迭代可以用 bfloat16 运行；
- 只用于隐藏层的二维矩阵（卷积核展平成矩阵后也可以），Embedding、输出层、偏置与归一化增益仍然交给 AdamW。

**直觉**：Transformer 中权重的梯度（动量）矩阵往往由少数几个奇异方向主导。正交化把所有奇异方向的步长拉平，让原本被压制的「稀有方向」也能得到有效的更新。

- A 错：Muon 只保存一份动量，不维护二阶矩，优化器状态约为 AdamW 的一半。
- B 错：精确的 SVD 太慢，Muon 用的是只含矩阵乘法的 Newton–Schulz 迭代来近似，适合 GPU 计算，迭代后的奇异值只是大致落在 1 附近。
- C 错：Embedding 与输出层的作用与隐藏层不同，按照提出者的建议仍使用 AdamW。

**15. B**

<sub>TRN-DIST-029</sub>　**结论**：1F1B 下第 $i$ 段（从 0 计）在第一次反向之前要先做 $p-i$ 个前向，因此最多同时持有 $p-i$ 个 micro-batch 的激活：第一段 8 个，最后一段 1 个。

直观理解：第一个 micro-batch 的反向要等它走完全部 8 段再传回来，在此期间第一段一直在接收新的 micro-batch 做前向。

工程影响：第一段往往最先 OOM。常见做法是对前几段开启（选择性）重计算，或给第一段少分几层；同时第一段还放着 Embedding、最后一段放着输出层和 loss（大词表的 logits 也很占显存），切分时要综合考虑。Llama 3 405B 的训练就从第一段和最后一段各减少了一个 Transformer 层来平衡负载。

- A 错：最后一段每个 micro-batch 做完前向马上做反向，只需缓存 1 个。
- C 错：稳定期的交替不改变「在途 micro-batch 数」在各段之间的差异，第 $i$ 段是 $p-i$ 个，只有第一段达到 $p$。
- D 错：收发激活、梯度的缓冲很小，不决定激活峰值。

**16. D**

<sub>AGT-PROMPT-029</sub>　**结论**：硬压缩输出的仍是文本，软压缩输出的是向量，二者的适用前提完全不同。

- D 对：LLMLingua（Jiang 等, 2023）用一个小语言模型估计每个 token 的信息量，删掉信息量低的 token，压缩后的提示仍是普通文本，可以直接发给任何 API；LLMLingua-2 进一步把它做成 token 级的分类任务（保留或丢弃），速度更快。Gist token（Mu 等, 2023）训练模型把一段提示「压」进几个特殊 token 的表示中，必须能修改、训练模型，并能把这些向量输入模型。
- A 错：商用 API 只接受文本 token，无法传入自定义的向量表示。
- B 错：硬压缩不需要训练目标模型，大模型对删减过的「电报体」文本通常仍有不错的理解力。
- C 错：硬压缩后的文本常常不通顺，软压缩的向量人根本读不懂，二者都会降低可读性和可审查性。

**17. A**

<sub>LLM-NEW-007</sub>　**结论**：delta 规则把「只会累加」的写入，变成了「先读后改」的写入。

原始更新只做累加：同一个 key 写入多次，旧值和新值混在一起；不同 key 不正交时，读出的结果还会相互干扰，序列越长越严重。delta 规则先读出 $S_{t-1}^\top k_t$（当前状态对这个 key 的「记忆」），再按误差 $v_t-S_{t-1}^\top k_t$ 修正，同一个 key 再次出现时会被改写而不是不断叠加，缓解了容量有限的状态被反复写入后的相互干扰。这相当于以 $\beta_t$ 为学习率，对目标 $\|S^\top k_t-v_t\|^2$ 做一步在线梯度下降（即经典的 Widrow-Hoff 学习规则）。

- B 错：状态大小仍然固定为 $d_k\times d_v$。
- C 错：线性注意力的核心就是去掉 Softmax；delta 规则改变的是写入方式。
- D 错：对整个状态做衰减是 GLA、Mamba-2 等的门控思路（见下方延伸），会无差别地淡化所有记忆；delta 规则中的 $\beta_t$ 是写入强度，只修改当前 key 对应的那条记忆。

**延伸**：
- GLA、Mamba-2 等的思路是给状态加上**衰减门** $\alpha_tS_{t-1}$，可以快速整体遗忘；
- Gated DeltaNet 把「门控（快速擦除）」与「delta 规则（定点修改）」结合，被 Qwen3-Next、Qwen3.5 的线性注意力层采用；Kimi Linear 的 KDA 在 Gated DeltaNet 的基础上使用更细粒度的门控；
- 这些模型都依赖分块并行的训练算法，才能在 GPU 上高效训练。

**18. B**

<sub>RAG-ADV-021</sub>　**结论**：Late Chunking 在「向量层面」引入上下文，Contextual Retrieval 在「文本层面」引入上下文。

- **Late Chunking**（Günther 等, 2024）：先把整篇文档（在模型长度上限内）送进长上下文 Embedding 模型，得到每个 token 的向量，再按块的边界对 token 向量做平均池化。每个 token 在编码时都看过全文，所以块向量自带上下文。它不需要 LLM 生成文字，每篇文档只做一次前向，成本低；但需要能输出 token 级向量的 Embedding 模型，文档长度受模型窗口限制，也不会改变 BM25 索引。
- **Contextual Retrieval**（Anthropic, 2024）：每块调用一次 LLM 生成文字前缀，拼在块前面，再建向量和 BM25 索引。适用于任何 Embedding 模型，BM25 也能受益；代价是每块一次 LLM 调用（可用 Prompt Caching 降低）。

- A 错：把两者说反了。
- C 错：Late Chunking 不调用 LLM。
- D 错：Late Chunking 作用于向量，不影响 BM25；Contextual Retrieval 对两者都有帮助。

**应用**：前向模式适合输入维度小、输出维度大的情形，例如对少数几个超参数求灵敏度，或计算海森-向量积时的「前向套反向」组合。

**36. 错误**

<sub>FND-MATH-014</sub>　**错误**。不相关只能保证方差：$\mathrm{Var}(X+Y)=1+1+2\mathrm{Cov}(X,Y)=2$；而 $X+Y$ 是否服从正态，要求 $X$、$Y$ **联合**正态（例如相互独立）。只知道两个边缘分布都是正态、且不相关，既推不出联合正态，也推不出独立。

**反例**：取 $S$ 等概率为 $\pm1$，与 $X$ 独立，令 $Y=SX$。由对称性，$Y$ 也服从 $\mathcal{N}(0,1)$，而且 $\mathrm{Cov}(X,Y)=E[S]E[X^2]=0$。但 $X+Y=(1+S)X$ 以 1/2 的概率恰好等于 0，以 1/2 的概率等于 $2X$。它的均值为 0、方差恰好是 2，却在 0 处有一个概率质量为 1/2 的点，不可能是正态分布。

**正确说法**：若 $X$、$Y$ **相互独立**且都服从正态分布（或更一般地联合正态），则 $X+Y$ 服从正态分布，均值、方差分别为两者之和（联合正态但相关时，方差还要加 $2\mathrm{Cov}$）。只有在联合正态的前提下，「不相关」才等价于「独立」。

**37. 错误**

<sub>FND-DL-023</sub>　**错误**。「减少内部协变量偏移」是 BN 原论文（Ioffe 与 Szegedy, 2015, arXiv:1502.03167）提出的动机，但后续研究并不支持这个解释。

Santurkar 等（2018, arXiv:1805.11604）做了正是题目中的实验：在 BN 之后注入随时间变化、均值和方差都不为 0 的随机噪声，人为制造严重的分布偏移。结果这种「带噪 BN」的网络训练表现与标准 BN 几乎一样，仍远好于不加 BN 的网络。他们还发现 BN 并不一定减少内部协变量偏移。

他们给出的解释是：BN 让损失函数及其梯度更加平滑（Lipschitz 常数更小），梯度方向更可靠，因此可以用更大的学习率、对初始化更不敏感。另一个常被提及的角度是 BN 带来的尺度不变性：权重整体放缩不改变输出，与权重衰减一起会影响有效学习率。

面试中谈到 BN 为什么有效时，应说明 ICS 是原始动机，并指出后来的研究更倾向于「平滑优化地形」的解释。

**38. 错误**

<sub>ALN-RWD-021</sub>　**错误**。平均只能抵消成员之间**彼此独立**的误差，抵消不了它们**共有**的偏差。用相似的数据、相似的方法训练出来的奖励模型，往往有相同的系统性偏差（例如都偏爱长回答、都偏爱某种格式）：每个成员都高估同一类回答，平均之后照样高估。集成的收益来自成员之间不一致的那部分误差。

Eisenstein 等（2023）在 Helping or Herding? 中发现：奖励模型集成能缓解、但不能消除奖励黑客，一些钻空子的行为在集成后依然存在，原因正是各成员表现出相似的错误模式；预训练种子不同的集成比只换微调种子的集成更有效，因为成员之间差异更大。

实践中，集成要配合保守聚合（最小值、均值减方差）、KL 约束、长度控制和人工抽检一起使用，并且承认它增加了训练与推理成本。

**48.** 参考实现：

```python
import torch
import torch.nn.functional as F

def clip_loss(img_emb, txt_emb, logit_scale):
    img = F.normalize(img_emb, dim=-1)
    txt = F.normalize(txt_emb, dim=-1)
    scale = logit_scale.exp().clamp(max=100.0)          # 缩放系数不超过 100
    logits = scale * img @ txt.t()                       # (N, N)，第 i 行：第 i 张图对所有文本
    labels = torch.arange(img.shape[0], device=img.device)
    return (F.cross_entropy(logits, labels) + F.cross_entropy(logits.t(), labels)) / 2
```

<sub>LLM-MM-004</sub>　**思路**：
1. L2 归一化后，点积就是余弦相似度；
2. 乘以可学习的缩放系数（即温度的倒数，CLIP 初始化为 $1/0.07$，上限 100），得到 $N\times N$ 的 logits；
3. 第 $i$ 行是「第 $i$ 张图对 $N$ 条文本」的打分，正确答案在对角线上，所以标签是 `arange(N)`；对行做交叉熵是图→文，对列（转置后的行）做交叉熵是文→图，两者取平均。

**要点**：
- 负例来自同一 batch，batch 越大负例越多，CLIP 训练用的 batch 为 32768；
- 学温度的对数而不是温度本身，保证缩放系数始终为正、优化更平稳；截断上限是为了防止训练不稳定；
- 大规模分布式训练时，需要把各卡的嵌入汇总（all-gather）后再算相似度矩阵，否则负例只来自本卡。

**易错点**：忘了归一化；只算一个方向的损失；标签写成全 1 或 one-hot 矩阵；直接把 `logit_scale` 当作缩放系数使用而不取指数。

**Self-RAG（Asai 等, 2023）**
- 训练：先用 GPT-4 标注反思 token 训练评判模型，再用评判模型离线给训练语料插入反思 token 与检索段落，最后训练生成模型，让它在生成时自己输出反思 token。
- 推理：模型先输出 Retrieve 判断是否需要检索（按需检索）；需要时检索若干段落，对每个段落并行生成候选片段，并输出 IsRel（段落是否相关）、IsSup（内容是否被支持）、IsUse（是否有用）；用这些 token 的概率加权打分，在片段级做束搜索。权重可以在推理时调整，例如更看重 IsSup。

**CRAG（Yan 等, 2024）**
- 训练一个轻量的检索评估器（论文中基于 T5-large），给每篇召回文档打分。
- 按置信度采取三种动作：Correct（至少一篇高于上阈值）时把文档分解成知识片段、过滤无关片段后重组；Incorrect（全部低于下阈值）时丢弃检索结果，改写查询后用网页搜索；Ambiguous 时两者结合。
- 生成模型不变；论文也展示了它可以与 Self-RAG 等方法组合。

**比较**：

| 维度 | Self-RAG | CRAG |
|---|---|---|
| 训练 | 要训练生成模型（及评判模型） | 只训练轻量评估器 |
| 接入现有系统 | 难，必须换成训练过的模型，闭源 API 无法改造 | 容易，对生成模型即插即用 |
| 推理开销 | 对多个段落并行生成、束搜索，生成侧开销大 | 评估器对每篇文档打分，可能额外调用网页搜索，延迟受外部服务影响 |
| 适用场景 | 能自训、自部署模型，希望细粒度控制检索与忠实度 | 已有 RAG 系统想加一层检索质量把关与兜底 |

**工程启示**：很多团队用「重排分数阈值 + 低分时改写重查或换数据源」实现类似 CRAG 的轻量版本；外部搜索要考虑信息泄露与来源可靠性。

评分要点：

- 讲清 Self-RAG 的反思 token、按需检索与片段级自我评估（3 分）
- 讲清 CRAG 的检索评估器与三种动作（含精炼与网页搜索）（3 分）
- 比较训练成本与能否接入现有系统（2 分）
- 比较推理开销与适用场景（2 分）

<sub>RAG-ADV-012</sub>　**常见失分点**：把两者都说成「不需要训练」；记不清 CRAG 三种动作分别对应什么；把 Self-RAG 的反思 token 说成提示词里的普通文字（其实是训练时加入词表、由模型自己生成的特殊 token）；只描述做法，不讲落地的取舍。

## 十、场景分析题（每题 12 分，共 12 分）

**52.** 参考答案：

**暴露的问题**
1. **冻结只是一句话**：「代码冻结」只存在于对话里，平台层面没有任何强制机制。模型的服从是概率性的，在长任务中，约束可能被遗忘，或被「把问题解决掉」的目标压过。
2. **权限过大**：开发过程中的 Agent 能直接访问生产数据库，而且拥有删除权限；开发与生产没有隔离。
3. **自主过度**：破坏性命令执行前没有任何人工确认。
4. **缺少兜底**：执行前没有识别危险命令；「能不能恢复」本该由系统（备份、时间点恢复）回答，模型的说法不能作数。
5. **没有攻击者也会出事**：这次事故没有任何注入，模型自己的误操作同样是 Agent 安全要防的对象。

**整改方案**
1. **环境隔离**：开发与生产数据库分离；Agent 默认只接触开发或预发环境，生产凭证根本不进入它的运行环境。
2. **最小权限**：Agent 使用的数据库账号默认只读；需要写入的场景用受限账号（只能写指定的表，不能 DROP、TRUNCATE）。
3. **冻结机制化**：冻结期在权限系统里切换为只读、禁止部署，而不是写进提示词。
4. **高危操作人审**：生产环境的写操作、破坏性 SQL、批量删除一律人工审批；审批界面展示完整命令与预估影响行数。
5. **执行前守卫**：在钩子或工具网关中拦截危险模式（DROP、TRUNCATE、不带 WHERE 的 DELETE 和 UPDATE）。
6. **可恢复**：定期备份并支持时间点恢复，定期演练；关键操作前自动快照。
7. **审计与告警**：记录 Agent 执行的每一条命令，对生产环境的任何写操作实时告警。

评分要点：

- 指出冻结只写在对话或提示词里，没有平台层面的强制机制（2 分）
- 指出权限过大：能接触生产、有删除权限，开发与生产未隔离（2 分）
- 指出破坏性操作无确认，并认识到模型自身的误操作也是安全问题（2 分）
- 给出环境隔离、只读与受限账号、冻结机制化、生产写操作人审、执行前守卫、备份与演练等整改（4 分）

<sub>SEC-AGENT-006</sub>　**常见失分点**：把原因归结为「模型不听话」，建议换模型或把提示词写得更严厉；只加一个「删除前请确认」的提示词；没有提到开发与生产隔离；把模型说的「数据无法恢复」当真，而不是依靠可验证的备份。这类事故的教训是：凡是不能发生的事，就要让它在机制上不可能发生。

## 十一、系统设计题（每题 15 分，共 15 分）

**53.** 参考答案：

**1. 显存估算（BF16 混合精度 + Adam）**
- Actor、Critic 全参训练：各约 $7\times10^9\times16\approx112$ GB；奖励模型、参考模型 BF16 推理：各约 14 GB；合计约 252 GB。16 卡共 1280 GB，总量够，但单卡放不下任何一个训练模型的完整状态，必须切分。
- rollout 的 KV Cache：每 token $2\times32\times4096\times2$ 字节 $=512$ KiB，一条 2048 token 的回答约 1 GiB，512 条同时生成约 512 GiB，需要推理引擎分页管理、分批生成。

**2. 放置方案（两种思路）**
- **共置（colocate，verl 风格）**：16 卡都承载 Actor，训练时用 FSDP / ZeRO-3 切分，生成时切换成推理引擎的张量并行（如 TP=2、8 个副本并行生成）；Critic、参考模型、奖励模型同样分布在 16 卡上，按阶段轮流使用，暂时不用的卸载到 CPU。优点是 GPU 不空闲；代价是阶段切换要重分布权重、精细管理显存。
- **分离（OpenRLHF 的经典部署方式，它也支持共置模式）**：例如 8 卡给 vLLM 生成（多副本），4 卡训练 Actor（ZeRO-3），2 卡训练 Critic，2 卡跑参考模型与奖励模型，用 Ray 调度。优点是各组件独立扩展、可以流水线化；代价是阶段之间可能互相等待，需要调好资源配比。

**3. 一步的数据流**：推理引擎生成 512 条回答 → 奖励模型打分 → 训练侧前向计算 old log-prob（Actor）、参考 log-prob、价值 → 计算逐 token 的 KL 奖励与 GAE 优势并白化 → Actor 用裁剪损失、Critic 用价值损失，多个 mini-batch、1～2 个 epoch → 新权重同步给推理引擎。

**4. 权重同步**：共置时在进程内重分布；分离时通过 NCCL 广播（7B 的 BF16 权重约 14 GB），按层分桶、与其他计算重叠；同步后抽样比对一次 log-prob，确认推理端与训练端一致。

**5. 吞吐优化**（生成是大头，优先优化）：连续批处理；按长度分桶、合理设置最大长度；参考模型、奖励模型的前向与 Critic 计算并行；若用 LoRA，用关闭 adapter 的底座代替参考模型；训练端梯度检查点、序列打包。

**6. 监控与容错**：奖励、KL、长度与截断率、熵、裁剪比例、value loss、梯度范数，以及各阶段耗时（生成 / 打分 / 训练 / 同步）与 GPU 利用率；定期保存四个模型、优化器状态与数据游标，支持断点续训；对超长、乱码等异常 rollout 过滤并告警。

**7. 风险与取舍**：分离架构的资源配比要随回答长度调整；训练与推理引擎的数值差异需要持续监控；长尾回答拖慢整体时可考虑异步或部分 rollout，但要处理随之而来的 off-policy 问题。

评分要点：

- 正确估算四个模型的显存，并意识到 rollout 的 KV Cache 同样很大（2 分）
- 给出合理的模型放置与并行方案，比较共置与分离的取舍（3 分）
- 写清一步训练的数据流与权重同步方式（2 分）
- 给出以生成为重点的吞吐优化（2 分）
- 给出监控与容错方案（1 分）

<sub>ALN-RLHF-038</sub>　**常见失分点**：只算权重，不算梯度与优化器状态；忽略 rollout 的 KV Cache；直接用训练框架的 generate 做生成；不提权重同步；没意识到生成通常是整步耗时的大头；监控只看奖励曲线。
