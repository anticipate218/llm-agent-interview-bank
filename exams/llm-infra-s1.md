## 一、单选题（每题 2 分，共 30 分）

**1.** CUDA Graph 在大模型推理中解决的主要问题及其约束是：

- A. 把一步的 kernel 序列录制成图、整图发射，省去 CPU 逐个发射的开销；形状与地址须固定，batch 按若干档补齐
- B. 把每步几百个小 kernel 合并调度，减少 GPU 上的总 FLOPs 与执行时间，而且对 batch 大小没有限制
- C. 把一步中的多个 kernel 自动融合成一个大 kernel，中间结果留在片上，减少 HBM 读写
- D. 让 Prefill 与 Decode 在同一张图、同一个 kernel 中执行，消除两阶段切换时的同步等待

**2.** 用 Hugging Face 的 `generate` 对一批长度不同的提示词做批量生成（静态批处理，需要补齐）时，官方文档建议把 Decoder-only 模型分词器的 `padding_side` 设为 `'left'`。主要原因是：

- A. 左侧补齐需要的 pad token 比右侧补齐少，可以减少整批前向的计算量和 KV Cache 显存占用
- B. 右侧补齐时 attention mask 会失效，模型会把 pad token 当成正常内容参与注意力计算
- C. vLLM 等推理引擎内部也会把一批请求左对齐补齐后再计算，左侧补齐便于与它们的结果保持一致
- D. 新 token 追加在末尾；右侧补齐时短提示词末尾是 pad，模型要接在 pad 后面续写，而它没学过这种情况

**3.** 投机解码（speculative decoding）能加速自回归生成，最根本的原因是：

- A. 草稿模型在简单 token 上比目标模型更准，由它代写这部分内容，整体质量与速度一并提升
- B. Decode 受带宽限制，一次前向验证多个位置与生成 1 个 token 耗时相近
- C. 草稿模型替目标模型完成了大部分 token 的计算，目标模型执行的总浮点运算量因此减少
- D. 验证时目标模型只需对草稿 token 做前向、不再读写 KV Cache，省掉了读 KV 的时间

**4.** 在 H100 上部署 FP8 W8A8 推理时，权重和激活通常选用哪种 FP8 格式？

- A. 都用 E4M3：范围由逐通道 / 逐 token 缩放解决，多 1 位尾数精度更高
- B. 都用 E5M2：最大值可达 57344，不容易溢出，省去了缩放因子的计算
- C. 权重用 E4M3，激活用 E5M2：激活里有离群值，需要更大的动态范围
- D. 不区分格式：FP8 推理在 H100 上实际走 INT8 Tensor Core，FP8 只是 INT8 的另一种叫法

**5.** 有人用下面的代码测量 GPU 上一次大矩阵乘的耗时，结果只有几十微秒，远低于按算力估计的毫秒量级：

```python
x = torch.randn(8192, 8192, device="cuda")
t0 = time.time()
y = x @ x
t1 = time.time()
print(t1 - t0)
```

最主要的原因是：

- A. GPU 上的矩阵乘本来就是微秒级完成的，几十微秒的测量结果是准确的，无需修改
- B. `time.time()` 的精度不够，换成精度更高的 `time.perf_counter()` 就能得到准确的耗时
- C. PyTorch 会缓存相同输入的计算结果，矩阵乘实际上没有执行，换一个新的随机输入再测一次即可
- D. CUDA 算子异步执行，`x @ x` 只是提交核函数就返回；计时前后要 `torch.cuda.synchronize()`

**6.** 一个 8B 模型单张 H100 就能放下。团队在两种部署之间犹豫：4 个单卡副本（多副本，DP = 4），或 2 组 TP = 2。下列对比最准确的是：

- A. TP = 2 单步时延更低，适合 TPOT 要求严的场景；多副本无卡间通信，总吞吐通常更高
- B. TP = 2 让单步时延严格减半，两组 TP 的总吞吐也与 4 个副本相同，应优先选 TP
- C. 多副本没有 all-reduce，单步时延比 TP = 2 更低、总吞吐也更高，TP 只在模型放不下时才有用
- D. TP = 2 每层要做两次 all-reduce，单步时延反而高于单卡，推理中只在模型放不下单卡时才用

**7.** 客服 Agent 一期已经上线「退款建议 + 用户确认后执行」。业务方希望二期放开小额退款由 Agent 自动执行。下列放开条件中最合理的是：

- A. 客服主管随机抽查了 50 个对话，一致认为 Agent 已经准确掌握退款政策的各项条款，可以直接放开小额退款
- B. 换用最新版本的模型后，离线评测集上的退款判断准确率提升了 5 个百分点，达到历史最高的 97%，超过人工客服
- C. 用户普遍反馈确认步骤繁琐，确认页的放弃率达到 15%，放开自动执行可以明显提升体验和处理效率
- D. 确认环节的采纳率持续高于 95%、错误退款连续一个月为 0；只对小额合规订单放开，并有每日对账和一键关闭

**8.** 某长对话助手为了控制上下文长度，每一轮都用「只保留最近 10 轮」的滑动窗口裁剪历史；同时开启了 Prompt Caching，却发现除了系统提示词，历史部分几乎从不命中缓存，输入成本居高不下。下列改法中，最能同时控制上下文长度、又保住缓存命中的是：

- A. 每一轮都把全部历史压缩成一段新的摘要，放在系统提示词开头，上下文始终保持在 2K 以内
- B. 关闭 Prompt Caching，只依靠滑动窗口控制长度，省下缓存写入的 1.25 倍溢价
- C. 历史只追加不改写，长度超过阈值时才一次性把较早部分压缩成摘要，之后继续只追加
- D. 每一轮随机丢弃一部分较早的历史消息，把上下文控制在固定长度以内

**9.** 用 FP16 做混合精度训练通常必须配合 loss scaling，而用 BF16 时一般不需要。最主要的原因是：

- A. BF16 的尾数位比 FP16 更多，有效数字更长，量级很小的梯度在 BF16 中也不会被舍入为 0
- B. BF16 有 8 位指数、范围与 FP32 相当，小梯度不会下溢；FP16 只有 5 位指数，小梯度易变成 0
- C. BF16 训练时 Tensor Core 会自动把梯度放大 $2^{16}$ 倍再输出，相当于内置了 loss scaling
- D. BF16 训练时反向传播全程在 FP32 中计算和存储梯度，下溢问题与 BF16 格式本身无关

**10.** 某服务的并发上限是 4、每个请求处理 1 秒（处理能力 4 个/s），遭遇 8 个/s 的流量，持续 20 秒。对比「无界队列，来者不拒」与「最多排队 4 个，满了立即返回 429 并带上 Retry-After」两种方案，下列说法正确的是：

- A. 无界队列不拒绝任何请求，处理能力始终满载、没有浪费，所以被接收请求的平均时延反而更低
- B. 两种方案每秒处理完成的请求数不同：有界队列拒绝了一部分请求，单位时间完成的请求更少
- C. 有界队列会让被拒绝的客户端立即重试、形成重试风暴，所以无界队列更安全，代价只是时延略高一些
- D. 无界队列越积越长，最晚到的要等约 20 秒；有界队列让部分请求快速失败，被接收的时延稳定在约 2 秒

**11.** 连续批处理的调度器在「有新请求等待 Prefill」时有两种基本倾向：Prefill 优先（新请求一到就尽快做完它的 Prefill）与 Decode 优先（先保证正在生成的请求每步都前进，只用剩余能力做 Prefill）。下列说法正确的是：

- A. Prefill 优先压低 TTFT、吞吐高，但会让生成卡顿；Decode 优先保护 ITL，但 TTFT 变长
- B. Prefill 优先能尽快扩大 batch，摊薄权重读取，因此 TTFT 与 TPOT 会同时下降
- C. Decode 优先让每步只含 Decode、batch 保持稳定，因此吞吐更高、新请求的 TTFT 也更短
- D. 在连续批处理下两者等价：每步会同时包含 Prefill 与 Decode，区别只在实现复杂度

**12.** Basic Paxos 中，提案者以编号 n 发出 prepare 请求，收到了多数接受者的承诺（promise）。其中一个承诺附带「我已接受过编号 7、值为 X 的提案」，另一个附带「已接受过编号 9、值为 Y 的提案」，其余承诺没有附带已接受的提案。提案者原本想提议的值是 Z。第二阶段它应当发出的 accept 请求是：

- A. (n, Z)：附带的已接受值互不一致，说明还没有值被选定，提案者可以坚持原值
- B. (n, X)：应采用最早被接受的值，它最可能已被多数派接受
- C. (n, Y)：必须采用承诺中编号最大的已接受提案的值
- D. (9, Y)：沿用编号最大的已接受提案的编号和值，以免与它冲突

**13.** 在丢包率较高的移动网络下，某团队把服务从 HTTP/1.1（浏览器对同一域名开 6 个并行连接）升级到 HTTP/2（同一域名只用 1 个连接）后，页面加载反而变慢了。最主要的原因是：

- A. HTTP/2 的二进制分帧和流优先级调度需要更多 CPU，弱网下手机还要频繁重组乱序到达的帧，算力跟不上
- B. HPACK 的动态表依赖收发双方状态同步，丢包会让动态表失步，后续请求只能退回发送未压缩的完整头部
- C. 所有请求复用同一个 TCP 连接，一个包丢失时，该连接上所有流的后续数据都要等它重传（TCP 层队头阻塞）
- D. HTTP/2 的多路复用会打乱 TCP 的 ACK 节奏，使快速重传无法触发，丢包后只能等待重传超时

**14.** 在 H100（BF16 拐点约 295 FLOP/B）上服务 8B 模型。若把 Chunked Prefill 的每步 token 预算设得很小（例如 64），最主要的副作用是：

- A. 长提示词被切开后，后面的块看不到前面块的 token，注意力只在块内计算，KV Cache 会算错
- B. 每步都夹带 Prefill 块并多读一遍权重，正在 Decode 的请求的 ITL 会明显变长
- C. 每步 token 太少，算术强度远低于拐点，算力利用率低，长提示词的 TTFT 明显变长
- D. 分块后各块是分步写入的，块哈希与完整提示词不一致，前缀缓存会因此失效

**15.** 在 Linux 上用 PyTorch 训练时，Dataset 用一个很大的 Python 列表保存了几百万条样本的文件路径（字符串对象）。开启 `num_workers=8`，worker 进程以 fork 方式创建（这是 Linux 上 Python 3.13 及更早版本的默认方式）。之后，每个 worker 的物理内存占用随训练逐渐上涨，总内存远超预期，而代码从未修改这个列表。最可能的原因是：

- A. fork 后内核会在后台逐步把父进程的物理页完整复制给每个子进程，复制完成前内存持续上涨
- B. fork 出的子进程中 Python 的循环垃圾回收器默认被禁用，worker 每轮产生的临时对象无法回收、逐步累积
- C. 读取列表元素也会修改对象头部的引用计数，这次写入触发写时复制，相关内存页被逐页复制到各个 worker
- D. DataLoader 每个 epoch 都会把整个 Dataset 对象重新序列化，通过管道发给每个 worker，旧副本不会释放

**19.** 关于模型合并（model merging），下列说法**正确**的有：

- A. Model Soups 平均同一预训练模型用不同超参数微调出的多个模型，效果往往能达到甚至超过其中最好的单个模型
- B. DARE 按概率 $p$ 随机丢弃任务向量的元素并把其余元素放大 $1/(1-p)$ 倍，$p$ 很大时效果仍基本不变
- C. TIES 修剪小幅度改动、按符号总和选出方向、只平均方向一致的值，以减少任务向量间的干扰
- D. 合并后推理时仍要分别运行各个源模型再对输出加权平均，推理成本随被合并模型的数量线性增长
- E. 多数合并方法只对权重做算术运算，不需要梯度训练，最多用小验证集调缩放系数等超参数

**20.** 关于 CAP 的延伸 PACELC，以及常见系统的取舍，下列说法**正确**的有：

- A. AP 系统放弃了线性一致性，副本之间只能各自为政，无法提供最终一致或读己之写这类较弱的保证
- B. 配置中心、选主、分布式锁这类元数据服务（如 etcd、ZooKeeper）通常选择 AP，因为它们必须永远可写
- C. PACELC：发生分区时在可用性与一致性之间取舍；否则（正常运行时）在延迟与一致性之间取舍
- D. Abadi 把默认配置下的 Dynamo、Cassandra、Riak 归为 PA/EL：分区时保可用，平时为低延迟也放松一致性
- E. 写入要同步复制到多数副本才返回成功的系统，即使没有发生网络分区，也要为一致性付出额外的写延迟

**21.** 关于长上下文推理中的 KV 压缩与淘汰方法，下列说法正确的有：

- A. SnapKV 用提示词末尾「观察窗口」内 query 的注意力，为每个头挑选要保留的提示词位置
- B. H2O 按 token 在提示词中的位置决定淘汰顺序，越靠前的越先淘汰，以保留最近的上下文
- C. StreamingLLM 只按位置保留开头的 sink 与最近窗口，不依赖注意力分数，但窗口外的内容会被遗忘
- D. 多轮对话沿用压缩后的 KV 时，后续问题若需要已被淘汰的内容，模型无法再看到它
- E. 淘汰类方法基本无损：被淘汰 token 的注意力权重在淘汰时已接近 0，之后也不会再变大

