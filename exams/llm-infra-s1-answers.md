<sub>INF-KERNEL-026</sub>　**结论**：CUDA Graph 省的是 CPU 侧的发射开销，不改变 GPU 上执行的 kernel。

Decode 每步的计算量很小，几百个 kernel 中很多只运行几微秒，而 CPU 发射一个 kernel 也要几微秒，GPU 常常在等 CPU。CUDA Graph 先录制一遍完整的 kernel 序列（连同参数与指针），之后用一次调用重放整张图。约束：
- 形状与显存地址固定：输入要拷进录制时使用的固定缓冲区，batch 大小只能取若干档，不足的补齐（vLLM 预先为一组常用 batch 大小录制）；
- 图中不能有依赖 CPU 的动态控制流或同步（如 `.item()`）；
- 录制需要时间与额外显存，拉长冷启动。vLLM 可以用 `--enforce-eager` 关闭它，便于调试。

- B 错：kernel 本身不变，FLOPs 不变；而且图中张量的形状固定，batch 大小要按档位分别录制。
- C 错：图里仍是原来的多个 kernel，只是发射方式变了；融合需要算子融合技术。
- D 错：与 Prefill、Decode 的划分无关。

**2. D**

<sub>INF-BASE-043</sub>　**结论**：生成是在序列末尾续写，补齐用的 pad 不能挡在「提示词」和「新生成的 token」之间。

批处理张量要求每条序列一样长，`generate` 每一步都在所有序列的末尾追加一个新 token。右侧补齐时，短提示词后面跟着一串 pad，新 token 接在 pad 之后，模型没有学过「从 pad 后面续写」；Hugging Face 文档的例子中，右侧补齐会生成「1, 2, 33333333333」这样的错误输出。左侧补齐后，所有序列的真实内容右对齐，最后一个位置都是提示词的最后一个 token。左侧补齐仍然需要 attention mask 屏蔽 pad，并据此计算位置编号。文档还提到，右侧补齐对状态空间模型和混合架构的影响更大：它们的循环状态会被末尾的 pad 继续更新。

- A 错：两种补齐方式补的 pad 数量相同，计算量一样；要减少浪费，得靠按长度分桶或不补齐的变长批处理。
- B 错：两种方式都可以用 attention mask，问题不在掩码，而在续写的起点。
- C 错：vLLM 等引擎把各请求的 token 拼接成一维序列，用变长注意力和块表区分不同请求，根本不做补齐；左侧补齐是静态补齐的批处理接口（如 `generate`）才有的要求。

**3. B**

<sub>INF-SPEC-001</sub>　**结论**：投机解码利用的是 Decode 阶段「算力闲置、带宽打满」的特点。

Decode 每步都要把全部权重从显存读一遍，batch 小时算术强度只有个位数，算力利用率很低。一次前向处理 1 个 token 与处理 5 个 token，读权重的成本相同，额外的计算几乎是「免费」的。于是先让便宜的草稿连续猜 γ 个 token，再让目标模型一次前向把 γ+1 个位置全部验证：草稿猜对时，一次前向就能产出多个 token，猜对几个就前进几个，每次前向至少前进 1 个 token。

- A 错：草稿通常比目标模型弱；输出由目标模型的验证规则决定，草稿质量只影响接受率（速度）。
- C 错：总计算量反而增加——被拒绝的草稿 token 白算了，草稿模型自己也要计算。它省的是串行的前向次数。
- D 错：目标模型照常使用并更新 KV Cache，被拒绝 token 的 KV 还要回滚。

**4. A**

<sub>INF-QUANT-030</sub>　**结论**：推理中权重与激活都用 E4M3。

| 格式 | 指数 / 尾数位 | 最大值 | 特点 |
|---|---|---|---|
| E4M3 | 4 / 3 | 448 | 精度较高，范围较小 |
| E5M2 | 5 / 2 | 57344 | 范围大，精度低 |

- B 错：有了 scale 就不需要靠格式本身的范围扛离群值，E5M2 只有 2 位尾数，精度明显更差。
- C 错：激活的离群值同样由逐 token（或逐张量）的 scale 处理；主流推理框架的 FP8 W8A8 对激活也用 E4M3。
- D 错：FP8 是浮点格式，刻度在 0 附近密、远处疏，与均匀刻度的 INT8 不同；H100 有专门的 FP8 Tensor Core。

<sub>CS-TORCH-003</sub>　**结论**：CPU 端的 Python 代码只负责把 CUDA 核函数**提交**到 GPU 的流（stream）中，提交后立即返回，GPU 在后台执行。上面量到的只是「提交」所花的时间。

正确的计时方法：
```python
for _ in range(3):                # 预热：首次调用含 cuBLAS 初始化、显存分配等开销
    x @ x
torch.cuda.synchronize()
t0 = time.perf_counter()
y = x @ x
torch.cuda.synchronize()          # 等 GPU 真正算完
print(time.perf_counter() - t0)
```
也可以用 `torch.cuda.Event(enable_timing=True)` 记录前后两个事件，或者直接用 `torch.utils.benchmark`。

- A 错：8192 阶矩阵乘约 1.1 TFLOP，即使在最快的 GPU 上也要毫秒量级。
- B 错：问题不在计时器精度，而在于没有等待 GPU 完成。
- C 错：PyTorch 不会缓存运算结果。

**延伸**：`.item()`、`.cpu()`、`print(tensor)` 等需要读取 GPU 数据的操作都会隐式同步。训练循环中每一步都 `loss.item()` 会让 CPU 等待 GPU，打断流水线；一般每隔若干步才取一次标量。

**6. A**

<sub>INF-SERVE-011</sub>　**结论**：单卡放得下时，默认用多副本；只有当 TPOT 的 SLO 单卡达不到时，才用 TP 换更低的单步时延。

- **TP 的收益**：Decode 卡在带宽，每张卡只读 $1/\text{TP}$ 的权重与 KV，单步耗时近似按 TP 下降，直接改善 TPOT。
- **TP 的代价**：每层 2 次 all-reduce，batch 小时以延迟为主，占比随 TP 增大而上升；单步时延不会严格减半，每张卡的吞吐效率下降。
- **多副本**：副本之间不通信，4 张卡就是 4 份完整的吞吐，加一个负载均衡器即可，扩缩容也最简单。

- B 错：通信开销使 TP 达不到线性加速，同样卡数下总吞吐通常不如多副本。
- C 错：多副本中每个请求仍在单卡上跑，单步时延与单卡相同，比 TP = 2 更高。
- D 错：Decode 卡在带宽，TP 让每张卡读的字节减半，通信开销通常抵不过这部分收益；推理中 TP 对降低单步时延、放下单卡装不下的模型都很关键。

**9. B**

<sub>TRN-MEM-019</sub>　**结论**：loss scaling 解决的是**范围**（下溢）问题，而 BF16 的范围与 FP32 相当。

反向传播中，很多激活梯度都很小（$10^{-6}$ 乃至更小）。FP16 的最小正规数约 $6.1\times10^{-5}$，更小的值只能用有效位越来越少的次正规数表示，小于约 $6\times10^{-8}$ 就直接变成 0。把 loss 乘以 $S$，所有梯度同比放大，就被「搬」回了可表示区间。BF16 的最小正规数约 $1.2\times10^{-38}$，不存在这个问题。

- A 错：BF16 只有 7 位尾数，比 FP16 的 10 位少，它的弱点恰恰是精度。
- C 错：硬件不会自动缩放梯度，loss scaling 要由训练框架显式实现。
- D 错：矩阵乘内部用 FP32 累加，但输出的激活梯度仍以 BF16 存储和传递。

**10. D**

<sub>ENG-STAB-039</sub>　**结论**：无界队列是「时延放大器」。

处理能力固定为 4 个/s，到达 8 个/s，积压以每秒 4 个的速度增长，20 秒后积压约 80 个，最后到达的请求要排约 $80/4=20$ 秒。很多请求处理完时用户早已离开或客户端已超时重试，处理了也是白处理，还挤占了本来能按时完成的请求。有界队列最多排一轮再处理一轮，时延约 2 秒；被拒绝的请求拿到 Retry-After，可以退避或降级。模拟结果：无界队列最大时延 20.5 s，有界队列稳定在 2.0 s。

- A 错：无界队列下被接收请求的时延随时间线性增长，平均值远高于有界队列。
- B 错：两种方案都让服务满负荷运行，每秒都完成 4 个，吞吐相同；区别在于时延分布和「有效」完成数。
- C 错：只要带上 Retry-After、客户端按退避与预算重试，就不会形成风暴；无界队列的问题恰恰更严重。

**11. A**

<sub>INF-SCHED-035</sub>　**结论**：两种倾向各保护一个指标，Chunked Prefill 是折中。

Sarathi-Serve 把调度器分为两类：Prefill 优先（如早期 vLLM 的默认调度、Orca）吞吐高，但会造成生成卡顿（generation stall）；Decode 优先（如静态批时代的做法）ITL 平稳，但新请求要等很久、吞吐也低。它提出的 stall-free batching 每步先放入所有 Decode，再用剩余预算处理 Prefill 块，在两者之间取得平衡。

- B 错：Prefill 插队会让同一步里的 Decode 变慢，TPOT 与 ITL 变差。
- C 错：Decode 优先会推迟新请求的 Prefill，TTFT 变长，batch 也补得慢。
- D 错：两者对 TTFT、ITL 与吞吐的影响截然不同；连续批处理只决定「每步可以换人」，每步放多少 Prefill 正是这两种倾向的分歧所在。

<sub>CS-DIST-015</sub>　**结论**：第二阶段的值不能自由选择。只要多数派的承诺中带有已接受的提案，就必须采用其中**编号最大**的那个提案的值；只有所有承诺都没有附带已接受的提案时，才能用自己的值。

**直觉**：某个值可能已经被「选定」（被多数接受者接受）了，只是提案者不知道。设值 v 以编号 m 被选定，那么任何一个多数派中都至少有一个接受者接受过编号不小于 m 的提案；Paxos 又保证编号在 m 与 n 之间的提案值都是 v（归纳）。所以多数派的承诺中编号最大的已接受提案，其值一定是 v。采用它，新提案就不会推翻已选定的值。

- A 错：已接受的值互不一致，并不说明还没有值被选定；坚持 Z 可能推翻已经选定的 Y，破坏「只选定一个值」的安全性。
- B 错：编号 7 的 X 可能早已被编号更大的提案取代，「最早」没有意义。
- D 错：accept 请求必须使用本轮 prepare 的编号 n。接受者已承诺不再接受小于 n 的提案，用 9 发出会被拒绝。

**两个阶段的分工**：第一阶段（prepare / promise）既是「抢占」（让接受者承诺不再接受更小编号的提案），也是「学习」（获知可能已被选定的值）；第二阶段（accept / accepted）才真正提议值。

**13. C**

<sub>CS-NET-012</sub>　**结论**：HTTP/2 解决了**应用层**的队头阻塞（不必等前一个响应完成才能发下一个），却把全部请求压到一条 TCP 连接上，**TCP 层**的队头阻塞反而影响更大。

丢包时，TCP 必须等缺失的字节重传到达，才能把后面已经收到的数据交给应用，不管这些数据属于哪个流；HTTP/1.1 的 6 个连接则互不影响，一个连接丢包只拖慢它自己。另外，单连接丢包后拥塞窗口减半，影响的是全部流量；6 个连接各自独立地进行拥塞控制，整体退让更温和。

这正是 HTTP/3 改用 QUIC 的动机：QUIC 在传输层就区分各个流，丢包只阻塞所在的流。

- A 错：二进制分帧比文本解析更省 CPU；帧的先后由 TCP 的有序交付保证，应用层不需要重组乱序的帧。
- B 错：HPACK 动态表的同步由 TCP 的有序交付保证，丢包只会延迟，不会让双方失步或压缩失效。
- D 错：HTTP/2 跑在普通 TCP 上，快速重传照常工作，与上层是否多路复用无关。

<sub>INF-SCHED-012</sub>　**结论**：预算太小时，每一步都要完整读一遍权重，却只处理几十个 token：线性层的算术强度约等于本步的 token 数，远低于拐点，Prefill 变成带宽瓶颈，TTFT 变长，总吞吐下降。

以 8B 模型为例：每步读权重约 4.8 ms，64 个 token 的计算只需约 1 ms，每步仍约 5 ms，Prefill 速度只有约 $64\div5\ \text{ms}\approx1.3$ 万 token/s；预算为 2048 时每步受算力限制，约 33 ms 处理 2048 个 token，速度约 6 万 token/s。一个 8K 提示词，前者要 128 步、约 0.64 s，后者只要 4 步、约 0.13 s。

所以预算至少要让每步的 token 数（Decode 加 Prefill）明显超过拐点，常见设置在几百到几千之间，再在 TPOT / ITL 的 SLO 约束下通过压测确定。

- A 错：后面的块会读取前面各块已写入的 KV，分块 Prefill 的结果与一次做完相同。
- B 错：每步本来就要读一遍权重，夹带少量 Prefill token 并不会多读；预算越小，每步越短，ITL 越平稳。
- D 错：块哈希只取决于 token 内容和前缀，与分几步写入无关；命中的部分照样跳过。

**15. C**

<sub>CS-OS-024</sub>　**结论**：这是「读也会触发写时复制」的典型问题，PyTorch 的 issue #13246 详细讨论过。

fork 之后，父子进程共享物理页，页被标记为只读；任何一方**写**某一页时，内核才为它复制一份（写时复制，COW）。CPython 中每个对象的头部都有引用计数，仅仅是读取 `paths[i]`，也会增加、减少这个字符串的引用计数，这就是一次写操作。几百万个小对象散布在大量内存页上，随着训练遍历数据集，几乎每一页都被「写」过一次，每个 worker 最终都拥有了一份副本。内存因此是**逐渐**上涨，而不是 fork 时立刻翻倍。

**解决**：把这类数据存成不带逐元素引用计数的形式，例如 numpy 数组（字符串可以编码成定长字节数组）或 PyArrow 的列式数据（字符串存放在连续的缓冲区里）；也可以把数据放进共享内存或按需从磁盘读取。

- A 错：fork 采用写时复制，只有被写过的页才会复制，内核不会在后台主动复制物理内存。
- B 错：子进程中的垃圾回收照常工作（开关状态随 fork 继承，默认开启）；问题与回收无关，是复制造成的。
- D 错：在 fork 模式下，worker 直接继承父进程的内存，不需要序列化数据集，也不存在每个 epoch 重发一份的情况。

**版本提示**：Python 3.14 起，Linux 上 multiprocessing 的默认启动方式改为 forkserver（Windows 一直是 spawn，macOS 自 Python 3.8 起默认为 spawn）。这些方式下数据集会被序列化后传给每个 worker，每个 worker 一启动就持有一份完整副本，表现不同，但「每个 worker 一份」的内存账同样要提前算清楚。

**22. 错误**

<sub>CS-PY-002</sub>　**错误**。Python 只有一种传参方式：把**对象的引用**传给形参（call by sharing，也叫传对象引用）。无论实参是否可变，形参与实参一开始都指向**同一个对象**：

```python
def f(n, lst):
    print(id(n) == id(x), id(lst) == id(y))   # True True：都没有拷贝
    n += 1          # int 不可变：生成新对象，只是让局部名字 n 指向它
    lst.append(1)   # 原地修改：调用方能看到
    lst = [99]      # 重新绑定局部名字：调用方看不到

x, y = 10, []
f(x, y)             # 之后 x 仍是 10，y 变成 [1]
```

所谓「不可变对象像按值传递」，只是因为它**没有原地修改的方法**，任何「修改」都会创建新对象并重新绑定局部名字，调用方自然看不到。区别不在传参方式，而在「原地修改」与「重新绑定名字」。

实践：不想让函数改到调用方的列表，就在函数内先拷贝一份，或约定只读、返回新对象。

**23. 错误**

<sub>CS-ALGO-003</sub>　**错误**。均摊（amortized）复杂度描述的是「一串操作的总代价 ÷ 操作次数」的上界，不保证单次操作的上界。触发扩容的那一次 `append` 要复制全部 $n$ 个元素，是 $O(n)$；只是这样的操作很少，摊到每次只有常数。

还要区分两个概念：均摊分析针对**最坏情况下的操作序列**，不涉及概率；「平均情况」复杂度则是对随机输入取期望，例如快速排序平均 $O(n\log n)$。

工程含义：对时延敏感的系统，均摊 O(1) 的结构也会出现偶发的长停顿。例如哈希表一次性扩容（rehash）会卡住所有请求，Redis 的字典因此采用渐进式 rehash：同时保留新旧两张表，每次增删查改时顺带搬迁一小部分，把一次大停顿拆成许多小步。

容易被忽略的是 SDK：很多官方 SDK 默认就会对 429、5xx 自动重试（例如 Anthropic 的 SDK 默认重试两次），业务代码外面再包一层重试，就等于多了一层乘数。做法是明确规定在哪一层重试，其余层关闭重试或设为 0 次；同时配上重试预算和熔断器，下游整体故障时自动停止重试。

**25. 错误**

<sub>TRN-PEFT-002</sub>　**错误**。两者都为零时：
$$\frac{\partial\mathcal{L}}{\partial B}=\frac{\alpha}{r}\,g\,(Ax)^\top=0,\qquad \frac{\partial\mathcal{L}}{\partial A}=\frac{\alpha}{r}\,B^\top g\,x^\top=0$$
其中 $g$ 是该层输出的梯度。$A=0$ 让 $B$ 的梯度为零，$B=0$ 让 $A$ 的梯度为零，两者永远停在原点（这是一个鞍点），LoRA 支路学不到任何东西。

所以只能让其中一个为零：标准做法是 $A$ 随机（论文用高斯分布，PEFT 库默认用 Kaiming 均匀分布）、$B$ 为零。也有工作换一种思路，例如 PiSSA 用原权重的主奇异向量同时初始化 $A$、$B$，再从 $W_0$ 中减去这部分，同样保证初始输出不变。

**30. 错误**

<sub>ENG-OBS-026</sub>　**错误**。每看一次都是一次检验，看得越多，至少有一次「碰巧显著」的概率就越高，这就是多次查看（peeking）问题。各次检验用的是不断累积的同一批数据，并不独立，误报率不会像独立检验那样高达 $1-0.95^K$，但仍明显高于 5%：模拟显示，看 6 次后误回滚率约 15%。

常见的校正方法：
- Bonferroni：每次用 $\alpha/K$，如看 6 次时每次用 $0.05/6\approx0.0083$，简单但偏保守；
- 成组序贯检验：用 α 消耗函数（如 O'Brien-Fleming 边界），前几次查看更严、后面逐渐放宽；
- 允许随时查看的序贯检验（如 mSPRT）。

注意区分：严重的安全事件、错误率暴涨这类硬护栏应立即回滚，不需要等统计检验；统计校正针对的是成功率这类需要样本积累的指标。

<sub>TRN-PT-039</sub>　**错误**。梯度裁剪限制的是梯度的范数，但 AdamW 的更新量是 $\eta\,\hat m/(\sqrt{\hat v}+\epsilon)$，分子、分母随梯度同步缩放，对梯度的整体缩放近似不敏感：一个长期梯度很小（$m$、$v$ 都接近 0）的参数突然收到梯度 $g$ 时，即使 $g$ 已经被裁剪，更新量仍约为

**33.** (8, 7, 6, 5) / (8,7,6,5) / [8, 7, 6, 5]；(4, 5, 3) / (4,5,3) / [4, 5, 3]

<sub>CS-TORCH-004</sub>　**规则**：把两个形状**右对齐**，从最后一维往前逐维比较：两者相等、其中一个为 1、或其中一个不存在（视为 1），就可以广播，结果取较大者；否则报错。

```
8 1 6 1          4 1 3
  7 1 5            5 1
-------          -----
8 7 6 5          4 5 3
```

- 第一题：最后一维 1 与 5 → 5；倒数第二维 6 与 1 → 6；倒数第三维 1 与 7 → 7；第一维 8 与「不存在」→ 8。
- 第二题：3 与 1 → 3；1 与 5 → 5；4 与「不存在」→ 4。

反例：`(2, 3)` 与 `(3, 2)` 最后一维 3 对 2，既不相等也没有 1，报错。广播不会真的复制数据：被扩展的维度步长为 0，只是逻辑上「重复」。但广播出的**结果**是实打实分配的，`(N, 1) - (N,)` 会得到 N×N 的张量，这是许多隐蔽 bug 和显存暴涨的来源。

<sub>TRN-PEFT-038</sub>　**拆解反向的 $4N$**：对每个线性层 $Y=XW$，反向要算两件事，各约 $2N$：

- 对权重的梯度 $\partial\mathcal{L}/\partial W=X^\top\cdot\partial\mathcal{L}/\partial Y$，用来更新参数。

LoRA 冻结了 $W_0$，第二项可以省掉，但第一项必须保留（前面层的 LoRA 参数还等着梯度）。所以每 token 约 $2N+2N=4N$，是全参的 $4/6=2/3$。

若开启全量重计算，全参为 $8N$，LoRA 约 $6N$，比例为 $3/4$。LoRA 论文在 GPT-3 175B 上报告训练吞吐比全参提升约 25%，与这一估算的量级相符；QLoRA 还要加上反量化的开销。

## 六、代码改错题（每题 6 分，共 6 分）

**40.** 参考答案：

**问题**：`except ConnectionError as e:` 绑定的名字 e 只在 except 块内有效。离开 except 块时，Python 会自动执行相当于 `del e` 的操作，所以循环结束后在最后一行引用 e，抛出 UnboundLocalError（e 是函数的局部变量，此时没有绑定值）。

**修正**：在 except 块里把异常另存到一个变量中：

```python
last_exc = None
for _ in range(times):
    try:
        return fn()
    except ConnectionError as e:
        last_exc = e
raise RuntimeError(f"failed after {times} attempts") from last_exc
```

<sub>CS-PY-047</sub>　**为什么要删除 e**：异常对象通过 `__traceback__` 引用着当前的栈帧，栈帧又通过局部变量 e 引用着异常对象，形成循环引用。如果不删除，栈帧里的所有局部变量（可能包括很大的张量、响应体）都要等循环垃圾回收器才能释放。语言参考中明确规定：用 `as` 绑定的异常在 except 子句结束时被清除。

**异常链的三种写法**：
- `raise New() from e`：显式链接，设置 `__cause__`，traceback 中显示「The above exception was the direct cause of ...」；
- 在 except 块中直接 `raise New()`：隐式链接，设置 `__context__`，显示「During handling of the above exception, another exception occurred」；
- `raise New() from None`：不显示原异常，适合把内部实现细节替换成对外的错误。

做重试封装时保留原始异常链，排查线上问题时才能看到真正的根因。

## 七、编程题（每题 12 分，共 12 分）

**41.** 参考实现：

```python
import torch

def collate(batch, pad_id=0):
    B = len(batch)
    L = max(len(s["input_ids"]) for s in batch)
    ids = torch.full((B, L), pad_id, dtype=torch.long)
    labels = torch.full((B, L), -100, dtype=torch.long)
    mask = torch.zeros((B, L), dtype=torch.long)
    for i, s in enumerate(batch):
        n = len(s["input_ids"])
        ids[i, :n] = torch.tensor(s["input_ids"], dtype=torch.long)
        labels[i, :n] = torch.tensor(s["labels"], dtype=torch.long)
        mask[i, :n] = 1
    return {"input_ids": ids, "attention_mask": mask, "labels": labels}
```

<sub>CS-TORCH-034</sub>　**为什么需要自定义 collate_fn**：默认的 collate 会把每个字段 `torch.stack` 起来，要求同一字段在各样本中形状相同，变长序列会直接报错。

**思路**：先求本 batch 的最大长度 L，用 `torch.full` 预分配好 pad 值、-100 和 0，再逐个样本把真实内容写进前 n 个位置。也可以用 `torch.nn.utils.rnn.pad_sequence(seqs, batch_first=True, padding_value=...)` 一次完成填充。

**三个输出各自的作用**：
- `input_ids` 中的填充值是什么不重要，但模型必须靠 `attention_mask` 忽略这些位置；
- `labels` 的填充位置设为 -100，与 CrossEntropyLoss 默认的 `ignore_index` 一致，不参与损失计算；提示词部分的 -100 由上游数据处理负责；
- 训练时一般右侧填充；批量生成时，Decoder-only 模型通常改用**左侧**填充，保证每条序列的最后一个位置都是真实 token。

**工程细节**：
- `num_workers > 0` 且使用 spawn 启动 worker 时（Windows、macOS 的默认方式），collate_fn 要能被 pickle，应定义在模块顶层，需要额外参数时用 `functools.partial`，不要用 lambda；
- 按长度把样本分桶再组 batch，或者把多条样本拼接打包（packing），可以显著减少填充带来的无效计算。

**42.** 参考答案：

1. **切分方式**：TP 在**层内**切矩阵（MLP 先列后行，注意力按头切），每张卡参与每一层的计算；PP 按**层**切成 $p$ 段，每张卡只负责连续的若干层。
2. **通信**：TP 每层前向 2 次、反向 2 次 all-reduce，每次是整个 $(b,s,h)$ 的激活，频繁、量大且处在关键路径上，需要 NVLink，一般只在机内、规模不超过 8；PP 只在相邻段之间点对点传递边界激活和梯度，通信量小，适合跨机。
3. **效率损失**：TP 度越高，每卡的矩阵越小，GPU 利用率下降，但没有空等；PP 有流水线气泡，比例约 $(p-1)/(m+p-1)$，需要足够多的 micro-batch，还要保证各段负载均衡。
4. **显存**：TP 同时切分参数和激活（配合序列并行几乎按 $1/t$ 下降）；PP 每卡只存部分层的参数，但 1F1B 调度下第一段要同时缓存最多 $p$ 个 micro-batch 的激活。
5. **搭配**：机内用 TP，跨机用 PP，最外层再套数据并行（常配 ZeRO-1）；总卡数 = TP × PP × DP。

**43.** 参考答案：

**(1) TTL**
- 节点里增加过期时刻 `expire_at`，用单调时钟（如 `time.monotonic()`）计算，不受系统改时间的影响；
- 惰性删除：`get` 时发现已过期，就删除并按未命中处理；
- 只靠惰性删除，过期但再没被访问的条目会一直占着容量，所以还要定期清理：按过期时间建最小堆或时间轮，或者像 Redis 那样定期抽样检查带过期时间的 key；淘汰时优先淘汰已过期的条目；
- 给 TTL 加随机抖动，避免大量条目在同一时刻集中过期，回源请求被瞬间放大。

**(2) 高并发**
- `get` 也要移动链表节点，所以读操作同样必须加锁；GIL 不能保证「查哈希表 + 移动节点」这种复合操作的原子性；
- 一把全局锁会成为瓶颈：按 `hash(key) % N` 分成 N 个分段，每段一把锁、一个独立的 LRU，结果是近似的全局 LRU；
- 缩短持锁时间：未命中时不要在锁内调用工具或模型；对同一个 key 合并并发的回源请求（single flight），避免缓存击穿时同时发出大量相同的昂贵调用；
- 进一步优化：命中时只把访问记录写入缓冲区、批量更新链表（Caffeine 的做法），或改用近似 LRU（如 CLOCK），避免每次命中都改链表。

**(3) 多进程、多机**
- 每个进程各自缓存，命中率低、彼此还可能不一致；改为共享缓存（如 Redis），设置 TTL 和淘汰策略（Redis 的 LRU 是基于采样的近似 LRU）；
- 常见做法是两级缓存：进程内的小 L1（TTL 很短）+ 共享的 L2；数据更新时通过消息通知失效，或者只依赖短 TTL；
- 多个缓存节点之间用一致性哈希分片，扩缩容时只迁移少量 key；
- 缓存键要包含工具名、规范化后的参数和工具版本；有副作用的工具（下单、发邮件）绝不能缓存；结果与用户权限相关时，键里要带上用户或租户，防止越权读到别人的数据。

评分要点：

- 讲清 TTL 的实现：过期时间戳、惰性删除，并补充定期清理或优先淘汰过期条目（3 分）
- 指出 get 也要加锁，并给出分段锁、缩短持锁时间、合并并发回源等至少两项并发优化（4 分）
- 给出多进程或多机的方案（共享缓存、两级缓存、一致性哈希、失效通知等）（2 分）
- 提到缓存键设计、副作用工具不能缓存或权限隔离等工程细节（1 分）

## 九、场景分析题（每题 12 分，共 12 分）

**44.** 参考答案：

1. **选型**：用 WSD（或类似的多阶段阶梯式调度），不用按 1T 设定的余弦。余弦的形状由总步数决定：中途的检查点学习率还高、没有退火，拿出去效果偏差；训完 1T 后学习率已降到很低，追加训练只能重新 warmup，loss 会先上升，效率也不如一开始就按更长的总量规划。
2. **训练主线**：warmup（如 2000 步）后保持恒定的峰值学习率；定期保存完整检查点，包括优化器状态和数据加载的位置。
3. **发布策略**：需要可用版本时，从最近的主线检查点分出一支，做一段衰减（约为已训 token 数的 10%，或固定几十 B token），衰减段可上采样高质量数据，得到的模型交给下游；主线不受影响，继续以恒定学习率训练。每个分支额外消耗约 10% 的算力，发布频率要权衡。
4. **追加预算后**：从主线（未衰减）的最新检查点继续以峰值学习率训练，到新的终点前再做最终的衰减与退火；不要从已经衰减的分支接着训。如果只剩衰减后的检查点，就要重新 warmup 到适中的学习率再衰减，并接受短暂的 loss 上升。
5. **注意事项**：按新的总量重新规划数据，避免高质量数据提前用尽或重复过多；只在「衰减后」的模型之间比较效果，稳定阶段的 loss 偏高是正常的；续训一定要加载优化器状态，否则 Adam 的 $m$、$v$ 需要重新积累，等于重新开始一段不稳定期。

评分要点：

- 选择 WSD 并说明余弦在训练长度不确定时的问题（3 分）
- 给出从稳定阶段分支衰减、得到可用版本的策略（3 分）
- 说明追加预算时从未衰减的主线续训，以及只剩衰减检查点时需重新 warmup（2 分）
- 提到数据规划、比较口径、保存优化器状态等细节（2 分）
