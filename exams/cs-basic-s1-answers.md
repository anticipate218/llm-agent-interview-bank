**1. C**

<sub>CS-SQL-018</sub>　**结论**：数据库的瓶颈在于按页读取存储（磁盘或 SSD，即使在缓冲池中也以页为单位管理），设计目标是让一次查找经过的页尽可能少，并且支持范围查询。

- **对比二叉树**：二叉树每个节点只有两个分支，千万行的数据树高约 24 层，每层都可能是一次页访问；B+ 树一个节点就是一个页，有上千个分支，3～4 层就够了。
- **对比 B 树**：B 树的内部节点也存数据，一页能放的分支更少，树更高；范围查询要在树中来回中序遍历。B+ 树的数据只在叶子，叶子串成链表，`BETWEEN`、`ORDER BY`、`LIMIT` 都只需顺序扫描。
- **对比哈希**：哈希索引的等值查询平均 O(1)，但不支持范围查询、排序和前缀匹配。

- A 错：B+ 树的查找是 $O(\log_f n)$，f 为扇出，只是 f 很大使得树高很小，不是 O(1)。
- B 错：描述的是 B 树的特点，而且正是 B+ 树要避免的设计。
- D 错：哈希索引不支持范围查询。

**补充**：写入极多的场景（如日志、时序数据）也会使用 LSM 树（如 RocksDB），以顺序写换取更高的写吞吐，代价是读放大和后台合并。

**2. C**

<sub>CS-NET-028</sub>　**结论**：一个请求、多个响应，就是服务端流式调用。

gRPC 的四种调用方式：
- **一元调用**：一个请求、一个响应，如普通的同步推理接口；
- **服务端流式**：一个请求、多个响应，如逐 token 输出；
- **客户端流式**：多个请求、一个响应，如分块上传一段音频，最后返回转写结果；
- **双向流式**：双方各自独立地收发消息，如实时语音对话，用户可以随时打断。

gRPC 基于 HTTP/2，每次调用对应一个 HTTP/2 流；它支持截止时间（deadline）在服务之间传递，客户端取消调用时服务端能收到取消信号，可以借此及时停止生成、释放 GPU。浏览器不能直接使用原生 gRPC，需要通过 gRPC-Web 等代理转换。

**4. C**

<sub>CS-PY-048</sub>　**结论**：CPython 以**引用计数**为主、**循环垃圾回收**为辅。

- **引用计数**：每个对象记录有多少引用指向它，降为 0 时立即释放。好处是及时、确定：没有循环引用的对象，最后一个引用消失时马上被回收。
- **循环垃圾回收**（`gc` 模块）：两个对象互相引用时，即使外界已无法访问它们，引用计数也不会降到 0。分代的循环垃圾回收器在对象分配数量达到阈值时运行，找出「只被彼此引用、从外部不可达」的对象组并回收。

- A 错：`del x` 只是删除名字 x 这个引用，使引用计数减 1；还有其他引用时，对象照样存活。
- B 错：循环引用由循环垃圾回收器处理，只是回收得比引用计数晚。自 Python 3.4（PEP 442）起，定义了 `__del__` 的对象处在循环中也能被回收。
- D 错：GC 只回收**不可达**的对象，仍被引用的对象无论多大都不会被回收。

**补充**：对象被释放后，内存通常先回到 Python 的内存池中复用，不一定立刻归还操作系统，所以进程的 RSS 不会马上下降。「内存泄漏」在 Python 中更常见的成因是对象仍被意外地引用着，例如无界缓存、只增不删的全局容器。

**7. A**

<sub>CS-OS-005</sub>　**结论**：线程切换要陷入内核，经过调度器选择下一个线程，保存和恢复完整的寄存器上下文；协程切换在用户态完成，切换点由程序决定，要保存的东西少得多（几个寄存器和栈指针，或状态机中的局部状态），也不涉及地址空间的切换。

两类实现：
- **有栈协程**（如 Go 的 goroutine）：每个协程有自己的小栈，切换时保存少量寄存器并切换栈指针；
- **无栈协程**（如 Python 的 async/await、Rust 的 async）：编译器或解释器把函数变成状态机，局部变量保存在协程对象里，切换只是从一个函数返回、调用另一个。

- B 错：成千上万个协程通常跑在一个或少数几个线程上，靠交替执行实现并发。
- C 错：内核看不到协程，它只调度线程。
- D 错：协程至少要保存「执行到哪里」以及局部变量，恢复时从上次让出的位置继续，而不是从头执行。

**代价**：协作式调度意味着协程不让出就没人能抢占它，一段长时间的 CPU 计算或阻塞调用会卡住同一线程上的所有协程。

<sub>CS-ALGO-001</sub>　**结论**：内层的总工作量是一个等比数列的和，被 $2n$ 封顶，所以是 $\Theta(n)$。

设外层循环执行 $k$ 次，`i` 依次为 $1,2,4,\dots,2^{k-1}$，其中 $2^{k-1}<n\le2^k$（$n\ge2$）。内层总次数为 $1+2+\dots+2^{k-1}=2^k-1$，介于 $n-1$ 与 $2n-1$ 之间。例如 $n=10$ 时 `i` 取 1、2、4、8，共 15 次。

- A 错：只数了外层循环的次数，忽略了内层的工作量。
- B 错：「外层 $\log n$ 次 × 内层最多 $n$ 次」只是一个上界，并不紧：内层只有最后一轮接近 $n$，前面各轮依次减半。
- D 错：把它当成了两层都跑 $n$ 次的普通嵌套循环。

延伸：同样的「等比级数求和」论证，正是动态数组倍增扩容均摊 $O(1)$ 的原因。对比 `for i in range(n)` 里套一个 `j *= 2` 的 while 循环：外层每轮都要跑满 $\log n$ 次，那才是 $\Theta(n\log n)$。

<sub>CS-NET-003</sub>　**结论**：`CLOSE_WAIT` 表示「对方已经关闭，等待本端应用调用 close()」。它停留多久完全取决于应用，内核不会替应用关闭；大量堆积几乎总是应用层的资源泄漏：每个这样的连接都占着一个文件描述符，最终耗尽上限，报出「Too many open files」。

- A 错：那是 TIME_WAIT，而且出现在主动关闭方。
- C 错：那样本端会停在 `SYN_SENT`（或连接已建立却迟迟得不到响应），不会出现 `CLOSE_WAIT`。
- D 错：同样表现为握手阶段的状态，与 `CLOSE_WAIT` 无关。

**15. B**

<sub>CS-OS-026</sub>　**结论**：「free 了但 RSS 不降」多数是分配器的策略与碎片造成的，不一定是泄漏。

glibc malloc（ptmalloc）的行为：
- 小于 mmap 阈值的块从堆（`brk` 扩展的连续区域）或各线程的 arena 中切分。释放后进入空闲链表，等待复用；只有堆顶部连续的空闲空间超过一定阈值时，才会通过收缩堆顶归还给系统。高地址处只要还有一个存活的小对象，下面大片的空闲内存就还不回去。
- 大于等于 mmap 阈值的块单独用 `mmap` 分配，`free` 时直接 `munmap`，RSS 立即下降。这个阈值初值是 128 KiB，而且是动态的：释放过较大的 mmap 块后，阈值会自动调高。
- 多线程程序每个线程可能有自己的 arena，进一步加剧碎片。

**应对**：调用 `malloc_trim` 尝试归还空闲内存；限制 arena 数量（`MALLOC_ARENA_MAX`）；换用 jemalloc 或 tcmalloc；调整分配模式（复用缓冲区、对象池）。确认是否泄漏，要看 RSS 是否随请求数**持续线性增长**，并借助内存分析工具。

- A 错：free 只是把内存还给分配器；只有用 mmap 单独分配的大块才会在 free 时直接 munmap，64 KiB 的块是否还给操作系统由分配器决定。
- C 错：内存归还后，物理页就会被系统回收。
- D 错：RSS 是实际驻留在物理内存中的大小；虚拟地址空间大小是 VSZ。

**24. 正确**

<sub>CS-OS-019</sub>　**正确**。一次读操作分两个阶段：① 等待数据就绪（数据到达内核缓冲区）；② 把数据从内核拷贝到用户缓冲区。

- 阻塞 IO、非阻塞 IO、IO 多路复用、信号驱动 IO 的差别都在第 ① 阶段怎么等；第 ② 阶段都由应用线程调用 read 同步完成，所以都属于**同步 IO**。
- **异步 IO**（如 POSIX AIO、Windows 的 IOCP、Linux 的 io_uring）把两个阶段都交给内核，数据已经放进用户缓冲区之后才通知应用。

<sub>CS-PY-052</sub>　**正确**。`groupby` 的行为类似 Unix 的 `uniq`：顺序扫描，键一变化就开始新的一组，不会把不相邻的相同键合并。它的优点是流式处理、只占 O(1) 的额外内存，适合处理已排好序的大文件。

常见用法与坑：

[(k, list(g)) for k, g in groups]                # [('a', []), ('b', []), ('a', [])]

**30. 正确**

<sub>CS-PY-040</sub>　**正确**。数据模型规定：重写了 `__eq__` 却没有定义 `__hash__` 的类，`__hash__` 会被隐式设为 None。原因是默认的 `__hash__` 基于对象 id，与新的「按值相等」语义矛盾：两个相等的对象会落到不同的哈希槽里，集合去重、字典查找都会出错。于是 Python 干脆让它不可哈希：

```python
class P:
    def __init__(self, x): self.x = x
    def __eq__(self, o): return isinstance(o, P) and self.x == o.x

P.__hash__ is None      # True
{P(1)}                  # TypeError: unhashable type: 'P'
```

**哈希契约**：`a == b` 为真，则必须有 `hash(a) == hash(b)`；反过来不要求（哈希冲突是允许的，只影响性能）。常见实现是用参与比较的字段组成元组再求哈希：`def __hash__(self): return hash((self.x, self.y))`，而且这些字段在对象作为键期间不能被修改。dataclass 遵循同样的规则：`eq=True` 且 `frozen=False` 时 `__hash__` 被设为 None，`frozen=True` 时才自动生成 `__hash__`。

17
(['hi', 'tcp', ''], 0)

**33.** 输出：

**34.** 参考答案：

**问题**：第 5 行的容量循环是从小到大。计算 `dp[c]` 时用到的 `dp[c - cost]` 可能**在本轮已经更新过**，也就是已经包含了当前这个片段，于是同一个片段被选了多次，算成了「完全背包」。例如只有一个 `(3, 5)` 的片段、预算 6 时，`dp[3] = 5` 之后 `dp[6] = dp[3] + 5 = 10`，相当于选了两次。

**修正**：容量从大到小遍历，保证 `dp[c - cost]` 仍是上一轮（不含当前片段）的值：

```python
for c in range(budget, cost - 1, -1):
    dp[c] = max(dp[c], dp[c - cost] + score)
```

<sub>CS-ALGO-035</sub>　二维写法是 $dp[i][c]=\max(dp[i-1][c],\ dp[i-1][c-w_i]+v_i)$，右边都来自上一行 $i-1$。压缩成一维后，倒序遍历容量，才能在覆盖 `dp[c]` 时保证 `dp[c - cost]` 尚未被本轮改写；正序遍历则对应「每件物品可以无限次选取」的完全背包。

复杂度为 $O(n\cdot\text{budget})$，是伪多项式时间：预算为 8000 个 token、候选片段 100 个时约 80 万次运算，完全可以接受。

**为什么不按「分数 / token」贪心**：0/1 背包不能贪心。例如预算 500、片段为 (260, 7)、(250, 6)、(250, 6)：按单位分数先选 (260, 7)，剩下的 240 个 token 放不下任何片段，总分 7；最优是两个 250，总分 12。只有物品可以切分（分数背包）时，按单位价值贪心才是最优的。

## 六、编程题（每题 12 分，共 24 分）

**35.** 参考实现：

```python
import threading
from collections import deque


class BoundedQueue:
    def __init__(self, capacity):
        if capacity <= 0:
            raise ValueError("capacity 必须为正")
        self._items = deque()
        self._cap = capacity
        lock = threading.Lock()
        self._not_full = threading.Condition(lock)    # 两个条件变量共用一把锁
        self._not_empty = threading.Condition(lock)

    def put(self, item, timeout=None):
        with self._not_full:
            if not self._not_full.wait_for(lambda: len(self._items) < self._cap, timeout):
                return False                          # 等到超时仍是满的
            self._items.append(item)
            self._not_empty.notify()                  # 唤醒一个等待取数据的消费者
            return True

    def get(self, timeout=None):
        with self._not_empty:
            if not self._not_empty.wait_for(lambda: len(self._items) > 0, timeout):
                raise TimeoutError
            item = self._items.popleft()
            self._not_full.notify()                   # 腾出一个空位
            return item

    def __len__(self):
        with self._not_full:
            return len(self._items)
```

<sub>CS-OS-015</sub>　**思路**：
1. 一把锁保护队列，两个条件变量共用这把锁：`not_full` 让生产者等空位，`not_empty` 让消费者等数据；
2. 等待用 `wait_for(条件, timeout)`：内部在循环里检查条件，能正确处理虚假唤醒和被其他线程抢先的情况，超时返回条件的最终取值；
3. 放入后通知 `not_empty`，取出后通知 `not_full`。每次只改变了一个位置，`notify()` 唤醒一个等待者就够了。

**为什么用两个条件变量**：只用一个条件变量时，生产者和消费者在同一个等待队列里，「放入后通知」可能唤醒的是另一个生产者，它检查条件不满足后又睡回去，真正该醒的消费者没有被唤醒。只用一个条件变量就得改用 `notify_all()`，代价是大量无谓的唤醒。

**易错点**：用 `if` 而不是循环检查条件；忘了在超时分支返回；在锁外修改队列；忘了通知另一类等待者，导致对方永远阻塞。

**与大模型应用的联系**：批处理推理的请求队列、限速的任务队列，本质上都是有界队列：队列满时让上游等待或失败，形成背压，防止请求无限堆积。

```python
import heapq
from collections import Counter


class _Entry:
    __slots__ = ("cnt", "word")

    def __init__(self, cnt, word):
        self.cnt, self.word = cnt, word

    def __lt__(self, other):           # 「更差」的更小：次数少；次数相同则字典序大
        if self.cnt != other.cnt:
            return self.cnt < other.cnt
        return self.word > other.word


def top_k_frequent(words, k):
    if k <= 0:
        return []
    heap = []                          # 小顶堆，堆顶是当前入选者中最差的一个
    for word, cnt in Counter(words).items():
        e = _Entry(cnt, word)
        if len(heap) < k:
            heapq.heappush(heap, e)
        elif heap[0] < e:              # 新词比堆顶好，替换堆顶
            heapq.heapreplace(heap, e)
    out = []
    while heap:
        out.append(heapq.heappop(heap).word)
    return out[::-1]                   # 弹出顺序是从差到好，反转
```

<sub>CS-ALGO-016</sub>　**思路**：先用 `Counter` 计数（$O(n)$），再维护大小为 $k$ 的**小顶堆**，堆顶是当前入选者中「最差」的一个：新词比堆顶好才替换堆顶。最后依次弹出（从差到好），反转即可。

**关键是比较规则**：「好」的定义是次数多，次数相同时字典序小。堆顶要放最差的，所以 `__lt__` 写成：次数少的更小；次数相同时**字典序大**的更小。如果直接把 `(次数, 词)` 元组放进小顶堆，次数相同时会把字典序小的词当成更差的先淘汰，结果正好反了：`["b", "a", "c", "a", "b", "c"]`、`k = 2` 会得到 `["c", "b"]`，正确答案是 `["a", "b"]`。

**复杂度**：计数 $O(n)$，堆操作 $O(m\log k)$，空间 $O(m)$。另一种 $O(n)$ 的做法是按次数分桶（桶的下标就是次数），再从高到低收集。

**工程上**：直接写 `heapq.nsmallest(k, cnt.items(), key=lambda kv: (-kv[1], kv[0]))` 即可，它内部同样维护大小为 $k$ 的堆。数据大到单机放不下时，先按词的哈希分片计数，每片求局部 Top-K，再归并。

## 七、简答题（每题 8 分，共 16 分）

**37.** 参考答案：

1. **进程**：资源分配的单位，拥有独立的虚拟地址空间、文件描述符表等。由内核抢占式调度；切换要换页表、刷新或失效 TLB，开销最大（微秒量级，加上缓存失效的间接开销）。隔离性最好，一个崩溃不影响别人；通信要靠 IPC。适合 CPU 密集且需要绕开 Python GIL 的计算、需要隔离的任务（代码沙箱、浏览器标签页）。
2. **线程**：CPU 调度的单位，同一进程的线程共享内存。由内核抢占式调度；切换要进入内核、保存恢复寄存器，开销在微秒量级，但不换地址空间。通信方便，但要自己同步，有竞态与死锁风险；每个线程有自己的栈（常见默认为 MB 级），线程数难以上万。适合 IO 密集、或需要调用阻塞库的任务。
3. **协程**：用户态的执行单元，由程序自己（事件循环或语言运行时）在等待点主动让出，协作式调度。切换只需保存少量上下文，不进内核，开销远小于线程；一个线程可以跑成千上万个协程。缺点是一个阻塞调用或长时间的计算会卡住同一线程上的所有协程。适合「连接多、大部分时间在等待」的高并发 IO。
4. **选择**：同时等几百个大模型 API 的响应，CPU 基本空闲，瓶颈在等待网络，首选协程（如 asyncio 加异步 HTTP 客户端），用信号量限制并发；如果只有阻塞的 SDK，可以放进线程池；如果拿到结果后还要做大量 CPU 计算，再把计算交给进程池。

评分要点：

- 说清进程是资源分配单位、线程是调度单位、协程是用户态执行单元（3 分）
- 说清三者的调度方式（抢占式与协作式）与切换开销差异的来源（3 分）
- 说出各自的适用场景与主要风险（2 分）
- 对「并发调用大量 API」给出协程为主、合理配合线程池或进程池的选择（2 分）

**38.** 参考答案：

1. **互斥锁（mutex）**：保证同一时刻只有一个线程进入临界区，保护共享数据。有「所有权」，谁加锁谁解锁。例：多个线程更新同一个 token 用量计数器、写同一个结果字典。
2. **信号量（semaphore）**：一个计数器，P 操作减 1（为 0 时阻塞），V 操作加 1；没有所有权，可以由别的线程释放。计数信号量用于限制同时使用某类资源的数量。例：上游 API 限制最多 20 个并发请求，用初值为 20 的信号量包住每次调用。
3. **条件变量（condition variable）**：配合互斥锁使用，让线程在「某个条件不满足」时睡眠，在其他线程改变状态并通知后醒来重新检查。例：工作线程等待「请求队列非空」或「凑够一个批次」，生产者放入请求后通知。
4. **区别小结**：互斥锁回答「谁能进来」；信号量回答「还能进来几个」；条件变量回答「什么时候该醒来」。二值信号量看起来像互斥锁，但没有所有权，也没有优先级继承等机制，不宜替代互斥锁。
5. **常见错误**：
   - 在持锁期间调用大模型 API 等耗时操作，锁被长时间占用，并发退化为串行；
   - 条件变量用 `if` 检查条件，没有用循环，被虚假唤醒或被抢先时出错；
   - 信号量的 P 与 V 不成对（异常路径漏掉 V），名额逐渐泄漏，最后所有请求都卡住，应该用 `with` 语句保证释放；
   - 多把锁的加锁顺序不一致，导致死锁。

评分要点：

- 说清互斥锁的作用与所有权，并给出例子（2 分）
- 说清信号量的计数语义与限制并发的用途，并给出例子（3 分）
- 说清条件变量要配合互斥锁、等待条件的用途，并给出例子（3 分）
- 说出至少两项常见错误（2 分）

<sub>CS-OS-016</sub>　**常见失分点**：把信号量和互斥锁说成一回事；说不出条件变量为什么必须配合锁使用（检查条件与进入等待必须是原子的，否则会丢失通知）；举例脱离场景；忽略「持锁做 IO」这个最常见的性能问题。
