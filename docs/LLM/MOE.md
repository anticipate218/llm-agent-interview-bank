<a name="LLM-MOE-001"></a>

### LLM-MOE-001　基础 · 考频 ★★★

Mixtral 8×7B 每层有 8 个专家、每个 token 选 2 个。它的总参数约为 46.7B，而不是 $8\times7=56$B，主要原因是：

- **A.** 8 个专家共享 FFN 的门控与升维矩阵，只有降维矩阵各自独立，因此省下了约 10B
- **B.** 只有 FFN 被复制成 8 份，注意力、Embedding、输出层等都只有一份
- **C.** 训练完成后路由器把 8 个专家蒸馏合并成 2 个，发布的权重只保存合并后的专家
- **D.** 每个专家只有 Mistral 7B 的一半大小，8 个专家加起来才相当于 4 个 7B 模型

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：MoE 只把 FFN 换成多个并列的专家，其余部分与稠密模型一样只有一份。

Mixtral 每层注意力约 41.9M 参数、每个专家约 176M 参数。56B 的算法相当于把整个 7B 模型复制 8 份，多算了 7 份注意力、Embedding 和输出层。按公开配置精确计算，总参数 46.7B，每个 token 激活约 12.9B，同样不是 $2\times7=14$B。

- A 错：专家之间不共享参数，各自是独立的 SwiGLU FFN。
- C 错：不存在合并专家的步骤；所有专家都要保存在显存里，路由器只决定每个 token 用哪几个。
- D 错：专家的结构与 Mistral 7B 的 FFN 相同，「7B」指的是对应的稠密模型规模，不是专家大小。

<sub>考点：MoE基本结构、代表模型　｜　出处：Mixtral of Experts, arXiv:2401.04088</sub>

</details>

<a name="LLM-MOE-003"></a>

### LLM-MOE-003　进阶 · 考频 ★★★

路由器为某个 token 输出 $E$ 个 logits $z$。做法甲：先对全部 $E$ 个 logits 做 Softmax，取概率最大的 $k$ 个，再在这 $k$ 个之内重新归一化；做法乙（Mixtral 的写法）：先保留最大的 $k$ 个 logits、其余置为 $-\infty$，再做 Softmax。两种做法得到的门控权重：

- **A.** 完全相同
- **B.** 甲的权重之和小于 1，乙的权重之和等于 1
- **C.** 只有 $k=1$ 时才相同
- **D.** 乙会让未被选中的专家也得到很小的非零权重

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：「先 Softmax、取 top-k、再归一化」与「先取 top-k、再 Softmax」在数学上等价。

Softmax 单调，两种做法选出的专家集合 $K$ 相同；对 $i\in K$：
$$\frac{p_i}{\sum_{j\in K}p_j}=\frac{e^{z_i}/Z}{\sum_{j\in K}e^{z_j}/Z}=\frac{e^{z_i}}{\sum_{j\in K}e^{z_j}}$$
分母里的全局归一化常数 $Z$ 被约掉，正好是只在 $k$ 个 logits 上做 Softmax 的结果，梯度也完全相同。

- B 错：描述的是「Softmax 后取 top-k 但**不再归一化**」，那时权重之和小于 1，与这两种做法都不同。是否归一化是真正会改变输出尺度的设计选择，不同模型的配置并不一样。
- C 错：对任意 $k$ 都成立。
- D 错：$e^{-\infty}=0$，未选中的专家权重严格为 0。

延伸：DeepSeek-V3 用 Sigmoid 为每个专家单独打分，再在选中的专家之间归一化，各专家的分数不再相互竞争同一个 Softmax 分母。

<sub>考点：门控路由与top-k　｜　出处：Mixtral of Experts, arXiv:2401.04088；DeepSeek-V3 技术报告 arXiv:2412.19437</sub>

</details>

<a name="LLM-MOE-007"></a>

### LLM-MOE-007　进阶 · 考频 ★★★

Switch Transformer 的负载均衡损失为 $\mathcal{L}_{aux}=\alpha\cdot N\sum_{i=1}^{N}f_iP_i$（$N$ 为专家数），其中 $f_i$ 是本批次中实际分给专家 $i$ 的 token 比例，$P_i$ 是路由器给专家 $i$ 的平均概率。下列说法正确的是：

- **A.** $f_i$ 由各 token 的 Softmax 概率直接求和得到，与 $P_i$ 一样可导，梯度经两者同时传回路由器
- **B.** 所有 token 都分给同一个专家时损失最小，这样能鼓励专家专精、减少跨设备的通信开销
- **C.** 乘以 $N$ 是为了让专家越多时均衡损失越重：专家多时失衡更严重，需要更强的约束
- **D.** $f_i$ 由 argmax 计数得到、不可导，梯度只经过 $P_i$；乘以 $N$ 使损失尺度与专家数无关

<details>
<summary>答案与解析</summary>

**答案：D**

**解析：**

**结论**：$f_i$ 衡量「实际分了多少」，$P_i$ 提供「可导的把手」，两者相乘让负载越高的专家受到越强的压制。

- $f_i=\frac1T\sum_x\mathbb{1}[\arg\max p(x)=i]$ 是计数，不可导；$P_i=\frac1T\sum_x p_i(x)$ 来自 Softmax，可导。对 $P_i$ 的梯度是 $\alpha Nf_i$：分到的 token 越多，其平均概率被往下压得越用力。
- 均匀时 $f_i=P_i=1/N$，$\sum_if_iP_i=N\cdot\frac{1}{N^2}=\frac1N$，乘以 $N$ 后恒为 1，换不同专家数时损失的尺度不变；论文中 $\alpha=10^{-2}$。

- A 错：$f_i$ 是按 argmax 计数得到的比例，不可导；由 Softmax 概率求平均、可导的是 $P_i$。
- B 错：恰好相反，损失在均匀分配时最小；全部集中到一个专家时 $N\sum_if_iP_i$ 接近 $N$。
- C 错：乘以 $N$ 是为了让损失与专家数无关，而不是放大。

<sub>考点：负载均衡辅助损失　｜　出处：Fedus 等, Switch Transformers, arXiv:2101.03961</sub>

</details>

<a name="LLM-MOE-012"></a>

### LLM-MOE-012　挑战 · 考频 ★★

训练 Decoder-only 的 MoE 模型时，某个专家收到的 token 超出了容量。有人提议：不按 token 在序列中的先后顺序决定丢弃谁，而是在整个序列（包括位置靠后的 token）里比较路由分数，优先保留分数高的 token（ST-MoE 中称为 Batch Prioritized Routing）。这样做的主要问题是：

- **A.** 需要对整个批次的路由分数做全局排序，开销随序列长度平方增长，大规模训练难以承受
- **B.** 分数高的 token 往往集中在少数热门专家上，按分数保留会让专家负载更加不均衡
- **C.** token 的去留取决于后面 token 的路由分数，相当于训练时偷看未来，推理时无法复现
- **D.** 优先保留的高分 token 会在多个专家中被重复计算，抵消了 MoE 稀疏计算的收益

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：在因果模型里，任何依赖「未来 token」的路由决策都会泄露信息。

ST-MoE 明确说明：容量不足时按从左到右的顺序丢弃，就是为了避免模型作弊；Batch Prioritized Routing 只能用在 Encoder 一侧，用在 Decoder 上模型会学会利用未来 token 的信息来改进当前预测。推理时后面的 token 还不存在，这种「信息」就消失了，效果会下降。

同样的问题出现在 Expert Choice 路由（让专家挑选 top-k 个 token）：论文在局限一节指出，它的实现需要同时看到过去与未来的 token，不能直接用于自回归生成。

- A 错：排序只需 $O(n\log n)$，开销并不大，问题不在算力。
- B 错：它只改变超出容量时「留下哪些 token」，每个 token 被路由到哪个专家并没有变，不会让负载更不均衡。
- D 错：每个 token 仍按 top-k 路由，只是在容量内被保留或丢弃，不会被重复计算。

<sub>考点：容量因子与token丢弃　｜　出处：Zoph 等, ST-MoE, arXiv:2202.08906（附录 D）；Zhou 等, Mixture-of-Experts with Expert Choice Routing, arXiv:2202.09368</sub>

</details>

<a name="LLM-MOE-014"></a>

### LLM-MOE-014　基础 · 考频 ★★

DeepSeekMoE 在路由专家之外设置了少量「共享专家」，它们对每个 token 都生效。引入共享专家最主要的目的是：

- **A.** 共享专家为路由器提供额外的训练信号，使负载自然趋于均衡，从而可以去掉均衡损失
- **B.** 承载各类 token 都需要的通用知识，减少路由专家之间的重复学习，让它们更专精
- **C.** 共享专家的参数冻结、不参与梯度更新，可以节省优化器状态，降低训练显存
- **D.** 保证每个 token 至少被一个专家处理，从而可以把路由专家的容量因子设为 0

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：共享专家是「知识分工」的设计：通用知识集中放一份，路由专家只学各自擅长的部分。

DeepSeekMoE 论文指出：常规路由下，分到不同专家的 token 可能都需要一些共同知识，于是多个专家各自学了一遍，造成参数冗余。把共享专家隔离出来专门承载这些共同知识，就能减轻冗余，让模型更省参数、路由专家更专精。为了保持计算量不变，激活的路由专家数会相应减少（如 DeepSeekMoE 16B 为 2 个共享专家 + 64 选 6 的路由专家）。

- A 错：共享专家不参与路由，与负载均衡无关。
- C 错：共享专家和其他参数一样正常训练。
- D 错：容量因子为 0 意味着路由专家完全不工作，没有意义。

<sub>考点：共享专家　｜　出处：Dai 等, DeepSeekMoE, arXiv:2401.06066</sub>

</details>

<a name="LLM-MOE-018"></a>

### LLM-MOE-018　进阶 · 考频 ★★★

DeepSeek-V3 的「无辅助损失负载均衡」给每个路由专家维护一个偏置 $b_i$。关于这个偏置，下列说法正确的是：

- **A.** 偏置同时加在选专家的分数和门控权重上，过载专家即使被选中，输出权重也会被压低
- **B.** 偏置是可学习参数，与路由器一起由反向传播更新，梯度来自序列级的均衡损失
- **C.** 偏置在推理时对路由分数做随机扰动，让各专家都有机会被选中，起到探索作用
- **D.** 偏置只影响选哪些专家，门控权重仍用原始分数；每步按负载规则增减，不靠反向传播

<details>
<summary>答案与解析</summary>

**答案：D**

**解析：**

**结论**：偏置只决定「选谁」，不决定「权重多少」，并且由规则更新而不是由梯度更新。

DeepSeek-V3 的做法：用 $s_i+b_i$ 做 top-k 选择，选中后门控权重仍由原始亲和度 $s_i$ 归一化得到；每步统计整个批次上各专家的负载，过载的 $b_i$ 减去 $\gamma$，欠载的加上 $\gamma$。由于不引入额外的损失项，均衡不再与语言模型目标争夺梯度。报告中 $\gamma$ 在前 14.3T token 取 0.001，最后 500B token 设为 0。

- A 错：如果偏置进入门控权重，就会直接扭曲输出的加权方式，这正是该方法刻意避免的。
- B 错：偏置不参与反向传播，按负载规则更新；序列级均衡损失是另一个独立的小项。
- C 错：偏置是训练中统计负载得到的确定值，推理时直接使用，不做随机扰动。

<sub>考点：无辅助损失负载均衡　｜　出处：DeepSeek-V3 技术报告 arXiv:2412.19437；Wang 等, Auxiliary-Loss-Free Load Balancing Strategy for Mixture-of-Experts, arXiv:2408.15664</sub>

</details>

<a name="LLM-MOE-022"></a>

### LLM-MOE-022　进阶 · 考频 ★★

DeepSeek-V3 训练时采用「节点受限路由」：每个 token 最多被发往 4 个节点。做法是先按「每个节点上亲和度最高的若干专家的分数之和」选出节点，再只在这些节点的专家中选 top-8。这样设计的主要目的是：

- **A.** 节点间 IB 带宽远低于 NVLink，限制节点数可压低跨节点通信，让它被计算掩盖
- **B.** 让每个 token 最多只激活 4 个路由专家，从而减少每个 token 的计算量和激活显存
- **C.** 保证各节点收到的 token 数相同，这样就不再需要偏置调节等其他负载均衡手段
- **D.** 每个节点只需存放被选中节点上的专家副本，从而降低模型的总参数量与显存占用

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：节点受限路由是为跨节点的专家并行通信「设上限」。

DeepSeek-V3 的集群中节点内用 NVLink、节点间用 InfiniBand，报告给出的 NVLink 带宽约为 IB 的 3.2 倍。token 先经 IB 发到目标节点，再在节点内经 NVLink 转发给对应的 GPU。限制每个 token 最多去 4 个节点，就把跨节点流量限制在可控范围，配合专门的通信内核与计算重叠，使 all-to-all 的开销基本被掩盖。DeepSeek-V2 也有类似的「设备受限路由」（最多 3 个设备）。

- B 错：每个 token 仍然激活 8 个路由专家，只是这 8 个专家分布在至多 4 个节点上。
- C 错：节点受限路由只限制每个 token 去几个节点，不能保证各节点负载相同；负载均衡靠的仍是偏置调整等手段。
- D 错：路由方式与参数量无关，每个节点存放的专家由专家并行的划分决定。

<sub>考点：专家并行与All-to-All　｜　出处：DeepSeek-V3 技术报告 arXiv:2412.19437；DeepSeek-V2 技术报告 arXiv:2405.04434</sub>

</details>

<a name="LLM-MOE-028"></a>

### LLM-MOE-028　进阶 · 考频 ★★★

把一个 MoE 模型与两个稠密模型比较：稠密模型 A 的参数量等于 MoE 的**激活参数**，稠密模型 B 的参数量等于 MoE 的**总参数**，三者用相同的数据训练。下列判断最符合经验的是：

- **A.** MoE 与 A 每个 token 的计算量相同，推理成本与效果也基本相同，多出的专家主要起冗余备份作用
- **B.** 在相同训练数据下，MoE 的效果通常超过 B，因为专家分工更细、参数利用更专
- **C.** 与 A 计算量相当、效果通常更好，但显存与通信开销大得多；与 B 相比计算量小得多，效果通常不如 B
- **D.** MoE 的显存需求与 A 相同（只加载激活专家），每个 token 的计算量却与 B 相同

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：MoE 用「更多参数（显存）」换「同等算力下更好的效果」，效果一般介于同激活量的稠密模型和同总参数的稠密模型之间。

- 同算力比较：Switch Transformer 报告在相同计算量下，预训练速度相对 T5-Base 最高提升约 7 倍；Mixtral（激活约 13B）在多数基准上达到或超过 Llama 2 70B。
- 同总参数比较：稠密模型每个 token 用上全部参数，计算量大得多，同样数据下通常效果更好，但训练与推理都贵得多。
- 工程代价：MoE 要装下全部专家，专家并行带来 all-to-all 通信，还需要负载均衡。

- A 错：计算量相当，但显存、通信和小 batch 效率都不同；多出的专家提供了额外容量，效果通常更好。
- B 错：相同数据下，每个 token 都用上全部参数的稠密模型 B 通常更强；MoE 的优势在同等算力，而不是同等总参数。
- D 错：说反了，显存按总参数、计算按激活参数。

<sub>考点：Dense与MoE对比　｜　出处：Fedus 等, Switch Transformers, arXiv:2101.03961；Mixtral of Experts, arXiv:2401.04088</sub>

</details>

<a name="LLM-MOE-033"></a>

### LLM-MOE-033　进阶 · 考频 ★★

推荐系统中的 MMoE（Multi-gate Mixture-of-Experts）与大模型中的稀疏 MoE 都叫「混合专家」。二者最主要的区别是：

- **A.** MMoE 为每个任务设门控、对全部专家软加权；稀疏 MoE 为每个 token 只选 top-k 专家
- **B.** MMoE 对每个样本只激活 1 个专家以节省计算，大模型的 MoE 则对每个 token 激活全部专家
- **C.** 二者结构和门控方式完全一致，只是应用领域不同：一个用于推荐排序，一个用于语言模型
- **D.** MMoE 的专家是完整的 Transformer 模型，而大模型 MoE 的专家通常是单个注意力头

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：MMoE 解决「多个任务如何共享表示」，稀疏 MoE 解决「如何在计算量不变时扩大参数」。

MMoE（Ma 等, KDD 2018）中，各任务的输出为 $f^k(x)=\sum_i g^k(x)_i\,f_i(x)$，其中 $g^k$ 是任务 $k$ 自己的 Softmax 门控；通常所有专家都参与计算，属于稠密的软门控。大模型的 MoE 则对每个 token、每一层做稀疏的 top-k 选择，未被选中的专家不计算，并因此引出负载均衡、容量与专家并行等问题。

- B 错：说反了，而且 MMoE 一般不做稀疏选择。
- C 错：目标、门控方式和计算模式都不同。
- D 错：大模型 MoE 的专家通常是 FFN，不是注意力头；MMoE 的专家一般是小型神经网络。

<sub>考点：MoE基本结构　｜　出处：Ma 等, Modeling Task Relationships in Multi-task Learning with Multi-gate Mixture-of-Experts, KDD 2018</sub>

</details>

<a name="LLM-MOE-009"></a>

### LLM-MOE-009　进阶 · 考频 ★★

关于 MoE 训练中的负载均衡辅助损失及相关手段，下列说法**正确**的有：

- **A.** 训练时除了看损失值，还应监控各专家的负载分布、路由熵和丢弃率，及早发现路由崩塌
- **B.** DeepSeek-V3 主要改用无辅助损失的偏置调节来均衡负载，减少对语言模型目标的干扰
- **C.** 均衡损失的目标是让每个专家学到相同的知识，这样任一专家都能替代其他专家，提高容错
- **D.** ST-MoE 的路由器 z-loss 惩罚过大的路由 logits，主要用于提升训练的数值稳定性
- **E.** 均衡损失系数过大会与语言模型目标相互拉扯、损害效果，Switch Transformer 取 0.01

<details>
<summary>答案与解析</summary>

**答案：ABDE**

**解析：**

**结论**：A、B、D、E 正确。

- A 对：负载曲线发散、路由熵持续下降，常是路由崩塌的前兆。
- B 对：DeepSeek-V3 给每个路由专家维护一个偏置，只在选 top-k 时加到亲和度分数上，每个训练步后按负载增减，不经过反向传播；均衡因此主要不再依赖辅助损失的梯度，只保留了一个系数极小（0.0001）的序列级均衡损失，防止单条序列内部极端失衡。另外注意，均衡损失只是软约束，批次内的瞬时失衡仍会超出容量；不丢 token 需要容量足够大或采用 dropless 的实现。
- C 错：均衡的是 **token 的分配**，不是知识。专家恰恰要有所分工，「让所有专家一样」会让 MoE 失去意义。
- D 对：z-loss 对每个 token 的 log-sum-exp 取平方再平均：$L_z=\frac1B\sum_i\big(\log\sum_je^{x_{ij}}\big)^2$，系数取 0.001。它鼓励 logits 保持较小的数值，减少指数运算中的舍入误差，ST-MoE 报告它稳定训练且不损失效果。
- E 对：Switch 在 $10^{-1}$～$10^{-5}$ 之间扫描后选了 $10^{-2}$，既能较快均衡，又不干扰训练损失。这也是后来出现无辅助损失方案的动机。

<sub>考点：负载均衡辅助损失　｜　出处：Fedus 等, Switch Transformers, arXiv:2101.03961；Zoph 等, ST-MoE, arXiv:2202.08906；DeepSeek-V3 技术报告 arXiv:2412.19437</sub>

</details>

<a name="LLM-MOE-017"></a>

### LLM-MOE-017　进阶 · 考频 ★★

关于细粒度专家与共享专家，下列说法**正确**的有：

- **A.** 共享专家对每个 token 都计算，不参与路由选择，相当于一条始终开启的稠密分支
- **B.** 有了共享专家吸收通用 token 的负载，路由专家之间就不再需要负载均衡措施
- **C.** 专家切得越细，单个矩阵乘越小，GPU 利用率可能下降，分发通信也更碎
- **D.** 细粒度切分在保持每个 token 计算量不变的同时，也把模型的总参数量缩小为原来的 1/m
- **E.** 细粒度切分把专家中间维度缩为 1/m、激活数扩大为 m 倍，每个 token 的计算量基本不变

<details>
<summary>答案与解析</summary>

**答案：ACE**

**解析：**

- A 对：共享专家相当于一个始终开启的稠密 FFN 分支，与路由专家的输出相加。
- B 错：路由专家之间仍可能负载失衡，DeepSeek-V3 在使用共享专家的同时，仍然采用了无辅助损失的偏置均衡和序列级均衡损失。
- C 对：细粒度的代价在工程侧，路由与 all-to-all 分发的开销都会增加：每个专家分到的 token 更少、矩阵更小，算子效率下降；每个 token 要发往更多专家，分发与回收的通信更碎，需要专门的分组矩阵乘与通信优化。
- D 错：切分只是把同样多的参数分成更多份，总参数量不变。
- E 对：这是 DeepSeekMoE 的做法，例如 DeepSeek-V3 每个路由专家的中间维度只有 2048，每个 token 激活 8 个。

- **A.** 在无辅助损失的偏置均衡之外，还保留了一个系数极小（0.0001）的序列级均衡损失，防止单条序列内部极端失衡

- **D.** 偏置的更新速度 $\gamma$ 在整个预训练过程中保持不变

### LLM-MOE-027　进阶 · 考频 ★★

关于 MoE 模型的推理部署，下列说法**正确**的有：

- **A.** Mixtral 8×7B 的每个专家都带有独立的注意力层，因此每个 token 的 KV Cache 约为 Mistral 7B 的 8 倍

- **C.** 与同总参数的稠密模型相比，MoE 每个 token 的计算量更大，因为额外多了路由器的计算

- D 对：没有被选中的专家也随时可能被下一个 token 用到，必须常驻。
- E 错：吞吐还受 batch 大小（每个专家分到的 token 少时矩阵乘受带宽限制）、专家并行的 all-to-all 通信、负载失衡等因素影响，实际往往低于同激活参数的稠密模型。

## 判断题

<a name="LLM-MOE-004"></a>

### LLM-MOE-004　进阶 · 考频 ★★

Switch Transformer 每个 token 只选 1 个专家（top-1）。如果把门控改成「先选出 top-1，再只在被选中的那 1 个专家上做 Softmax」，门控权重就恒为 1，语言模型损失将无法通过门控权重把梯度传回路由器。

<details>
<summary>答案与解析</summary>

**答案：✅ 正确**

**解析：**

**正确**。只有一个元素的 Softmax 恒等于 1，输出变成 $y=E_i(x)$。路由器的 logits 只通过「选哪个专家」这个离散的 argmax 影响输出，而 argmax 不可导，语言模型损失的梯度传不到路由器。

Switch 的做法是用**全体专家上的 Softmax** 概率 $p_i(x)$ 乘以被选专家的输出：$y=p_i(x)E_i(x)$，$p_i(x)<1$ 且依赖于所有 logits，路由器因此可导。论文明确指出门控值让路由器可微。早先 Shazeer 等（2017）曾推测必须 $k>1$ 才能让路由器学到有意义的梯度，Switch 用这种门控证明 top-1 也可行。

注意：即使门控恒为 1，负载均衡辅助损失仍能通过 $P_i$ 给路由器梯度，但那只告诉它「要均衡」，不告诉它「哪个专家对当前 token 更有用」。

<sub>考点：门控路由与top-k　｜　出处：Fedus 等, Switch Transformers, arXiv:2101.03961</sub>

</details>

<a name="LLM-MOE-011"></a>

### LLM-MOE-011　基础 · 考频 ★★

某个 token 在一个 MoE 层因超出专家容量而被丢弃后，它在这一层的输出是全零向量，这个 token 的信息在后续层中就丢失了。

<details>
<summary>答案与解析</summary>

**答案：❌ 错误**

**解析：**

**错误**。MoE 子层外面有残差连接：$h_{out}=h+\mathrm{MoE}(h)$。token 被丢弃时 $\mathrm{MoE}(h)=0$，但 $h$ 本身原样传到下一层。Switch Transformer 的描述就是被丢弃的 token「通过残差连接直接传到下一层」。

所以丢弃的代价是「这个 token 少经过了一次 FFN 加工」，而不是信息丢失。top-k 路由时，若只是其中一个分配被丢弃，token 仍会得到其他专家的输出。不过丢弃过多仍会伤害效果，Switch 报告的丢弃比例通常低于 1%，近年的模型更倾向于完全不丢弃。

<sub>考点：容量因子与token丢弃　｜　出处：Fedus 等, Switch Transformers, arXiv:2101.03961</sub>

</details>

<a name="LLM-MOE-026"></a>

### LLM-MOE-026　进阶 · 考频 ★★

MoE 模型推理时，某个请求的输出只取决于它自己的输入：即使推理框架给每个专家设置了容量上限，一个 token 会不会被丢弃也只与它自己的路由分数有关，与同一批次的其他请求无关。

<details>
<summary>答案与解析</summary>

**答案：❌ 错误**

**解析：**

**错误**。容量是按批次分配的：一个 token 能否进入某个专家，取决于同一批次里还有多少其他 token 也选了这个专家、排在它前面。于是同一个请求和不同的请求拼在一起时，可能一次被丢弃、一次没有，输出随批次组成而变化，既带来不确定性，也会出现「别人的请求影响我的结果」。

## 填空题

<a name="LLM-MOE-010"></a>

### LLM-MOE-010　基础 · 考频 ★★

某 MoE 层有 16 个专家、top-2 路由，一个批次共 4096 个 token，容量因子 CF = 1.25。按「容量 = CF × 每专家的平均分配数」计算，每个专家最多接收 ____ 个 token 分配；若专家 3 这一批收到 800 个分配，其中 ____ 个会被丢弃。

<details>
<summary>答案与解析</summary>

**答案：** (1) 640；(2) 160

**解析：**

- 总分配数 $4096\times2=8192$，平均每个专家 $8192/16=512$；
- 容量 $=1.25\times512=640$；
- 专家 3 收到 800 个，超出 $800-640=160$ 个，这些分配不经过专家 3 的计算。

Switch Transformer（top-1）的公式是「每批 token 数 / 专家数 × 容量因子」；top-k 时平均分配数要乘以 $k$。容量因子越大，丢弃越少，但每个专家都要按容量预留计算、显存和通信缓冲，空出来的部分就是浪费。ST-MoE 的测量中，训练容量因子从 1.25 提到 2.0，单步耗时增加 7%～14%。

<sub>考点：容量因子与token丢弃　｜　出处：Fedus 等, Switch Transformers, arXiv:2101.03961；Zoph 等, ST-MoE, arXiv:2202.08906</sub>

</details>

**解析：**

- 切分后：$\binom{32}{8}=10{,}518{,}300$，组合方式多了约 37 万倍；
- 隔离 1 个共享专家后：$\binom{31}{7}=2{,}629{,}575$。

<a name="LLM-MOE-008"></a>

### LLM-MOE-008　进阶 · 考频 ★★★

一个 4 专家、top-1 路由的 MoE 层，某批次统计到：实际分配比例 $f=(0.5,\ 0.25,\ 0.125,\ 0.125)$，平均路由概率 $P=(0.4,\ 0.3,\ 0.15,\ 0.15)$，系数 $\alpha=0.01$。

(1) 计算 $\mathcal{L}_{aux}=\alpha N\sum_i f_iP_i$；
(2) 与完全均匀的路由相比，这个值高多少？
(3) 把 $f$ 视为常数，$\mathcal{L}_{aux}$ 对 $P_1$ 与 $P_3$ 的偏导各是多少？这说明梯度如何推动路由器？

<details>
<summary>答案与解析</summary>

**答案：(1) 0.0125；(2) 均匀时为 0.01，现在高 25%；(3) ∂L/∂P₁ = 0.02，∂L/∂P₃ = 0.005，负载越高的专家概率被压得越用力**

**解析：**

**(1)** $\sum_if_iP_i=0.5\times0.4+0.25\times0.3+0.125\times0.15\times2=0.2+0.075+0.0375=0.3125$；
$\mathcal{L}_{aux}=0.01\times4\times0.3125=0.0125$。

**(2)** 均匀时 $f_i=P_i=0.25$，$\sum_if_iP_i=4\times0.0625=0.25$，$\mathcal{L}_{aux}=0.01\times4\times0.25=0.01$。现在高出 $0.0025$，即 25%。

**(3)** $\frac{\partial\mathcal{L}}{\partial P_i}=\alpha Nf_i$：$P_1$ 为 $0.01\times4\times0.5=0.02$，$P_3$ 为 $0.01\times4\times0.125=0.005$。由于各专家的概率经 Softmax 相互关联、总和为 1，下降的梯度会把概率质量从高负载专家（专家 1）挪向低负载专家（专家 3、4），路由逐渐趋于均衡。

**补充**：这个损失的绝对值很小（0.0125 对比语言模型损失的 2～3），但它的作用是持续施加方向一致的梯度；$\alpha$ 太大会与语言模型目标相互拉扯。

### LLM-MOE-023　挑战 · 考频 ★★

一个 MoE 层用 8 张卡做专家并行，每张卡放 8 个专家。某一步 dispatch 之后，前 7 张卡各收到 4096 个 token 分配，第 8 张卡因为放着两个热门专家收到 8192 个。假设每张卡的专家计算时间与收到的分配数成正比，各卡要等最慢的卡算完才能进入下一次 all-to-all。

(1) 与完全均衡（各卡收到同样多的分配）相比，这一层专家计算的耗时是多少倍？8 张卡的平均利用率是多少？
(2) 若按「每卡容量 = 1.25 × 平均分配数」截断，第 8 张卡要丢弃多少个分配？约占全部分配的百分之几？
(3) 推理部署时，DeepSeek-V3 用什么手段缓解这种热点专家问题？

<details>
<summary>答案与解析</summary>

**答案：(1) 约 1.78 倍，平均利用率约 56%；(2) 丢弃 2432 个，约占全部分配的 6.6%；(3) 冗余专家：按统计的负载把高负载专家复制到其他卡上，并定期调整**

**解析：**

**(1)** 总分配数 $7\times4096+8192=36864$，均衡时每卡 $36864/8=4608$。实际耗时由最慢的卡决定：$8192/4608\approx1.78$ 倍；平均利用率 $4608/8192\approx56\%$，即近一半的算力在等待。

**(2)** 每卡容量 $1.25\times4608=5760$，第 8 张卡丢弃 $8192-5760=2432$ 个分配，占 $2432/36864\approx6.6\%$。这些分配对应的 token 只能经残差连接跳过这一层的专家计算。

**(3)** DeepSeek-V3 推理时部署**冗余专家**：根据线上统计的专家负载，把高负载专家复制到其他卡上（Prefill 阶段有 32 个冗余专家，每卡在 8 个原专家之外再放 1 个冗余专家），并定期（如每 10 分钟）重新调整。训练侧则依靠负载均衡（偏置调整）让热点不出现。

**启示**：专家并行下，负载失衡不只是「某些专家训练不足」的问题，还直接变成「整层被最慢的卡拖住」的系统问题，所以负载均衡既是算法问题也是性能问题。

### LLM-MOE-025　挑战 · 考频 ★★

某 MoE 模型每层有 256 个路由专家，每个 token 激活 8 个。Decode 时一步共处理 $B$ 个 token，路由大致均匀。对一个专家的 FFN 矩阵乘：要从显存读入它的全部权重（BF16，每参数 2 字节），对分到的每个 token 做「每参数 2 次浮点运算」的计算（忽略激活的读写）。

(1) 每个专家平均分到多少个 token？写成 $B$ 的函数。
(2) 这个矩阵乘的算术强度（浮点运算数 / 读取的权重字节数）约为多少？
(3) 以 H100 为例（BF16 稠密算力约 989 TFLOPS，显存带宽约 3.35 TB/s），一步大约要处理多少个 token，专家矩阵乘才能从带宽受限进入计算受限？$B=64$ 时每个专家分到几个 token？

<details>
<summary>答案与解析</summary>

**答案：(1) 8B/256 = B/32；(2) 约等于每个专家分到的 token 数，即 B/32 FLOPs/字节；(3) 拐点约 295 FLOPs/字节，需要 B ≈ 9400；B = 64 时每个专家平均只分到 2 个 token**

**解析：**

**(1)** 一步共有 $8B$ 次分配，均分到 256 个专家，每个专家平均 $n=B/32$ 个 token。

**(2)** 设专家参数为 $P$：计算量 $2nP$，读权重 $2P$ 字节，算术强度 $\approx n$ FLOPs/字节。

**(3)** 计算受限的拐点约为 $989/3.35\approx295$ FLOPs/字节，需要 $n\approx295$，即 $B\approx295\times32\approx9400$ 个 token。$B=64$ 时 $n=2$，算术强度只有拐点的 1% 左右，专家矩阵乘几乎完全受带宽限制。

**结论**：激活越稀疏（专家越多、$k/E$ 越小），每个专家分到的 token 越少，需要的总 batch 越大。这就是大 MoE 推理要靠**大规模专家并行**把很多请求的 token 汇聚起来（DeepSeek-V3 的 Decode 部署单元有 320 张卡，每卡约放一个专家），并配合 PD 分离给 Decode 阶段攒出大 batch 的原因；小 batch 场景下，MoE「按激活参数计费」的计算优势很难兑现。

### LLM-MOE-005　进阶 · 考频 ★★

下面的代码对 3 个 token、4 个专家的路由 logits 做 top-2 选择。输出是什么？

```python
import numpy as np

logits = np.array([[2.0, 1.0, 0.0, -1.0],
                   [0.0, 3.0, 1.0, 2.0],
                   [1.0, 1.5, 3.0, 0.5]])
k = 2
idx = np.argsort(-logits, axis=1)[:, :k]
top = np.take_along_axis(logits, idx, axis=1)
w = np.exp(top) / np.exp(top).sum(axis=1, keepdims=True)      # 只在 top-k 内做 Softmax
p = np.exp(logits) / np.exp(logits).sum(axis=1, keepdims=True)  # 全体 Softmax
pk = np.take_along_axis(p, idx, axis=1)                          # 不重新归一化
print(idx.tolist())
print(np.round(w, 2).tolist())
print(np.round(pk.sum(axis=1), 2).tolist())
print(np.bincount(idx.ravel(), minlength=4).tolist())
```

<details>
<summary>答案与解析</summary>

**答案（程序输出）：**

```text
[[0, 1], [1, 3], [2, 1]]
[[0.73, 0.27], [0.73, 0.27], [0.82, 0.18]]
[0.88, 0.88, 0.85]
[1, 3, 1, 1]
```

**解析：**

1. **选专家**：按 logits 从大到小取前 2 个。token 0 选专家 0、1；token 1 选专家 1（3.0）、3（2.0）；token 2 选专家 2（3.0）、1（1.5）。
2. **门控权重**：只在两个 logits 上做 Softmax。差值为 1 时是 $\sigma(1)\approx0.73$ 与 0.27；差值为 1.5 时是 $\sigma(1.5)\approx0.82$ 与 0.18。
3. **不重新归一化**：全体 Softmax 后，被选中的两个概率之和只有 0.88、0.88、0.85，其余概率分给了未选中的专家。如果直接用它们加权，输出的尺度会随路由的「确定程度」波动。
4. **负载**：专家 1 被 3 个 token 选中，其余各 1 次。即使只有 3 个 token，负载也已经不均匀，这正是需要负载均衡的原因。

**解析：**

## 编程题

<a name="LLM-MOE-006"></a>

### LLM-MOE-006　挑战 · 考频 ★★★

用 numpy 实现一个 MoE 层的前向计算，并同时返回 Switch 式负载均衡损失：

```python
def moe_forward(x, W_r, experts, k) -> tuple[np.ndarray, float]: ...
```

- `x`：形状 `(N, d)`，N 个 token；`W_r`：路由器权重，形状 `(d, E)`；
- `experts`：长度为 E 的列表，第 $e$ 个元素是 `(W1, W2)`，该专家的输出为 `relu(x @ W1) @ W2`；
- 路由：对 `x @ W_r` 做数值稳定的 Softmax 得到概率，每个 token 取概率最大的 k 个专家（并列时取编号小的），门控权重为这 k 个概率在其内部重新归一化；
- 输出 `y`：每个 token 的输出是被选中专家输出的加权和；要求按专家批量计算（可以对专家循环，不要对 token 循环）；
- 均衡损失（不乘 $\alpha$）：$E\sum_i f_iP_i$，其中 $f_i$ 是全部 $N\cdot k$ 次分配中落到专家 $i$ 的比例，$P_i$ 是全部 token 对专家 $i$ 的平均路由概率。

<details>
<summary>答案与解析</summary>

**参考实现：**

```python
import numpy as np


def moe_forward(x, W_r, experts, k):
    N, d = x.shape
    E = W_r.shape[1]
    logits = x @ W_r
    logits = logits - logits.max(axis=1, keepdims=True)          # 数值稳定
    probs = np.exp(logits)
    probs /= probs.sum(axis=1, keepdims=True)                     # (N, E)
    idx = np.argsort(-probs, axis=1, kind="stable")[:, :k]        # (N, k) 选出的专家
    gate = np.take_along_axis(probs, idx, axis=1)
    gate = gate / gate.sum(axis=1, keepdims=True)                 # 在 k 个之内归一化
    y = np.zeros_like(x)
    for e, (W1, W2) in enumerate(experts):                        # 按专家收集 token
        tok, slot = np.nonzero(idx == e)
        if tok.size:
            h = np.maximum(x[tok] @ W1, 0) @ W2
            np.add.at(y, tok, gate[tok, slot, None] * h)
    f = np.bincount(idx.ravel(), minlength=E) / idx.size          # 实际分配比例 f_i
    P = probs.mean(axis=0)                                        # 平均路由概率 P_i
    aux = E * float(np.sum(f * P))
    return y, aux
```

**测试用例：**

```python
rng = np.random.default_rng(0)

x = rng.normal(size=(N, d))
W_r = rng.normal(size=(d, E))
experts = [(rng.normal(size=(d, H)), rng.normal(size=(H, d))) for _ in range(E)]

def ref(x, k):
    p = np.exp(x @ W_r)
    p /= p.sum(1, keepdims=True)
    out, cnt = np.zeros_like(x), np.zeros(E)
    for n in range(N):
        top = np.argsort(-p[n])[:k]
        g = p[n, top] / p[n, top].sum()
        for gi, e in zip(g, top):
            W1, W2 = experts[e]
            out[n] += gi * (np.maximum(x[n] @ W1, 0) @ W2)
            cnt[e] += 1
    return out, E * np.sum(cnt / (N * k) * p.mean(0))

for k in (1, 2, 3):
    y, aux = moe_forward(x, W_r, experts, k)
    y0, aux0 = ref(x, k)
    assert y.shape == (N, d) and np.allclose(y, y0) and np.isclose(aux, aux0)

# k = E 时退化为所有专家的稠密加权混合
y, _ = moe_forward(x, W_r, experts, E)
p = np.exp(x @ W_r)
p /= p.sum(1, keepdims=True)
dense = sum(p[:, [e]] * (np.maximum(x @ W1, 0) @ W2) for e, (W1, W2) in enumerate(experts))
assert np.allclose(y, dense)

# 路由概率均匀时 aux = 1
_, aux = moe_forward(x, np.zeros((d, E)), experts, 2)
assert np.isclose(aux, 1.0)

# 全部 token 挤到同一个专家且概率接近 1 时，aux 接近 E
W_big = np.zeros((d, E))
W_big[:, 0] = 50.0
_, aux = moe_forward(np.abs(x) + 0.1, W_big, experts, 1)
assert abs(aux - E) < 1e-6

# 数值稳定：logits 很大时不出现 NaN
y, aux = moe_forward(x * 1000, W_r, experts, 2)
assert np.isfinite(y).all() and np.isfinite(aux)
```

**解析：**

**思路**：
1. 路由：减去每行最大值后做 Softmax；稳定排序取前 k 个，门控权重在 k 个之内归一化；
2. 分发：对每个专家，用 `np.nonzero(idx == e)` 找出选中它的 token 及其所在的槽位，一次矩阵乘算完这批 token，再按门控权重加回各自的输出位置。真实系统中这一步就是专家并行的 all-to-all 分发与回收；
3. 均衡损失：$f_i$ 用分配计数（不可导），$P_i$ 用路由概率均值（可导）。路由均匀时 $P_i=1/E$，$E\sum_if_iP_i=\sum_if_i=1$；全部挤到一个专家时接近 $E$。

**复杂度**：路由 $O(NdE)$；专家计算 $O(Nk\cdot d\cdot H)$，只与 $k$ 有关，与专家总数 $E$ 无关。

**易错点**：门控权重用了未归一化的概率或 logits；$f_i$ 的分母写成 $N$ 而不是 $N\cdot k$（$k>1$ 时比例之和不为 1）；逐 token 循环导致无法批量计算；Softmax 前没有减最大值。

<sub>考点：MoE基本结构、门控路由与top-k、负载均衡辅助损失　｜　出处：Switch Transformers, arXiv:2101.03961</sub>

</details>

### LLM-MOE-013　进阶 · 考频 ★★

什么是专家容量与容量因子？容量因子设大、设小各有什么代价？被丢弃的 token 会怎样？为什么近年的大模型（如 DeepSeek-V3）倾向于训练和推理都不丢 token，它们靠什么做到？

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **定义**：为了让每个专家的计算形状固定、便于批量计算与通信，给每个专家设上限：容量 = 容量因子 × 每个专家的平均分配数（$\mathrm{CF}\times Tk/E$）。
2. **设小**：容量紧，瞬时失衡时超出的分配被丢弃，token 少经过一次 FFN，效果下降；
   **设大**：丢得少，但每个专家都要按容量预留计算、激活显存和 all-to-all 的缓冲，空位就是浪费。ST-MoE 中训练容量因子从 1.25 升到 2.0，单步耗时增加 7%～14%。
3. **被丢弃的 token**：通过残差连接原样进入下一层，丢的是这一层的专家计算，而不是信息本身；被丢弃的往往集中在热门专家上。训练与评测时的容量因子还可以不同（评测时调大能略微提升效果）。
4. **为什么倾向于不丢**：丢弃让输出依赖于同一批次里的其他 token（训练、推理行为不一致，结果不确定），并直接损伤效果；容量缓冲在大规模专家并行下代价也很高。
5. **怎么做到**：
   - 更好的负载均衡：DeepSeek-V3 用只影响选择的偏置做无辅助损失均衡，再加系数极小的序列级均衡损失；
   - 限制路由范围：每个 token 最多发往 4 个节点，控制通信；
   - 推理侧部署冗余专家，把热门专家复制到多张卡上；
   - 工程上用可变长度的分组矩阵乘（如 MegaBlocks 把 MoE 计算改写为块稀疏运算），不再需要固定容量。

**评分要点（共 10 分）：**

- 正确给出容量与容量因子的定义及公式（2 分）
- 说明容量因子大小两方面的代价（2 分）
- 说明被丢弃的 token 经残差传递，以及训练与评测容量可以不同（2 分）
- 说明不丢 token 的动机（效果、确定性、一致性）（2 分）
- 给出实现不丢弃的手段：更好的均衡、限制路由、冗余专家、dropless 计算（2 分）

**讲解：**

**常见失分点**：把容量因子说成「激活专家数」；认为被丢弃的 token 输出为零、信息丢失；只说「容量因子越大越好」；不知道 dropless 实现与负载均衡是两个互补的方向。

<sub>考点：容量因子与token丢弃　｜　出处：Fedus 等, arXiv:2101.03961；Zoph 等, ST-MoE, arXiv:2202.08906；Gale 等, MegaBlocks, arXiv:2211.15841；DeepSeek-V3 技术报告 arXiv:2412.19437</sub>

</details>

<a name="LLM-MOE-021"></a>

### LLM-MOE-021　挑战 · 考频 ★★

「辅助损失」与「无辅助损失」两种负载均衡方案分别是怎样工作的？为什么说辅助损失存在两难？无辅助损失方案在落地时又有哪些需要注意的细节或局限？

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **辅助损失**：在语言模型损失之外加 $\alpha N\sum_if_iP_i$。$f_i$（实际分配比例）不可导，梯度经 $P_i$（平均路由概率）推动路由器把概率从高负载专家挪向低负载专家。还可以按设备、按节点再加一层均衡损失（如 DeepSeek-V2 的设备级与通信均衡损失）。
2. **两难**：均衡损失的梯度与语言模型目标方向不同。$\alpha$ 大了，路由被迫追求均匀，挑选专家时不再完全按「谁更合适」，效果受损；$\alpha$ 小了又压不住「强者愈强」的路由崩塌。
3. **无辅助损失**：给每个专家一个偏置，只在 top-k 选择时加到分数上，门控权重仍用原始分数；每步按负载做符号更新（过载减 $\gamma$、欠载加 $\gamma$），不经过反向传播，不与主目标争夺梯度。Wang 等（2024）报告它的效果与均衡度都优于辅助损失方案，DeepSeek-V3 采用了它。
4. **注意事项与局限**：
   - **均衡的粒度**：偏置按批次统计，单条序列或单个微批次内仍可能失衡，DeepSeek-V3 因此保留了系数极小的序列级损失；反过来，在过细的粒度上强制均衡会妨碍专家按领域分工，Qwen3 采用全局批次的均衡损失就是为了鼓励专家专精；
   - **步长 $\gamma$**：太大会让负载来回振荡，太小则调整太慢；DeepSeek-V3 在训练末期把 $\gamma$ 设为 0；
   - **路由偏离**：偏置会把部分 token 送到并非亲和度最高的专家，用「选择上的小偏离」换取均衡；
   - **推理时的负载**：线上流量的分布与训练数据不同，仍需要冗余专家等部署手段；
   - **监控**：依然要看每个专家的负载、路由熵和偏置的变化范围。

**评分要点（共 10 分）：**

- 正确说明辅助损失的公式与梯度作用方式（2 分）
- 说明辅助损失系数的两难（2 分）
- 正确说明无辅助损失方案：偏置只用于选择、门控用原分数、符号更新且不经过反向传播（3 分）
- 指出至少两项落地细节或局限（均衡粒度、γ 选择、路由偏离、推理负载等）（3 分）

**讲解：**

**常见失分点**：以为无辅助损失方案「完全不需要任何均衡损失」（DeepSeek-V3 仍有极小的序列级损失）；把偏置说成会影响门控权重；只背公式不说两难的本质（两个目标争夺同一组梯度）；忽略均衡粒度对专家专精的影响。

<sub>考点：无辅助损失负载均衡、负载均衡辅助损失　｜　出处：Wang 等, arXiv:2408.15664；DeepSeek-V3 技术报告 arXiv:2412.19437；Qwen3 技术报告 arXiv:2505.09388</sub>

</details>

<a name="LLM-MOE-029"></a>

### LLM-MOE-029　进阶 · 考频 ★★★

MoE 为什么能在大幅增加参数量的同时，不明显增加每个 token 的计算量？它的代价有哪些？什么场景更适合 MoE，什么场景更适合稠密模型？

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **原理（条件计算）**：MoE 把 FFN 换成 $E$ 个专家，路由器为每个 token 只选 $k$ 个计算。总参数随 $E$ 增长，而每个 token 的计算只涉及注意力、共享部分和 $k$ 个专家，训练约 $6N_{act}$、推理约 $2N_{act}$ FLOPs/token。
2. **代价**：
   - 显存：所有专家都要常驻，部署成本按总参数算；
   - 通信：专家并行每层两次 all-to-all，跨节点时尤其昂贵；
   - 负载均衡：需要辅助损失或偏置调整，失衡会导致路由崩塌、丢 token、整层被最慢的卡拖住；
   - 训练稳定性：路由 logits 容易数值不稳，需要 FP32 路由、z-loss 等；
   - 微调：ST-MoE 发现稀疏模型微调更容易过拟合，对批大小与学习率的偏好与稠密模型不同；
   - 推理效率：小 batch 时每个专家分到的 token 很少，矩阵乘受带宽限制，计算优势难以兑现；分组矩阵乘、通信内核等工程复杂度高。
3. **适合 MoE**：算力受限但想要更强的模型；云端大规模、高并发服务，有足够的卡做专家并行和大 batch；训练与推理团队有能力处理通信与负载均衡。
4. **适合稠密**：单卡、端侧、显存紧张；低并发、小 batch 的低延迟场景；需要频繁微调、团队工程资源有限；对结果确定性要求高。

**评分要点（共 10 分）：**

- 用条件计算解释总参数与激活参数的区别，并说明计算量按激活参数算（3 分）
- 列出至少四项代价：显存、通信、负载均衡、稳定性、微调、小 batch 效率等（4 分）
- 给出合理的场景选择并说明理由（3 分）

**讲解：**

**常见失分点**：说「MoE 省显存」；说「8×7B 就是 8 个 7B 模型」；只讲优点不讲通信与负载均衡；不知道小 batch 推理时 MoE 的计算优势难以兑现；场景选择只说「大就用 MoE」。

<sub>考点：Dense与MoE对比、MoE推理特点　｜　出处：Zoph 等, ST-MoE, arXiv:2202.08906</sub>

</details>

## 场景分析题

<a name="LLM-MOE-034"></a>

### LLM-MOE-034　挑战 · 考频 ★★

团队从头预训练一个 64 专家、top-2、容量因子 1.25 的 MoE 模型，使用 Switch 式辅助损失（$\alpha=0.001$），路由器在 BF16 下计算。训练到第 2 万步左右，监控显示：路由熵持续下降；3 个专家拿走了约 40% 的分配，另有十几个专家几乎分不到 token；丢弃率从 1% 升到 15%；训练损失下降明显变慢，期间还出现了两次损失尖峰。请分析可能的原因，说明如何确认，并给出止损与修复方案。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 判断**：典型的**路由崩塌**（强者愈强）并伴随数值不稳定。少数专家因为早期略占优势，分到更多 token、训练得更好，于是更容易被选中；其余专家得不到训练信号，被闲置。

**2. 可能原因**：
- 均衡力度不足：$\alpha=0.001$ 比 Switch 常用的 $10^{-2}$ 小一个数量级，压不住失衡；
- 路由数值问题：路由器在 BF16 下计算、没有 z-loss，logits 不断变大，Softmax 饱和，也容易引发损失尖峰；
- 其他：学习率或 warmup 不合适、路由器初始化尺度过大、某段数据分布单一（如大量重复样本）。

**3. 如何确认**：
- 分层查看每个专家的负载随训练的变化（最大 / 平均负载比、负载为 0 的专家数）和每层的路由熵；
- 查看路由 logits 的最大值与均值、log-sum-exp 的大小、路由器的梯度范数，确认是否持续增长；
- 对照损失尖峰的时间点检查对应批次的数据与梯度；
- 用崩塌前的检查点在小规模上复现，比较改动前后的负载曲线。

**4. 止损与修复**：
- 回滚到崩塌前的检查点，不要在已崩塌的状态上硬训；
- 加强均衡：把 $\alpha$ 提到 $10^{-2}$ 量级，或换成无辅助损失的偏置均衡（偏置只用于选择、按负载做符号更新），辅以极小的序列级损失；
- 稳住路由：路由器的输入与 Softmax 用 FP32 计算（Switch 的 selective precision），加入 router z-loss（系数约 $10^{-3}$）；必要时降低学习率、延长 warmup，或缩小路由器初始化尺度；
- 降低丢弃：恢复期间临时调大容量因子，或使用不丢 token 的分组矩阵乘实现；
- 闲置专家：均衡生效后通常能重新获得 token；如长期无法恢复，可考虑用活跃专家的权重加扰动重新初始化。

**5. 长期**：把每层负载最大 / 平均比、路由熵、丢弃率、z-loss 和路由 logits 的最大值做成看板与告警，失衡刚出现时就介入；在小规模实验中先验证均衡策略和系数。

**评分要点（共 10 分）：**

- 判断为路由崩塌并解释强者愈强的机制（2 分）
- 指出均衡系数过小与路由数值不稳（BF16、无 z-loss）等原因（2 分）
- 给出可操作的确认方法（分层负载、路由熵、logits 大小、尖峰批次）（2 分）
- 给出止损与修复方案：回滚、加强均衡或换无辅助损失、FP32 路由与 z-loss、容量调整（3 分）
- 提出长期监控与告警（1 分）

**讲解：**

**常见失分点**：只说「调大辅助损失」而忽略数值稳定；不回滚直接在崩塌状态上继续训练；把损失尖峰归因于数据而不检查路由 logits；只调容量因子掩盖问题（丢弃率下降但失衡依旧）；不提监控指标。

<sub>考点：负载均衡辅助损失、无辅助损失负载均衡、容量因子与token丢弃　｜　出处：Fedus 等, Switch Transformers, arXiv:2101.03961；Zoph 等, ST-MoE, arXiv:2202.08906；DeepSeek-V3 技术报告 arXiv:2412.19437</sub>

</details>

## 系统设计题

<a name="LLM-MOE-035"></a>

### LLM-MOE-035　挑战 · 考频 ★★

你要把一个 7B 稠密模型的配方（32 层，$d=4096$，GQA 8 个 KV 头，SwiGLU 中间维度 11008，词表约 15 万）改成 MoE：目标是每个 token 的计算量与原 7B 稠密模型相近、效果更好，总参数不超过 50B，训练集群为 8 台机器 × 8 张 GPU。请给出 MoE 层的设计：哪些层用 MoE、专家数与粒度、每个 token 激活几个、是否用共享专家、路由与负载均衡方案、容量策略、并行方式，并估算参数量，说明要监控的指标与主要风险。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 参考配置**
- 前 2 层保留稠密 FFN（DeepSeek 系列的做法，前几层路由信息少、负载容易失衡），其余 30 层换成 MoE；
- 细粒度专家：每个路由专家的中间维度 1408（约为原 FFN 的 1/8），每层 64 个路由专家，每个 token 选 6 个；
- 1 个共享专家（中间维度 2816，相当于 2 个小专家），承载通用知识；
- 激活的 FFN 规模：$6\times1408+2816=11264$ 的中间维度，约等于原稠密 FFN 的 11008。

**2. 参数估算**
- 每个小专家 $3\times4096\times1408\approx17.3$M，共享专家约 34.6M，GQA 注意力约 41.9M；
- MoE 层：$41.9+64\times17.3+34.6\approx1.18$B，30 层约 35.5B；2 层稠密层约 0.35B；Embedding 与输出层约 $2\times150\text{K}\times4096\approx1.23$B；
- **总参数约 37B，激活约 7.0B**（原稠密模型约 6.9B），满足约束。

**3. 路由与负载均衡**
- 路由器在 FP32 下计算，加 router z-loss（约 $10^{-3}$）；
- 无辅助损失的偏置均衡（偏置只用于选择，$\gamma\approx10^{-3}$ 量级，训练末期冻结），外加极小的序列级或全局批次均衡损失；
- 门控权重在选中的专家间归一化。

**4. 容量策略**：优先采用不丢 token 的分组矩阵乘实现；若框架需要固定容量，训练时容量因子取 1.25 左右并监控丢弃率，评测与推理不丢弃。

**5. 并行方式**
- 专家并行放在**机内**：EP = 8，每张卡 8 个路由专家，all-to-all 走 NVLink，避免跨机通信；
- 机间做数据并行（非专家参数可配合 ZeRO / FSDP 切分）；专家参数在持有同一专家的卡之间同步梯度；
- 通信与计算重叠，监控 all-to-all 在每步时间中的占比。

**6. 监控指标**：每层专家负载的最大 / 平均比、路由熵、偏置的取值范围、丢弃率、z-loss 与路由 logits 最大值、损失尖峰、all-to-all 耗时占比与 MFU；与等计算量的稠密基线对比验证集损失和下游评测。

**7. 主要风险与对策**
- 路由崩塌或数值不稳：上述均衡与稳定手段，异常时回滚；
- 通信开销：EP 留在机内，必要时减少激活专家数或增大专家粒度；
- 小专家矩阵乘效率低：使用分组矩阵乘内核，保证每卡足够大的 batch；
- 微调敏感：稀疏模型微调更易过拟合，需要重新调批大小与学习率；
- 部署成本：37B 总参数在 BF16 下约 74 GB，推理需要多卡或 FP8 / INT4 量化，要提前与推理侧对齐。

**评分要点（共 10 分）：**

- 给出合理的层分配、专家数、粒度、激活数与共享专家设计，并说明理由（2 分）
- 参数量估算正确，总参数与激活参数满足约束（2 分）
- 路由与负载均衡方案完整（无辅助损失或辅助损失、z-loss、FP32 路由）（2 分）
- 给出容量策略与并行方案（EP 放机内、机间 DP）（2 分）
- 列出监控指标与主要风险及对策（2 分）

**讲解：**

**常见失分点**：只说「换成 8 个专家 top-2」而不估算参数和计算量；忽略专家并行的通信拓扑（把 EP 跨机布置）；没有负载均衡与数值稳定方案；不和等计算量的稠密基线对比；不考虑部署时的显存。
