## 单选题

<a name="ENG-STAB-001"></a>

### ENG-STAB-001　基础 · 考频 ★★★

与普通后端接口相比，Agent 服务在崩溃恢复时特别强调「存下每一步的输出，恢复时直接使用，而不是把这一步重新执行一遍」。导致这一要求的根本特点是：

- **A.** Agent 服务单次耗时长，重新执行一步往往要几十秒，加上排队就会超过网关的超时时间
- **B.** 模型输出来自采样，重算同一步可能做出不同的决定，与已经发生的副作用对不上
- **C.** 大模型按 token 计费，重新执行一遍要再付一次费用，长任务的重算成本远高于普通接口
- **D.** Agent 依赖的外部工具不受自己控制，恢复时集中重新执行会触发对方的限流与封禁

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：普通后端的计算是确定的，重算一遍结果相同，「重试等于重放」；LLM 每次都是重新采样，「重试不等于重放」。

例如第 5 步模型决定「给订单 A 退款」并已执行，进程随后崩溃。如果恢复时重新生成第 5 步，模型这次可能决定「先查物流」，于是状态机认为还没退款，后续步骤与真实世界对不上，甚至再退一次。所以检查点要存每一步的**输出**和副作用账本（幂等键与回执），恢复时用存下的结果。

- A 错：耗时长是要做异步和检查点的原因，但不能解释「为什么不能重算这一步」。
- C 错：成本是额外的考虑，即使重算免费，结果不一致的问题依然存在。
- D 错：限流可以通过退避与错峰解决，与「输出是否可重放」无关。

<sub>考点：Agent服务特点</sub>

</details>

<a name="ENG-STAB-005"></a>

### ENG-STAB-005　基础 · 考频 ★★★

某 Agent 产品的「深度研究」功能平均要运行 3 分钟，前端通过一个同步 HTTP 接口等待结果。上线后常见两类故障：网关的空闲超时把连接掐断；每次发版重启时，进行中的任务全部丢失、用户只能从头再来。最根本的改法是：

- **A.** 把网关与负载均衡的空闲超时调到 30 分钟，并在发版时优雅停机，等进行中的请求全部结束再重启
- **B.** 把 Agent 的最大步数减半并换用更快的模型，让每个任务都能在 1 分钟内完成，避开网关超时
- **C.** 提交即返回 task_id：任务入队，Worker 按步写检查点，前端用 SSE 或轮询获取进度
- **D.** 给前端加自动重试：连接断开后用同样的参数重新提交请求，并在页面上提示用户耐心等待

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：长任务要异步化，连接与任务解耦。

同步请求有三个硬伤：连接被长期占用，会被网关、负载均衡的空闲超时掐断；处理请求的进程一重启（发版、扩缩容、OOM），任务就丢了；流量突增时请求直接压到模型 API，无法削峰。「任务队列 + Worker + 检查点 + 进度推送」同时解决这三点：断线不影响后台任务，客户端可以重连续看；Worker 崩溃后租约过期，别的 Worker 从检查点继续；队列缓冲突发流量。

- A 错：调大超时只能缓解断连；优雅停机要等几分钟的长任务全部跑完，发版会被拖得很慢，进程崩溃时任务照样丢失；大量长连接还会占满接入层资源。
- B 错：砍步数、换小模型会直接损害任务质量，也解决不了重启丢任务。
- D 错：重新提交等于从头再跑一遍，既浪费钱，又可能重复执行有副作用的步骤。

注意：秒级的单轮问答用「同步 + SSE 流式」就够了，只有长任务、需要恢复和削峰时，才值得引入队列和状态管理。

<sub>考点：同步与异步架构</sub>

</details>

<a name="ENG-STAB-009"></a>

### ENG-STAB-009　基础 · 考频 ★★

跨服务传递超时信息时，通常传「剩余时长」而不是「绝对截止时刻」（例如 gRPC 用 `grpc-timeout` 请求头传剩余时间）。主要原因是：

- **A.** 机器之间的时钟有偏差，传绝对时刻会让下游算错剩余时间；剩余时长由下游按本机时钟换算
- **B.** 剩余时长用一个整数就能表示，比绝对时间戳少占十几个字节，能减小每个请求头的开销
- **C.** 绝对时间戳的精度通常只到秒，表示不了亚秒级的时间，不适合毫秒级的超时控制
- **D.** 传剩余时长可以让下游在超时后按剩余预算自动发起重试，上游不必再介入

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：截止时刻要用「本机时钟」来解释，跨机器传绝对时间会受时钟偏差影响。

两台机器的系统时钟可能相差几百毫秒甚至更多，上游说「12:00:05.000 截止」，下游的时钟若快了 2 秒，就会以为只剩很少的时间而过早放弃，慢了则会超额等待。传「还剩 4.2 s」，下游收到后用自己的单调时钟加上这个值重建截止时刻，偏差只剩网络传输时间（这部分只会让下游略微多等，必要时可以再减去一个小余量）。

进程内则相反：用单调时钟（如 `time.monotonic()`）记录绝对截止时刻，放进 contextvars 这类上下文变量里，每次调用时算剩余时间。

- B 错：字节数差别可以忽略，不是设计原因。
- C 错：时间戳完全可以表示毫秒甚至更细的精度（如 Unix 毫秒时间戳、带小数秒的 RFC 3339）。
- D 错：超时信息只是告诉下游「最多还能用多久」，是否重试由调用方根据错误类型和剩余时间决定。

<sub>考点：超时分层</sub>

</details>

<a name="ENG-STAB-012"></a>

### ENG-STAB-012　基础 · 考频 ★★★

下游服务重启时，成百上千个客户端会在同一时刻失败。给指数退避再加上随机抖动（如 full jitter），最主要的目的是：

- **A.** 缩短每次重试的平均等待时间：full jitter 的期望等待只有退避上限的一半，请求更快拿到结果
- **B.** 让每个客户端的重试间隔各不相同，从而保证重试最终一定能够成功
- **C.** 让服务端能从请求到达的时间间隔中识别出重试请求，并优先处理它们，减少用户等待
- **D.** 把同一时刻扎堆的重试在时间上打散，避免同步的重试尖峰把刚恢复的下游再次打垮

<details>
<summary>答案与解析</summary>

**答案：D**

**解析：**

**结论**：抖动的作用是「去同步」。

不加抖动时，同时失败的客户端会按完全相同的时间表重试：第 1 秒一起来、第 2 秒一起来、第 4 秒一起来……下游每次刚恢复，就被一波整齐的尖峰打回去。加上随机抖动后，重试时刻被均匀摊开，下游看到的是接近平稳的流量。AWS 架构博客《Exponential Backoff And Jitter》的模拟显示：不加抖动的指数退避是「明显的输家」，调用量更多、完成时间也更长；full jitter 和 decorrelated jitter 都能大幅减少调用量。一个模拟实验中，100 个客户端同时失败，不加抖动时第一次重试全部挤在同一个 50 ms 内，加了 full jitter 后最挤的 50 ms 只有 16 个。

- A 错：full jitter 的期望等待确实只有上限的一半，但这是附带效果，目的在于打散。
- B 错：重试只能提高暂时性故障下的成功概率，下游持续故障时重试多少次都没用；间隔各不相同也改变不了这一点。
- C 错：服务端无法从请求的到达间隔识别出哪些是重试，也不应优先处理重试流量。

<sub>考点：重试与退避抖动　｜　出处：AWS Architecture Blog: Exponential Backoff And Jitter</sub>

</details>

<a name="ENG-STAB-016"></a>

### ENG-STAB-016　进阶 · 考频 ★★

某服务对下游的重试用「预算」控制：每次调用成功就存入 0.1 个令牌（最多存 10 个），每次重试消耗 1 个令牌，令牌不足 1 个就不重试、直接返回失败。关于它的效果，下列说法正确的是：

- **A.** 偶发失败时令牌充足、重试照常；下游整体宕机时令牌只出不进、很快耗尽，额外重试不超过已存令牌数
- **B.** 重试预算会让偶发故障时的成功率明显下降：每 10 次成功才攒够 1 次重试，大多数失败请求都得不到重试
- **C.** 重试预算保证每个请求都至少能重试一次，余下的令牌再按先到先得分配，避免个别请求运气不好
- **D.** 有了重试预算，下游故障时的流量放大已经被控制住，就不再需要熔断器了

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：重试预算让「重试量」与「成功量」挂钩，长期看重试不超过成功调用的 10%。

- 偶发故障（如 1% 的请求失败）：每 100 次调用约有 99 次成功、攒下约 9.9 个令牌，却只需要支付约 1 次重试，预算绰绰有余，重试照常进行，几乎不影响成功率；
- 下游整体宕机：成功调用为 0，令牌只出不进，最多再花掉已存的 10 个就停止重试。模拟实验：下游全挂时，100 个请求在没有预算时打出 400 次调用，有预算时只有 105 次。

gRPC 的重试节流（retry throttling）是同样的思路：客户端为每个服务端维护一个令牌数，失败减 1、成功加 tokenRatio，令牌数不大于上限的一半时停止重试。

- B 错：偶发故障时预算是充足的：失败率 1% 时每 100 次调用攒下约 9.9 个令牌，只需支付约 1 次重试，不会明显影响成功率。
- C 错：预算耗尽时就是不重试，它保护的是下游，而不是单个请求。
- D 错：两者互补：预算只限制「重试」，熔断器在下游故障时连**首次请求**也不发，直接走降级，并在恢复后通过半开探测逐步放量。

<sub>考点：重试风暴　｜　出处：gRPC A6 Client Retries https://github.com/grpc/proposal/blob/master/A6-client-retries.md</sub>

</details>

<a name="ENG-STAB-018"></a>

### ENG-STAB-018　基础 · 考频 ★★★

某支付工具网关的去重逻辑是：先 `SELECT` 查询幂等键是否存在，不存在就执行扣款，成功后再 `INSERT` 一条记录。压测发现，同一个键的两个请求并发到达时，偶尔会重复扣款。最合适的修复是：

- **A.** 在 SELECT 之前随机 sleep 0～50 ms，把并发到达的同键请求错开，让后到的请求能查到先到者写入的记录
- **B.** 在服务进程内按幂等键加一把 asyncio.Lock，让同一个键的请求串行执行，后到的请求就能查到记录
- **C.** 给幂等键建唯一索引，先插入「处理中」记录，插入成功才扣款；插入失败就按记录状态返回 409 或重放结果
- **D.** 让客户端每次重试都生成一个新的幂等键，服务端就能区分出不同的请求，并按键分别记录结果

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：「先查后做」是典型的竞态（check-then-act）：两个请求同时查到「不存在」，于是都去扣款。要把「占位」做成原子操作。

唯一索引让「插入处理中记录」这一步只有一个请求能成功，成功者执行业务并写回响应；失败者根据记录状态处理：已完成就重放保存的响应，仍在处理就返回 409 或等待。用 Redis 时可以用 `SET key value NX PX 毫秒数` 达到同样的效果。注意给「处理中」记录也设一个租约：进程崩溃后由对账任务去下游查询真实状态，再决定补写结果还是允许重试。

- A 错：随机等待只能降低冲突概率，不能消除竞态；扣款耗时比 50 ms 长时，后到的请求照样查不到记录。
- B 错：进程内的锁只管住单个进程，多实例部署时，同一个键的请求可能落到不同实例上。
- D 错：每次换键等于没有幂等键，重试一定会被当成新请求，重复扣款更严重。

<sub>考点：幂等键</sub>

</details>

<a name="ENG-STAB-022"></a>

### ENG-STAB-022　基础 · 考频 ★★★

工程上常说「至少一次投递 + 幂等处理 = 效果上的恰好一次」。单靠网络协议无法做到端到端「恰好一次」投递，根本原因是：

- **A.** 消息队列的吞吐量不够高，无法为每条消息都同步等待确认，于是改为批量确认，批内失败就整批重发
- **B.** 超时后发送方无法区分「对方没收到」和「已处理但确认丢了」，重发可能重复、不重发可能丢失
- **C.** TCP 在网络拥塞时会重传数据包，应用层可能收到同一个数据包的多份副本
- **D.** 恰好一次要靠全局统一的时钟给每条消息排序去重，而分布式系统没有可靠的全局时钟

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：不确定性来自「确认」本身也可能丢。

发送方只能在「重发」和「不重发」之间选：重发，就可能让对方处理两次（至少一次）；不重发，就可能丢消息（至多一次）。没有任何协议能让发送方在超时那一刻知道对方是否已经处理。所以工程上的标准答案是：允许重复投递，让接收方做成幂等，多次到达只生效一次。

- A 错：问题与吞吐无关，即使逐条同步等待确认，确认丢失的问题依然存在。
- C 错：TCP 在传输层有序号和去重，重传造成的重复包会被丢弃，应用层看到的字节流不会重复；重复来自应用层的超时重发。
- D 错：全局时钟解决不了「确认丢失」这个信息缺失问题。

<sub>考点：投递语义</sub>

</details>

<a name="ENG-STAB-025"></a>

### ENG-STAB-025　基础 · 考频 ★★

订行程 Agent 的流程是「订机票 → 订酒店 → 扣款 → 发确认邮件」，跨越多个外部系统，无法用一个数据库事务包住，因此用 Saga 组织。扣款被银行拒绝时，正确的处理方式是：

- **A.** 按执行顺序先取消机票、再取消酒店；确认邮件放在最前面发，让用户尽早知道预订进度
- **B.** 只把扣款这一步撤销即可，机票和酒店都已订好，留给用户自行决定是否取消
- **C.** 同时执行所有补偿操作，顺序无关紧要；邮件发错了可以再发一封更正
- **D.** 按逆序先取消酒店、再取消机票；不可撤回的确认邮件放在最后，等前面都成功后再发

<details>
<summary>答案与解析</summary>

**答案：D**

**解析：**

**结论**：Saga 把长事务拆成一串本地步骤，每步配一个补偿操作；某一步失败，就按**逆序**执行已完成步骤的补偿。

逆序的原因：后面的步骤可能依赖前面步骤的结果（如酒店预订挂在机票行程下），先撤销后做的那一步最安全，与数据库回滚的顺序一致。设计时还要注意：
- **不可补偿的步骤放最后**：邮件发出去收不回来，要等前面都成功了再发；
- **补偿也要幂等、可重试**：补偿到一半进程崩溃，恢复后要能接着补；一直补偿失败就转人工并告警，不能静默放弃；
- **编排式**（一个协调者按状态机推进）便于观测和恢复，Agent 场景常用；**协同式**（各服务监听事件自行反应）耦合低，但流程散落各处，难以追踪。

- A 错：补偿顺序反了，而且邮件放最前面，后面失败时无法撤回。
- B 错：扣款本身失败了，没有可撤销的扣款；已订的机票和酒店若不补偿，就留下不一致的中间状态，还可能产生费用。
- C 错：互不依赖的补偿有时可以并行，但不能一概而论；「发错再更正」也不能替代「不可补偿的步骤放最后」。

<sub>考点：持久化执行与Saga</sub>

</details>

<a name="ENG-STAB-030"></a>

### ENG-STAB-030　基础 · 考频 ★★

需要以严格匀速（每秒 20 次）调用一个第三方接口：突发请求宁可排队等待，也不能在任何时刻超过这个速率。最合适的限流方式是：

- **A.** 固定窗口计数：每秒最多放行 20 个，整秒时计数清零，超出的请求排到下一秒
- **B.** 令牌桶：令牌以每秒 20 个的速率生成，桶容量 100，没有令牌的请求排队等待
- **C.** 漏桶：请求先进入队列，以每秒 20 个的恒定速率流出，队列满则拒绝
- **D.** 滑动窗口日志：统计最近 1 秒内的放行次数，不超过 20 次就放行

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：漏桶限制的是「输出速率」，输出绝对平滑，突发只能排队。

- A 错：固定窗口在每秒开头可以一次放满 20 个，而且窗口交界前后各放一批，短时间内可能达到 40 个。
- B 错：令牌桶允许最多 100 个的突发，空闲时攒下的令牌可以一次用掉，适合 API 入口按用户或租户限流，不适合要求严格匀速的下游。
- D 错：滑动窗口能保证任意 1 秒内不超过 20 个，但这 20 个可以在同一瞬间发出，仍然不是匀速。

漏桶的代价是引入排队时延，所以队列要有上限，并且排队时间超过请求的 deadline 时直接丢弃。

### ENG-STAB-034　基础 · 考频 ★★

某工具的熔断器配置为「最近 10 次调用中失败率达到 50% 就打开」。夜间低峰时，这个工具经常因为 2 次调用里失败 1 次就被熔断，用户抱怨功能时有时无。最直接的改进是：

- **A.** 把失败率阈值从 50% 调高到 90%，低峰期 2 次调用里失败 1 次就不会再跳闸，高峰期也够用
- **B.** 增加「最小调用数」：窗口内调用数达到一定样本量（如 20 次）才计算失败率
- **C.** 去掉熔断器，改为对该工具按指数退避无限次重试，直到成功为止，用户就不会看到功能时有时无
- **D.** 去掉半开状态，熔断后一律等值班人员确认下游恢复、再手动关闭熔断器，避免反复开合

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：样本太少时失败率没有统计意义，「2 次失败 1 次」就是 50%。

加上最小调用数后，低峰期调用量不够，熔断器就不计算失败率、也不会跳闸。Resilience4j 的熔断器有 `minimumNumberOfCalls` 参数，默认值为 100：调用数不到这个值时，即使全部失败也不会打开。另外，按次数的窗口在低流量时可能装的是几分钟前的旧数据，按时间分桶的窗口更贴近现状，Resilience4j 两种都支持。

- A 错：阈值调高会让高峰期真正的故障迟迟不能熔断，治标不治本；样本太少的问题也还在（2 次调用全失败就是 100%）。
- C 错：无限重试（即使有退避）会把故障的下游压得更惨，也让 Agent 一直撞墙。
- D 错：半开状态的作用是自动、谨慎地恢复：冷却期满后放少量探测请求，成功则关闭，失败则重新打开。去掉它会让恢复依赖人工，时间更长。

### ENG-STAB-037　基础 · 考频 ★★

某 Agent Worker 的所有工具调用共用一个大小为 20 的并发池。某天浏览器工具因目标网站故障，每次调用都卡满 10 秒，结果计算器这类本来 0.1 秒就返回的工具，P95 时延也涨到了十几秒。最对症的改进是：

- **A.** 为每类工具设独立的并发池（舱壁），给浏览器工具配较短的超时与熔断，池满即拒绝或降级
- **B.** 把共用池从 20 扩大到 200，让浏览器的慢请求不再挤占计算器等快工具的名额
- **C.** 把计算器工具的超时调大到 30 秒，避免它在排队期间被误判超时而反复重试
- **D.** 在提示词里要求 Agent 尽量少调用浏览器工具，必要时先用搜索 API 代替网页浏览

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：这是典型的「慢依赖耗尽共享资源池」，解法是舱壁隔离：一个舱进水，整条船不沉。

每类依赖一个独立的并发池（信号量或线程池），浏览器卡死只会耗尽它自己的名额，计算器有自己的池，不受影响。模拟实验：浏览器卡 10 s 时，共用一个池的计算器 P95 被拖到 16.2 s；各用一个池时计算器保持 0.1 s，浏览器多出来的请求被立即拒绝。池的大小可以用利特尔定律按目标吞吐和下游时延估算，再用压测校准。

- B 错：扩大池子只是推迟被耗尽的时间，慢请求越积越多，还会把更多压力推给故障的下游。
- C 错：计算器并不慢，它是在排队等名额；调大超时只会让用户等得更久。
- D 错：提示词无法可靠地约束调用行为，也解决不了资源隔离问题。

<sub>考点：舱壁隔离</sub>

### ENG-STAB-039　进阶 · 考频 ★★

某服务的并发上限是 4、每个请求处理 1 秒（处理能力 4 个/s），遭遇 8 个/s 的流量，持续 20 秒。对比「无界队列，来者不拒」与「最多排队 4 个，满了立即返回 429 并带上 Retry-After」两种方案，下列说法正确的是：

- **A.** 无界队列不拒绝任何请求，处理能力始终满载、没有浪费，所以被接收请求的平均时延反而更低
- **B.** 两种方案每秒处理完成的请求数不同：有界队列拒绝了一部分请求，单位时间完成的请求更少
- **C.** 有界队列会让被拒绝的客户端立即重试、形成重试风暴，所以无界队列更安全，代价只是时延略高一些
- **D.** 无界队列越积越长，最晚到的要等约 20 秒；有界队列让部分请求快速失败，被接收的时延稳定在约 2 秒

<details>
<summary>答案与解析</summary>

**答案：D**

**解析：**

**结论**：无界队列是「时延放大器」。

处理能力固定为 4 个/s，到达 8 个/s，积压以每秒 4 个的速度增长，20 秒后积压约 80 个，最后到达的请求要排约 $80/4=20$ 秒。很多请求处理完时用户早已离开或客户端已超时重试，处理了也是白处理，还挤占了本来能按时完成的请求。有界队列最多排一轮再处理一轮，时延约 2 秒；被拒绝的请求拿到 Retry-After，可以退避或降级。模拟结果：无界队列最大时延 20.5 s，有界队列稳定在 2.0 s。

- A 错：无界队列下被接收请求的时延随时间线性增长，平均值远高于有界队列。
- B 错：两种方案都让服务满负荷运行，每秒都完成 4 个，吞吐相同；区别在于时延分布和「有效」完成数。
- C 错：只要带上 Retry-After、客户端按退避与预算重试，就不会形成风暴；无界队列的问题恰恰更严重。

<sub>考点：背压</sub>

</details>

### ENG-STAB-042　进阶 · 考频 ★★

Agent 任务通过 Amazon SQS 分发，队列的可见性超时（visibility timeout）用的是默认的 30 秒，redrive 策略的 maxReceiveCount 为 3。某些任务的单步要跑 2 分钟。上线后发现这些任务被重复执行，最后进入了死信队列，可日志显示它们其实一直在正常运行。原因与修复是：

- **A.** SQS 的投递语义是至多一次，消息处理失败就会被直接丢进 DLQ，应改用支持重放的 Kafka
- **B.** maxReceiveCount 设得太小，调到 100 就能解决：消息不再进 DLQ，任务也就不会被重复执行
- **C.** 可见性超时短于处理时长，任务还在跑消息就重新可见、被再次领取；应调大超时并用心跳续期
- **D.** 死信队列配置有误，关闭 DLQ、让消息一直留在主队列里由 Worker 继续处理即可

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：可见性超时决定「消息被领走后多久会重新出现」，它必须覆盖处理时长。

SQS 中消息被消费者接收后暂时对其他消费者不可见，消费者处理完要删除消息；超时前没删，消息就会重新可见，被同一个或另一个消费者再次领取，接收次数加 1，达到 maxReceiveCount 后被移入死信队列。默认可见性超时是 30 秒，单步跑 2 分钟的任务必然被重复领取。AWS 文档建议用心跳机制（调用 ChangeMessageVisibility）定期延长可见性超时，处理逻辑本身也要幂等；注意从首次接收算起总共不能超过 12 小时，延长不会重置这个上限，更长的任务要拆成小步骤或改用工作流服务。

- A 错：SQS 标准队列是**至少一次**投递，即使在可见性超时内也不保证绝不重复，所以处理逻辑必须幂等。
- B 错：调大 maxReceiveCount 只是推迟进入 DLQ，重复执行照样发生。
- D 错：关闭 DLQ 后，真正的毒消息会无限循环，堵住队列、反复让 Worker 崩溃。

<a name="ENG-STAB-013"></a>

### ENG-STAB-013　进阶 · 考频 ★★★

Agent 调用大模型 API 时遇到下列错误，处理方式**正确**的有：

- **A.** 503 或部分厂商表示过载的 529：指数退避加抖动后重试，持续失败时交给熔断器
- **B.** 输入超过了模型的上下文窗口：这是服务端的暂时性错误，退避后原样重试几次通常就会成功
- **C.** 429 限流：退避后重试并优先遵守 Retry-After；若是触发了账户的消费上限，重试也无济于事
- **D.** 工具参数不符合 JSON Schema：把校验错误回填给模型让它修正，并限制修复轮数
- **E.** 401 鉴权失败：可能是密钥轮换期间的短暂不一致，先按指数退避重试 3 次再报错

<details>
<summary>答案与解析</summary>

**答案：ACD**

**解析：**

**结论**：A、C、D 正确。可重试的是暂时性错误（429、5xx、过载、超时、连接重置），请求本身有问题的错误要先修正。

- A 对：服务端错误和过载是典型的暂时性错误（Anthropic 用 529 `overloaded_error` 表示 API 暂时过载）；持续失败说明下游整体出了问题，应由熔断器快速失败、切到降级路径。
- B 错：上下文超长是请求本身的问题（通常返回 400 类错误），不是暂时性错误，重发多少次都一样，应先压缩或裁剪上下文再发。
- C 对：429 说明配额暂时不够，等一等可能就好；但并非所有 429 都会恢复。例如 Anthropic 的文档说明，触发用量等级的月度消费上限时返回的 429 不带 retry-after，会一直失败直到额度恢复，这种情况应告警而不是重试。
- D 对：这是「语义失败」，原样重发同一个请求只是重新采样碰运气；把具体的校验错误告诉模型，它通常能改对，同时要限制修复轮数，避免死循环。
- E 错：用同一个无效凭证重试多少次结果都一样，应刷新凭证（如重新读取轮换后的密钥）或直接报错。

另外，写操作超时意味着「结果未知」，可以重试，但必须带同一个幂等键，或先查询对方状态。

<a name="ENG-STAB-019"></a>

### ENG-STAB-019　进阶 · 考频 ★★★

服务端实现幂等键（Idempotency-Key）时，下列处理方式**正确**的有：

- **A.** 同一个键、首个请求仍在处理中：可以返回 409（IETF Idempotency-Key 草案的建议），或等首个请求完成后返回同一结果
- **B.** 幂等记录的保留时间要长于客户端的最长重试窗口，过期清理后同一个键会被当成新请求
- **C.** 同一个键、请求体不同：说明调用方把键用在了不同的请求上，应当拒绝（草案建议返回 422）
- **D.** 下游调用超时、结果未知：立即删除幂等记录，允许客户端用同一个键马上重新执行一遍
- **E.** 同一个键、同样的请求体、首个请求已完成：直接返回保存的首次响应，不再执行业务

<details>
<summary>答案与解析</summary>

**答案：ABCE**

**解析：**

**结论**：A、B、C、E 正确。去重表一般存：键（唯一索引）、请求指纹（参数哈希）、状态（处理中 / 已完成）、响应、过期时间。

- A 对：IETF 的 Idempotency-Key 请求头草案建议，重复请求到达时首个请求仍在处理，返回 409 Conflict。
- B 对：保留时间必须长于客户端的最长重试窗口，否则客户端稍后重试时记录已经没了，会被当成新请求再执行一次。Stripe 的公开文档说明，幂等键至少保留 24 小时后才可能被清理，清理后再用同一个键会被当作新请求。
- C 对：草案建议对「同一个键配不同请求体」返回 422；通过比较请求指纹发现。
- D 错：结果未知意味着下游可能已经扣款。此时应保留「处理中」记录，交给对账流程用幂等键或业务单号去下游查询真实状态；只有**确认没有产生副作用**的失败（如参数校验不过、下游明确拒绝），才可以删除记录、允许重试。
- E 对：这就是幂等的含义：执行一次和执行多次效果相同，重复请求拿到同一份结果。

### ENG-STAB-033　进阶 · 考频 ★★★

关于 Agent 服务的限流，下列说法**正确**的有：

<summary>答案与解析</summary>

**答案：CDE**

**解析：**

**结论**：C、D、E 正确。Agent 的瓶颈是 token 而不是 QPS，限流要多维：用户 / API Key、租户、模型（RPM、TPM）、工具（QPS、并发）、单个任务（步数、token、金额）。

### ENG-STAB-036　进阶 · 考频 ★★

在 Agent 服务中使用熔断器，下列做法**正确**的有：

- **A.** 按依赖分别设熔断器：每个模型供应商（细到具体模型）、每个工具各一个

- **D.** 熔断条件除了错误率，还要包括慢调用比例（如首 token 时延超过阈值的调用占比）
- **E.** 工具被熔断时，把「该工具暂不可用」作为工具结果回填给模型，让它换一条路或如实告知用户

<details>
<summary>答案与解析</summary>

**答案：ABDE**

**解析：**

**结论**：A、B、D、E 正确。

- E 对：不要让 Agent 一遍遍撞墙；把不可用的信息作为工具结果告诉模型，它可以改用其他工具、缩小任务范围或请用户稍后再试。

### ENG-STAB-043　进阶 · 考频 ★★

关于死信队列（DLQ）的使用，下列做法**正确**的有：

- **A.** DLQ 只是兜底存储，消息进去后不会再影响主队列，平时不需要专门监控和告警，季度巡检时清理即可
- **B.** 超过最大重试次数、参数非法或数据损坏等不可重试的错误，以及反复让 Worker 崩溃的毒消息，适合转入 DLQ
- **C.** 转入 DLQ 的消息应带上失败原因与堆栈、重试次数、trace_id 和最后一个检查点
- **D.** 按接收次数（如 SQS 的 maxReceiveCount）转入 DLQ 时，可见性超时过短会让正常的消息也被误送进来
- **E.** 修复问题后把消息重驱动（redrive）回主队列前，要确认处理逻辑是幂等的，并分批、限速地回放

<details>
<summary>答案与解析</summary>

**答案：BCDE**

**解析：**

**结论**：B、C、D、E 正确。DLQ 收容「处理不了的消息」，防止它们堵住主队列或无限重试。

- A 错：要对 DLQ 的积压量和增长速度告警，定期处理或归档；DLQ 突然增长往往意味着新版本出了确定性错误，等到季度巡检就太晚了。只进不出、没人看，DLQ 就成了数据坟场。
- B 对：确定性错误重试多少次都一样，毒消息会让 Worker 反复崩溃，都应尽早隔离。
- C 对：带上足够的上下文才能排查，trace_id 可以直接跳到当时的调用链，检查点决定修好后从哪里续跑。

- E 对：重驱动等于再执行一遍，必须幂等；分批限速，避免瞬间把下游压垮。AWS SQS 提供 redrive 功能，RabbitMQ 有死信交换机。

<a name="ENG-STAB-017"></a>

### ENG-STAB-017　基础 · 考频 ★★

在「客户端 → 网关 → Agent 服务 → 模型 SDK」这样的多层调用链中，通常只应在一层（最了解请求语义、最靠近失败的那一层）做重试，其他层快速失败；否则各层的重试次数会相乘，在下游最脆弱的时候把流量放大很多倍。

<details>
<summary>答案与解析</summary>

**答案：✅ 正确**

**解析：**

**正确**。四层各自最多尝试 4 次，最底层的一次故障会被放大成 $4^4=256$ 次调用。Google SRE 书的建议是：在紧挨着「拒绝请求的那一层」之上做重试；这一层重试也失败后，向上返回「已过载，不要重试」的错误，上层不再重试。

容易被忽略的是 SDK：很多官方 SDK 默认就会对 429、5xx 自动重试（例如 Anthropic 的 SDK 默认重试两次），业务代码外面再包一层重试，就等于多了一层乘数。做法是明确规定在哪一层重试，其余层关闭重试或设为 0 次；同时配上重试预算和熔断器，下游整体故障时自动停止重试。

</details>

<a name="ENG-STAB-021"></a>

### ENG-STAB-021　挑战 · 考频 ★

在 Stripe API（v1）的幂等机制中，带幂等键的请求一旦开始执行，Stripe 就会保存首次的状态码和响应体；即使首次返回的是 500 错误，用同一个键重试也会拿到同样的 500，而不会重新执行。

<details>
<summary>答案与解析</summary>

**答案：✅ 正确**

**解析：**

**正确**。Stripe 的文档说明：对于 API v1，接口开始执行后，Stripe 保存该幂等键下首个请求的状态码和响应体，之后用同一个键重试都返回保存的结果，**包括 500 错误**。几个细节：
- 参数没通过校验、或与另一个正在执行的同键请求冲突时，接口并没有开始执行，不会保存结果，可以重试；
- 幂等层会比较新请求与首个请求的参数，不一致就报错；
- 键至少保留 24 小时后才可能被清理，清理后再用同一个键会被当作新请求；
- API v2 的行为不同：重试时 Stripe 会尽量把失败或部分失败的工作执行完，并返回更新后的响应。

**为什么这样设计**：500 发生时，操作可能已经执行了一部分，结果未知。如果重试就重新执行，可能扣两次款。把「结果未知」原样重放给客户端，迫使客户端去核实状态，而不是盲目重做。对我们自己的设计也有启发：幂等层要区分「确认没执行」与「结果未知」两种失败。

<sub>考点：幂等键　｜　出处：Stripe Idempotent requests, https://docs.stripe.com/api/idempotent_requests</sub>

</details>

Kafka 开启幂等生产者和事务后提供「恰好一次」语义，因此消费者处理消息时调用外部支付接口，也能保证每条消息只扣一次款。

<a name="ENG-STAB-038"></a>

### ENG-STAB-038　挑战 · 考频 ★

Envoy 中名为「circuit breaking」的配置（如集群的最大连接数、最大挂起请求数、最大并发请求数、最大并发重试数）本质上是并发与排队的上限，更接近舱壁；而按失败情况把表现异常的上游实例踢出负载均衡，是另一个功能「异常检测」（outlier detection）。

<details>
<summary>答案与解析</summary>

**答案：✅ 正确**

**解析：**

**正确**。Envoy 文档列出的 circuit breaking 阈值包括：集群最大连接数、最大挂起请求数（等待连接池空闲连接时最多排队多少个）、最大并发请求数、最大并发重试数、最大并发连接池数，超出时立即失败并计入对应的溢出指标。它们限制的都是「同时存在多少个」，与 Resilience4j 那种按失败率跳闸、有半开探测的经典熔断器不同，更接近舱壁和背压。Envoy 文档的说法是：尽早快速失败、向下游施加背压，几乎总是更好的选择。

### ENG-STAB-006　基础 · 考频 ★★

某 Agent 服务每秒新到 15 个任务，每个任务平均运行 40 秒。由利特尔定律，系统中同时在处理的任务约有 ____ 个；若每个 Worker 进程用 asyncio 同时推进 150 个任务，至少需要 ____ 个进程（不含冗余）；若在飞的任务中平均有 40% 正在等待模型的流式输出，模型网关需要同时承载约 ____ 个流式连接。

<details>
<summary>答案与解析</summary>

**答案：** (1) 600；(2) 4；(3) 240

**解析：**

- 利特尔定律 $L=\lambda W$：$15\times40=600$ 个任务同时在飞；

<sub>考点：同步与异步架构</sub>

### ENG-STAB-015　基础 · 考频 ★★

客户端、网关、Agent 服务三层各自「最多尝试 3 次」（首次 + 2 次重试）。最底层的模型 API 持续失败时，一次用户请求最多会打到模型 API ____ 次；若改为只在一层重试、其他层快速失败，则最多 ____ 次。Google SRE 的做法是再给每个客户端设约 10% 的重试预算（重试量不超过正常请求量的 10%），这样下游整体故障时，总请求量大约只放大到正常的 ____ 倍。

<details>
<summary>答案与解析</summary>

**答案：** (1) 27；(2) 3；(3) 1.1

**解析：**

- 每层 3 次相乘：$3\times3\times3=27$ 次，故障被放大 27 倍，正好发生在下游最脆弱的时候；
- 只在一层重试：最多 3 次。通常选择最了解语义、最靠近失败的那一层重试，其他层快速失败并把「已过载，别再重试」的信号向上传；
- 重试预算：Google SRE 书《Handling Overload》一章建议每个请求最多尝试 3 次，同时按客户端统计重试占比、超过 10% 就不再重试。只有逐请求上限时，最坏会放大到接近 3 倍；加上预算后，一般情况下只放大约 1.1 倍。

**工程提示**：官方 SDK 往往自带重试（例如 Anthropic 的 SDK 默认重试两次），在外面再包一层重试，就又多了一层乘数。统一在一处配置重试，其余地方关掉。

### ENG-STAB-031　进阶 · 考频 ★★

某网关用「滑动窗口计数法」限流，限额为每分钟 100 次：估算值 = 当前窗口的计数 + 上一窗口的计数 × 上一窗口与「最近 60 秒」重叠的比例。上一分钟放行了 80 次，当前这一分钟已经过去 15 秒、放行了 30 次。此时估算的最近 60 秒请求数为 ____，现在最多还能再放行 ____ 次。如果改用固定窗口计数，在两个窗口交界前后各 0.1 秒内，最多可能放行 ____ 次。

<details>
<summary>答案与解析</summary>

**答案：** (1) 90；(2) 10；(3) 200

**解析：**

- 最近 60 秒覆盖了上一分钟的后 45 秒，重叠比例 $45/60=0.75$；估算值 $=30+80\times0.75=90$；
- 还能再放行 $100-90=10$ 次；
- 固定窗口在整分钟清零：上一分钟最后 0.1 秒放满 100 次，新一分钟最初 0.1 秒再放满 100 次，0.2 秒内放行 200 次，是限额的 2 倍。

**几种窗口算法的取舍**：
- 固定窗口：最简单、内存 O(1)，边界两侧可达 2 倍限额，适合「每日调用量」这类粗粒度配额；
- 滑动窗口日志：记录每次放行的时刻，任何窗口都不会超限，但内存与限额成正比；
- 滑动窗口计数：假设上一窗口内的请求均匀分布，用两个计数器近似，内存 O(1)、有少量误差，网关的分钟级限流常用。

### ENG-STAB-002　进阶 · 考频 ★★

一个 Agent 任务平均要调用模型和工具共 30 次，每次调用的成功率为 99%，任何一次失败都会导致整个任务失败。
(1) 不做重试时，任务的成功率是多少？
(2) 若每次调用失败后最多重试 1 次，且失败相互独立，任务成功率变为多少？
(3) 此时每次逻辑调用平均要发出多少次请求？
(4) 这个计算成立需要哪些前提？

<details>
<summary>答案与解析</summary>

**答案：(1) 约 74.0%；(2) 约 99.70%；(3) 约 1.01 次；(4) 失败相互独立、调用可安全重复、重试不会压垮下游**

**解析：**

**(1)** $0.99^{30}\approx0.740$，每四个任务就有一个失败。串联调用的成功率会相乘，这是 Agent 服务比普通接口更脆弱的根本原因之一。

**(3)** 第一次必发，失败（概率 0.01）时再发一次，期望为 $1+0.01=1.01$ 次，放大很小。

**(4) 前提**：
- **失败相互独立**：如果是模型供应商整体宕机几分钟，第二次大概率也失败，重试不仅救不回来，还会加重下游负担，这时要靠熔断和降级；
- **调用可以安全地重复**：写操作重试前必须有幂等键，否则可能重复扣款、重复下单；
- **重试不会压垮下游**：要有退避、抖动和重试预算，避免下游一抖动就引发重试风暴。

这三个前提，正是超时、重试、幂等、熔断这一整套稳定性设计要解决的问题。

### ENG-STAB-008　进阶 · 考频 ★★★

一个交互式 Agent 请求的端到端 deadline 是 45 s。各类调用的超时上限为：规划 10 s，工具 8 s，最终回答 30 s；每次调用的超时取「该类上限」与「剩余时间」的较小值。实际执行：规划第一次调用在 10 s 时超时，重试一次用了 4 s；随后 3 个工具并行执行，最慢的用了 7 s。
(1) 最终回答这次调用的超时应设为多少？
(2) 如果不传递 deadline，各层只用自己的固定上限（规划允许重试 1 次，工具和最终回答各 1 次），最坏情况下这个请求总共可能耗时多少？这说明了什么问题？

<details>
<summary>答案与解析</summary>

**答案：(1) 24 s；(2) 最坏 58 s，超过 45 s 的 deadline**

**解析：**

**(1)** 已用时间 $10+4+7=21$ s，剩余 $45-21=24$ s；最终回答的超时 $=\min(24,30)=24$ s。

**(2)** 最坏情况：规划两次都超时 $10+10=20$ s，工具 8 s，最终回答 30 s，合计 $58$ s。

**问题**：45 s 时用户（或上游）已经放弃，后面 13 s 的工作纯属浪费：还占着连接、烧着 token，处理完也没人要结果。各层各拿一个固定超时，叠加起来就会超过端到端的预算。

**正确做法**：
1. 请求进入时定下 deadline，向下传递「还剩多少」；
2. 每次调用的超时 = min(剩余时间, 该类上限)；
3. 剩余时间不够一次有意义的调用（如低于最终回答的 P50 时延）就别发了，直接降级或返回部分结果；
4. 区分两种超时：单次调用超时可以重试，整体 deadline 到了就不该再重试。

<sub>考点：超时分层</sub>

### ENG-STAB-011　进阶 · 考频 ★★★

某客户端采用带 full jitter 的指数退避：第 $n$ 次重试（$n$ 从 0 开始）之前等待 $\mathrm{U}\big(0,\ \min(\text{cap},\ \text{base}\cdot2^n)\big)$ 秒，其中 base = 0.5 s，cap = 8 s，最多重试 6 次。
(1) 6 次重试前等待时间的上限依次是多少？6 次等待时间之和的期望和最大值各是多少？
(2) 若第 3 次重试（$n=2$）之前，服务端返回了 `Retry-After: 5`，且实现规定「实际等待时间至少为 Retry-After」，6 次等待之和的期望变为多少？

<details>
<summary>答案与解析</summary>

**答案：(1) 上限依次为 0.5、1、2、4、8、8 s；期望 11.75 s，最大 23.5 s；(2) 期望 15.75 s**

**解析：**

**(1)** 上限 $\min(8,\ 0.5\times2^n)$：$n=0\sim5$ 依次为 0.5、1、2、4、8、8 s（$n=5$ 时 $0.5\times32=16$，被 cap 截到 8）。均匀分布 $\mathrm{U}(0,c)$ 的期望是 $c/2$，所以期望总等待 $=(0.5+1+2+4+8+8)/2=23.5/2=11.75$ s，最大值为上限之和 23.5 s。

**(2)** 第 3 次重试的等待变为 $\max(\mathrm{U}(0,2),\ 5)=5$ s（随机值不会超过 2），期望从 1 s 变为 5 s，总期望 $11.75-1+5=15.75$ s。

**要点**：
- full jitter 把等待时间在 $[0,\text{上限}]$ 内均匀打散，同时失败的大量客户端不会在同一时刻重试；
- 服务端给出的 Retry-After 是对其配额的直接提示，至少要等那么久；
- 所有等待加起来要放进整体 deadline 里：每次重试前检查剩余时间，不够就不重试；重试次数、总时长、全局重试预算三重设限。

<sub>考点：重试与退避抖动　｜　出处：AWS Architecture Blog: Exponential Backoff And Jitter</sub>

### ENG-STAB-029　进阶 · 考频 ★★★

某 API 入口按租户用令牌桶限流：补充速率 $r=10$ 个/s，桶容量 $b=50$，每个请求消耗 1 个令牌。某租户空闲很久之后（桶已满），在 $t=0$ 时瞬间涌入 120 个请求，之后每秒稳定到达 30 个请求。
(1) $t=0$ 这一刻能放行多少个请求？
(2) 从 $t=0$ 到 $t=10$ s（含 $t=0$ 的突发），总共最多放行多少个请求？
(3) $t=10$ s 时桶内剩 0.3 个令牌，一个需要消耗 2 个令牌的大请求到达（如按 token 量折算），应返回的 Retry-After 是多少秒？

<details>
<summary>答案与解析</summary>

**答案：(1) 50 个；(2) 150 个；(3) 0.17 s**

**解析：**

**(1)** 桶满时有 50 个令牌，瞬间最多放行 50 个，其余 70 个被拒绝（返回 429）。令牌桶允许的最大突发就是容量 $b$。

**(2)** 之后每秒补充 10 个令牌，而到达速率 30 个/s 远大于补充速率，令牌一补上就被用掉；10 s 内补充 100 个。总计 $b+r\cdot T=50+10\times10=150$ 个。一般地，任意 $T$ 秒内放行数不超过 $b+rT$：长期速率不超过 $r$，短期允许 $b$ 的突发。

**(3)** 还差 $2-0.3=1.7$ 个令牌，补充需要 $1.7/10=0.17$ s。令牌桶的好处之一就是能精确算出还要等多久，作为 Retry-After 返回，客户端据此退避，而不是立即重试。

**实现提示**：令牌桶不需要定时器，每次请求到来时按流逝时间一次补齐：$\text{tokens}\leftarrow\min(b,\ \text{tokens}+r\cdot\Delta t)$；时间间隔用单调时钟计算。多实例共享配额时，把「补充、判断、扣减」放进 Redis 的 Lua 脚本里原子执行。

### ENG-STAB-026　进阶 · 考频 ★★

下面的工作流把每次状态变化追加写入事件日志，进程崩溃重启后通过重放日志决定下一步：若有步骤失败，就按逆序补偿尚未补偿的步骤；否则继续执行尚未完成的步骤。三份日志对应三次重启，输出是什么？

```python
STEPS = ["flight", "hotel", "pay", "email"]

def replay(log):
    done, undone, failed = [], set(), False
    for ev in log:
        kind, step = ev.split(":")
        if kind == "done":
            done.append(step)
        elif kind == "fail":
            failed = True
        elif kind == "undo":
            undone.add(step)
    return done, undone, failed

for log in (["done:flight", "done:hotel", "fail:pay", "undo:hotel"],
            ["done:flight", "done:hotel"],
            ["done:flight", "done:hotel", "done:pay", "done:email"]):
    done, undone, failed = replay(log)
    if failed:
        print("补偿:", [s for s in reversed(done) if s not in undone])
    else:
        print("执行:", [s for s in STEPS if s not in done])
```

<details>
<summary>答案与解析</summary>

**答案（程序输出）：**

```text
补偿: ['flight']
执行: ['pay', 'email']
执行: []
```

**解析：**

- **第一份日志**：扣款失败，已经补偿（取消）了酒店，然后崩溃。重放得到已完成 `[flight, hotel]`、已补偿 `{hotel}`、有失败；逆序遍历后过滤掉已补偿的，只剩 `flight`。恢复后接着补偿，不会重复取消酒店。
- **第二份日志**：机票、酒店已完成，没有失败，继续执行 `pay` 和 `email`。
- **第三份日志**：全部完成，无事可做。

**要点**：
- 当前状态由「重放只追加的事件日志」得到，崩溃恢复就是「读日志、重放、接着跑」；
- 最危险的窗口是「副作用已经发生、完成事件还没写下」：恢复后这一步一定会再执行一遍，只能靠幂等键（如「工作流 ID + 步骤名」，重放时不变）让下游去重；
- 日志越来越长时，定期做快照，恢复时加载「最近的快照 + 之后的事件」。

<a name="ENG-STAB-035"></a>

### ENG-STAB-035　挑战 · 考频 ★★

下面是一个简化的熔断器：closed 时统计最近 4 次调用，样本达到 4 次且失败率不低于 50% 就打开；open 状态冷却 10 秒后进入 half_open，放一个探测请求，成功则关闭、失败则重新打开。输出是什么？

```python
class Breaker:
    def __init__(self, min_calls=4, threshold=0.5, cooldown=10):
        self.min_calls, self.threshold, self.cooldown = min_calls, threshold, cooldown
        self.state, self.results, self.opened_at = "closed", [], 0
    def allow(self, now):
        if self.state == "open" and now - self.opened_at >= self.cooldown:
            self.state = "half_open"
        return self.state != "open"
    def record(self, now, ok):
        if self.state == "half_open":
            self.state, self.results, self.opened_at = ("closed", [], 0) if ok else ("open", [], now)
            return
        self.results = (self.results + [ok])[-4:]
        n, fails = len(self.results), self.results.count(False)
        if n >= self.min_calls and fails / n >= self.threshold:
            self.state, self.opened_at = "open", now

b, trace = Breaker(), []
for now, ok in [(0, True), (1, False), (2, True), (3, False), (5, True), (13, False), (25, True), (26, True)]:
    if b.allow(now):
        b.record(now, ok)
        trace.append(f"{now}:{b.state}")
    else:
        trace.append(f"{now}:reject")
print(" ".join(trace))
```

<details>
<summary>答案与解析</summary>

**答案（程序输出）：**

```text
0:closed 1:closed 2:closed 3:open 5:reject 13:open 25:closed 26:closed
```

**解析：**

逐步推演：
- t=0～2：调用数不足 4 次，不计算失败率，保持 closed；
- t=3：最近 4 次为「成功、失败、成功、失败」，失败率 50%，打开，记下 opened_at = 3；
- t=5：距打开只过了 2 s，仍在冷却期，直接拒绝（快速失败，走降级），这次调用根本没有发给下游；
- t=13：距打开已满 10 s，进入 half_open 放行一个探测，探测失败，重新打开，opened_at = 13；
- t=25：又过了 12 s，进入 half_open，探测成功，关闭并清空统计；
- t=26：closed 状态正常放行。

**要点**：
- 最小调用数防止低峰期「2 次失败 1 次」就跳闸；
- open 状态下的快速失败让故障的下游得到喘息，调用方不必每次都等到超时；
- half-open 只放少量探测，避免大量请求一拥而上，把刚恢复的下游再次打挂。不同实现的判定规则不同：这里是「一次探测定成败」，Resilience4j 则在半开状态放行一批调用，按这批调用的失败率（或慢调用比例）决定关闭还是重新打开；
- 实际的熔断器还应按**慢调用比例**触发，因为模型故障常常表现为变慢而不是报错。

<sub>考点：熔断器　｜　出处：Resilience4j CircuitBreaker 文档</sub>

</details>

### ENG-STAB-014　挑战 · 考频 ★★

实现一个同步的重试函数（为了便于测试，等待和随机数都通过参数注入）：

```python
class RetryableError(Exception):
    def __init__(self, msg="", retry_after=None): ...

def retry_call(fn, *, max_attempts=4, base=0.5, cap=8.0,
               sleep=time.sleep, rand=random.uniform): ...
```

- 调用 `fn()`，成功则返回其结果；
- 只重试 `RetryableError`；其他异常立即原样抛出，不再重试；
- 第 $n$ 次重试（$n$ 从 0 开始）之前，等待 `rand(0, min(cap, base * 2 ** n))` 秒（full jitter）；若该异常带有 `retry_after`，等待时间至少为 `retry_after`；通过 `sleep(秒数)` 等待；
- 最多调用 `fn` 共 `max_attempts` 次，全部失败时抛出最后一次的 `RetryableError`。

参考实现中需包含 `RetryableError` 的定义。

<details>
<summary>答案与解析</summary>

**参考实现：**

```python
import random
import time

class RetryableError(Exception):
    def __init__(self, msg="", retry_after=None):
        super().__init__(msg)
        self.retry_after = retry_after

def retry_call(fn, *, max_attempts=4, base=0.5, cap=8.0,
               sleep=time.sleep, rand=random.uniform):
    for attempt in range(max_attempts):
        try:
            return fn()
        except RetryableError as e:
            if attempt == max_attempts - 1:
                raise                                # 次数用尽，抛出最后一次的错误
            wait = rand(0, min(cap, base * 2 ** attempt))
            if e.retry_after is not None:
                wait = max(wait, e.retry_after)      # 至少等服务端要求的时长
            sleep(wait)
```

**测试用例：**

```python
def make(seq):
    it = iter(seq)
    def fn():
        x = next(it)
        if isinstance(x, Exception):
            raise x
        return x
    return fn

upper = lambda a, b: b                     # 让「随机」取上限，结果可预测
waits = []
assert retry_call(make([RetryableError("503"), RetryableError("503"), "ok"]),
                  sleep=waits.append, rand=upper) == "ok"
assert waits == [0.5, 1.0]

waits.clear()                              # Retry-After 至少要等那么久
assert retry_call(make([RetryableError("429", retry_after=3.0), "done"]),
                  sleep=waits.append, rand=upper) == "done"
assert waits == [3.0]

calls = []                                 # 不可重试的错误立即抛出
def bad():
    calls.append(1)
    raise ValueError("400 参数错误")
try:
    retry_call(bad, sleep=waits.append, rand=upper)
    assert False
except ValueError:
    pass
assert calls == [1]

waits.clear()                              # 次数用尽抛出最后一个错误；退避封顶
try:
    retry_call(make([RetryableError(str(i)) for i in range(6)]), max_attempts=6,
               base=1.0, cap=5.0, sleep=waits.append, rand=upper)
    assert False
except RetryableError as e:
    assert str(e) == "5"
assert waits == [1.0, 2.0, 4.0, 5.0, 5.0]

waits.clear()                              # 真随机时等待落在 [0, 上限] 内
r = random.Random(0)
try:
    retry_call(make([RetryableError("x")] * 4), base=1.0, cap=8.0,
               sleep=waits.append, rand=r.uniform)
except RetryableError:
    pass
assert len(waits) == 3 and all(0 <= w <= ub for w, ub in zip(waits, [1, 2, 4]))
assert retry_call(lambda: 42, sleep=waits.append, rand=upper) == 42
```

**解析：**

**思路**：
1. 循环最多 `max_attempts` 次；只捕获 `RetryableError`，其他异常（参数错误、代码 bug）自然向上传播；
2. 最后一次失败时用裸 `raise` 抛出当前异常，保留原始堆栈；
3. 等待时长先按 full jitter 取随机值，再与 `retry_after` 取较大值；
4. `sleep` 与 `rand` 可注入，测试时不用真睡，结果可预测。

**易错点**：
- 用 `except Exception` 一把抓，把 400、401 乃至 `KeyError` 这类 bug 也重试好几遍；
- 最后一次失败后仍然 sleep，白白多等一轮；
- 忽略 Retry-After，或者反过来用它**替代**随机退避（大量客户端拿到同一个 Retry-After 会再次同步，取「至少」更稳妥，有的实现还会在其上再加少量抖动）。

**生产环境还要加**：每次尝试单独限时、整体 deadline 检查、全局重试预算、与熔断器配合；异步版本中 `asyncio.CancelledError` 继承自 `BaseException`，不会被 `except Exception` 捕获，用户取消能直接穿过重试循环。

<sub>考点：重试与退避抖动</sub>

### ENG-STAB-020　挑战 · 考频 ★★

为扣款接口实现一个单进程的幂等层：

```python
class Conflict(Exception): ...

class IdempotencyStore:
    def __init__(self, ttl: float, clock): ...
    def execute(self, key: str, body: dict, handler): ...
```

- `clock` 是无参函数，返回当前时间（秒）；`handler(body)` 执行真正的业务并返回响应；
- **指纹**：把请求体按键排序后序列化为 JSON，再取 SHA-256；键的顺序不同视为同一个请求；
- 键有记录且未过期（当前时间 < 过期时刻）：指纹相同则直接返回保存的响应、**不再调用** handler；指纹不同则抛出 `Conflict`；
- 键没有记录或已过期：调用 `handler(body)`；成功则保存「指纹、响应、过期时刻 = 当前时间 + ttl」并返回响应；handler 抛出异常时**不保存**记录、原样抛出（视为没有副作用的失败，允许用同一个键重试）。

<details>
<summary>答案与解析</summary>

**参考实现：**

```python
import hashlib
import json

class Conflict(Exception):
    pass

class IdempotencyStore:
    def __init__(self, ttl, clock):
        self.ttl, self.clock, self.records = ttl, clock, {}

    @staticmethod
    def _fingerprint(body):
        return hashlib.sha256(json.dumps(body, sort_keys=True).encode()).hexdigest()

    def execute(self, key, body, handler):
        fp, now = self._fingerprint(body), self.clock()
        rec = self.records.get(key)
        if rec is not None and now < rec["expire"]:
            if rec["fp"] != fp:
                raise Conflict(f"键 {key} 已用于另一个请求")
            return rec["resp"]                 # 重放首次的响应
        resp = handler(body)                   # 抛异常时不写记录
        self.records[key] = {"fp": fp, "resp": resp, "expire": now + self.ttl}
        return resp
```

**测试用例：**

```python
t = [0.0]
store = IdempotencyStore(ttl=86400, clock=lambda: t[0])
charges = []
def charge(body):
    charges.append(body["amount"])
    return f"ch_{len(charges)}"

assert store.execute("o-1:pay", {"amount": 99, "cur": "CNY"}, charge) == "ch_1"
assert store.execute("o-1:pay", {"cur": "CNY", "amount": 99}, charge) == "ch_1"  # 键序不同，同一请求
assert charges == [99]

try:                                            # 同一个键换了金额
    store.execute("o-1:pay", {"amount": 199, "cur": "CNY"}, charge)
    assert False
except Conflict:
    pass

def boom(body):
    raise RuntimeError("bank 503")
try:                                            # 失败不留记录
    store.execute("o-2:pay", {"amount": 5}, boom)
    assert False
except RuntimeError:
    pass
assert store.execute("o-2:pay", {"amount": 5}, charge) == "ch_2"

t[0] = 86399.0                                  # 未过期：仍然重放
assert store.execute("o-1:pay", {"amount": 99, "cur": "CNY"}, charge) == "ch_1"
t[0] = 86400.0                                  # 过期：当作新请求
assert store.execute("o-1:pay", {"amount": 99, "cur": "CNY"}, charge) == "ch_3"
assert charges == [99, 5, 99]
```

**解析：**

**思路**：
1. 指纹用排序后的 JSON 做哈希，避免「同一个请求、字段顺序不同」被误判为冲突；
2. 有未过期记录时先比指纹：一致就重放，不一致就拒绝，说明调用方误用了键；
3. 业务失败抛异常时不写记录，客户端可以用同一个键重试；成功才写入响应和过期时刻。

**易错点**：
- 只存「是否处理过」而不存响应，重复请求拿不到首次结果（比如交易号）；
- 不比对指纹，同一个键换了金额也被当作重复请求，静默返回旧结果，掩盖调用方的 bug；
- 过期时间太短：TTL 必须长于客户端的最长重试窗口；
- 把「结果未知」（如下游超时）也当成失败删掉记录。本题的约定只适用于确认没有副作用的失败，真实系统要区分。

**走向生产**：这个版本只适合单进程、串行调用。并发时同一个键可能同时进入 `handler`，需要先原子地插入「处理中」记录（数据库唯一索引，或 Redis `SET NX PX`）；多实例部署要把记录放到共享存储；「处理中」记录要有租约，崩溃后交给对账流程处理。

<sub>考点：幂等键</sub>

</details>

### ENG-STAB-032　挑战 · 考频 ★★

实现一个可注入时钟的令牌桶：

```python
class TokenBucket:
    def __init__(self, rate: float, capacity: float, clock): ...
    def try_acquire(self, n: float = 1) -> tuple[bool, float]: ...
    def refund(self, n: float) -> None: ...
```

- 初始时桶是满的；`clock()` 返回当前时间（秒）；
- 每次调用时按流逝的时间惰性补充令牌：$\text{tokens}\leftarrow\min(\text{capacity},\ \text{tokens}+\text{rate}\cdot\Delta t)$；
- `try_acquire(n)`：`n` 大于容量时返回 `(False, float("inf"))`；令牌足够则扣减并返回 `(True, 0.0)`；不够则**不扣减**，返回 `(False, 还需等待的秒数)`；
- `refund(n)`：退还 `n` 个令牌（补充后再加，不超过容量），用于多层限流中后一层拒绝、或 TPM 预扣后按实际用量退还。

<details>
<summary>答案与解析</summary>

**参考实现：**

```python
class TokenBucket:
    def __init__(self, rate, capacity, clock):
        self.rate, self.capacity, self.clock = rate, capacity, clock
        self.tokens, self.last = float(capacity), clock()

    def _refill(self):
        now = self.clock()
        self.tokens = min(self.capacity, self.tokens + self.rate * (now - self.last))
        self.last = now

    def try_acquire(self, n=1):
        if n > self.capacity:
            return False, float("inf")      # 永远攒不够
        self._refill()
        if self.tokens >= n:
            self.tokens -= n
            return True, 0.0
        return False, (n - self.tokens) / self.rate

    def refund(self, n):
        self._refill()
        self.tokens = min(self.capacity, self.tokens + n)
```

**测试用例：**

```python
t = [0.0]
b = TokenBucket(rate=4, capacity=8, clock=lambda: t[0])
assert sum(b.try_acquire()[0] for _ in range(30)) == 8   # 突发上限 = 容量
assert b.try_acquire() == (False, 0.25)                  # 还差 1 个，要等 0.25 s

passed = 0                                                # 之后 10 s，每 0.125 s 来一个请求
for i in range(1, 81):
    t[0] = i * 0.125
    passed += b.try_acquire()[0]
assert passed == 40                                       # 稳态 rate × T

assert b.try_acquire(9) == (False, float("inf"))          # 超过容量
t[0] = 100.0                                              # 空闲很久，桶满
assert b.try_acquire(8)[0] and not b.try_acquire(1)[0]
b.refund(3)
assert b.try_acquire(3)[0]
b.refund(100)                                             # 退还不超过容量
assert b.try_acquire(8)[0] and not b.try_acquire(1)[0]
t[0] = 100.5                                              # 补了 2 个，还差 1 个
assert b.try_acquire(3) == (False, 0.25)
```

**解析：**

**思路**：令牌桶不需要后台定时器，每次请求时根据距上次的时间差一次补齐，封顶为容量；拿不到时算出「还差多少 ÷ 补充速率」，作为 Retry-After 返回给客户端。

**测试里的数字**：容量 8，所以 30 个突发请求只放行 8 个；之后每 0.125 s 补 0.5 个令牌，每两个请求放行一个，10 s 共放行 $4\times10=40$ 个，正好是 $r\cdot T$。测试特意选用二进制能精确表示的时间间隔，避免浮点累积误差影响断言。

**易错点**：
- 拿不到令牌时也扣减了，导致令牌变成负数、后续请求被长期拒绝；
- `n` 大于容量时返回有限的等待时间，客户端会无限等待下去；
- 退还时不封顶，桶里的令牌超过容量，突发上限被突破；
- 用 `time.time()` 计算间隔，系统时间被校准或回拨时会出错，应使用单调时钟。

**Agent 场景**：按 token 限流（TPM）时，请求进入时按「输入 token + max_tokens」预扣，完成后用 `refund` 退还没用到的部分；多层限流（用户 → 租户 → 模型）中后一层拒绝时，要把前一层已扣的令牌退回。

<sub>考点：限流算法</sub>

</details>

### ENG-STAB-003　进阶 · 考频 ★★★

面试官说：「超时、重试、限流、熔断这些后端稳定性套路大家都会背，Agent 服务有什么不一样？」请先从耗时、调用链、依赖、输出、成本五个方面对比 Agent 服务与普通后端，再说明这些差异如何改变超时、重试、幂等、限流和监控的设计。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 五个不同**
| 维度 | 普通后端 | Agent 服务 |
|---|---|---|
| 耗时 | 几十到几百毫秒 | 几秒到几十分钟 |
| 调用链 | 固定几跳 | 模型临场决定，几步到上百步 |
| 依赖 | 自家数据库与服务 | 模型 API、搜索、浏览器、沙箱、第三方工具 |
| 输出 | 确定，可重放 | 采样有随机性，重算结果不同 |
| 成本 | 单次几乎免费 | 按 token 计费，长任务一次几十万 token |

**2. 设计如何变形**
- **架构与超时**：长任务改为「提交即返回 task_id + 队列 + Worker + 检查点 + SSE 推进度」；端到端 deadline 向下传递，每次调用的超时取「上限」与「剩余时间」的较小值；流式调用分首 token 超时、间隔超时和总时长。
- **重试**：重试是重新采样，结果会变、要花钱、可能有副作用；所以只重试单次调用、不重跑整个循环，次数更少并计入任务预算，格式错误这类语义失败回填给模型修正，429 / 5xx 可以换备用模型。
- **幂等**：幂等键由运行时生成（如 run_id + step_id + 调用序号），不能让模型生成；工具网关对写操作强制带键；检查点存每步输出和副作用账本。
- **限流**：瓶颈是 token 而不是 QPS，模型 TPM 是全局硬上限；按「输入 + max_tokens」预扣、完成后退还；再加上按租户、按工具、按单任务（步数、token、金额）的多维限流，防止死循环烧钱。
- **监控**：一个任务一条 trace，span 带模型名和 token 数；SLI 除了可用性和时延，还要有质量（任务成功率、转人工率）和成本（每任务 token 与金额的分布）；Agent 最常见的「故障」是答得差、花得多，接口却一直返回 200。

**3. 落地举例**：讲一次真实故障时，按「现象 → 定位（哪条 trace、哪一步）→ 止血（降级开关）→ 根因 → 改进」讲，并给出数字。

**评分要点（共 10 分）：**

- 准确说出耗时、调用链、依赖、输出不确定、按 token 计费五个差异（3 分）
- 说明长耗时带来的异步化与 deadline 传播（2 分）
- 说明输出不确定与成本如何改变重试和幂等的设计（3 分）
- 说明限流按 token、监控要有质量与成本指标（2 分）

**讲解：**

**常见失分点**：通篇背后端八股，不提 token、采样随机性和副作用；把 Agent 的重试等同于 RPC 重试；只说「加监控」，却没有质量和成本类指标。面试官想听的是「同一个手段，在 Agent 场景下要怎么改」，而不是手段的名字。

<sub>考点：Agent服务特点</sub>

<a name="ENG-STAB-004"></a>

### ENG-STAB-004　进阶 · 考频 ★★★

调用大模型 API 的重试，和普通 RPC 的重试有什么不同？请从结果、成本、副作用、错误类型、备用路径等方面说明，并给出设计要点。

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **结果会变**：普通 RPC 默认「重试结果相同」，LLM 重试是重新采样，第二次可能调用不同的工具、给出不同的回答。已经推给用户的半段回答、已经执行的工具调用，不能被重试结果悄悄覆盖：要么接着续写，要么明确告诉用户「已重新生成」。
2. **要花钱**：失败或中断的调用可能已经计费（流式输出到一半断开，前面的 token 通常照样收费）。所以 LLM 调用的重试次数要比普通 RPC 少，并计入任务的成本预算。
3. **可能已有副作用**：重试的粒度要小，重试「一次模型调用」，而不是重跑「整个 Agent 循环」；已执行的工具调用记入检查点，重试时不再执行。
4. **按错误类型区别对待**：
   - 429：退避后重试，优先遵守 Retry-After；但触发账户消费上限时重试无用；
   - 5xx 与过载（部分厂商用 529）：指数退避加抖动，持续失败交给熔断器；
   - 上下文超长：压缩上下文后再发，原样重试没用；
   - 输出不是合法 JSON、调用了不存在的工具：属于语义失败，把错误回填给模型让它修正，并限制修复轮数；
   - 400、401、403：不重试。
5. **可以换路**：同一模型的其他区域、备用供应商、小一号的模型。不同模型的提示词和工具调用格式未必兼容，备用路径要提前评测。
6. **对冲请求要慎用**：每次对冲都要多付一份钱，只适合便宜的短调用，或只在首 token 迟迟不来时对冲。
7. **避免层层叠加**：官方 SDK 往往自带重试（如默认重试两次），外面再包一层就会相乘，要统一在一层做。

**评分要点（共 10 分）：**

- 指出重试即重新采样、结果会变，以及已消费输出的处理（2 分）
- 指出成本与副作用：次数更少、计入预算、只重试单次调用、已执行工具不重做（3 分）
- 按错误类型给出不同处理，尤其区分语义失败与暂时性失败（3 分）
- 提到换备用模型、对冲请求的取舍或避免多层重试（2 分）

**讲解：**

**常见失分点**：把 LLM 当纯函数，崩溃恢复时重新生成，结果和已发生的副作用对不上；对所有错误统一「重试 3 次」；重跑整个 Agent 循环导致工具被重复执行；不知道 SDK 自带重试，在外面又包了一层。

<sub>考点：Agent服务特点、重试与退避抖动　｜　出处：Claude API errors https://platform.claude.com/docs/en/api/errors</sub>

</details>

<a name="ENG-STAB-024"></a>

### ENG-STAB-024　进阶 · 考频 ★★

重试、至少一次投递、幂等三者是什么关系？结合「Agent 调用退款、发邮件等写操作工具」的场景，说明如何落地「效果上的恰好一次」，以及事务性发件箱（transactional outbox）解决的是什么问题。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 三者的关系**
- 网络不可靠，所以要重试；重试意味着同一个请求可能到达多次，这就是至少一次投递；
- 接收方做成幂等，多次到达只生效一次；
- 三者合起来就是「效果上的恰好一次」。单靠协议做不到端到端的恰好一次，因为发送方分不清「对方没收到」和「确认丢了」。

**2. 三种投递语义怎么选**
- 至多一次：发出不管，丢了就丢了，适合采样日志、指标上报；
- 至少一次：处理成功才确认，超时重投，是消息队列和重试的默认语义；
- 效果上的恰好一次：至少一次 + 幂等处理，适合支付、下单、发邮件、写库。

**3. Agent 写操作的落地**
- **键由运行时生成**：如 `run_id + step_id + 调用序号`，在首次调用前生成、重试时复用；不能让模型生成（重新采样后键会变），也不能用时间戳或随机数；
- **先记意图再执行**：调用前把「准备给订单 o-42 退款 99 元，键 K」写入检查点，执行后写回执；
- **工具网关强制带键**：写操作工具没有幂等键就拒绝；下游用唯一索引去重、重放首次结果；
- **结果未知先对账**：超时后先用键或业务单号查询对方状态，确认没做过再重试；第三方不支持幂等键时，自己在调用侧加这一层意图记录与对账；
- **队列消费者**：按消息 ID 或业务键去重。

**4. 事务性发件箱**
- 问题：「写数据库」和「发消息」是两个系统，无法放进一个事务。先写库后发消息，可能库写成功、消息没发出；先发消息后写库，可能消息发了、库回滚了；
- 做法：在同一个本地事务里同时写业务表和发件箱表（待发消息），由后台进程读取发件箱并投递，投递成功后标记；
- 注意：后台进程可能重复投递，所以消费者仍要幂等。Kafka 的恰好一次也只覆盖 Kafka 内部，写外部系统时同样要靠消费端幂等。

**评分要点（共 10 分）：**

- 讲清重试导致至少一次、幂等让重复无害、合起来是效果上的恰好一次（3 分）
- 对比至多一次、至少一次、效果上的恰好一次的适用场景（2 分）
- 给出 Agent 写操作的落地：运行时生成键、先记意图、网关强制、结果未知先对账（3 分）
- 说明事务性发件箱解决的双写不一致问题，以及消费端仍需幂等（2 分）

**讲解：**

**常见失分点**：认为「用了支持恰好一次的消息队列就不用幂等」；让模型生成幂等键；超时后直接换个键重试；只在客户端内存里去重，进程一重启状态就丢了；不知道发件箱模式要解决的是「库」和「消息」之间的双写问题。

<sub>考点：投递语义、幂等键</sub>

</details>

<a name="ENG-STAB-027"></a>

### ENG-STAB-027　挑战 · 考频 ★★

长任务的 Worker 用「租约 + 心跳」占住任务。为什么这还不足以保证同一个任务不会被两个 Worker 同时执行？围栏令牌（fencing token）怎样解决这个问题？如果 Worker 恰好在「副作用已经执行、完成事件还没写入」时崩溃，又该靠什么保证恢复后不重复？

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 租约为什么不够**
- Worker A 可能「假死」：长时间 GC 停顿、虚拟机被挂起、网络分区，时间超过了租约；
- 租约过期后，任务被 Worker B 接手；A 醒来后并不知道自己已经失效，还会继续写状态、调用工具；
- 即使 A 在每次写之前检查租约，检查和写入之间也可能发生停顿，问题依旧。

**2. 围栏令牌**
- 每次授予租约时，任务的版本号（令牌）单调递增：A 拿到 33，B 接手时拿到 34；
- 每次写状态库（以及支持的话，写下游资源）都带上令牌，存储层只接受不小于当前最大值的令牌，用比较并交换（CAS）实现；
- A 醒来后带着 33 写入，被直接拒绝。关键在于由**存储方**来检查，而不是靠写入方自觉；
- 「谁持有租约」这类元数据要求强一致，通常放在 etcd、ZooKeeper 这类基于共识协议的存储里。

**3. 「副作用已执行、完成事件未写入」的窗口**
- 恢复后这一步一定会重新执行（至少一次），无法避免；只能让重复执行无害；
- 幂等键由「工作流 ID + 步骤名（+ 调用序号）」生成，重放时保持不变；下游按键去重，返回首次的结果；
- 下游不支持幂等键时：执行前先记意图，恢复后先用业务单号查询对方状态（对账），确认没做过再执行；能两阶段的先预留后确认（TCC）；
- 持久化执行引擎（如 Temporal）把这套机制做进了框架：工作流代码可确定性地重放，副作用放在活动（activity）里，活动有自己的超时与重试策略，但活动本身仍然要求幂等，因为它可能已经执行完、结果还没记下 Worker 就崩溃了。

**评分要点（共 10 分）：**

- 讲清假死与租约过期导致双 Worker 并发写，检查租约无法避免（3 分）
- 讲清围栏令牌单调递增、由存储层拒绝旧令牌写入的机制（3 分）
- 指出崩溃窗口内的重复执行无法避免，只能靠稳定的幂等键或对账让其无害（3 分）
- 提到持久化执行引擎或租约元数据需要强一致存储（1 分）

**讲解：**

**常见失分点**：以为「心跳续约」就能防止双写；让写入方自己检查租约；幂等键用随机数或时间戳，重放时变了；以为用了 Temporal 之类的框架，活动就不需要幂等。围栏令牌的核心是「把判断放到存储侧」，这一点讲清楚很加分。

<sub>考点：持久化执行与Saga</sub>

</details>

### ENG-STAB-040　进阶 · 考频 ★★

什么是背压（backpressure）？Agent 服务应该怎样做过载保护？为什么「拒绝一部分请求」反而能让更多请求按时完成？

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 定义**：下游处理不过来时，把「慢一点」的信号传回上游，让上游减速或停止，而不是在中间无限堆积。

**2. 过载保护手段**
- **有界队列**：进程内流水线用有上限的队列（如 `asyncio.Queue(maxsize=...)`），满了 `put` 会等待，生产者自然减速；
- **并发上限与舱壁**：每类依赖（每个模型、每个工具）一个信号量，一个依赖卡住只耗尽自己的名额；
- **快速拒绝**：服务边界上不能让客户端无限等，排队超过阈值直接返回 429 / 503 并带上 Retry-After；
- **按 deadline 丢弃**：请求在队列里等待的时间已超过它的截止时间，就不再处理；
- **按优先级取舍**：高负载时先保交互式请求和付费用户，批量任务排队或延后；
- **自适应并发**：并发上限不写死，像 TCP 拥塞控制一样按时延升降（AIMD），Netflix 开源的 concurrency-limits 是这个思路；Facebook 介绍过按排队时延管理队列（受 CoDel 启发）、高负载时改为后进先出的做法；
- **客户端自适应节流**：客户端统计被拒绝的比例，在本地按概率拒绝一部分请求，避免把资源浪费在注定被拒的请求上（Google SRE 的 client-side throttling）。

**3. 为什么拒绝更好**
- 处理能力固定时，队列越长，每个请求的时延越长（利特尔定律）；无界队列会让所有人一起变慢、一起超时；
- 超过用户耐心的请求即使处理完也没有价值，却占用了本可以按时完成的请求的资源；
- 拒绝一部分并告诉客户端多久后再来，按时完成的请求（goodput）反而更多。

**4. Agent 的特殊点**：模型配额（TPM）和下游容量往往扩不动，多加 Worker 只是把压力推给更脆弱的地方，所以要在模型网关和工具网关处也做背压。

**评分要点（共 10 分）：**

- 准确定义背压：向上游传递减速信号，而不是无限堆积（2 分）
- 列出有界队列、并发上限或舱壁、快速拒绝加 Retry-After、按 deadline 丢弃等至少三种手段（4 分）
- 解释无界队列放大时延、拒绝能提高按时完成数的原因（3 分）
- 提到优先级、自适应并发或模型配额扩不动等 Agent 场景的要点（1 分）

**讲解：**

**常见失分点**：把背压理解成「把队列设大一点」；只说「扩容」；拒绝时不带 Retry-After，客户端立即重试，把限流变成重试风暴；不区分交互式与批量流量。

<sub>考点：背压　｜　出处：Google SRE Book, Handling Overload；Envoy circuit breaking 文档</sub>

</details>

### ENG-STAB-041　进阶 · 考频 ★★★

主模型供应商大面积故障，或持续返回 429 时，Agent 服务怎样保持可用？请给出由轻到重的降级阶梯，说明每一级的代价，以及降级机制在工程上要提前做好哪些准备。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 降级阶梯（代价从小到大）**
1. **换路**：同一模型的其他区域、备用供应商、小一号的模型。代价：质量可能下降，提示词和工具调用格式未必兼容；
2. **关闭非核心环节**：反思、多路并行、重排序、长链路规划。代价：答案不够深入；
3. **缩小预算**：减少最大步数、缩短上下文。代价：复杂任务成功率下降；
4. **返回缓存**：相同或相似问题的已有答案，语义缓存要设相似度阈值。代价：可能过时或答非所问；
5. **非 AI 回退**：规则引擎、模板回复、FAQ 检索、表单流程，或直接转人工。代价：覆盖面窄、人力成本高；
6. **只读模式**：关闭写操作工具，只给建议、不办事。代价：用户需要自己操作；
7. **延后处理**：告诉用户「已受理，完成后通知您」，任务排队等待恢复。代价：等待时间长；
8. **明确拒绝**：超过容量上限时拒绝一部分请求，保住系统整体。

**2. 工程准备**
- **提前埋好开关**：每一级都用特性开关实现，由配置中心下发、秒级生效，故障时一键切换，不在现场改代码；
- **备用路径提前验证**：备用模型在回归集上评测过，提示词做过适配，配额提前申请或预留；
- **自动与手动结合**：熔断器打开时自动切到备用路径，同时保留人工的全局急停开关；
- **定期演练**：注入 429、503、变慢等故障，验证降级确实会触发、确实可用；
- **可观测**：监控当前处于哪一级降级、各级的流量占比与质量；告知用户当前是降级服务；
- **逐步恢复**：主路径恢复后通过半开探测和灰度逐步切回，避免一次性回切再次打挂。

**评分要点（共 10 分）：**

- 给出由轻到重、至少五级的降级阶梯（3 分）
- 说明各级的代价，并包含非 AI 回退或转人工（2 分）
- 提到特性开关提前埋好、一键切换（2 分）
- 提到备用模型提前评测与配额预留、定期演练（2 分）
- 提到降级状态的监控或恢复时的逐步回切（1 分）

**讲解：**

**常见失分点**：只会说「切备用模型」；降级路径从没演练过，真出事时才发现备用模型的提示词不兼容、配额不够；故障时现场改代码发版；忘了非 AI 回退和转人工这条底线；恢复时一次性切回。

<sub>考点：降级策略</sub>

</details>

## 场景分析题

<a name="ENG-STAB-046"></a>

### ENG-STAB-046　挑战 · 考频 ★★

某天下午，主模型供应商没有返回任何错误，但首 token 时延从 1 秒涨到了 15 秒。随后 20 分钟里，你们的 Agent 服务出现了一连串问题：所有功能（包括不调用模型的工具类接口）的时延都飙升；Worker 的连接池和协程数被打满；对模型 API 的请求量涨到平时的 5 倍；当天的模型费用异常上涨；最后大量任务超时失败。请分析故障是如何一步步扩大的，给出止血措施和长期改进方案。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 故障如何扩大**
1. **慢而不错**：熔断器只按错误率触发，供应商「变慢不报错」，熔断没有打开；
2. **超时太宽**：没有首 token 超时，或单次超时设得很长，每个请求占着连接和协程十几秒以上。按利特尔定律，在飞请求数 = 到达率 × 时长，时长涨 15 倍，在飞数也涨约 15 倍，连接池和协程被打满；
3. **没有舱壁**：工具类接口与模型调用共用连接池和执行资源，被一起拖垮；
4. **多层重试叠加**：客户端、网关、SDK、Agent 循环各自超时重试，请求量放大到 5 倍，让供应商侧更慢，形成恶性循环（重试风暴）；
5. **成本上涨**：超时被放弃的流式调用，已生成的 token 照样计费；重试又从头生成一遍；
6. **无界排队**：新任务不断进来，在队列里积压，最终全体超过 deadline。

**2. 止血（几分钟内）**
- 打开降级开关：切到预先验证过的备用供应商或小模型；关闭反思、多路并行等非核心环节；
- 收紧超时：首 token 超时设为如 5 秒，超时即放弃或切换；
- 关掉多余层的重试，只保留一层，并启用重试预算；
- 入口限流：优先保交互式请求，低优先级与批量任务返回 429 加 Retry-After 或延后处理；
- 把工具类接口的流量隔离到独立的资源池或实例。

**3. 长期改进**
- **熔断**：按模型、按供应商分别设熔断器，触发条件加入慢调用比例（如首 token 超过 5 秒的比例超过 50%）；
- **超时**：端到端 deadline 向下传递；流式调用分首 token 超时、token 间隔超时、总时长；
- **重试**：只在一层重试，统一 SDK 的重试配置，加重试预算，熔断打开时不重试；
- **舱壁与背压**：按依赖拆分并发池，队列有界，排队超过 deadline 直接丢弃；
- **成本护栏**：单任务的 token 与金额上限（预算熔断），每小时花费异常告警；
- **监控告警**：首 token 时延分位数、在飞请求数、重试率、降级状态；按 SLO 燃烧率告警；
- **演练**：定期注入「变慢」类故障，验证熔断、降级、超时真的生效。

**评分要点（共 10 分）：**

- 指出「变慢不报错」导致按错误率的熔断不触发，并讲清长超时占满资源的机制（3 分）
- 指出缺少舱壁、多层重试放大、无界排队等扩大因素，并解释成本上涨（2 分）
- 给出可在几分钟内执行的止血措施：降级切换、收紧超时、关重试、限流（2 分）
- 给出长期改进：慢调用熔断、deadline 与分层超时、单层重试与预算、舱壁、成本护栏（2 分）
- 提到监控告警或故障演练（1 分）

**讲解：**

**常见失分点**：只说「供应商的问题，等它恢复」；没意识到「变慢」比「报错」更危险；把扩容当成止血手段（模型侧的瓶颈扩不动，扩 Worker 只会打出更多请求）；忽略重试叠加和成本。好的回答要把这几个机制串成一条因果链，再一一对应改进措施。

<sub>考点：超时分层、重试风暴、熔断器、舱壁隔离、降级策略</sub>

</details>

<a name="ENG-STAB-047"></a>

### ENG-STAB-047　挑战 · 考频 ★★

某多租户 Agent 平台的所有租户共享同一个模型账号的配额（TPM 为 200 万）。某天租户 A 上线了批量报告功能：每个请求输入约 6 万 token、max_tokens 设为 8000，并发 300。几分钟内，所有租户都开始大量收到模型返回的 429，交互式对话几乎不可用。平台入口的限流规则是「每个租户 100 QPS」，A 远没有触发。请分析原因，并设计改进方案。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 原因分析**
- **限流维度错了**：瓶颈是 token 而不是 QPS。A 的每个请求约 6.8 万 token（输入 6 万 + 最多 8000 输出），每分钟只要约 30 个请求就能用完 200 万 TPM，100 QPS 的入口限额形同虚设；
- **没有租户隔离**：所有租户共享一个配额，一个租户就能把配额耗尽，其他租户一起被 429；
- **流量没有分级**：批量任务与交互式对话同等对待，抢占同一份配额；
- **max_tokens 过大**：有的厂商在请求进入时按 max_tokens 估算占用，进一步放大消耗；
- **缺少背压**：所有人一起撞 429，客户端各自重试，让情况更糟。

**2. 改进方案**
- **按 token 的多维限流**：租户级 TPM 令牌桶，请求进入时按「输入 + max_tokens」预扣，完成后按实际用量退还；模型网关再设全局 TPM 桶；单任务设 token 与金额上限；
- **配额分配与隔离（舱壁）**：按租户签约等级分配份额，为交互式流量预留保底配额；大租户或批量流量使用独立的模型账号、区域或部署；
- **流量分级**：批量任务进入离线队列，在低峰执行，或改用厂商的批处理接口（通常更便宜）；交互式请求优先；
- **背压与快速失败**：配额不足时在网关排队几秒（受 deadline 约束），仍不够就返回 429 并带上 Retry-After，客户端按退避与预算重试；
- **治理**：max_tokens 按业务需要设置；大请求、大并发的新功能上线前做容量评估；按租户监控 TPM 使用率，接近上限时告警。

**3. 验证**：压测时模拟「一个租户突发批量请求」，确认其他租户的交互式请求时延与成功率不受影响。

**评分要点（共 10 分）：**

- 指出按 QPS 限流与 token 瓶颈不匹配，并算出约 30 个请求每分钟即可耗尽配额（3 分）
- 指出缺少租户隔离与流量分级（2 分）
- 给出按租户的 TPM 令牌桶、预扣与退还、全局 TPM 限流（2 分）
- 给出配额隔离或保底、批量流量离线化等方案（2 分）
- 提到背压与 Retry-After、监控或压测验证（1 分）

**讲解：**

**常见失分点**：只说「给 A 限流」，不指出限流维度错了；不做量级估算；只在入口限流，模型网关不限；把批量任务和交互式流量混在一起；忽视 max_tokens 设置对配额的影响。

<sub>考点：限流算法、舱壁隔离、背压</sub>

</details>

<a name="ENG-STAB-049"></a>

### ENG-STAB-049　挑战 · 考频 ★★★

一个跨境汇款 Agent 的流程是：校验收款信息 → 锁定汇率 → 调用银行接口发起汇款 → 通知用户。某次调用银行接口等了 30 秒后超时，Agent 运行时按「超时自动重试 2 次」的通用策略又发了两次请求，结果用户的账户被扣了三次款。请分析原因，并设计一套保证资金安全的方案，重点说明「超时之后应该怎么做」。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 原因**
- **把「超时」当成了「失败」**：超时只说明没等到响应，银行可能早已处理成功；
- **写操作没有幂等保护**：三次请求没有携带同一个幂等键（或银行侧不去重），被当成三笔新汇款；
- **重试策略不分读写**：资金类写操作套用了读操作的「超时即重试」；
- **缺少意图记录与对账**：系统不知道「这笔钱到底汇出去没有」，只能盲目重发。

**2. 资金安全方案**
- **业务单号即幂等键**：发起前由运行时生成 transfer_id（不由模型生成），先写入意图记录（状态 pending、金额、收款方、transfer_id），再调用银行；银行接口按商户订单号或幂等键去重；
- **超时之后的处理**：
  1. 不立即重发；
  2. 用 transfer_id 查询银行的交易状态：已成功则记录结果并通知用户；明确未受理，才用**同一个** transfer_id 重发；
  3. 查询也失败或状态未知：任务保持 pending，进入对账队列，由定时对账和日终对账文件确认，期间告知用户「处理中」，不允许再次发起；
- **重试策略分级**：资金类工具默认不自动重试，只有在幂等键与状态查询都具备时，才允许受控重试；
- **两阶段**：锁定汇率与资金预授权（Try），确认后执行（Confirm），失败释放（Cancel）；
- **持久化与并发**：每步写检查点；幂等键随检查点保存，崩溃恢复后复用；数据库唯一索引防止多实例并发重复发起；
- **权限与人工**：模型只生成「待执行汇款单」，由确定性代码执行；大额或异常汇款需要人工确认；设单笔、单日限额；
- **监控与补救**：监控同一 transfer_id 的多笔扣款、对账差异并告警；一旦发生重复扣款，走退款补偿流程并通知用户。

**评分要点（共 10 分）：**

- 指出超时等于结果未知，以及缺少幂等键、重试策略不分读写是根因（3 分）
- 给出业务单号或幂等键由运行时生成、先记意图再调用的设计（2 分）
- 讲清超时后的处理顺序：先查状态，再决定是否用同一个键重发，未知则进入对账（3 分）
- 提到两阶段、唯一索引防并发、人工确认与限额等加固措施（1 分）
- 提到重复扣款的监控与补偿（1 分）

**讲解：**

**常见失分点**：只说「加幂等键」，却说不出超时之后先查状态、未知则对账；让模型生成幂等键或每次重试换新键；认为「把超时调长」就能解决；忽略多实例并发与崩溃恢复；没有事后的检测与补偿。资金类场景的核心原则是：结果未知时宁可挂起等待确认，也不能盲目重做。

<sub>考点：幂等键、投递语义、持久化执行与Saga</sub>

</details>

## 系统设计题

<a name="ENG-STAB-048"></a>

### ENG-STAB-048　挑战 · 考频 ★★★

请为一个 Agent 任务执行平台设计稳定性方案。已知：每天约 50 万个任务，峰值是平均值的 3 倍；每个任务平均运行 3 分钟、调用模型与工具 20～40 次，部分任务包含下单、退款等写操作；要支持延迟任务（如「30 分钟后重试」「明早 9 点执行」）；要求进程崩溃或发版时任务不丢失、写操作不重复。请给出估算、架构与关键设计。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 估算**
- 平均到达率 $500000/86400\approx5.8$ 个/s，峰值约 17 个/s；
- 在飞任务数（利特尔定律）：$17\times180\approx3100$ 个；
- 每个 Worker 进程用 asyncio 同时推进 200 个任务，需要约 16 个进程，留 30%～50% 余量部署 21～24 个；
- 模型侧：峰值每秒发起的模型调用约 $17\times30=510$ 次，据此申请 RPM / TPM 配额，并准备第二家供应商。

**2. 架构**
- 接入层：鉴权、按用户与租户限流，创建任务后立即返回 task_id；
- 任务存储与队列：任务表（状态、版本号、run_at、租约到期时间）+ 消息队列；
- Worker：持租约执行 Agent 循环，每步写检查点与事件；
- 模型网关：多模型路由、TPM 配额、熔断与降级、计量；工具网关：按工具的舱壁、幂等键强制、审计；
- 旁路：状态库、进度事件流（SSE）、死信队列、可观测（Trace、指标、日志）。

**3. 关键设计**
- **持久化执行**：状态机 + 只追加的事件日志，崩溃后重放恢复；检查点存每步输出与副作用账本；租约 + 心跳 + 围栏令牌防止双 Worker 写；
- **写操作**：幂等键由运行时生成（run_id + step_id + 调用序号），先记意图再执行，结果未知先对账；跨系统写用 Saga 编排，补偿幂等，不可补偿的步骤放最后；高风险操作人工确认；
- **延迟任务**：任务表按 run_at 建索引，调度器定期取出到期任务（如 `SELECT ... FOR UPDATE SKIP LOCKED` 加租约，避免多个调度器重复取），再投入执行队列；量更大时可以用 Redis 有序集合或时间轮。没有现成消息队列时，这张任务表本身就能充当队列；
- **超时与重试**：端到端 deadline 向下传递；只在一层重试，指数退避加抖动、重试预算；
- **过载保护**：多维限流（租户、TPM、工具、单任务预算），按依赖的熔断器与舱壁，有界队列与快速拒绝，降级开关提前埋好；
- **死信队列**：超次数、不可重试、毒消息进入 DLQ，带原因与 trace_id，积压告警，修复后幂等地重驱动；
- **发版**：Worker 优雅退出（停止领取、等待当前步骤完成或写检查点后释放租约）；检查点带版本号，进行中的任务按旧版本跑完或在检查点处迁移。

**4. 可观测与演练**：一个任务一条 trace；RED 看任务、模型、工具，USE 看队列、Worker、配额；按 SLO 燃烧率告警；定期演练 429、变慢、畸形输出、在副作用后杀 Worker、状态库短暂不可用；按真实轨迹回放做压测，找拐点规划容量。

**评分要点（共 10 分）：**

- 给出到达率、在飞任务数、Worker 与模型调用量的估算（2 分）
- 架构包含接入、任务存储与队列、Worker、模型与工具网关、旁路组件（2 分）
- 持久化执行与写操作安全：检查点、租约与围栏、幂等键、对账、Saga（3 分）
- 给出延迟任务的实现方式，以及超时、重试、限流、熔断、DLQ 等过载与失败处理（2 分）
- 提到发版时的优雅退出、可观测与故障演练（1 分）

**讲解：**

**常见失分点**：只画「用户 → LLM → 工具」三个框；不做估算；只说「用消息队列」，不讲重复投递和幂等；忽略发版时进行中的任务；延迟任务只说「用定时器」，不考虑多实例重复调度与崩溃恢复。设计题要把「每一跳失败后去哪儿」讲清楚。

<sub>考点：同步与异步架构、幂等键、持久化执行与Saga、限流算法、死信队列、故障演练</sub>

</details>
