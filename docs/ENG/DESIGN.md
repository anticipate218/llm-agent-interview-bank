<a name="ENG-DESIGN-001"></a>

### ENG-DESIGN-001　基础 · 考频 ★★★

某候选人在 45 分钟的 Agent 系统设计面试中：开场先报出技术选型（某 Agent 框架 + 某向量库），接着画了约 20 分钟架构图，然后被面试官追问细节又讲了约 20 分钟，时间耗尽时还没讲失败模式和上线方案。对照常用的答题框架，下列改进中**最关键**的是：

- **A.** 把架构图画得更完整，覆盖网关、编排、检索、记忆、评测等所有组件，减少被面试官追问的机会
- **B.** 先花约 5 分钟澄清需求与约束，再定指标、做估算，并为失败模式与上线方案留出约 5 分钟
- **C.** 把估算环节延长到 15 分钟左右，把 QPS、token 用量和月成本都算到小数点后两位，以体现量化能力
- **D.** 省掉定指标的环节，北极星与护栏属于产品经理的职责，面试官主要考察的是技术实现能力

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：问题不在架构画得不够细，而在于缺了「澄清 → 指标 → 估算」的前置步骤和「风险与演进」的收尾，主线失控。

常用的时间分配：澄清需求与约束（并复述确认）约 5 分钟 → 定指标约 3 分钟 → 估算容量与成本约 5 分钟 → 画架构约 10 分钟 → 深挖 2～3 个难点约 15 分钟 → 风险与演进约 5 分钟 → 收尾约 2 分钟。每一步的产出是下一步的输入：不澄清就可能在解错的题；没有指标就无法判断方案是否达标；没有估算就无从决定调 API 还是自部署。面试官的评分维度里，「风险意识」和「落地经验」要靠最后几分钟体现，宁可压缩架构细节，也要留出时间讲失败模式和上线方案。

- A 错：每个组件平均用力、框图堆名词是典型的减分项，面试官更想看到数据流、信任边界和取舍。
- C 错：估算只需量级正确、假设讲清，花 15 分钟算精确数字会挤掉深挖和风险。
- D 错：北极星与护栏是设计的验收标准，决定了很多技术取舍（如要不要人审、延迟预算多少），是系统设计题的必答环节。

<sub>考点：答题框架</sub>

</details>

<a name="ENG-DESIGN-004"></a>

### ENG-DESIGN-004　基础 · 考频 ★★★

面试题是「为公司设计一个内部的 Coding Agent 平台」。如果只能先问一个问题，下列问题中对后续设计影响**最大**的是：

- **A.** 平台的管理后台前端用 React 还是 Vue 实现，以便尽早确定前端团队的人力安排
- **B.** 任务执行日志保留 30 天还是 90 天，这决定了日志存储集群的容量规划
- **C.** Agent 的修改以 PR 形式交给人评审后合并，还是允许它直接合入主干
- **D.** 代码托管平台的 Webhook 推送 JSON 还是表单格式，这决定了事件接入层的解析方式

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：好的澄清问题要能说出「答案会怎样改变设计」，「PR 评审后合并还是直接合入主干」直接决定了权限边界、不可逆风险和整条验证链路。

如果产出是 PR、由人评审后合并：Agent 只需要推送自己分支、开 PR 的权限，北极星可以定为 PR 合并率，评审是最后一道人工校验。如果允许直接合入主干：合并是不可逆动作，需要更强的自动验证与回滚机制、更严格的权限与审计，风险等级完全不同。同类的高价值问题还有：做哪类任务（修 CI、补单测还是写新功能）、代码能否出域、规模多大。

- A 错：管理后台的前端选型和人力安排都不影响 Agent 平台的核心架构，属于浪费时间的问题。
- B 错：日志保留期是实现细节，可以按合规要求后定，对存储容量的影响也只是线性的。
- D 错：Webhook 的格式是集成细节，接入层两种都能解析。

<sub>考点：需求澄清</sub>

</details>

<a name="ENG-DESIGN-007"></a>

### ENG-DESIGN-007　进阶 · 考频 ★★

某公司要做一个 HR 助手 Agent。历史工单中：制度与政策咨询占 50%，请假与调休申请占 30%，薪资与考勤争议占 12%，离职手续办理占 8%。第一期方案最符合 MVP 裁剪原则的是：

- **A.** 政策咨询全自动并附原文引用；请假由 Agent 预填、员工确认后提交；薪资争议与离职转人工并附摘要
- **B.** 四类业务第一期全部上线并全自动处理，统一使用能力最强的模型，再根据线上反馈逐步修正错误
- **C.** 第一期只做离职手续办理：它流程最长、涉及的系统最多，每单能节省的人力最多，最能体现 Agent 的价值
- **D.** 政策咨询与请假全自动执行；薪资争议由 Agent 按考勤记录直接计算补发金额并发起打款

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：按「业务价值 × 不可逆风险」排序，先做高价值、低风险的部分；写操作按「只给建议 → 人确认后执行 → 低风险自动执行」三步放开。

这一方案的覆盖率：政策咨询 50% 全自动，请假 30% 半自动（人确认），第一期就覆盖了 80% 的工单，却没有任何「模型自己决定、无法撤回」的环节。政策咨询只读、能用引用核对；请假申请可撤回，且员工确认后才提交；薪资和离职涉及资金、个人信息和多个系统，留给人工。

- B 错：模型能力再强也消除不了不可逆风险，把薪资、离职这类高风险操作直接自动化、等线上出错再修正，违背了「先只读，后写入」。
- C 错：离职只占 8%；流程长意味着依赖的系统多、故障源多、权限问题多，不适合作为第一刀。
- D 错：「计算补发金额并打款」是资金类不可逆动作，第一期应当只给建议、由人审核。

<sub>考点：MVP裁剪</sub>

</details>

<a name="ENG-DESIGN-012"></a>

### ENG-DESIGN-012　进阶 · 考频 ★★

某 Agent 每一步都把完整历史重新输入模型：基础上下文 $S=8000$ token，每步追加 $\Delta=2000$ token。若任务的平均步数从 20 步增加到 40 步，每个任务累计输入的 token 数大约变为原来的：

- **A.** 约 2 倍：步数翻倍，每个任务的输入也随步数线性翻倍
- **B.** 约 4 倍：累计输入与步数的平方成正比，步数翻倍即变为 4 倍
- **C.** 约 8 倍：每步的上下文变长一倍，步数也翻倍，再叠加历史累积
- **D.** 约 3.5 倍：线性增长的基础部分与平方增长的历史部分叠加

<details>
<summary>答案与解析</summary>

**答案：D**

**解析：**

**结论**：累计输入 $T_{in}=kS+\Delta\,k(k-1)/2$，线性项与平方项叠加，增长倍数介于 2 和 4 之间。

- $k=20$：$20\times8000+2000\times190=160000+380000=540000$；
- $k=40$：$40\times8000+2000\times780=320000+1560000=1880000$；
- 比值 $1880000/540000\approx3.48$。

步数越多，平方项占比越高（$k=40$ 时已占 83%），倍数越接近 4。

- A 错：只考虑了基础上下文，忽略了每步都要重读的历史。
- B 错：只有平方项时才是 4 倍，基础上下文那部分是线性的。
- C 错：把「每步上下文变长」和「步数变多」重复计算了。

这就是 Agent 的输入常是输出的几十倍、前缀缓存和上下文压缩是降本第一手段的原因；估算时最该问清的是「一个任务几步、每步上下文多长」。

<sub>考点：容量估算、成本估算</sub>

</details>

<a name="ENG-DESIGN-017"></a>

### ENG-DESIGN-017　基础 · 考频 ★★

某 Agent 平台把提示词、工具定义、模型版本和灰度规则存放在配置中心（控制面），网关和编排器（数据面）启动时加载配置，之后定期拉取更新。某天配置中心故障，暂时无法提供配置。数据面最合理的行为是：

- **A.** 暂停接收新请求，等配置中心恢复后再放行，避免用可能已经过期的配置产生错误结果
- **B.** 用本地缓存的最后一份有效配置继续服务并告警，同时暂停新的配置发布
- **C.** 回退到代码里写死的默认提示词和默认模型，等配置中心恢复后再切换回来
- **D.** 每个请求处理前都同步向配置中心拉取一次最新配置，拉取失败就带退避重试

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：控制面与数据面分离的目的之一，就是让控制面故障不拖垮数据面：数据面用最后一份有效配置（last known good）继续服务。

控制面管的是变化慢、需要审计的东西（提示词、工具定义、模型版本、权限策略、灰度规则）；数据面是每个请求都要经过的实时路径，要求低延迟、可水平扩展。配置中心短暂不可用时，正在生效的配置本来就经过了评测和灰度，继续使用它是最安全的选择；同时要告警，并冻结发布，避免恢复过程中出现半新半旧的状态。

- A 错：把控制面故障放大成全站不可用，正是分离要避免的耦合。
- C 错：代码里的默认配置往往没有和当前的工具、索引版本一起验证过，相当于一次未经评测的发布。
- D 错：每个请求都同步依赖配置中心，既增加延迟，又会在故障时形成重试风暴（退避只能减缓），拖慢配置中心的恢复。

<sub>考点：控制面与数据面</sub>

</details>

<a name="ENG-DESIGN-024"></a>

### ENG-DESIGN-024　进阶 · 考频 ★★

关于 FMEA 中的难检测度 D 与 Agent 的「安静的失败」，下列说法正确的是：

- **A.** D 分越高表示失败越容易被监控发现，所以在其他条件相同时，D 分高的失败模式可以往后排
- **B.** 接口错误率、超时率和 P99 时延三项监控都齐全时，Agent 的主要失败模式基本都能被及时发现并告警
- **C.** 接口一切正常、结果看似合理却是错的，这类失败 D 分高，要用引用校验、抽样评审等手段专门检测
- **D.** 严重度最高的失败模式，若发生频率低、RPN 排名靠后，可以按 RPN 顺序排到后面再做缓解

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：最难检测的是「安静的失败」：接口返回 200、延迟正常，内容却是错的，D 分高，需要专门设计检测手段。

检测手段包括：引用存在性与支撑度校验、评审模型抽检、人工抽样评审、点踩与「换个说法再问」的比例、转人工后的结论对比、业务对账（如退款记录与订单系统核对）。

- A 错：D 越高表示**越难**发现，RPN 越大，越应该优先处理。
- B 错：错误率、超时率和时延只能发现「响亮的失败」，Agent 的大量失败是内容层面的：接口返回 200、延迟正常，答案却是错的。
- D 错：资损、数据泄露这类最高严重度的失败模式，不论发生频率和 RPN 多少都必须有缓解措施，RPN 只用于其余模式的排序。

<sub>考点：FMEA风险分析</sub>

</details>

<a name="ENG-DESIGN-026"></a>

### ENG-DESIGN-026　基础 · 考频 ★★★

周一上午告警：某 Agent 的任务成功率从 85% 跌到 76%。周日晚上刚发布了一个新的配置包（更新了提示词和一个工具的 schema）。下列做法中，第一步最合理的是：

- **A.** 先回滚周日的配置包止血，同时核对埋点、分母口径和评审模型是否变化，确认是不是真跌
- **B.** 立即把主模型换成更强的版本，先把成功率拉回 85%，再慢慢排查是哪里出了问题
- **C.** 先不动线上，花一两天抽样失败轨迹、做对比回放，彻底定位根因后再决定是否回滚
- **D.** 直接修改提示词，补上新工具 schema 的字段说明和调用示例，跑通冒烟测试后重新发布

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：排障的顺序是「止血 → 确认真跌 → 对齐时间线 → 切片 → 轨迹抽样 → 对比回放 → 根治与回流」。有可疑变更时先回滚，不要边查边流血。

确认真跌同样重要：埋点或数据管道延迟、分母口径变化、评审模型换了版本，都可能制造「假下跌」。止血与确认可以并行进行。回滚后再用新旧配置包对同一批输入做对比回放，二分定位是提示词还是工具 schema 的问题。

- B 错：没定位就换模型，等于又引入一个变量，可能越改越乱，也没解决真正的原因。
- C 错：定位根因很重要（抽样轨迹、对比回放都该做），但不该以继续损失两天的线上成功率为代价；先回滚，现场（Trace、配置包版本、样本）保留下来照样可以分析。
- D 错：同样是没定位就改动；冒烟测试只能拦住明显的格式错误，未经完整评测的「热修复」可能引入新的回归。

<sub>考点：排障方法</sub>

</details>

<a name="ENG-DESIGN-030"></a>

### ENG-DESIGN-030　进阶 · 考频 ★★

某 SaaS 知识库助手平台有三类客户：约 2,000 家中小企业（每家几千篇文档）；约 20 家大型企业（每家上百万篇文档，查询量大）；1 家银行，监管要求其数据不得与其他客户共用存储和计算资源。下列数据隔离方案中最合理的是：

- **A.** 所有客户共用一个向量集合，在系统提示词里要求模型只使用当前客户的资料
- **B.** 每家客户各建一套独立部署（独立的索引、模型服务与存储），彻底隔离
- **C.** 所有客户共用一个向量集合，检索返回 Top-K 结果后，再按租户 ID 过滤掉其他客户的内容
- **D.** 中小客户共用索引、在检索引擎内按租户前过滤；大客户使用独立集合或分区；银行独立部署

<details>
<summary>答案与解析</summary>

**答案：D**

**解析：**

**结论**：隔离强度按租户规模与合规要求分档，而不是「一刀切」。

- **中小客户**：共用索引最经济，但租户过滤必须在检索引擎内部执行（前过滤），入库时强制校验租户字段、缺失即拒绝；
- **大客户**：独立集合或分区，既避免「一个过滤条件写错就全量泄露」，也避免过滤条件很严格时图索引召回下降、大租户的查询量影响别人；
- **强合规客户**：独立部署，满足数据驻留与资源独占的监管要求。

- A 错：提示词不是隔离手段，数据一旦进入上下文就可能被注入或换个问法带出来。
- B 错：2,000 套独立部署的成本和运维量不可接受，绝大多数资源长期闲置。
- C 错：后过滤时其他客户的数据已经流经检索链路（重排、缓存、日志），过滤后 Top-K 里还可能一条不剩；隔离必须在检索阶段生效。

<sub>考点：多租户隔离</sub>

</details>

<a name="ENG-DESIGN-033"></a>

### ENG-DESIGN-033　进阶 · 考频 ★★

为企业知识库问答助手定北极星指标「有效回答率」。下列口径中最合理的是：

- **A.** 给出了回答（没有拒答）的问题占全部问题的比例，拒答越少说明知识覆盖越全
- **B.** 回答带引用、未被点踩，且用户没有在短时间内换个说法重问的比例
- **C.** 用户点击了「有帮助」的回答占全部回答的比例，这是用户对价值最直接的表态
- **D.** 模型对自己回答的置信度自评高于 0.8 的比例，可以实时计算、不依赖用户反馈

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：北极星要贴近用户价值、能被团队的改动影响、口径无歧义。「有效回答」的口径把「有依据」（带引用）、「没有负反馈」（未被点踩）和「问题真的解决了」（没有换个说法再问）结合起来，是知识库场景较好的口径。

- D 错：模型的自评置信度校准性差，能实时计算不代表有意义，也不代表用户得到了价值。

### ENG-DESIGN-031　进阶 · 考频 ★★★

关于多租户 Agent 平台的隔离设计，下列说法**正确**的有：

- **A.** 多租户隔离属于基础设施的职责，用跨租户探针用例做回归测试没有必要
- **B.** 按租户设置限流与配额，并用舱壁把大租户的批量任务与其他租户的在线流量隔开
- **C.** 工具层以「租户 + 用户」的身份调用业务系统，不能使用一个跨租户共享的高权限账号
- **D.** 只要向量索引按租户隔离了，会话记忆、语义缓存和 Trace 就可以全平台共用
- **E.** 租户定制的提示词与工具直接改在全平台共用的模板上，改动对全平台同时生效，便于统一维护

<details>
<summary>答案与解析</summary>

**答案：BC**

**解析：**

**结论**：B、C 正确。多租户隔离要覆盖四个面：数据、权限、资源、配置。

- E 错：违反了**配置隔离**。租户定制的提示词或工具只应作用于该租户，并能按租户灰度和回滚；改在共用模板上，一个租户的需求会悄悄改变其他租户的行为，出了问题也没法只回滚这一个租户。

**结论**：C、D、E 正确。故障切换不只是「换一个能用的地址」，还要守住合规、质量与可追溯三条线。

- A 错：不同模型的输出无法无缝拼接，把两段内容接起来会得到前后不一致甚至自相矛盾的回答。流式请求中途失败时应返回明确的错误，由业务决定是否整体重试；在尚未输出任何内容之前（如首 token 超时）切换才是安全的。
- B 错：只记请求时的主模型名、不记实际使用的模型，事后无法排查质量问题、核对账单，也无法评估切换对效果的影响。
- C 对：路由策略属于控制面，版本化、可审计；数据面缓存最后一份有效配置，控制面故障时照常转发。
- D 对：不同模型在提示词适配、工具调用格式、结构化输出上存在差异，未经评测的自动切换可能让业务「安静地失败」；关键业务宁可降级也不要换成没验证过的模型。
- E 对：合规约束优先于可用性。数据驻留要求不会因为主供应商故障而失效，切到境外供应商就是一次合规事故；可以预先准备满足驻留要求的备选（如境内的自建模型）。

<sub>考点：LLM网关设计、控制面与数据面</sub>

</details>

<a name="ENG-DESIGN-027"></a>

### ENG-DESIGN-027　进阶 · 考频 ★★

如果按意图切片后，每个意图的成功率都没有下降，那么总体成功率也不可能下降。

<details>
<summary>答案与解析</summary>

**答案：❌ 错误**

**解析：**

**错误**。总成功率是各切片成功率按流量占比的加权平均，流量构成变化（结构效应）本身就能让总体下跌。

例子：下跌前查订单占 80%、成功率 90%，退换货占 20%、成功率 70%，总体 86%；大促后两者各占 50%，两个切片的成功率都没变，总体却变成 $0.5\times90\%+0.5\times70\%=80\%$，跌了 6 个点。这不是故障，而是难任务变多了。

反过来，流量向容易的切片迁移，也可能掩盖某个切片的真实退化（辛普森悖论）。所以排障时要把跌幅拆成**结构效应**（流量构成变了）和**率效应**（切片自身变差了）：只有率效应才指向故障。

<sub>考点：排障方法</sub>

</details>

## 填空题

<a name="ENG-DESIGN-009"></a>

### ENG-DESIGN-009　基础 · 考频 ★★

Coding Agent 平台高峰期平均每分钟到达 18 个任务，每个任务在沙箱中平均运行 25 分钟。按 Little 定律，高峰期需要同时维持约 ____ 个沙箱；若每个沙箱分配 4 GiB 内存，仅沙箱内存一项就约需 ____ GiB。

<details>
<summary>答案与解析</summary>

**答案：** (1) 450；(2) 1800

**解析：**

**Little 定律**：系统中平均在飞的数量 = 到达率 × 平均停留时间，即 $L=\lambda W$。

- 并发沙箱：$18\ \text{个/分钟}\times25\ \text{分钟}=450$ 个；
- 内存：$450\times4\ \text{GiB}=1800$ GiB（约 1.76 TiB），这是按机型规划资源池的依据。

注意到达率和耗时的时间单位要一致。实际规划还要加冗余：任务耗时是长尾分布，P95 可能是均值的两三倍；到达率要按峰值算，用日均会低估并发。镜像拉取、依赖安装这类慢操作要靠预热池和快照挪出关键路径。

<sub>考点：容量估算、Coding Agent平台设计</sub>

</details>

### ENG-DESIGN-023　基础 · 考频 ★★

用 FMEA 给企业知识库助手的三个失败模式打分（严重度 S、发生频率 O、难检测度 D，各 1～10 分，D 越高越难发现）：①工具调用超时 S=4、O=7、D=2；②跨租户数据串读 S=10、O=2、D=6；③引用了已作废的旧版制度 S=6、O=5、D=7。三者的风险优先数 RPN 依次为 ____、____、____。

<details>

**答案：** (1) 56；(2) 120；(3) 210

**解析：**

$\text{RPN}=S\times O\times D$：
- ① $4\times7\times2=56$；
- ② $10\times2\times6=120$；
- ③ $6\times5\times7=210$。

## 计算题

<a name="ENG-DESIGN-010"></a>

### ENG-DESIGN-010　进阶 · 考频 ★★★

某企业办公助手：日活 120 万，人均每天发起 3 个任务，峰值 QPS 是日均的 4 倍；每个任务调用模型 3 次，每次平均输入 4,000 token、输出 300 token。
(1) 日均与峰值的任务 QPS 各是多少？峰值时每秒调用模型多少次？
(2) 峰值时的输入 TPM 与输出 TPM 各是多少？
(3) 若供应商给该账号的输入 TPM 配额为 1 亿，会出现什么情况？应当怎么应对？

<details>
<summary>答案与解析</summary>

**答案：(1) 日均约 41.7、峰值约 166.7 任务/秒，峰值每秒约 500 次模型调用；(2) 输入 TPM 1.2 亿，输出 TPM 900 万；(3) 峰值输入超出配额 2000 万 TPM（约 1/6 的输入 token），会被限流（429），需提前提额或多账号、多区域分摊，并配合按租户限流排队与降级**

**解析：**

**(1) 流量**
- 日任务数 $=120\text{万}\times3=360$ 万；
- 日均 QPS $=3.6\times10^6/86400\approx41.7$；峰值 $=41.7\times4\approx166.7$ 任务/秒；
- 每任务 3 次调用，峰值每秒约 500 次模型调用。

**(2) TPM**（配额限制的是峰值，所以按峰值算）
- 每任务输入 $3\times4000=12000$ token，输出 $3\times300=900$ token；
- 输入 TPM $=166.7\times12000\times60=1.2\times10^8$；输出 TPM $=166.7\times900\times60=9\times10^6$。

**(3) 配额**：峰值需要 1.2 亿输入 TPM，比配额多 2000 万，峰值时段约 1/6 的输入 token 会被拒绝（429）。应对：
- 提前向供应商申请提额，或多账号、多区域分摊；
- 网关按租户、用户两级限流，低优先级请求排队；
- 降级：部分请求路由到小模型或其他供应商；
- 降需求：上下文裁剪、减少每任务调用次数可以直接降低 TPM；缓存命中的 token 是否计入配额取决于供应商的规则，要事先查清。

**易错点**：用日均 QPS 申请配额（峰值扛不住）；只算输出不算输入（本题输入 TPM 是输出的 13 倍多）。

<sub>考点：容量估算</sub>

</details>

<a name="ENG-DESIGN-011"></a>

### ENG-DESIGN-011　挑战 · 考频 ★★

某公司内部的 Coding Agent 平台每天处理 6,000 个任务。每个任务平均 30 步，每步都把完整历史重新输入模型：基础上下文（系统提示词、工具定义、任务描述、仓库地图）约 12,000 token，此后每步追加约 1,500 token（工具结果与上一步输出），每步输出约 400 token。
(1) 每个任务累计输入、输出各多少 token？
(2) 前缀缓存命中率 85%，命中部分按原价 0.1 倍计费；按假设单价输入 3 美元、输出 15 美元 / 百万 token，每个任务的成本和月成本（30 天）各是多少？
(3) 任务到达的峰值是日均的 2.5 倍，每个任务平均运行 18 分钟，高峰期需要多少个并发沙箱？
(4) 若 PR 合并率为 40%，每个被合并的 PR 摊到多少模型成本？

<details>
<summary>答案与解析</summary>

**答案：(1) 输入约 101 万 token，输出 1.2 万 token；(2) 每任务约 0.89 美元，月成本约 16.1 万美元；(3) 约 188 个并发沙箱；(4) 约 2.2 美元**

**解析：**

**(1) 累计 token**：基础上下文 $S$、每步追加 $\Delta$、共 $k$ 步时，第 $i$ 步的输入为 $S+(i-1)\Delta$，累计
$$T_{in}=kS+\Delta\frac{k(k-1)}{2}=30\times12000+1500\times435=360000+652500=1012500$$
约 101 万 token，其中第二项占 64%：步数越多，「重读历史」的成本越按平方增长。输出 $30\times400=12000$ token，输入是输出的 84 倍。

**(2) 成本**
- 有效输入 $=1012500\times[(1-0.85)+0.85\times0.1]=1012500\times0.235\approx237938$ token，费用约 $0.714$ 美元；
- 输出 $12000\times15/10^6=0.18$ 美元；
- 每任务约 $0.894$ 美元，月成本 $0.894\times6000\times30\approx16.1$ 万美元。

若没有前缀缓存，每任务约 $1012500\times3/10^6+0.18\approx3.22$ 美元，是现在的 3.6 倍：Agent 场景里，缓存是降本的第一手段。

**(3) 并发**（Little 定律）：日均到达率 $6000/86400\approx0.069$ 个/秒，峰值约 $0.174$ 个/秒；在飞任务 $=0.174\times1080\ \text{秒}\approx188$ 个并发沙箱。

**(4) 每个被合并 PR 的成本**：$0.894/0.4\approx2.2$ 美元。失败任务的花费也要摊到成功的产出上；即便如此，和工程师的时间成本相比依然便宜，这是论证项目价值的关键数字。

<sub>考点：容量估算、成本估算、Coding Agent平台设计</sub>

</details>

### ENG-DESIGN-013　进阶 · 考频 ★★★

某数据分析 Agent：日活 8,000 人，人均每天提 12 个问题；每个问题调用模型 4 次（选表、写 SQL、改错、解读），每次平均输入 5,000 token、输出 400 token；输入中 40% 命中前缀缓存，命中部分按原价 0.1 倍计费。按假设单价输入 2 美元、输出 8 美元 / 百万 token：

(2) 月成本（30 天）是多少？
(3) 若通过固定系统提示词与工具定义的顺序、把动态内容后置，使缓存命中率升到 80%，月成本降低多少？

<details>
<summary>答案与解析</summary>

**答案：(1) 每问约 0.0384 美元，输入费用约占 67%；(2) 约 11.06 万美元 / 月；(3) 降到约 6.91 万美元 / 月，降低 37.5%**

**解析：**

**公式**：$C_{task}=\dfrac{T_{in}[(1-h)+h\rho]\,p_{in}+T_{out}\,p_{out}}{10^6}$，$h$ 为缓存命中率，$\rho$ 为命中部分的价格系数。

- 输出：$4\times400=1600$ token，费用 $1600\times8/10^6=0.0128$ 美元；
- 合计 $0.0384$ 美元。输入单价只有输出的 1/4，却占 $0.0256/0.0384\approx67\%$。

**(2) 月成本**：每天 $8000\times12=96000$ 问，$96000\times0.0384\times30\approx110592$ 美元，约 11.06 万美元。

**(3) 命中率 80%**：有效输入 $=20000\times(0.2+0.08)=5600$，输入费用 $0.0112$ 美元，每问 $0.024$ 美元，月成本约 6.91 万美元，降低 $1-0.024/0.0384=37.5\%$。

此外别忘了数仓一侧：每个问题还会执行若干条 SQL，扫描量和并发同样要估算，并单独设上限与配额。

**(1)** 每会话 $=0.8\times0.012+0.2\times0.030=0.0156$ 美元；每成功会话 $=$ 总成本 ÷ 成功数 $=0.0156/0.8=0.0195$ 美元，比每会话成本高 25%。

**(2)** 每会话 $=0.85\times0.013+0.15\times0.030=0.01105+0.0045=0.01555$ 美元，几乎没变；每成功会话 $=0.01555/0.85\approx0.0183$ 美元，下降约 6.2%。

**(3)** 只看每会话成本，会得出「优化没省钱，成功会话还更贵了」的错误结论；实际上办成每件事的花费下降了约 6%。反过来，一个看似「省钱」的改动如果让成功率下降，每会话成本可能变低，每成功会话成本却在上升。所以成本指标要写清分母：分母是成功数，失败任务的花费照样计入分子。同理，延迟、步数等效率指标也要结合成功率一起看。

<sub>考点：成本估算、指标树</sub>

</details>

### ENG-DESIGN-028　挑战 · 考频 ★★

某客服 Agent 只有两类意图。下跌前：查询类占流量 70%，成功率 90%；售后类占 30%，成功率 70%。下跌后：查询类占 55%，成功率 89%；售后类占 45%，成功率 60%。
(1) 下跌前后的总成功率各是多少？跌了多少个百分点？
(2) 用 $\Delta SR=\sum_s (w^1_s-w^0_s)(p^0_s-SR^0)+\sum_s w^1_s(p^1_s-p^0_s)$ 把跌幅拆成结构效应（mix，前一项）与率效应（rate，后一项），各是多少？
(3) 哪个切片的率效应最大？占总跌幅的多少？据此给出排查方向。

<details>
<summary>答案与解析</summary>

**答案：(1) 84% → 75.95%，跌 8.05 个点；(2) 结构效应 −3.0 个点，率效应 −5.05 个点；(3) 售后类的率效应 −4.5 个点，约占总跌幅的 56%，应重点排查售后链路的变更**

**解析：**

**(1)** $SR^0=0.7\times0.9+0.3\times0.7=0.84$；$SR^1=0.55\times0.89+0.45\times0.6=0.7595$；$\Delta SR=-8.05$ 个点。

**(2) 结构效应**：
- 查询：$(0.55-0.70)\times(0.90-0.84)=-0.009$；
- 售后：$(0.45-0.30)\times(0.70-0.84)=-0.021$；
- 合计 $-3.0$ 个点：难的售后类占比从 30% 涨到 45%，即使各切片都不变，总体也会跌 3 个点。

**率效应**：
- 查询：$0.55\times(0.89-0.90)=-0.0055$；
- 售后：$0.45\times(0.60-0.70)=-0.045$；
- 合计 $-5.05$ 个点。

两项相加 $-3.0-5.05=-8.05$，严格等于总跌幅。

**(3)** 售后类的率效应 $-4.5$ 个点，占 $4.5/8.05\approx56\%$，它的成功率从 70% 掉到 60%，这才是真正的退化；查询类只掉了 1 个点，可能是正常波动。排查方向：对齐售后链路的变更时间线（退换货工具、政策库、提示词），在售后切片内按租户、渠道、模型版本做二级下钻，抽样失败轨迹找第一个出错的步骤。

**为什么结构效应里要减去 $SR^0$**：若不减，占比上升的切片即使成功率处于平均水平，也会显示为贡献；减去之后，只有「低于平均水平的切片变多了」才显示为负。因为各切片占比变化之和为 0，减去 $SR^0$ 不改变总和，只改变归因。

<sub>考点：排障方法</sub>

### ENG-DESIGN-047　挑战 · 考频 ★★

某审核流水线每天处理 1,000 万条内容，采用三层漏斗：
- 第一层（哈希与规则）：0.5% 的内容命中已知违规，直接处理，其余全部进入第二层；
- 第二层（轻量分类器，成本忽略不计）：对进入本层的内容，85% 判为高置信「通过」，1% 判为高置信「违规」，其余为灰区，送第三层；
- 第三层（大模型审核）：每条约 800 个输入 token、50 个输出 token，按假设单价输入 0.5、输出 2 美元 / 百万 token；大模型能对灰区中 90% 的内容给出结论，其余 10% 送人工审核；每条人工审核约 30 秒，每名审核员每天有效工作 6 小时。

(1) 每天有多少条内容送大模型？大模型每天、每月（30 天）的费用各是多少？
(2) 每天需要多少名审核员？
(3) 若审核员最多只有 100 人，大模型至少要对灰区中多大比例的内容给出结论？
(4) 如果不用漏斗、1,000 万条全部交给大模型，每月费用是多少？漏斗节省了多少？

<details>
<summary>答案与解析</summary>

**答案：(1) 约 139.3 万条，每天约 697 美元，每月约 2.09 万美元；(2) 约 194 人；(3) 至少约 94.8%；(4) 每月 15 万美元，漏斗节省约 86%**

**解析：**

**(1)**
- 进入第二层：$1000\text{万}\times(1-0.5\%)=995$ 万条；
- 灰区：$995\text{万}\times(1-85\%-1\%)=995\text{万}\times14\%=139.3$ 万条；
- 每条大模型费用 $=800\times0.5/10^6+50\times2/10^6=0.0004+0.0001=0.0005$ 美元；
- 每天 $139.3\text{万}\times0.0005\approx697$ 美元，每月约 $2.09$ 万美元。

**(2)** 人工审核量 $=139.3\text{万}\times10\%=13.93$ 万条；工时 $=13.93\text{万}\times30\ \text{秒}\approx1161$ 小时；$1161/6\approx193.5$，约需 **194** 名审核员（还没算请假、轮班与高峰余量）。

**(3)** 100 人每天能审 $100\times6\times3600/30=72000$ 条，最多只能有 $72000/139.3\text{万}\approx5.2\%$ 的灰区送人工，所以大模型至少要对约 **94.8%** 的灰区内容给出结论。这需要同时验证这些结论的准确率，否则只是把错误从人工转移到了线上。

**(4)** 全部交给大模型：$1000\text{万}\times0.0005=5000$ 美元/天，每月 **15 万美元**；漏斗每月约 2.09 万美元，节省约 $1-697/5000\approx86\%$。

**启示**：漏斗的价值不只是省钱：前两层还承担了 300 毫秒内的同步决策；真正的瓶颈常常是人工审核，所以提升大模型在灰区的「可决断率」与准确率，以及按严重度决定哪些内容必须由人看，是这类系统设计的关键权衡。

## 代码输出题

<a name="ENG-DESIGN-022"></a>

### ENG-DESIGN-022　进阶 · 考频 ★★

下面的代码按意图对 100 条客服轨迹做切片统计（1 表示成功，0 表示失败）。输出是什么？

```python
from collections import Counter

logs = ([("查订单", 1)] * 46 + [("查订单", 0)] * 4
        + [("退换货", 1)] * 14 + [("退换货", 0)] * 11
        + [("改地址", 1)] * 22 + [("改地址", 0)] * 3)
n = len(logs)
total = Counter(intent for intent, _ in logs)
fail = Counter(intent for intent, ok in logs if not ok)
n_fail = sum(fail.values())
print(f"总成功率 {1 - n_fail / n:.0%}")
for intent in total:
    print(intent, f"流量 {total[intent] / n:.0%}", f"失败占比 {fail[intent] / n_fail:.0%}")
worst = max(total, key=lambda i: fail[i] / n_fail - total[i] / n)
print("优先优化:", worst)
```

<details>
<summary>答案与解析</summary>

**答案（程序输出）：**

```text
总成功率 82%
查订单 流量 50% 失败占比 22%
退换货 流量 25% 失败占比 61%
改地址 流量 25% 失败占比 17%
优先优化: 退换货
```

**解析：**

共 100 条轨迹，失败 $4+11+3=18$ 条，总成功率 82%。`Counter` 按元素首次出现的顺序迭代，所以依次输出查订单、退换货、改地址：

- 查订单：流量 $50/100=50\%$，失败占比 $4/18\approx22\%$；
- 退换货：流量 $25\%$，失败占比 $11/18\approx61\%$；
- 改地址：流量 $25\%$，失败占比 $3/18\approx17\%$。

「失败占比 − 流量占比」最大的是退换货（$+36$ 个百分点）：它只占四分之一的流量，却贡献了六成的失败，切片成功率只有 56%。查订单的失败数虽然不少，但失败占比低于流量占比，是表现好于平均的切片。

**启示**：总体 82% 的成功率掩盖了切片之间的巨大差异。只按流量排优先级会先去优化查订单，按失败贡献排才能找到真正的短板；实际分析时还应结合成本占比和样本量（小切片的成功率置信区间很宽）。

<sub>考点：指标树</sub>

## 编程题

<a name="ENG-DESIGN-029"></a>

### ENG-DESIGN-029　挑战 · 考频 ★★

实现成功率下跌的切片拆分函数：

```python
def decompose(before: dict, after: dict) -> dict: ...
```

- `before`、`after`：切片名 → `(任务数, 成功数)`，分别是下跌前、后的统计；
- 返回：切片名 → `(mix, rate)`。记 $w$ 为切片的流量占比、$p$ 为切片成功率、$SR^0$ 为下跌前的总成功率，则 $\text{mix}=(w^1-w^0)(p^0-SR^0)$，$\text{rate}=w^1(p^1-p^0)$；
- 只在下跌后出现的新切片：取 $w^0=0$、$p^0=SR^0$；只在下跌前出现、下跌后消失的切片：取 $w^1=0$，率效应为 0；
- 所有切片的 mix 与 rate 之和必须等于总成功率的变化。

<details>
<summary>答案与解析</summary>

**参考实现：**

```python
def decompose(before, after):
    n0 = sum(c for c, _ in before.values())
    n1 = sum(c for c, _ in after.values())
    sr0 = sum(s for _, s in before.values()) / n0
    out = {}
    for k in set(before) | set(after):
        c0, s0 = before.get(k, (0, 0))
        c1, s1 = after.get(k, (0, 0))
        w0, w1 = c0 / n0, c1 / n1
        p0 = s0 / c0 if c0 else sr0          # 新切片以下跌前的总成功率为基准
        p1 = s1 / c1 if c1 else p0           # 消失的切片没有率效应
        out[k] = ((w1 - w0) * (p0 - sr0), w1 * (p1 - p0))
    return out
```

**测试用例：**

```python
before = {"查询": (700, 630), "售后": (300, 210)}
after = {"查询": (1100, 979), "售后": (900, 540)}
r = decompose(before, after)
assert abs(r["查询"][0] - (-0.009)) < 1e-9 and abs(r["查询"][1] - (-0.0055)) < 1e-9
assert abs(r["售后"][0] - (-0.021)) < 1e-9 and abs(r["售后"][1] - (-0.045)) < 1e-9


def total_sr(d):
    return sum(s for _, s in d.values()) / sum(c for c, _ in d.values())


def check_sum(b, a):
    res = decompose(b, a)
    s = sum(m + rt for m, rt in res.values())
    assert abs(s - (total_sr(a) - total_sr(b))) < 1e-9


check_sum(before, after)
# 新切片：结构效应为 0，率效应以下跌前的总成功率为基准
after2 = {"查询": (700, 630), "售后": (200, 140), "新渠道": (100, 50)}
r2 = decompose(before, after2)
assert abs(r2["新渠道"][0]) < 1e-12
assert abs(r2["新渠道"][1] - 0.1 * (0.5 - 0.84)) < 1e-9
check_sum(before, after2)
# 消失的切片：只有结构效应
after3 = {"查询": (1000, 900)}
r3 = decompose(before, after3)
assert r3["售后"][1] == 0
check_sum(before, after3)
# 前后完全相同：全部为 0
assert all(abs(m) < 1e-12 and abs(x) < 1e-12 for m, x in decompose(before, before).values())
```

**解析：**

**思路**：
1. 分别用下跌前、后的总任务数算每个切片的流量占比 $w^0$、$w^1$，用下跌前的总成功率作为结构效应的基准 $SR^0$；
2. 对两期切片的并集逐个计算：新切片没有「下跌前的成功率」，以 $SR^0$ 作基准，于是它的结构效应为 0，率效应 $=w^1(p^1-SR^0)$；消失的切片 $w^1=0$，率效应自然为 0；
3. 正确性：$\sum_s w^1_sp^1_s-\sum_s w^0_sp^0_s$ 恰好等于两项之和（$\sum_s(w^1_s-w^0_s)SR^0=0$），测试里用 `check_sum` 断言这一点。

**复杂度**：$O(S)$，$S$ 为切片数。实际数据先按维度聚合成计数，再调用本函数；可以对版本、模型、租户、意图、渠道等多个维度各拆一次，找率效应占比最高的切片，再在切片内部按另一个维度二级下钻。

**易错点**：结构效应忘了减 $SR^0$（总和不变，但单个切片的归因会错，测试第 1 组会失败）；新切片取 $p^0=0$ 导致率效应被夸大；占比用两期合并的总数来算；切片任务数为 0 时除以零。

<sub>考点：排障方法</sub>

</details>

### ENG-DESIGN-006　进阶 · 考频 ★★★

系统设计题的需求澄清环节应该从哪些维度提问？请至少列出 6 个维度，分别说明「答案会怎样改变设计」；再说明什么是非目标（non-goals），以及为什么要在澄清结束时明确说出来。

<details>
<summary>答案与解析</summary>

**参考答案：**

**澄清维度（每个问题都要能说出它如何改变设计）**：
1. **用户与场景**（谁用、从哪个入口、完成什么任务）：内部员工能接受确认步骤和较长延迟；C 端用户要求秒级响应、零学习成本。
2. **规模**（DAU、人均次数、峰值倍数、数据量）：决定调 API 还是自部署、索引如何分片、是否需要队列削峰。
3. **延迟**（交互式还是后台任务，首字和完成时间）：交互式要流式输出、限制步数；后台任务可以多步规划、跑几十分钟。

6. **预算**（每任务或每月能花多少）：决定模型档位、路由与缓存的力度。
7. **现有系统**（已有的 API、账号与权限体系、知识源、工单系统）：能复用就复用；没有稳定 API 的系统第一期不接。

**非目标**：第一期明确不做的事，如「不做跨租户检索、不自动执行退款、不支持多语言」。说出来的作用：
- 防止讨论中范围悄悄膨胀，让后面的估算与架构有清晰边界；
- 展示取舍能力：知道什么重要、什么可以延后；
- 和面试官对齐预期，避免后面被问「为什么不支持某功能」时陷入被动。

**收尾动作**：复述理解并给出自己的假设（如「按日活 50 万、P95 8 秒、数据不出域设计」），请面试官确认后进入指标与估算。

**评分要点（共 10 分）：**

- 列出至少 6 个澄清维度（2 分）
- 每个维度都说明答案如何改变设计，而不只是罗列问题（4 分）
- 说明非目标的含义并举例（2 分）
- 说明非目标的作用，并提到复述理解与给出假设（2 分）

**讲解：**

**常见失分点**：只罗列问题，说不出它们如何影响设计；问「用什么前端框架」这类与核心设计无关的问题；问了十几个问题、十分钟还没进入设计；澄清完不给结论和假设，等面试官替自己决定；忘了说非目标，导致后面不断被追加需求。

<a name="ENG-DESIGN-016"></a>

### ENG-DESIGN-016　进阶 · 考频 ★★★

请用分层模板讲一个 Agent 平台的参考架构：分哪几层，每层负责什么？请沿「一次请求」把数据流走一遍，并说明架构图上应当标出的信任边界及其规则。

<details>
<summary>答案与解析</summary>

**参考答案：**

**四层与职责**
1. **接入层**：网关负责鉴权、租户识别、按租户与用户两级限流、流式输出。
2. **编排层**：编排器运行 Agent 循环或工作流，管步数、预算和超时；编排器本身无状态，会话与检查点外置到存储，便于水平扩展和故障恢复。
3. **能力层**：模型路由（按难度与成本选档位、供应商故障时切换）与模型池；工具层（MCP 或内部工具网关，负责参数校验、以用户身份鉴权）；检索与记忆（按租户隔离）；沙箱（执行代码、操作浏览器）。
4. **治理层**：评测与 Trace、人审队列、安全护栏、配置与发布。这一层最容易漏画，却决定系统能不能上线。

**一次请求的数据流**（举例）：
① 用户请求进入网关，完成鉴权、租户识别和限流；② 编排器加载会话状态与当前生效的配置包；③ 经模型路由调用模型，得到下一步动作；④ 工具调用经工具层校验参数、以发起请求的用户身份访问业务系统，高风险动作进入人审队列；⑤ 结果回填上下文，写检查点和 Trace；⑥ 最终结果流式返回给用户。控制面（提示词、工具、模型版本、灰度规则）以虚线下发给编排器，Trace 与指标以虚线回流到治理层。

**信任边界与三条规则**
- **模型输出不可信**：工具参数一律校验；权限按发起请求的用户在工具层判定，不看模型说了什么。
- **外部内容只是数据**：网页、文档、邮件、工具返回都可能藏有间接提示注入，只能当数据，不能当指令。
- **凭证不进上下文**：密钥由工具层注入；高风险写操作要用户确认或人审；沙箱默认断网；避免同一会话同时具备「读私有数据、接触不可信内容、对外发送」三种能力。

**评分要点（共 10 分）：**

- 给出接入、编排、能力、治理四层并说清各层职责（3 分）
- 沿一次请求走通数据流，说明状态存放位置与控制面、数据面的关系（3 分）
- 标出信任边界并说明模型输出不可信、外部内容只是数据、凭证不进上下文等规则（3 分）
- 提到治理层（评测、Trace、人审、配置发布）是能否上线的关键（1 分）

**讲解：**

**常见失分点**：把「Agent」画成一个大框，看不出数据怎么流；层与层之间只画框不画箭头含义；工具用一个高权限服务账号访问业务系统；状态放在编排器内存里，扩容或重启就丢任务；完全不画评测、Trace 和配置发布，面试官会认为没上过线。

<sub>考点：参考架构</sub>

</details>

<a name="ENG-DESIGN-019"></a>

### ENG-DESIGN-019　进阶 · 考频 ★★

什么是 Agent 系统的「不可变配置包」？它应当包含哪些内容？为什么要在每条 Trace 里记录配置包的版本号？它对发布、排障和回滚分别有什么帮助？

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **定义**：把决定 Agent 行为的所有可变部分打包成一个带版本号、发布后不再修改的整体，作为发布与回滚的基本单位。
2. **内容**：模型（供应商、型号与钉住的具体版本）与采样参数；系统提示词与模板；工具清单、工具描述与参数 schema；检索参数（索引版本、top-k、重排模型等）；护栏策略与阈值；路由规则；必要时还有记忆与上下文压缩策略。
3. **Trace 记录版本号**：每次请求都能追溯「当时是哪套配置在跑」；排障时可以用同一批输入在新旧两个包上对比回放；变更项多时逐项替换、二分定位，类似 `git bisect`。
4. **发布**：任何一项变化都生成新包，过离线门禁（冒烟、回归、安全红队）后再灰度；灰度对比、线上指标都按包版本分组统计。
5. **回滚**：一步切回上一个包，避免「代码回滚了，提示词、工具版本或索引却没回」的半回滚；控制面故障时，数据面继续使用最后一个有效包。
6. **审计**：谁在什么时候发布了哪个包、相对上一版改了什么，都可以查询。

**评分要点（共 10 分）：**

- 说明配置包的定义：带版本、不可变、作为发布与回滚单位（2 分）
- 列出主要内容：模型版本、提示词、工具定义、检索参数、护栏策略等（3 分）
- 说明 Trace 记录版本号对回放与二分定位的作用（2 分）
- 说明对发布门禁、整体回滚与审计的帮助（3 分）

**讲解：**

**常见失分点**：只对代码做版本管理，提示词和工具定义在后台随手改；配置包发布后还能原地修改，导致回放结果不可信；模型只写「某某系列」而不钉具体版本，供应商静默升级后无从排查；回滚时只回了一部分组件。

<sub>考点：控制面与数据面、参考架构</sub>

</details>

### ENG-DESIGN-025　进阶 · 考频 ★★

请用 FMEA 的「失败模式 — 影响 — 检测 — 缓解」四列，为企业知识库问答助手列出至少 5 个失败模式，覆盖模型、检索与数据、外部依赖、安全、发布五类中的至少四类；并说明如何给这些失败模式排优先级。

<details>
<summary>答案与解析</summary>

**参考答案：**

| 失败模式 | 影响 | 检测 | 缓解 |
|---|---|---|---|
| 回答没有依据（幻觉） | 误导员工，信任下降 | 引用校验、评审模型抽检、点踩率 | 强制逐句引用，找不到依据就拒答 |
| 引用已作废的旧版制度 | 员工按旧规办事出错 | 引用的版本与生效时间巡检 | 变更事件触发增量索引，只检索生效版本，引用带版本号和更新时间 |
| 越权引用（权限同步延迟、缓存串用） | 数据泄露、合规事故 | 不同权限的探针账号持续巡检、审计日志 | 检索时按 ACL 前过滤，权限变更分钟级同步，缓存键带权限范围与知识库版本 |

| 模型供应商故障或限流 | 大面积不可用 | 错误率、429 比例 | 多供应商路由，降级到小模型，或只返回检索到的原文片段 |
| 检索服务或索引故障 | 拒答率突增 | 检索延迟、空结果率告警 | 副本与熔断，降级为关键词检索 |
| 新版本回归（改提示词、换 Embedding） | 有效回答率悄悄下降 | 离线回归集、灰度对比 | 配置包门禁、灰度、自动回滚 |

**排优先级**：
1. 对每个模式按严重度 S、频率 O、难检测度 D 打 1～10 分，用 RPN = S × O × D 排序；
2. 最高严重度（越权、泄露）不论 RPN 都必须有缓解措施；

- 列出至少 5 个失败模式，覆盖至少四类来源（3 分）
- 每个模式的影响、检测、缓解完整且具体（3 分）
- 识别安静的失败（幻觉、过期引用）并给出专门的检测手段（2 分）
- 说明 RPN 排序以及最高严重度必须处理的原则（2 分）

**讲解：**

**常见失分点**：只列模型的问题，忽略数据、依赖、发布和安全；检测一栏只写「加监控」，说不出看什么指标；缓解一栏只写「加重试」；不知道 RPN 排序之外还有「严重度一票否决」；没有覆盖越权引用这一知识库场景最致命的失败模式。

<a name="ENG-DESIGN-020"></a>

### ENG-DESIGN-020　挑战 · 考频 ★★

你在评审一份「企业内部 Agent 平台」的设计文档，摘录如下：

1. 所有业务工具统一使用一个高权限服务账号访问业务系统，「哪些用户能查什么」写在系统提示词里；
2. 编排器把会话历史和执行中的任务状态保存在进程内存中，靠增加实例数扩容；
3. 提示词与工具定义直接写在代码里，每次修改随代码一起发版；
4. 文档里没有评测、Trace 和人审的内容，作者表示「上线后再补」；
5. 架构图上只有一个大框「LLM Agent」，网关、检索、工具都连到这个框上。

请逐条指出问题与可能的后果，并给出改进方案。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 高权限服务账号 + 权限写在提示词里**
- 后果：模型一旦被注入或自己犯错，权限就放大到所有用户的数据（混淆代理人）；提示词里的规则可以被绕过，也可能被套出来。
- 改进：工具层以「租户 + 发起请求的用户」身份调用业务系统（OAuth 委托、最小范围、短时效）；权限由工具层和业务系统判定；凭证由工具层注入，不进入模型上下文。

**2. 状态放在进程内存**
- 后果：扩缩容、发版重启或实例故障时，进行中的任务全部丢失；同一会话的请求被路由到别的实例就找不到历史。
- 改进：编排器无状态，会话与检查点外置到数据库或 KV；长任务每步写检查点，实例故障后从检查点恢复。

**3. 提示词与工具定义写在代码里**
- 后果：改一句提示词也要整体发版；无法单独灰度、单独回滚；不能按租户配置。
- 改进：由控制面管理不可变配置包（模型版本、提示词、工具定义、检索参数、护栏策略），版本化、可审计、可灰度、可一键回滚；每条 Trace 记录配置包版本。

**4. 没有评测、Trace 和人审**
- 后果：上线前无法证明质量达标；出问题后无法定位到哪一步、哪个工具；高风险动作没有兜底。
- 改进：第一期就建评测集与离线门禁（含安全红队用例）、全链路 Trace、人审队列与审计日志。「裁功能可以，裁评测不行」。

**5. 一个大框代表所有逻辑**
- 后果：看不出数据流、状态存放位置、权限在哪里判定、失败时走哪条路，也就无法讨论瓶颈和风险。
- 改进：按接入、编排、能力、治理四层画图；给一次请求的数据流编号；用虚线标出信任边界、控制面与数据面；标注关键数字（峰值 QPS、P95 延迟预算、每任务 token）。

**评分要点（共 10 分）：**

- 指出高权限账号与提示词权限的放大风险，并给出以用户身份在工具层鉴权、凭证不进上下文的方案（2 分）
- 指出内存状态导致任务丢失，给出无状态编排器与检查点外置（2 分）
- 指出配置与代码耦合的问题，给出控制面管理的不可变配置包（2 分）
- 指出缺少评测、Trace、人审的后果，并要求第一期就具备（2 分）
- 指出大框架构图的问题，给出分层、数据流与信任边界的画法（2 分）

**讲解：**

**常见失分点**：只说「这样不好」而不说具体后果；第 1 条只建议「把提示词写得更严格」；第 3 条只说「改成配置文件」，没有版本化、灰度与回滚；把第 4 条当成可以延后的文档问题。评审意见要做到「问题 → 后果 → 改法」三段齐全。

<sub>考点：参考架构、控制面与数据面</sub>

</details>

<a name="ENG-DESIGN-032"></a>

### ENG-DESIGN-032　挑战 · 考频 ★★

某多租户 Agent 平台的所有租户共用一个模型服务账号，输入 TPM 配额为 2 亿，平时的峰值用量约 1.2 亿。上周发生了两起事故：

1. 周二上午，大客户 A 在后台发起了「批量总结 20 万份合同」的任务，半小时内平台的 429 错误率从 0.1% 升到 35%，所有租户的在线对话大面积失败；
2. 周四，运营同学为客户 B 调整了一段系统提示词（要求回答更简短），发布后其他 30 多个租户的回答也都变短了，部分租户的工具调用开始缺少参数。

请分析两起事故暴露出的隔离缺陷，给出改进方案，并说明如何验证隔离确实生效。

<details>
<summary>答案与解析</summary>

**参考答案：**

**事故 1：资源隔离缺失**
- 原因：全平台共用一个配额和同一条请求队列，没有租户级的限流与配额，也没有区分在线流量与离线批量任务；A 的批量任务耗尽了配额，所有人一起失败（「吵闹的邻居」）。
- 改进：
  1. 按租户（以及租户内按用户）设置 TPM 与并发配额，超额的请求在该租户内排队或拒绝，不影响别人；
  2. 在线与离线分池：批量任务走独立的队列、账号或批处理接口，限制并发，优先安排在低峰期，并能被在线流量抢占；
  3. 舱壁与优先级：为在线流量和重要租户预留配额，剩余部分共享；
  4. 按租户监控用量与 429 比例，接近上限时先降级（小模型、排队提示），再拒绝。

**事故 2：配置隔离缺失**
- 原因：系统提示词是全局配置，为 B 做的定制直接改动了所有租户共用的基础提示词；改动既没有评测，也没有按租户灰度，无法只对 B 生效。
- 改进：
  1. 配置分层：平台基础配置包 + 租户覆盖层，租户只能修改允许定制的字段（语气、长度、品牌信息等），工具定义和安全约束不在可定制范围内；
  2. 每个租户实际生效的配置 = 基础包版本 + 覆盖层版本，Trace 同时记录两者；
  3. 租户级变更先过该租户的评测集再灰度；平台级变更按租户分批灰度，支持按租户回滚；
  4. 配置修改有权限控制与审计。

**验证隔离生效**
- 资源：故障演练，模拟某个租户突发 10 倍流量，确认其他租户的成功率与 P95 延迟不受影响；
- 配置：任何租户的配置变更后，对其他租户的回归集做前后对比，结果应保持不变；
- 数据：跨租户探针持续巡检（用 A 的账号询问只有 B 才有的内容），并作为上线门禁。

**评分要点（共 10 分）：**

- 指出事故 1 的原因：共享配额、无租户级限流、在线与离线流量未隔离（2 分）
- 给出事故 1 的改进：租户配额、离线分池或批处理、舱壁与优先级、按租户监控（3 分）
- 指出事故 2 的原因：租户定制修改了全局配置，且无评测与按租户灰度（2 分）
- 给出事故 2 的改进：基础包 + 租户覆盖层、限定可定制范围、按租户灰度与回滚（2 分）
- 给出验证隔离的方法：演练、回归对比、跨租户探针（1 分）

**讲解：**

**常见失分点**：事故 1 只建议「申请更大的配额」，没有意识到问题在于缺少租户级隔离，配额再大也会被下一个批量任务吃光；事故 2 只建议「改之前多检查」，没有把租户定制与平台基础配置分层；只谈数据隔离，忽略资源与配置也是多租户隔离的组成部分。

<sub>考点：多租户隔离</sub>

</details>

### ENG-DESIGN-037　挑战 · 考频 ★★

某电商客服 Agent 平时日均约 80 万个会话，每个会话平均 12 次模型调用，每次平均输入 3,000 token、输出 150 token。下个月有一场大促，预计峰值流量是日均的 10 倍，持续约 2 小时。当前方案是全部调用外部 API，账号的输入 TPM 配额为 6,000 万。

(1) 估算日均与大促峰值的每秒模型调用次数，以及峰值所需的输入 TPM；
(2) 现有配额够不够？如果改成自建推理集群并按大促峰值配卡，会有什么问题？请给出更合理的容量方案；
(3) 大促期间如果容量仍然不足，如何降级与排队，既保住核心体验，又不放大资损风险？
(4) 大促前需要做哪些准备与演练？

<details>
<summary>答案与解析</summary>

**参考答案：**

**(1) 估算**
- 每天模型调用 $80\text{万}\times12=960$ 万次，日均约 111 次/秒；大促峰值约 1111 次/秒；
- 峰值输入 TPM $=1111\times3000\times60\approx2$ 亿（日均约 2000 万）；输出 TPM 约 1000 万。

**(2) 容量方案**
- 现有 6000 万配额只够日均的 3 倍，不到峰值需求的三分之一。
- 按峰值自建：一年中绝大多数时间只用到峰值容量的十分之一左右，卡的平均利用率不到 10%，非常不划算。
- 更合理的做法：自部署承接平稳的基线流量（如日均的 2～3 倍），峰值溢出到外部 API；提前向供应商申请临时提额，或多供应商、多账号分摊；同时降低需求本身：固定前缀提高缓存命中，简单意图路由到小模型，高频问题（如「什么时候发货」）走模板或缓存。

**(3) 降级与排队**（原则：降低体验，不降低安全标准）
- 按意图分级：订单与物流查询优先保障，可以退化为模板化回答；
- 写操作（退换货、改地址）不能为了省容量而跳过策略引擎或人审，只能排队，并告知用户预计等待时间；
- 复杂问题直接引导到人工或留言工单，避免 Agent 多轮绕圈占用容量；
- 按用户限流，防止刷请求；优先保障已在会话中的用户，新会话排队。

**(4) 准备与演练**
- 按预期峰值的 1.2～1.5 倍压测全链路，包括工具与订单系统等下游；
- 配额审批、预扩容与预热；
- 演练供应商故障切换、降级开关、熔断与只读模式；
- 大促期间冻结配置包变更，安排值班，准备按意图拆分的大盘与告警；
- 人审与人工坐席同步扩充排班，否则排队会转移到人工侧。

**评分要点（共 10 分）：**

- 正确算出日均与峰值的调用次数及峰值输入 TPM（2 分）
- 指出配额不足与按峰值自建利用率过低，给出自部署基线 + API 溢出等方案（3 分）
- 降级方案区分读写：读可退化，写操作不跳过策略引擎与人审（3 分）
- 给出压测、配额、演练、变更冻结、人工排班等准备措施（2 分）

**讲解：**

**常见失分点**：用日均流量规划大促容量；只想到「加卡」或「申请配额」一条路；降级时为了保吞吐而让写操作绕过审核，等于用资损换可用性；忘了下游订单系统和人工坐席同样有容量上限；不做演练，降级开关在真正需要时打不开。

## 系统设计题

<a name="ENG-DESIGN-034"></a>

### ENG-DESIGN-034　挑战 · 考频 ★★★

你负责为一款面向企业客户的办公套件设计「知识库问答助手」：员工可以就公司制度、产品文档、会议纪要提问，回答必须带引用。已知：日活约 50 万，人均每天约 4 个问题，峰值是日均的 3 倍；P95 首字时间小于 2 秒、完整回答小于 8 秒；多租户，最大的租户约有 100 万篇文档；**文档权限必须继承**（用户看不到的文档，答案里也不能出现）。

请给出完整设计：需求澄清与非目标、容量与成本估算、架构、关键设计（权限、时效、引用与拒答、缓存与延迟）、指标体系、主要风险与演进路线。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 澄清与非目标**
- 要确认：数据能否出域（决定调 API 还是私有化部署）；文档来源与更新频率；权限体系（SSO、用户组、密级）；是否需要多语言、是否要理解图片与扫描件。
- 非目标（第一期）：不做跨租户检索、不代写文档、不理解图片；只读，不执行任何写操作。

**2. 估算**（单价与吞吐均为假设）
- 流量：$50\text{万}\times4=200$ 万问/天，日均约 23 QPS，峰值约 70 QPS；
- token：每问 2 次调用（查询改写 + 生成），合计输入约 6000、输出约 500 token；峰值输入 TPM $\approx70\times6000\times60\approx2500$ 万，需提前申请配额；
- 成本：假设输入 0.1、输出 0.4 美元 / 百万 token，前缀缓存命中 50%（按 0.1 倍计），每问约 0.00053 美元，月成本约 3.2 万美元；第一期调 API，量大且稳定后再评估自部署；
- 索引：最大租户 100 万篇 × 约 20 块 ≈ 2000 万个向量，按租户分片，大租户独立集合。

**3. 架构**
- 在线链路：网关（SSO、租户识别、限流）→ 查询改写（小模型）→ 混合检索（BM25 + 向量，带 ACL 前过滤）→ 重排 → 生成（逐句引用、可拒答）→ 引用校验 → 流式返回；
- 离线链路：文档源变更事件与 ACL 同步 → 增量切块与向量化 → 按租户分片的索引；
- 治理：评测与 Trace、配置包与灰度、权限探针、审计。

**4. 关键设计**
- **权限继承**：同步文档时带上 ACL（用户、用户组、密级）；检索时把当前用户的可见范围交给检索引擎作为过滤条件，看不到的文档根本不进上下文；权限变更、文档删除分钟级同步，并级联到索引和各类缓存。
- **时效**：变更事件触发增量索引；引用带文档版本与更新时间；新旧制度冲突时只检索生效版本。
- **引用与拒答**：逐句标注引用，后处理检查引用存在且内容确实支持该句；检索不到就明确说没找到。
- **缓存**：系统提示词放在前缀以提高前缀缓存命中；语义缓存的键必须带租户、权限范围和知识库版本。
- **延迟预算**（示意）：网关与鉴权约 50 ms，改写约 300 ms，检索约 150 ms，重排约 200 ms，生成首字约 1 s，合计约 1.7 s；改写可与原问题的检索并行，进一步压缩。

**5. 指标**
- 北极星：有效回答率（带引用、未被点踩、用户没有换个说法重问）；
- 质量：引用准确率、拒答准确率；效率：P95 首字时间；成本：每问成本、缓存命中率；
- 护栏：越权引用数为 0，用不同权限的探针账号持续巡检。

**6. 风险与演进**
- 风险：越权（权限同步延迟、缓存串用）、引用过期内容、文档中藏有间接注入（检索内容只当数据、只渲染白名单链接）、供应商故障（多供应商路由、降级为只返回检索片段）。
- 演进：问答 → 表格与图片理解、多跳检索（Agentic RAG）→ 起草文档、发起审批等写操作（加确认与人审）。

**评分要点（共 10 分）：**

- 澄清关键约束并给出非目标（1 分）
- 估算 QPS、TPM、月成本与索引规模，量级正确且假设清楚（2 分）
- 架构包含在线链路、离线索引链路与治理层（2 分）
- 权限继承设计正确：ACL 前过滤、权限变更与删除的级联同步、缓存键带权限范围（2 分）
- 覆盖时效、引用校验与拒答、延迟预算（1 分）
- 给出北极星、护栏与探针巡检，并说明主要风险与演进路线（2 分）

**讲解：**

**常见失分点**：只讲 RAG 链路（切块、Embedding、重排），没有估算和指标；权限放在生成之后让模型「别说出来」；忽略权限变更与文档删除的同步，以及缓存造成的串读；没有拒答设计；不给延迟预算，答不出 2 秒首字怎么保证；把写操作塞进第一期。

<sub>考点：知识库助手设计、容量估算、多租户隔离</sub>

</details>

### ENG-DESIGN-036　挑战 · 考频 ★★★

为一家约 3,000 名工程师的公司设计内部 Coding Agent 平台。已知：约 2,000 个代码仓库；任务类型为修复 CI 失败、修复简单 bug、补充单元测试，由 issue、CI 失败事件或 IDE 指令触发；预计每天约 8,000 个任务，每个任务平均 35 步、运行约 20 分钟，要求 P95 完成时间小于 40 分钟；**代码不得离开公司网络**；Agent 不能合并代码、不能接触生产环境。

请给出设计：需求澄清与非目标、估算（token 量、模型服务容量、并发沙箱）、架构、关键设计（沙箱、验证、权限、上下文与恢复、模型部署）、指标、主要风险与演进路线。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 澄清与非目标**
- 产出形式：一律以 PR 交给代码负责人评审合并；
- 代码不出域：模型只能私有化部署，或使用在公司网络内的专属部署，这一条决定了后面的容量规划；
- 依赖来源：沙箱断网时，依赖只能从内部镜像拉取；
- 非目标：自动合并、跨仓库大规模重构、任何生产环境操作。

**2. 估算**（吞吐为假设值，实际以压测为准）
- 每任务累计输入：基础上下文约 12K、每步追加约 1.5K，$35\times12000+1500\times\frac{35\times34}{2}\approx131$ 万 token；输出 $35\times400=1.4$ 万 token；
- 每天输入约 $8000\times131\text{万}\approx105$ 亿 token；前缀缓存命中 85% 时，需要真正做 prefill 的约 16 亿 token/天，日均约 1.8 万 token/s，峰值（2.5 倍）约 4.6 万 token/s；输出日均约 1300 token/s，峰值约 3200 token/s；
- 模型服务：若单个 8 卡节点在 SLO 内可输出约 3000 token/s、处理约 3 万 token/s 的 prefill，则峰值负载约 $3240/3000+45600/30000\approx2.6$ 个节点，加 30% 冗余约需 4 个节点；
- 并发沙箱（Little 定律）：峰值到达率 $8000\times2.5/86400\approx0.23$ 个/秒，乘以 1200 秒约 280 个并发沙箱；按 P95 时长与突发留余量，资源池按约 350 个规划，每个 4 GiB 内存约需 1.4 TiB。

**3. 架构**
触发与队列（按优先级与团队配额）→ 编排器（Agent 循环、步数与 token 预算、每步检查点）→ 沙箱池（每任务一个容器或 microVM，挂仓库快照，预热）→ 验证（构建、单测、lint）→ 开 PR 并附复现与测试证据 → 人工评审；旁路：私有化模型服务（大小模型路由）、代码检索与仓库地图、Trace 与评测、配置包与灰度。评审打回的原因回流到评测集。

**4. 关键设计**
- **沙箱**：一任务一环境，默认断网，只放行内部依赖镜像；限 CPU、内存与时长，结束即销毁；沙箱内没有长期凭证。
- **验证驱动**：先写能复现问题的失败测试，再修复，最后跑相关测试与 lint；防假绿灯：不允许修改已有测试的断言，检测被跳过的测试，测试文件的改动单独标注。
- **权限**：只能推送自己的分支、开 PR；git 凭证由沙箱外的代理注入并限制可推送的分支；完全不接触生产。
- **上下文与恢复**：仓库地图加代码检索做定位；项目说明文件记录构建命令与约定；每步写检查点，沙箱崩溃后从检查点重建。
- **模型部署与路由**：私有化部署代码能力强的模型承接主流程，简单子任务（如生成提交说明、分类）路由到小模型；队列按团队配额防止单个团队占满资源。

**5. 指标**
- 北极星：PR 合并率（合并数 ÷ Agent 创建的 PR 数，合并后 7 天内被回滚的不算）；
- 护栏：合并后 7 天回滚率、越权命令拦截数；
- 质量：评审打回率、首次 CI 通过率；效率：P95 完成时间、排队时长；成本：每个被合并 PR 的成本（含 GPU 摊销）。

**6. 风险与演进**
- 假绿灯 → 测试改动单独审查；供应链（引入可疑依赖）→ 依赖白名单，锁文件变更必须人审；issue 中的注入 → issue 内容只当数据、沙箱断网、无凭证；评审疲劳 → 低置信度只给建议、限制每人每天的 PR 数；成本失控 → 每任务步数与 token 上限。
- 演进：补单测（最容易验证）→ 修 CI → 修 bug → 跨文件重构；人工触发 → 自动触发；读多写少的调研子任务再拆给并行子 Agent。

**评分要点（共 10 分）：**

- 澄清产出形式与代码不出域的约束，并推导出私有化部署，给出非目标（1 分）
- 估算累计 token、模型服务容量与并发沙箱，量级正确、假设清楚（2 分）
- 架构完整：队列与配额、编排与检查点、沙箱池、验证、PR 与评审、回流（2 分）
- 沙箱、验证驱动与防假绿灯、权限与凭证的设计到位（3 分）
- 给出北极星与护栏，并覆盖主要风险与演进路线（2 分）

**讲解：**

**常见失分点**：忽略「代码不出域」对模型部署方式的决定性影响；只算 token 不算并发沙箱；沙箱联网、带长期凭证；没有防假绿灯的措施；北极星选「任务完成数」而不是 PR 合并率，也没有回滚率护栏；把重点放在多 Agent 编排，而不是验证与沙箱这两个核心难点。

<sub>考点：Coding Agent平台设计、容量估算</sub>

</details>

<a name="ENG-DESIGN-038"></a>

### ENG-DESIGN-038　挑战 · 考频 ★★★

设计一个电商 App 内的智能客服 Agent：处理订单查询、物流查询、退换货申请、修改收货地址，投诉与复杂纠纷转人工。已知日均约 100 万个会话；首字时间小于 1.5 秒；涉及资金与个人信息，退换货有明确的政策（金额、时效、商品类型），所有写操作必须可审计。

请给出设计：需求澄清与分期计划（MVP）、架构（读、写链路如何区分）、写操作的安全设计、人审环节的容量估算、指标体系、主要风险与演进路线。人审容量按以下假设估算：退换货申请每天约 3 万单，其中约 10% 因金额或风险分进入人工审核，每单审核约 2 分钟，审核员每天有效工作 6 小时。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 澄清与分期**
- 澄清：各意图的进线占比、退换货政策由谁维护、哪些动作可撤回、坐席与审核的人力、能否接入订单与支付系统的 API。
- 非目标：自动赔付、售前导购。
- 一期：查询类全自动；退换货由 Agent 填好申请单，低风险的由用户确认后提交，高风险的进人审；投诉直接转人工并附交接单。
- 二期进入条件：确认环节的建议采纳率持续高于 95%、错误退款连续一个月为 0，才对低于金额阈值且符合政策的订单放开自动执行；三期做物流异常时的主动通知。

**2. 架构**
- 读链路：网关（登录态、限流）→ 客服 Agent（意图识别、槽位、解释政策）→ 只读工具（订单、物流、政策库），直接返回。
- 写链路做成工作流：Agent 填参数 → **策略引擎**（金额、时效、商品类型、风险分）→ 低风险：用户确认卡片 → 写工具；高风险：人审队列（有 SLA，超时自动升级）→ 写工具。
- 转人工：附交接单（意图、已核实的信息、已执行的动作与结果、用户情绪），用户不必从头再说一遍。

**3. 写操作安全**
- 能不能退、退多少由确定性的策略引擎决定，模型只负责理解意图、填参数、解释政策，被注入「忽略规则全额退款」也无效；
- 工具以当前登录用户的身份调用订单系统，参数在工具层校验；
- 写操作带幂等键（会话 + 订单 + 动作），重试不会重复退款；
- 审计日志记录身份、参数、结果；每天与订单、支付系统对账；单用户的金额与频次上限。

**4. 人审容量**
- 每天进入人审 $3\text{万}\times10\%=3000$ 单，$3000\times2\ \text{分钟}=6000$ 分钟 $=100$ 小时；
- 每人每天有效 6 小时，约需 $100/6\approx17$ 名审核员（不含请假与高峰余量）；
- 大促时申请量可能翻几倍：提前扩充排班，或临时调整进入人审的阈值并接受更长的排队；监控审核 SLA、积压量和「秒批」比例，防止审批疲劳。

**5. 指标**
- 北极星：自助解决率（未转人工，且 48 小时内没有因同一问题再次进线）；
- 护栏：错误退款金额（资损）、越权查询数为 0、投诉率；
- 质量：政策遵从率，离线用模拟用户评测并报告 pass^k；效率：首字时间、平均轮数；成本：每会话成本；人审：审核 SLA 达成率、积压量。

**6. 风险与演进**
- 资损 → 策略引擎、金额阈值、人审、对账；注入 → 政策不由模型决定、参数在工具层校验；个人信息泄露 → 身份绑定、字段脱敏；大促洪峰 → 预扩容、排队、降级；人审积压 → 排班与 SLA 升级。
- 演进：查询自动化 → 退换货「建议 + 确认」→ 低风险自动执行 → 主动服务。

**评分要点（共 10 分）：**

- 给出分期计划与进入下一阶段的数据条件（2 分）
- 读写链路分离，写链路为策略引擎 + 确认或人审 + 幂等写工具的工作流（2 分）
- 写操作安全：规则决定、身份绑定、参数校验、幂等、审计与对账（2 分）
- 正确估算人审工作量（约 100 小时、约 17 人）并考虑高峰与 SLA（2 分）
- 给出北极星与护栏，覆盖主要风险与演进（2 分）

**讲解：**

**常见失分点**：让模型直接决定退不退、退多少；读写链路不分，所有操作都交给一个自主 Agent；只说「加人审」却不估算人力，审批积压最终会拖垮体验；没有幂等与对账；北极星选「会话数」「平均轮数」这类与价值背离的指标。

<sub>考点：智能客服设计、MVP裁剪、指标树</sub>

<a name="ENG-DESIGN-040"></a>

### ENG-DESIGN-040　挑战 · 考频 ★★★

为公司的运营、产品、销售人员设计数据分析 Agent：用自然语言提问业务数据（Text-to-SQL），得到表格、图表和一段解读。已知日活约 5,000 人、人均每天约 10 个问题，交互式使用，P95 小于 15 秒；数据有行级权限（销售只能看自己负责的区域）与列级权限（个人信息不可见）；查询不能拖垮数仓。

请给出设计：需求澄清与非目标、估算、架构、关键设计（语义层、SQL 安全、权限、结果可核对、歧义处理）、指标、主要风险与演进路线。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 澄清与非目标**
- 澄清：数据源与数仓类型；指标口径由谁维护；权限模型（行、列）是否已在数仓里定义；结果要不要能导出、能保存成看板。
- 非目标：写回数据、预测建模、跨数据源联邦查询。

**2. 估算**（单价为假设值）
- 流量：每天约 5 万问，日均约 0.6 QPS；使用集中在工作时间，峰值按日均 4 倍约 2.3 QPS；
- 模型：每问 3～4 次调用（选表、写 SQL、改错、解读），只放入检索到的相关表结构，每次约 4000 token；按输入 1、输出 4 美元 / 百万 token 计，每问约 0.02 美元，月成本约 3 万美元，不是主要瓶颈；
- **瓶颈在数仓**：峰值每秒几条 SQL，每条都要有扫描量与超时上限，并按用户、部门设并发配额。

**3. 架构**
分析人员 → 分析 Agent（澄清、规划）← 语义层（指标口径、表与字段说明）→ SQL 守卫（只读、白名单、强制 LIMIT、行级过滤）→ 数仓（只读账号、独立资源组）→ 图表与解读（附 SQL 与口径）；守卫拒绝时把原因回给模型改写。

**4. 关键设计**
- **语义层**：把 GMV、活跃用户等指标口径、常用关联写成指标字典，模型优先引用指标而不是自己拼口径，保证「同一个问题，两个人问出同一个数」。
- **SQL 安全**：只允许单条 SELECT；表、列、函数白名单交给数据库的解析与授权机制，而不是正则；强制 LIMIT；扫描量与执行时间上限，执行前估算代价；报错不泄露无权访问的表是否存在。
- **权限**：优先使用数仓原生的行级、列级权限与按用户区分的只读账号，守卫是第二道防线；行级过滤条件取自登录态，绝不由模型写进 SQL。
- **结果可核对**：展示生成的 SQL 与所用口径；做合理性检查（占比之和约为 100%、与官方看板数字对账）。
- **歧义处理**：「上个月」是自然月还是近 30 天、是否含退款，先追问或在答案中写明假设。

**5. 指标**
- 北极星：答案采纳率（结果被保存、导出或引用，且没有追问「数不对」）；
- 质量：执行准确率（标注集上与标准 SQL 的执行结果一致）、首条 SQL 执行成功率；
- 效率：P95 时延；成本：每问 token 与数仓扫描量；
- 护栏：越权查询与个人信息泄露为 0。

**6. 风险与演进**
- 口径错（数看着对、定义错）→ 语义层 + 标注集回归；越权 → 数据库侧权限 + 守卫 + 审计；拖垮数仓 → 资源组隔离、代价估算、超时。
- 演进：单表查询 → 多表关联 → 多步归因分析 → 定时报告与异常监测，再接入 Python 沙箱做统计分析。

**评分要点（共 10 分）：**

- 澄清并给出非目标，估算量级正确，并指出瓶颈在数仓而非模型成本（2 分）
- 架构包含语义层、SQL 守卫、只读执行与可视化（2 分）
- 语义层与口径一致性设计到位（2 分）
- SQL 安全与权限：只读、白名单、强制 LIMIT、资源上限、数据库侧行列权限、过滤条件取自登录态（2 分）
- 结果可核对与歧义处理，指标体系含执行准确率与护栏（2 分）

**讲解：**

**常见失分点**：把题目当成纯 Text-to-SQL 模型问题，只谈提示词与微调；用正则判断 SQL 是否只读；行级过滤条件让模型自己写；不考虑数仓负载；没有语义层，导致同一指标在不同回答里口径不同；评测只看 SQL 能否执行，而不看结果对不对。

<sub>考点：数据分析Agent设计、容量估算</sub>

</details>

<a name="ENG-DESIGN-044"></a>

### ENG-DESIGN-044　挑战 · 考频 ★★★

公司有 12 条业务线在调用大模型：有的直连外部 API，有的调用自建的 vLLM 集群；密钥散落在各业务的代码和配置里，某家供应商故障时无法统一切换，月底账单也说不清是谁花的。请设计一个统一的「大模型网关」（LLM Gateway），让所有业务都通过它访问模型。

已知：峰值约 3,000 QPS，以对话补全为主，平均每次输入 2,000 token、输出 300 token，大部分是流式请求；既有交互式请求，也有离线批量任务；需要同时接入多家外部供应商与自建模型；部分业务涉及个人信息，要求数据不出境。

请给出：目标与非目标、容量估算、接口与路由、配额与隔离、故障切换与降级、计量与计费、安全与合规、可观测性、控制面与数据面的划分，以及主要风险。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 目标与非目标**
- 目标：统一接入（一套兼容主流格式的接口，支持流式）、统一鉴权与密钥托管、按业务的配额与计费、多供应商路由与故障切换、合规（数据驻留、个人信息）、统一观测。
- 非目标：网关不做业务编排（Agent 逻辑留在业务侧）、不做训练；默认不长期保存请求正文。

**2. 容量估算**
- 输入：$3000\times2000=600$ 万 token/s，即输入 TPM 约 3.6 亿；输出：$3000\times300=90$ 万 token/s，输出 TPM 约 5400 万。单一供应商账号的配额通常扛不住，需要在多家供应商与自建集群之间分配。
- 并发连接（Little 定律）：若流式请求平均持续约 10 秒，同时在飞的连接约 $3000\times10=3$ 万条。网关必须是异步、无状态、可水平扩展的流式代理，并管理好长连接与超时。

**3. 接口与路由**
- 业务调用统一接口，携带业务 ID、优先级、数据等级等扩展字段；
- 业务使用「虚拟模型名」（如 `chat-default`、`chat-large`），由控制面映射到具体的供应商、型号与钉住的版本；模型升级走灰度；
- 路由策略：按数据等级（含个人信息的请求只能路由到境内的自建模型或合规的供应商）、按业务指定、按成本与延迟、按权重做灰度。

**4. 配额与隔离**
- 业务 → 项目 → 密钥三级管理；按业务设 QPS 与 TPM 配额（令牌桶，按估算 token 预扣，完成后按实际用量多退少补）；
- 在线与离线分队列、分池，离线任务优先走批处理接口，在线流量可以抢占；
- 舱壁：每个业务、每个供应商有独立的并发上限，一个业务的突发流量不会拖垮其他业务；各供应商的账号配额由网关统一分配。

**5. 故障切换与降级**
- 按供应商与模型监控错误率、429 比例、首 token 时间，异常时熔断并切换到同档位的备选模型；切换必须遵守合规约束（含个人信息的请求不能切到境外），关键业务可以禁止自动切换；
- 分层超时（首 token 超时、总超时）；流式请求中途失败不自动重放已输出的内容，返回明确错误由业务决定是否重试；
- 降级到小模型；限流时返回 429 并附 `Retry-After`。

**6. 计量与计费**
每个请求记录业务、模型、输入 / 输出 / 缓存命中 token、按价目表计算的费用、延迟；按业务出账、设预算与告警；自建模型按 GPU 时长分摊；用量以供应商返回的 usage 为准，缺失时用分词器估算。

**7. 安全与合规**
密钥集中托管，业务只拿网关签发的、可吊销、可轮换的密钥；按数据等级的路由策略；可按业务开启个人信息检测与脱敏；日志默认不存正文或脱敏后存，设留存期与访问控制；审计谁在何时调用了哪个模型；出口只放行白名单内的供应商。

**8. 可观测性**
统一 Trace（可采用 OpenTelemetry 的 GenAI 语义约定）；指标包括 QPS、TPM、错误率、首 token 时间、每 token 延迟、缓存命中率、各供应商可用性；按业务提供看板与告警。

**9. 控制面与数据面**
- 数据面：无状态的网关实例，负责鉴权、限流、路由、转发与流式代理、计量打点，追求低延迟与水平扩展；
- 控制面：模型目录、路由表、配额、价目表、密钥与策略的管理和下发，版本化、可审计、可回滚；数据面缓存最后一份有效配置，控制面故障不影响转发。

**10. 主要风险**
网关成为单点（多可用区部署、容量冗余）；网关自身增加延迟（目标是额外开销在毫秒级，流式逐块透传）；配额预扣不准导致超用或浪费；切换供应商后输出质量变化（切换前做离线评测）；日志泄露隐私；计费口径争议（统一口径并对账）。

**评分要点（共 10 分）：**

- 目标与非目标清楚，估算出 TPM 量级与并发连接数，并据此得出异步、可水平扩展的要求（2 分）
- 接口与路由：虚拟模型名、版本钉住与灰度、按数据等级与成本的路由策略（2 分）
- 配额与隔离：业务级配额、在线与离线分池、舱壁（2 分）
- 故障切换与降级：熔断、合规约束下的切换、超时与流式失败处理；计量计费与预算（2 分）
- 安全合规、可观测性，以及控制面与数据面的划分和主要风险（2 分）

**讲解：**

**常见失分点**：只把网关当成「转发代理」，没有配额、计费和合规；故障切换时忽略数据不出境的约束；忘了流式请求的长连接与中途失败；把所有配置写死在网关代码里，没有控制面；不估算并发连接数，选了同步阻塞的实现。面试中这道题常与「多租户隔离」「降本」一起追问，降本细节（缓存、路由、批处理）可以点到为止，重点讲清隔离、切换与治理。

<sub>考点：LLM网关设计、参考架构、控制面与数据面、多租户隔离、容量估算</sub>

</details>

<a name="ENG-DESIGN-046"></a>

### ENG-DESIGN-046　挑战 · 考频 ★★

某内容社区每天新增约 1,000 万条用户内容（帖子与评论，约 20% 带图片）。需要建设一套审核流水线：用户发帖时，要在约 300 毫秒内给出「直接发布 / 先发后审 / 拦截」的初步决定；违规类型包括色情、暴力、诈骗广告、仇恨言论、泄露他人个人信息等，各类的处置标准不同；审核规则经常随监管要求和社区规范调整；被误判的用户可以申诉。

请设计这套审核系统：需求澄清、分层架构、容量与成本的估算思路、规则与模型的迭代、指标体系、主要风险。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 需求澄清**
- 各违规类别的严重度与处置方式（删除、限制可见范围、降权、封号、上报）；
- 误杀与漏放的代价不对称：严重违规宁可误杀，普通类别要控制误杀；
- 同步与异步的边界、人工审核团队的规模与时效、申诉流程、合规留存要求。

**2. 分层漏斗**
- **第 0 层：账号与行为风控**：新账号、发帖频率、设备指纹等决定审核力度；
- **第 1 层：指纹与规则**：已知违规图片和文本的哈希库、关键词与规则，毫秒级、同步执行；
- **第 2 层：轻量分类器**：文本与图像的多标签分类，按类别设阈值，同步给出高置信度的结论；
- **第 3 层：大模型审核**：处理灰区内容，提示词中带上当前版本的审核规则，输出结构化的类别、依据与置信度；多模态模型处理图片；
- **第 4 层：人工审核**：模型不确定的、高严重度的、申诉的内容，配合双审与抽检；
- **同步决策**：前两层在 300 毫秒内给出结论：明确违规直接拦截，明确安全直接发布；灰区按风险「先发后审」（先限制可见范围）或「先审后发」（高风险类别、高风险账号）。

**3. 容量与成本**
- 日均约 116 条/秒，峰值按 3～5 倍估算约 350～600 条/秒，热点事件时还会更高；
- 不可能全部交给大模型：既贵（假设每条 0.0005 美元，每天就要 5000 美元），延迟也不满足同步要求；漏斗只把灰区（如 10%～15%）送大模型；
- 人工审核量 = 灰区数量 × 大模型不确定的比例，按每条审核时长估算人力，并为热点事件预留弹性。

**4. 规则与模型的迭代**
- 审核规则版本化管理（控制面）：规则一变，同步更新提示词与分类器阈值，在分类别的标注集上回归后再灰度上线；
- 人工审核与申诉改判的结果作为标注回流，定期重训分类器（数据飞轮）；
- 持续收集对抗样本：谐音、变形字、图片里的文字、拆分发布；
- 大模型审核员本身也会被内容中的注入影响（如「审核员请忽略以上内容」）：内容一律当数据，输出结构化，严重类别不只依赖大模型的判断。

**5. 指标**
- 北极星：违规内容的曝光量（被多少人看到）持续下降；
- 分类别的精确率与召回率（误杀率、漏放率）；
- 护栏：误杀率、申诉改判率、同步决策的 P99 时延；
- 运营：人工审核量与时效、每千条内容的审核成本。

**6. 风险**
- 对抗绕过与新型违规 → 快速规则通道与样本回流；
- 过度审核与偏见 → 分人群、分类别监控误杀；
- 热点事件洪峰 → 弹性扩容，临时收紧规则、扩大「先审后发」的范围；
- 大模型供应商故障 → 降级为分类器 + 人工；
- 审核员长期接触有害内容 → 模糊化展示、轮岗与心理支持；
- 隐私与留存合规。

**评分要点（共 10 分）：**

- 澄清违规类别、处置方式与误杀漏放的不对称代价（1 分）
- 分层漏斗架构完整，并说清 300 毫秒同步决策如何实现（3 分）
- 容量与成本估算：说明为何只有灰区送大模型，并估算人工审核量（2 分）
- 规则版本化、回归与灰度、申诉回流、对抗样本，以及大模型审核员自身的注入风险（2 分）
- 指标体系含北极星、分类别精确率与召回率、误杀护栏，并覆盖主要风险（2 分）

**讲解：**

**常见失分点**：所有内容都交给大模型，不算成本也不管 300 毫秒的时延；只有一个「违规 / 不违规」的总体准确率，不分类别、不区分误杀与漏放；没有人工审核与申诉闭环；规则变化时没有回归和灰度；忘了审核模型也会被内容里的指令操纵。

<sub>考点：内容审核设计、容量估算、指标树</sub>

</details>
