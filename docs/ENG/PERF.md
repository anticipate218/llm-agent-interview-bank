<a name="ENG-PERF-001"></a>

### ENG-PERF-001　基础 · 考频 ★★★

某客服 Agent 的月度账单中，输入 token 的费用约占 80%，而该模型的输出单价是输入单价的 4 倍。输入费用占大头，最可能的原因是：

- **A.** Agent 每步生成的工具调用参数按输入 token 计费，而这类调用占了模型输出的大部分
- **B.** 每次调用都要重发系统提示词、工具定义和完整历史，多步调用让输入不断累积，远超输出量
- **C.** 开启流式输出后，每个已生成的 token 会被重复计为下一个 token 的输入，按输入单价再收一次费
- **D.** 推理模型的思考 token 不返回给用户，按输入 token 计费，长思考因此推高了输入费用

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：大模型 API 是无状态的，每次调用都要把「全部上下文」作为输入重新发送并计费。

一个 Agent 任务常要调用模型十几次，每一步都重发系统提示词（数千 token）、工具定义（每个工具几百 token）和越来越长的历史与工具结果；而每一步的输出往往只是一次几十 token 的工具调用。累计下来，输入量可以是输出的几十倍，即使输出单价是输入的 4 倍，输入费用仍占大头。这也是 Prompt Caching、上下文裁剪对 Agent 降本最有效的原因。

- A 错：工具调用的参数是模型生成的，按**输出** token 计费；而且它通常只有几十个 token，撑不起 80% 的账单。
- C 错：流式只是传输方式；自回归生成时前面的 token 会参与计算，但不会被重复计费。
- D 错：推理模型的思考 token 通常按**输出** token 计费。

<sub>考点：Token成本构成</sub>

</details>

<a name="ENG-PERF-005"></a>

### ENG-PERF-005　进阶 · 考频 ★★

某 RAG 服务的提示词结构为：6K token 的固定系统提示词 → 每次都不同的检索结果（约 4K token）→ 用户问题。团队开启了「自动缓存」（断点自动放在请求的最后一个内容块上），一周后发现输入费用不降反升约 25%。最可能的原因与改法是：

- **A.** 命中缓存的 token 单价比普通输入更高，检索结果每次都命中旧缓存反而更贵，应关闭自动缓存
- **B.** 缓存要求前缀至少有一定长度，6K 的系统提示词太短、达不到最低门槛，应把检索结果也放进缓存前缀
- **C.** 自动缓存同时缓存输入和输出，每次生成的回答都要按写入价计费，应改为只缓存输入
- **D.** 断点落在每次都不同的内容之后，每次都按 1.25 倍写入读不到的缓存；应在系统提示词末尾设断点

<details>
<summary>答案与解析</summary>

**答案：D**

**解析：**

**结论**：缓存只能命中「之前的请求在相同位置写入过」的前缀；断点放在每次都不同的内容之后，就只有写入、没有命中。

本例中，自动断点落在请求末尾，缓存键覆盖了「系统提示词 + 本次检索结果 + 本次问题」，下一个请求的这段内容必然不同，永远读不到；而所有请求共享的 6K 系统提示词上又没有断点，也无法命中。于是每个请求都为整段输入多付 25% 的写入溢价，这正是「自动缓存遇到唯一尾部」的典型症状：每个请求都有 `cache_creation_input_tokens`，`cache_read_input_tokens` 却始终为 0 或很小。

**改法**：在系统提示词的最后一个块上显式放置断点（共享部分），检索结果和问题放在断点之后；多轮对话则再在历史末尾加断点。改完后用 usage 字段确认：第二个请求起，约 6K token 应出现在命中字段中。

- A 错：命中价远低于基础价（约 0.1 倍），问题在于根本没有命中。
- B 错：6K token 远超最小可缓存长度（视模型从 512 到 4096 token 不等）；问题不在长度而在断点位置，把每次都不同的检索结果放进前缀只会更糟。
- C 错：Prompt Caching 缓存的是输入前缀，输出不会写入缓存，也不按写入价计费。

<sub>考点：Prompt Caching利用　｜　出处：Anthropic Prompt Caching 文档 https://platform.claude.com/docs/en/build-with-claude/prompt-caching</sub>

</details>

<a name="ENG-PERF-008"></a>

### ENG-PERF-008　进阶 · 考频 ★★

某 FAQ 客服接入语义缓存（问题向量的余弦相似度超过阈值，就直接返回缓存中的答案）。在 2000 对人工标注的「两个问题能否共用同一个答案」数据上，不同阈值的结果为：

| 阈值 | 命中率 | 误命中率（命中中答案不适用的比例） |
|---|---|---|
| 0.95 | 18% | 0.5% |
| 0.90 | 35% | 3% |
| 0.85 | 52% | 11% |

业务要求误命中率不超过 2%。应该如何选择？

- **A.** 选 0.95：满足误命中约束的阈值中它的命中率最高，再靠问题规范化、意图分区来提高命中率
- **B.** 选 0.85：命中率最高、省下的调用费用最多，误命中的问题可以靠用户点踩后再人工修正
- **C.** 选 0.90：命中率比 0.95 高出近一倍，多省下的调用费足以抵消误命中带来的损失
- **D.** 阈值越低越好，误命中的答案用户可以自己判断是否适用，不适用时再点「重新回答」即可

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：阈值是「省钱」与「答错」之间的权衡，先满足质量约束，再在约束内最大化命中率。

语义相似不等于答案相同：「怎么退款」与「怎么退货」向量很接近，答案却不同。误命中的代价是用户拿到错误的答案、重复提问甚至投诉，往往远高于一次模型调用的费用。本例中只有 0.95 满足 2% 的约束；提高命中率应从「让相同意图的问题更像」入手：问题规范化、先做精确匹配、按意图或业务分区检索、只缓存经过审核的高频问答，而不是放宽阈值。

- B 错：违反了业务约束（误命中率 11%），等用户点踩再人工修正时，错误答案已经造成了损失。
- C 错：误命中率 3% 超过了 2% 的业务约束；误命中的代价（答错、重复提问、投诉）往往远高于一次模型调用的费用，不能拿省下的调用费去抵。
- D 错：把风险转嫁给用户，在客服场景不可接受；用户未必能判断答案是否适用。

阈值还应定期用新的标注数据复核，因为问题分布会变化。

<sub>考点：语义缓存</sub>

</details>

<a name="ENG-PERF-011"></a>

### ENG-PERF-011　进阶 · 考频 ★★★

关于「路由」（事前判断请求难度，直接交给小模型或大模型）与「级联」（先让小模型做，校验不通过再升级到大模型），下列说法正确的是：

- **A.** 级联总是比路由便宜：每个请求都先用便宜的小模型处理，只有少数校验不过的请求才升级到大模型
- **B.** 路由需要可靠的事后校验器来判断答案对不对，级联则只需要一个事前估计请求难度的分类器
- **C.** 路由误判会把难题交给小模型；级联依赖便宜可靠的校验器，被升级的请求要付两次费用
- **D.** 两种方案都能让每个请求的时延下降，因为多数请求都由更快的小模型处理

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：路由「先猜后做」，级联「先做后查」，各有适用条件。

- **路由**：用规则、小分类器或偏好数据训练的路由器（如 RouteLLM）事前估计难度；每个请求只调用一个模型，时延不增加。风险在于预测出错：难题被分给小模型，又没有补救。
- **级联**：小模型先回答，校验器（如单测、SQL 能否执行、JSON Schema 校验）判断是否可信，不可信再升级（如 FrugalGPT）。它用「事后检查」代替「事前预测」，在有可靠校验器时更准、也常更省；但被升级的请求付了两次费用，时延也叠加。开放式问答缺少可靠的校验器，级联的效果会打折扣。

- A 错：升级比例高、或校验器本身昂贵时，级联可能比路由更贵：被升级的请求付了两次费用。
- B 错：说反了。
- D 错：路由不改变被路由请求的时延（走小模型的会变快）；级联中被升级的请求时延更长，并非每个请求都下降。

<sub>考点：模型路由与级联　｜　出处：RouteLLM（Ong 等, 2024, arXiv:2406.18665）；FrugalGPT（Chen 等, 2023, arXiv:2305.05176）</sub>

</details>

<a name="ENG-PERF-015"></a>

### ENG-PERF-015　基础 · 考频 ★★

主流厂商的批处理接口（如 OpenAI 的 Batch API、Anthropic 的 Message Batches）对请求约按五折计费，能给出这个折扣最主要的原因是：

- **A.** 批处理请求会被自动路由到参数量更小的蒸馏版模型，推理成本因此降到原来的一半左右
- **B.** 请求不必即时返回，厂商可以错峰调度、攒成更大的 batch，提高 GPU 利用率
- **C.** 批处理请求的输出被限制在更短的长度内，平均生成的 token 数只有在线请求的一半
- **D.** 批处理请求跳过了安全审核与内容过滤等环节，省下的这部分算力折算成了价格优惠

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：批处理用「时间上的灵活性」换价格。

在线请求必须按 SLO 立即处理，厂商要按峰值预留算力，低谷时大量闲置；批处理请求没有时延要求，可以填进低谷、攒成大 batch 高效运行，单位 token 的成本显著降低，厂商再把省下的成本部分让利给用户。这和自部署时「把离线任务放到低峰期跑」是同一个道理。

以 2026 年的公开规则为例：两家的批处理都约为五折、最长 24 小时内完成（Anthropic 称多数批次在 1 小时内完成），Anthropic 的批处理折扣还可以与 Prompt Caching 的折扣叠加。

- A 错：使用的仍是请求中指定的模型，输出质量相同。
- C 错：输出长度由请求参数（如 max_tokens）决定，与是否批处理无关。
- D 错：批处理请求同样受使用政策与安全机制约束。

<sub>考点：批处理API　｜　出处：Anthropic Batch Processing 文档 https://platform.claude.com/docs/en/build-with-claude/batch-processing；OpenAI Batch API https://platform.openai.com/docs/api-reference/batch</sub>

</details>

<a name="ENG-PERF-017"></a>

### ENG-PERF-017　进阶 · 考频 ★★★

对一个对话应用做降本时，团队发现「缩短回答长度」比「缩短等量的输入」效果更明显。下列解释最准确的是：

- **A.** 输出单价通常是输入的数倍，而且输出逐 token 串行生成，长度直接决定生成耗时
- **B.** 输入在 Prefill 阶段并行处理、几乎不占 GPU 时间，所以厂商实际上不对输入计费
- **C.** 缩短回答不会影响用户体验，用户普遍更喜欢简短的回答，所以总是最优选择
- **D.** 输出越短，模型「说多错多」的机会越少，回答的准确率就一定越高

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：输出 token 又贵又慢。

- **贵**：主流 API 的输出单价一般是输入的数倍。原因在推理侧：输入在 Prefill 中并行处理，算力利用率高；输出每生成一个 token 都要读一遍权重和 KV，单位成本高得多。
- **慢**：端到端时延 ≈ TTFT + TPOT × 输出长度，回答长度翻倍，生成时间几乎翻倍。

所以「把 600 token 的回答压到 300 token」往往比「把 2000 token 的输入压到 1700 token」省得多，还顺带降低了时延：压缩输出能同时降低费用和端到端时延。

- B 错：输入同样计费，只是单价低一些；Prefill 并行计算效率高，但并不免费。Agent 场景中输入的总费用甚至常常超过输出。
- C 错：过度压缩会丢掉必要的信息，长度要按任务需求设定，并用评测验证。
- D 错：长度与准确率没有这种必然关系；对推理类任务，过度限制思考或输出长度反而会降低准确率。

<sub>考点：输出长度控制</sub>

</details>

<a name="ENG-PERF-020"></a>

### ENG-PERF-020　基础 · 考频 ★★

某报告生成功能平均要 25 秒才能完整输出，用户抱怨「卡住了」。在不更换模型的前提下，最能改善用户感知延迟的做法是：

- **A.** 把 max_tokens 调大，避免报告被截断后用户还要重新生成一次，减少总的等待时间
- **B.** 改用批处理接口：批处理的吞吐量更高，单个报告的生成速度也会随之加快
- **C.** 等生成全部完成后再一次性返回，减少网络往返和前端反复渲染带来的额外延迟
- **D.** 开启流式输出并让模型先写提纲或结论，用户等待首屏的时间从约 25 秒降到首 token 时延

<details>
<summary>答案与解析</summary>

**答案：D**

**解析：**

**结论**：感知延迟主要取决于「多久开始看到有用的内容」，而不是总耗时。

流式输出（SSE）让用户在 TTFT 之后就能开始阅读，生成速度通常快于阅读速度，体验从「干等 25 秒」变成「几百毫秒后开始出字」。再让模型先输出提纲或结论，用户更早拿到关键信息。

- A 错：max_tokens 与等待感无关，调大还可能让输出更长。
- B 错：批处理是异步的，最长可能 24 小时才返回，只适合离线任务；它提升的是厂商侧的整体吞吐，不会让单个请求更快。
- C 错：这正是「卡住」的原因；网络往返和渲染的开销与 25 秒的生成时间相比微不足道。

注意流式不会缩短总生成时间，也不减少费用；如果结果需要被程序整体解析（如 JSON），流式对最终用户的价值有限，需要增量解析或先展示进度。

<sub>考点：流式与感知延迟</sub>

</details>

<a name="ENG-PERF-022"></a>

### ENG-PERF-022　进阶 · 考频 ★★

某长对话助手为了控制上下文长度，每一轮都用「只保留最近 10 轮」的滑动窗口裁剪历史；同时开启了 Prompt Caching，却发现除了系统提示词，历史部分几乎从不命中缓存，输入成本居高不下。下列改法中，最能同时控制上下文长度、又保住缓存命中的是：

- **A.** 每一轮都把全部历史压缩成一段新的摘要，放在系统提示词开头，上下文始终保持在 2K 以内
- **B.** 关闭 Prompt Caching，只依靠滑动窗口控制长度，省下缓存写入的 1.25 倍溢价
- **C.** 历史只追加不改写，长度超过阈值时才一次性把较早部分压缩成摘要，之后继续只追加
- **D.** 每一轮随机丢弃一部分较早的历史消息，把上下文控制在固定长度以内

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：裁剪要「低频、批量」，让前缀在大多数轮次中保持不变。

滑动窗口每一轮都从历史开头删掉一条，系统提示词之后的内容每轮都在变，缓存只能命中系统提示词，历史部分每轮都按原价（甚至按写入价）重新计费。按阈值批量压缩时，两次压缩之间历史只追加，绝大部分输入都能命中缓存；只有压缩的那一轮需要重新写入。

**粗略估算**（系统提示词 4K，每轮新增约 1K，命中按 0.1 倍、写入按 1.25 倍计）：
- 滑动窗口保留约 10K 历史：每轮约 $4\text{K}\times0.1+10\text{K}\times1=10.4\text{K}$ 等效 token；
- 历史超过 20K 时压缩成 2K 摘要：平均历史约 11K，每轮约 $4\text{K}\times0.1+10\text{K}\times0.1+1\text{K}\times1.25\approx2.65\text{K}$ 等效 token。

即使平均上下文更长，费用也只有前者的约 1/4（还要加上偶尔压缩时生成摘要的费用）。

- A 错：每轮都改写开头，缓存每轮全部失效，比滑动窗口更糟，而且每轮还要多一次生成摘要的调用。
- B 错：放弃了缓存折扣；省下的写入溢价远小于失去的命中折扣，成本更高。
- D 错：既改变前缀、破坏缓存，又可能丢掉关键信息。

<sub>考点：上下文裁剪　｜　出处：Anthropic Prompt Caching 文档 https://platform.claude.com/docs/en/build-with-claude/prompt-caching</sub>

</details>

### ENG-PERF-003　进阶 · 考频 ★★

关于大模型 API 的 token 计费，下列说法正确的有：

- **A.** 批处理接口的输入与输出 token 通常都按标准价的约五折计费，代价是结果异步返回
- **B.** 同一个会话中，系统提示词只在第一轮计费，之后的轮次不再收费
- **C.** 推理模型的思考 token 即使不返回给用户，通常也按输出 token 计费
- **D.** 工具定义（名称、描述、参数 Schema）会被拼进提示词，每次请求都按输入 token 计费
- **E.** 图片等多模态输入也会折算成 token 计费，分辨率越高通常越贵

<details>
<summary>答案与解析</summary>

**答案：ACDE**

**解析：**

- A 对：批处理不要求即时返回（一般承诺 24 小时内完成），OpenAI 的 Batch API、Anthropic 的 Message Batches 对输入和输出都按标准价的一半计费，适合评测、标注、离线摘要这类不急的任务。注意流式输出只改变返回方式，生成的 token 数与费用都不变。

### ENG-PERF-010　进阶 · 考频 ★★

关于语义缓存（按语义相似度复用之前的回答），下列说法正确的有：

- **A.** 语义缓存天然适合个性化强、依赖实时数据的问题，如「我的订单到哪了」「今天的汇率是多少」

- **C.** 缓存键只需包含规范化后的问题文本；模型或提示词升级后，已缓存的答案仍可以继续复用

- **E.** 可以先对规范化后的问题做精确匹配作为第一层，再做语义相似匹配作为第二层

<details>
<summary>答案与解析</summary>

**答案：BE**

**解析：**

- A 错：这类问题的答案依赖用户身份或随时间变化，不能跨用户、跨时间复用，应绕过缓存或设很短的 TTL。

- E 对：精确匹配几乎没有误命中、成本最低；先走精确匹配，再用语义匹配兜底，是常见的分层设计（开源的 GPTCache 等库提供了类似的组件）。

### ENG-PERF-018　进阶 · 考频 ★★

关于控制输出长度，下列做法或说法正确的有：

- **A.** 回答被 max_tokens 截断时，API 会返回错误状态码，客户端捕获异常就能发现，不必再检查停止原因
- **B.** 推理模型的思考 token 不计入输出上限，也不影响费用
- **C.** 在提示词中明确要求格式与篇幅（如「用 3 条要点回答，每条不超过 30 字」），比单纯依赖 max_tokens 更有效
- **D.** 对需要程序解析的结果使用结构化输出，只返回必要的字段，避免附带长篇解释
- **E.** 把 max_tokens 设得很小，模型就会自动把回答组织得更简洁

<details>
<summary>答案与解析</summary>

**答案：CD**

**解析：**

- A 错：截断是静默的，请求照常成功返回，只在停止原因里体现（如 OpenAI 的 `finish_reason` 为 `length`、Anthropic 的 `stop_reason` 为 `max_tokens`）。必须检查停止原因；JSON 等结构化结果被截断时会解析失败，需要重试或续写。
- B 错：思考 token 按输出计费，通常也计入输出 token 的上限（如 OpenAI 的 `max_completion_tokens`、Anthropic 的 `max_tokens` 都包含思考部分），上限设得太小还可能导致思考尚未结束就被截断。

- D 对：程序要的是字段，不是解释；结构化输出（约束解码）还能保证格式合法。
- E 错：`max_tokens` 是硬截断，模型生成时并不知道这个上限，回答会在中途被切断，而不是变简洁。

实践中常见的组合是：提示词约束篇幅 + 合理偏宽的 `max_tokens` 作为兜底 + 监控截断率与平均输出长度。

<a name="ENG-PERF-007"></a>

### ENG-PERF-007　基础 · 考频 ★★

评估 Prompt Caching 的效果时，用「有缓存命中的请求数 ÷ 总请求数」作为命中率，就能准确反映成本的节省程度。

<details>
<summary>答案与解析</summary>

**答案：❌ 错误**

**解析：**

**错误**。按请求计数会严重失真：
- 一个请求「有命中」可能只命中了很短的一段前缀（如 1K 的系统提示词），而 30K 的历史全部未命中；
- 长请求与短请求的费用相差几十倍，按请求平均会被大量短请求「稀释」；
- 写入缓存要付溢价，只看命中、不看写入会高估收益。

正确做法是按 token 统计：命中率 = 命中的输入 token ÷ 全部输入 token；成本节省 = 用实际费用（未命中 × 1 + 写入 × 写入倍率 + 命中 × 命中倍率）与「全部按基础价」比较。最好按业务、按模型分别统计，并对命中率的突降设告警。

<a name="ENG-PERF-004"></a>

### ENG-PERF-004　进阶 · 考频 ★★★

某厂商的 Prompt Caching 计费规则（以下为假设，与 Anthropic 公开文档中多数模型的倍率一致）：默认缓存存活 5 分钟，每次命中会刷新计时；写入缓存的 token 按基础输入价的 1.25 倍计，命中缓存的 token 按 0.1 倍计；也可以选择 1 小时的缓存，写入按 2 倍计，命中同样按 0.1 倍计。一段固定前缀在缓存存活期内被 $n$ 次请求使用（第 1 次写入，之后都命中）。

(1) 用 5 分钟缓存，$n$ 至少为多少才比不用缓存便宜？$n=10$ 时这段前缀的费用节省多少？
(2) 用 1 小时缓存，$n$ 至少为多少才划算？
(3) 某 Agent 每两次模型调用之间要等待工具执行 8～15 分钟，共调用 10 次。分别计算用 5 分钟缓存、1 小时缓存与不用缓存时这段前缀的费用（以「不用缓存时一次请求的前缀费用」为 1），并说明应该怎么选。

<details>
<summary>答案与解析</summary>

**答案：(1) n ≥ 2；n = 10 时费用为 2.15，节省 78.5%；(2) n ≥ 3；(3) 5 分钟缓存每次都过期重写，共 12.5，比不用缓存（10）还贵 25%；1 小时缓存为 2 + 9 × 0.1 = 2.9，节省 71%，应选 1 小时缓存**

**解析：**

以一次不用缓存的前缀费用为 1。

**(1)** 5 分钟缓存：$1.25+0.1(n-1)<n$，即 $n>1.28$，**至少 2 次**（1.35 对 2）。$n=10$：$1.25+0.9=2.15$，对比 10，节省 **78.5%**。

**(2)** 1 小时缓存：$2+0.1(n-1)<n$，即 $n>2.11$，**至少 3 次**（2.2 对 3）。

**(3)** 调用间隔 8～15 分钟，超过 5 分钟：
- 5 分钟缓存：每次调用时上一次的缓存都已过期，10 次都按 1.25 倍写入，共 **12.5**，比不用缓存还贵 25%；
- 1 小时缓存：首次 2，之后 9 次命中各 0.1，共 **2.9**，节省 71%；
- 不用缓存：10。

**结论**：TTL 要按「共享前缀的相邻两次请求的开始时间间隔」来选：间隔小于 5 分钟用默认缓存（每次命中都会续期，最便宜）；5～60 分钟用 1 小时缓存；更长的间隔两者都不划算，只能定时预热或接受冷启动。选错 TTL 会让缓存变成纯粹的加价。如果命中价足够低、相邻请求的间隔又略超过 TTL，也可以考虑在空闲时发送很短的请求给缓存续期，前提是续期成本低于重新写入的成本。

### ENG-PERF-009　挑战 · 考频 ★★

某客服问答每天 100 万次请求，每次调用大模型的平均成本为 0.002 美元。计划接入语义缓存：每个请求都要先做一次查询向量化与向量检索，成本 0.00005 美元；预计命中率 30%，命中的请求中有 2% 返回了不适用的答案（误命中）；每次误命中会引发用户重问、转人工等额外成本，折合 0.05 美元。

(1) 每天节省的模型调用费用、新增的缓存开销、误命中造成的损失各是多少？净收益是多少？
(2) 误命中率升到多少时，净收益降为 0？
(3) 除了成本账，决定是否上线还要考虑哪些因素？

<details>
<summary>答案与解析</summary>

**答案：(1) 节省 600 美元、开销 50 美元、损失 300 美元，净收益 250 美元 / 天；(2) 约 3.67%；(3) 用户体验与信任、答案时效、个性化与权限、合规与审计等**

**解析：**

**(1)**
- 节省：$10^6\times30\%\times0.002=600$ 美元；
- 开销：$10^6\times0.00005=50$ 美元（每个请求都要查缓存，无论是否命中）；
- 误命中损失：$10^6\times30\%\times2\%\times0.05=300$ 美元；
- 净收益：$600-50-300=$ **250 美元 / 天**。

**(2)** 设误命中率为 $f$：$600-50-10^6\times0.3\times f\times0.05=0$，$15000f=550$，$f\approx$ **3.67%**。

**(3)** 成本账之外：
- **体验**：一次明显答错的损害可能远超 0.05 美元的折算，尤其是涉及金额、政策的问题；
- **时效**：知识更新后旧答案要失效（缓存键带知识库版本，或设 TTL）；
- **个性化与权限**：依赖用户身份或实时数据的问题不能共用答案，缓存键要带租户与权限范围；
- **可观测**：记录命中与误命中的样本，持续评估。

**要点**：语义缓存的收益对误命中率非常敏感——本例中误命中的损失已经吃掉了一半的节省。上线前必须用标注数据估计误命中率，而不是只看命中率。

### ENG-PERF-012　挑战 · 考频 ★★★

某任务采用级联方案：先调用小模型（相对成本 0.1），再用校验器检查（相对成本 0.02），校验不通过就升级到大模型（相对成本 1，以大模型调用一次为 1）。已知小模型做对的比例为 80%；校验器对小模型做错的答案能发现 85%，对做对的答案有 5% 误报（误报也会触发升级）。

(1) 升级比例是多少？平均相对成本是多少？与「全部用大模型」相比省了多少？
(2) 有多大比例的请求，最终返回的是小模型的错误答案（且没有被发现）？
(3) 如果校验器的召回率只有 50%（误报率不变），(1)(2) 的结果如何变化？这说明了什么？

<details>
<summary>答案与解析</summary>

**答案：(1) 升级 21%，平均成本 0.33，节省 67%；(2) 3%；(3) 升级 14%、成本 0.26，看起来更省，但未被发现的错误答案升到 10%；级联的质量取决于校验器的召回率**

**解析：**

**(1)** 升级比例 = 做对但误报 + 做错且被发现 $=0.8\times5\%+0.2\times85\%=0.04+0.17=$ **21%**。平均成本 $=0.1+0.02+0.21\times1=$ **0.33**，比全用大模型（1.0）节省 **67%**。

**(2)** 小模型做错且未被发现：$0.2\times(1-85\%)=$ **3%**，这些请求直接返回了错误答案。

**(3)** 召回率 50%：升级比例 $=0.04+0.2\times50\%=0.14$，成本 $0.1+0.02+0.14=0.26$，账面上更省；但未被发现的错误答案升到 $0.2\times50\%=$ **10%**，是原来的 3 倍多。

**启示**：
- 级联的「质量」由校验器的召回率决定，「成本」由升级比例决定；校验器变差时，成本反而下降，问题被账面上的节省掩盖；
- 评估级联时要同时报告成本与最终质量（或未被拦截的错误率），并与「全用大模型」在同一测试集上比较；
- 误报只浪费钱（多升级），漏报才伤质量——设计校验器时应优先保证召回率。

### ENG-PERF-024　进阶 · 考频 ★★★

某业务每天处理 20 亿个 token（输入输出合计，比例稳定），有两个方案（价格与吞吐均为假设）：

- **调 API**：按该比例折算，平均 0.30 美元 / 百万 token；

(2) 自部署需要几张卡？每月的 GPU 费用与总成本各是多少？卡的日均利用率是多少？

<details>
<summary>答案与解析</summary>

**(1)** 每月 $20\times10^8\times30=6\times10^{10}$ token，即 60000 个百万 token，$60000\times0.30=$ **1.8 万美元**。

**(2)**

**(3)**

## 编程题

<a name="ENG-PERF-013"></a>

### ENG-PERF-013　进阶 · 考频 ★★

在校准集上为模型路由选阈值。实现：

```python
def evaluate(records, tau, c_small=0.1, c_large=1.0) -> tuple[float, float]: ...
def pick_threshold(records, taus, max_drop) -> tuple | None: ...
```

- `records` 中每一项为 `(score, small_ok, large_ok)`：`score` 是路由器给出的难度分（越大越难），`small_ok`、`large_ok` 为 0 / 1，表示小模型、大模型能否答对；
- 阈值为 `tau` 时，`score < tau` 的请求交给小模型（成本 `c_small`），其余交给大模型（成本 `c_large`）；`evaluate` 返回（质量 = 最终答对的比例，平均成本）；
- `pick_threshold` 在「质量 ≥ 全用大模型的质量 − `max_drop`」的约束下，从候选阈值 `taus` 中选平均成本最低的一个，返回 `(tau, 质量, 成本)`；成本相同时取较小的 `tau`；没有满足约束的阈值时返回 `None`；`records` 为空时抛出 `ValueError`。

<details>
<summary>答案与解析</summary>

**参考实现：**

```python
def evaluate(records, tau, c_small=0.1, c_large=1.0):
    ok = cost = 0.0
    for score, small_ok, large_ok in records:
        if score < tau:
            ok, cost = ok + small_ok, cost + c_small
        else:
            ok, cost = ok + large_ok, cost + c_large
    return ok / len(records), cost / len(records)

def pick_threshold(records, taus, max_drop):
    if not records:
        raise ValueError("records 不能为空")
    floor = sum(r[2] for r in records) / len(records) - max_drop   # 质量下限
    best = None
    for tau in sorted(taus):                    # 从小到大，成本相同时保留较小的 tau
        q, c = evaluate(records, tau)
        if q >= floor - 1e-12 and (best is None or c < best[2] - 1e-12):
            best = (tau, q, c)
    return best
```

**测试用例：**

```python
recs = [(0.1, 1, 1), (0.2, 1, 1), (0.5, 0, 1), (0.9, 0, 0)]
taus = [0.0, 0.3, 0.6, 1.0]
t, q, c = pick_threshold(recs, taus, 0.0)
assert t == 0.3 and q == 0.75 and abs(c - 0.55) < 1e-9          # 不许掉点：只放最简单的两个
t, q, c = pick_threshold(recs, taus, 0.25)
assert t == 1.0 and q == 0.5 and abs(c - 0.1) < 1e-9            # 允许掉 25 个点：全部走小模型
assert pick_threshold(recs, [0.25, 0.3], 0.0)[0] == 0.25          # 成本相同取较小的阈值
assert pick_threshold(recs, taus, -0.1) is None                  # 要求比全用大模型还好：无解
assert pick_threshold(recs, [1.0, 0.0, 0.3, 0.6], 0.0)[0] == 0.3  # 候选阈值无序
try:
    pick_threshold([], taus, 0.0)
    raise AssertionError("应抛出 ValueError")
except ValueError:
    pass

import random
rng = random.Random(0)
data = []
for _ in range(2000):
    d, u = rng.random(), rng.random()
    s = min(1.0, max(0.0, d + rng.gauss(0, 0.1)))
    data.append((s, int(u < 0.97 - 1.2 * d ** 2.5), int(u < 0.97 - 0.3 * d ** 2)))
grid = [i / 20 for i in range(21)]
t, q, c = pick_threshold(data, grid, 0.01)
base = sum(r[2] for r in data) / len(data)
assert q >= base - 0.01 - 1e-12 and c < 1.0
for tau in grid:                                                 # 与暴力枚举对拍
    q2, c2 = evaluate(data, tau)
    assert not (q2 >= base - 0.01 - 1e-12 and c2 < c - 1e-12)
```

**解析：**

**思路**：
1. `evaluate` 按阈值把每个请求分给小模型或大模型，累加答对数与成本；
2. 质量下限 = 全用大模型的质量 − 允许的下降；
3. 按阈值从小到大扫描，在满足下限的阈值中保留成本最低的；严格小于才替换，保证成本相同时取较小的阈值。阈值越大，交给小模型的请求越多，成本越低、质量通常越差，所以通常是找「满足质量约束的最大阈值」，但不能依赖这种单调性，逐个评估最稳妥。

**边界**：空数据报错，避免除以 0；没有可行解返回 `None`，由调用方决定是否放宽约束；浮点比较留一点容差。

**工程要点**：
- 在**校准集**上选阈值，在独立的**测试集**或线上 A/B 中报告效果，否则结果偏乐观；
- 难度分可以来自规则、小分类器，或用强弱模型历史成败训练的路由器；
- 扫描结果画成「成本—质量曲线」，便于与业务方讨论在哪个点运行。

<sub>考点：模型路由与级联</sub>

</details>

<a name="ENG-PERF-021"></a>

### ENG-PERF-021　进阶 · 考频 ★★

除了开启流式输出，还有哪些方法可以降低大模型应用的「感知延迟」？请说明各自的适用场景与代价，并说明流式输出在哪些情况下不适用或需要特殊处理。

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **缩短首 token 时延（TTFT）**：稳定前缀并开启 Prompt Caching，跳过重复的 Prefill；精简提示词与检索内容；首轮用更快的小模型；就近部署、复用连接。代价是需要整理上下文布局，或接受小模型的质量差异。
2. **先给结论、渐进展示**：让模型先输出要点或提纲，再展开细节；长报告分节生成、逐节展示。
3. **并行化**：相互独立的检索与工具调用并行执行；一个问题拆成几个独立子问题并行生成再汇总。代价是更多并发与更高的峰值费用。
4. **预取与推测**：用户输入时就开始检索、预热缓存；对高概率的下一步提前准备。代价是部分预取会被浪费。
5. **展示进度**：Agent 的多步任务流式展示「正在搜索 / 正在读取 / 已完成第 2 步」等状态，让等待可预期。
6. **缓存与降级**：高频问题走语义缓存或模板回答（毫秒级）；超时后先返回已有的部分结果。
7. **异步化**：生成时间很长的任务（深度调研、长报告）改为提交后通知，不让用户盯着页面等。
8. **流式的特殊情况**：
   - 结构化输出、工具调用需要完整结果才能解析，要做增量解析或只展示进度；
   - 内容安全审核：边生成边展示可能先露出违规内容，需要分段审核或缓冲一小段再发送；
   - 多字节字符、停止词可能跨 token，要攒够完整字符、压住疑似停止词的前缀；
   - 网关与反向代理可能缓冲 SSE（需要关闭缓冲），否则流式会退化成一次性返回。

**评分要点（共 10 分）：**

- 给出缩短 TTFT 的方法（缓存、精简上下文、小模型等）（2 分）
- 给出渐进展示、并行化、预取等改善感知的方法（3 分）
- 提到进度展示、异步化或缓存降级（2 分）
- 指出流式在结构化输出、内容审核、字符边界或代理缓冲上的特殊处理（3 分）

**讲解：**

**常见失分点**：只回答「用流式」；把流式说成能缩短总耗时或降低费用；忽略 Agent 多步任务中「中间步骤看不见」的问题；不知道代理缓冲会让流式失效，或流式输出与内容审核之间的冲突。

<sub>考点：流式与感知延迟</sub>

</details>

### ENG-PERF-023　进阶 · 考频 ★★

Agent 的上下文随步数膨胀，输入成本快速上升。请给出系统的上下文裁剪方案：哪些内容可以裁剪、分别用什么方法、可能带来什么风险，以及如何评估裁剪是否「伤了效果」。

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **工具返回结果**（通常是大头）：只保留需要的字段；网页、日志只保留正文或头尾，设长度上限；完整结果存到外部（文件、数据库），上下文里只放摘要与引用（如路径、ID），需要时再按需读取；已经用过的旧工具结果可以清除或折叠。
2. **检索内容**：减少 top-k，用重排挑出最相关的块；对块做抽取式压缩（注意需要逐句引用的场景不能改写原文）。
3. **对话历史**：较早的轮次压缩成摘要，已完成的子任务只保留结论；按阈值批量压缩，而不是每轮改写。
4. **固定开销**：精简系统提示词中重复、过时的指令；工具很多时按需加载工具定义（工具检索），而不是每次全量发送；图片按需降低分辨率。

6. **风险**：丢掉关键细节（订单号、数值、用户约束）导致后续步骤出错；摘要失真或幻觉；破坏工具调用与结果的配对；缓存失效反而更贵。
7. **评估**：在固定的任务评测集上对比裁剪前后的任务成功率、每个成功任务的 token 与成本、步数与时延；针对「被裁掉的信息后面还会用到」设计专门用例（如早期给出的约束在后期是否仍被遵守）；上线后灰度，监控成功率与成本。

**评分要点（共 10 分）：**

- 覆盖工具结果、检索、历史、固定开销等多类裁剪对象及方法（4 分）
- 说明与 Prompt Caching 的配合（2 分）

**常见失分点**：只说「做摘要」；忽略工具返回结果才是 Agent 上下文的大头；每轮都改写前缀，与 Prompt Caching 相冲突；只看 token 降了多少，不看成功率，导致「省了钱、丢了效果」。

<sub>考点：上下文裁剪</sub>

<a name="ENG-PERF-025"></a>

### ENG-PERF-025　进阶 · 考频 ★★★

面试官问：「你们为什么调 API 而不自己部署开源模型？」或者反过来问。请给出「自部署还是调 API」的决策框架：除了单价，还需要考虑哪些因素？在什么条件下应该切换方案？

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **成本结构不同**：API 按 token 线性计费，没有固定成本，与日均用量成正比；自部署按卡时计费，有固定成本（卡、运维人力、平台建设），单价取决于**利用率**——按峰值配卡时利用率往往只有 30% 左右，满载单价再低也会被摊高。比较时要用「实际利用率下的单价 + 人力」与 API 比，并找出盈亏点。
2. **模型能力**：最强的闭源模型只能通过 API 使用；开源模型在复杂推理、长上下文、工具调用上可能有差距，要用业务评测比较「每个成功任务的成本」。
3. **数据合规**：数据不能出域、需要私有化部署时，自部署是硬约束；否则看供应商的数据使用条款与数据驻留能力。
4. **定制需求**：需要全参或 LoRA 微调、多 LoRA 服务、特殊解码约束时，自部署更灵活；API 只有提示词与有限的微调能力。
5. **弹性与可用性**：API 由供应商扩容，但有 TPM 配额与限流，还要考虑多供应商容灾；自部署扩容慢（采购、冷启动），峰值难以应对。
6. **团队能力与时间**：自部署需要推理优化、监控、升级的持续投入；早期验证阶段应优先 API，快速迭代。
7. **切换条件**：量大且平稳、利用率能稳定超过盈亏点；有合规硬约束；需要深度定制；或 API 的配额、时延无法满足要求。常见的折中是混合架构：自部署承接平稳的基线流量与简单任务，峰值和难题走 API，通过统一网关路由。

**评分要点（共 10 分）：**

- 说明成本结构差异，强调利用率与盈亏点（3 分）
- 讨论模型能力差距并用每个成功任务的成本比较（2 分）
- 提到数据合规、定制需求（2 分）
- 提到弹性、配额与团队能力（1 分）
- 给出切换条件或混合架构（2 分）

**讲解：**

**常见失分点**：只比较「每百万 token 的单价」，忽略利用率与人力成本；用峰值吞吐算自部署单价；不提合规与模型能力；给出非此即彼的答案，不知道「基线自部署 + 峰值溢出到 API」的混合方案。

<sub>考点：自部署与API成本</sub>

## 场景分析题

<a name="ENG-PERF-026"></a>

### ENG-PERF-026　挑战 · 考频 ★★

某公司的内部知识助手上线「Agent 模式」（可以多步检索、调用工具）后，月账单从 3 万美元涨到 11 万美元，而日活只增长了 20%。抽样日志显示：

1. 平均每个任务调用模型 9 次（原来 2 次），每次都带上完整的系统提示词（5K）、工具定义（6K）和全部历史；
2. 缓存命中的 token 只占输入的 8%；
3. 工具返回的网页正文经常一次就有 1～2 万 token，并一直留在历史中；
4. 约 60% 的请求是「查某个制度条款」这类简单问题，也走了 Agent 模式和最强的模型。

请分析成本上涨的原因，并给出降本方案（尽量量化预期效果）。

<details>
<summary>答案与解析</summary>

**参考答案：**

**原因分析**
1. **调用次数放大**：每任务调用从 2 次变成 9 次（4.5 倍），叠加日活增长 20%，是账单涨到约 3.7 倍的主因。账单是「任务数 × 每任务调用次数 × 每次输入长度 × 单价」的乘法结构，应按这几项拆账，确认各自贡献了多少。
2. **输入随步数累积**：每次都重发 11K 的固定前缀与全部历史，第 $k$ 步的输入约为 11K + 之前所有步骤的输出与工具结果，累计输入近似随步数平方增长。
3. **缓存几乎没生效**：命中只占 8%，说明前缀不稳定（如开头有时间戳、工具列表顺序不固定）或断点位置不对，11K 的固定前缀每次都按原价计费。
4. **工具结果膨胀**：网页正文一次 1～2 万 token 且长期保留，后续每一步都要为它重复付费。
5. **没有路由**：60% 的简单问题本来用一次检索 + 一次生成就能回答，却走了多步 Agent 和最强的模型。

**降本方案**（括号中为粗略预期，需逐项测量）
1. **路由**：用规则或小分类器识别简单的查询类问题，走原来的 RAG 链路（2 次调用）并换用较小的模型；只有复杂任务进入 Agent 模式（这部分流量的成本可降 80% 以上，整体约降四到五成）。
2. **修好缓存**：固定内容放前面、去掉前缀中的动态字段、工具列表排序固定，在工具定义与系统提示词末尾设断点，历史只追加（目标命中率 70% 以上；命中部分按原价约 0.1 倍计费，具体倍率与写入溢价视厂商和模型而定）。
3. **裁剪工具结果**：网页只抽取正文中与问题相关的段落，设长度上限；完整内容存外部，只在上下文中保留摘要与引用；用过的旧结果折叠（输入量再降三到五成）。
4. **限制步数与预算**：设最大步数与每任务 token 预算，检测无进展的循环。
5. **按需加载工具**：6K 的工具定义按任务类型只加载相关子集。
6. **度量**：以「每个成功任务的成本」为核心指标，按任务类型拆分；对缓存命中率、平均步数、每步输入长度设监控与告警。

**验证**：在评测集上对比改造前后的任务成功率与成本，灰度上线，确保降本不以质量为代价。

**评分要点（共 10 分）：**

- 识别调用次数放大与输入随步数累积（2 分）
- 指出缓存失效与工具结果膨胀（2 分）
- 指出简单请求缺少路由（1 分）
- 给出路由、修复缓存、裁剪工具结果、步数预算等方案（3 分）
- 给出量化估算与以「每个成功任务的成本」为核心的度量与验证（2 分）

**讲解：**

**常见失分点**：只说「换便宜的模型」；不分析账单的乘法结构（调用次数 × 每次输入长度 × 单价）；忽略工具结果这一输入大头；方案没有量化，也没有说明如何保证质量不降。

<sub>考点：Token成本构成、Prompt Caching利用、上下文裁剪、模型路由与级联　｜　出处：Anthropic Prompt Caching 文档 https://platform.claude.com/docs/en/build-with-claude/prompt-caching；OpenAI Prompt caching 文档 https://developers.openai.com/api/docs/guides/prompt-caching</sub>

## 系统设计题

<a name="ENG-PERF-027"></a>

### ENG-PERF-027　挑战 · 考频 ★★

请为公司设计一个统一的「LLM 网关」降本方案。现状：大模型费用每月 20 万美元，调用来自 30 多个业务，全部使用同一个最强模型，没有缓存、没有路由；其中约 30% 的调用是离线任务（评测、数据标注、批量摘要）。目标：在核心质量指标下降不超过 1 个点的前提下，把月度费用降低 50%。请给出架构设计、各项手段的预期收益估算、质量保障与灰度方案、监控指标与主要风险。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 先摸清账单**：网关统一接入后按业务、模型、任务类型统计 token 与费用（输入、输出、思考 token 分开），找出费用最高的几个业务与调用模式；确定每个业务的核心质量指标与评测集。

**2. 架构**：业务 → 网关（鉴权、配额、计量）→ 策略层（缓存 → 路由 / 级联 → 输出控制）→ 模型池（多档 API 模型、可选的自部署模型）；离线请求走批处理通道；所有调用的用量与质量信号写入监控。

**3. 手段与收益估算**（假设输入占费用的 75%，各项收益不能简单相加，需按实际流量逐项测量）
- **批处理**：30% 的离线调用改走批处理接口，约五折，节省约 15%；
- **Prompt Caching**：在线调用中可缓存的固定前缀（系统提示词、工具定义、少样本示例、多轮历史）若占输入的一半、命中按约 0.1 倍计，约节省在线输入费用的 45%，折合总费用约 20%；
- **路由 / 级联**：按任务把分类、抽取、简单问答路由到小模型或调低推理强度；有可靠校验器的任务（如 SQL、JSON、代码）用级联。若 40% 的在线调用可下沉到成本约 1/10 的模型，再节省约 15%～20%；
- **输出控制**：精简回答格式、限制思考强度，节省数个百分点；
- **语义缓存**：只用于少数高频、无个性化的 FAQ 类业务，收益有限但时延改善明显；
- **自部署**：规模大且平稳的简单任务（如标注、分类）可考虑自部署承接基线流量，前提是利用率能超过盈亏点。

**4. 质量保障与灰度**
- 每项改动先在业务评测集上验证（路由与级联要在独立测试集上报告质量与成本）；
- 影子流量对比输出差异，再按业务逐步灰度，用 A/B 观察核心指标；
- 设护栏：核心指标下降超过阈值自动回滚；路由规则与阈值版本化管理。

**5. 监控指标**：每个成功任务的成本（按业务）、缓存命中率（按 token）、路由分布与升级比例、批处理占比、平均输入 / 输出 / 思考 token、质量指标（成功率、点踩率、格式错误率）、时延分位数。

**6. 主要风险**：路由误判导致质量悄悄下降（用抽检与在线指标兜底）；缓存因提示词变更失效（变更时自动检测命中率）；批处理的时效风险（为离线任务设截止时间与重试）；语义缓存误命中与跨租户泄露（缓存键带租户、权限与版本）；网关成为单点（多副本、降级为直连）。

**评分要点（共 10 分）：**

- 先做账单拆分与质量基线（1 分）
- 给出网关的整体架构（2 分）
- 覆盖批处理、缓存、路由 / 级联、输出控制等手段，并给出合理的收益估算（3 分）
- 给出评测、影子流量、灰度与自动回滚等质量保障（2 分）
- 给出监控指标与主要风险的对策（2 分）

**讲解：**

**常见失分点**：直接给出「换小模型」一个手段；收益估算没有前提假设，或把各项百分比直接相加；忽略质量保障与回滚；没有按业务计量，无法找到费用大头；把语义缓存当作主要手段而忽视其误命中风险。

<sub>考点：模型路由与级联、语义缓存、Prompt Caching利用、批处理API、自部署与API成本　｜　出处：RouteLLM（arXiv:2406.18665）；FrugalGPT（arXiv:2305.05176）</sub>

</details>
