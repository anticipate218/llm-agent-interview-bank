<a name="CS-OS-001"></a>

### CS-OS-001　基础 · 考频 ★★★

同一个进程中的多个线程，下列哪一项是每个线程**各自独有**的？

- **A.** 各线程在堆上用 malloc 或 new 分配的对象
- **B.** 全局变量，以及函数内的 static 局部变量
- **C.** 栈与寄存器上下文（含程序计数器、栈指针）
- **D.** 打开的文件描述符表与当前工作目录

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：线程是 CPU 调度的单位，每个线程要有自己的执行状态：程序计数器、寄存器、栈（局部变量与调用链），此外还有线程局部存储、`errno` 等。

同一进程的线程共享：地址空间中的代码段、全局与静态数据、堆；打开的文件描述符；信号处理方式；当前工作目录等。所以线程之间通信很方便（直接读写同一块内存），代价是必须自己做同步，否则会出现竞态条件。

- A 错：堆是整个进程共享的，一个线程分配的对象，其他线程拿到指针就能访问，这正是需要加锁的原因。
- B 错：全局变量和 static 局部变量都位于进程的数据段，所有线程共享；需要每个线程一份时，要用线程局部存储（如 `thread_local`、`threading.local`）。
- D 错：文件描述符表和当前工作目录都属于进程，一个线程打开的文件，其他线程也能用同一个 fd 读写。

<sub>考点：进程与线程</sub>

</details>

<a name="CS-OS-005"></a>

### CS-OS-005　进阶 · 考频 ★★

协程之间切换的开销远小于线程切换，最主要的原因是：

- **A.** 切换在用户态由程序主动让出完成，只需保存少量上下文，不经过内核调度
- **B.** 运行时会把每个协程绑定到独立的 CPU 核上执行，协程之间并行运行，几乎不需要切换
- **C.** 协程切换同样由内核完成，但内核为协程维护了专用的轻量级运行队列，跳过了完整的调度流程
- **D.** 协程不保存寄存器和局部变量，每次恢复都从函数开头重新执行，所以切换几乎没有开销

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：线程切换要陷入内核，经过调度器选择下一个线程，保存和恢复完整的寄存器上下文；协程切换在用户态完成，切换点由程序决定，要保存的东西少得多（几个寄存器和栈指针，或状态机中的局部状态），也不涉及地址空间的切换。

两类实现：
- **有栈协程**（如 Go 的 goroutine）：每个协程有自己的小栈，切换时保存少量寄存器并切换栈指针；
- **无栈协程**（如 Python 的 async/await、Rust 的 async）：编译器或解释器把函数变成状态机，局部变量保存在协程对象里，切换只是从一个函数返回、调用另一个。

- B 错：成千上万个协程通常跑在一个或少数几个线程上，靠交替执行实现并发。
- C 错：内核看不到协程，它只调度线程。
- D 错：协程至少要保存「执行到哪里」以及局部变量，恢复时从上次让出的位置继续，而不是从头执行。

**代价**：协作式调度意味着协程不让出就没人能抢占它，一段长时间的 CPU 计算或阻塞调用会卡住同一线程上的所有协程。

<sub>考点：协程、上下文切换</sub>

</details>

<a name="CS-OS-007"></a>

### CS-OS-007　进阶 · 考频 ★★

在同一个 CPU 核上，从一个进程的线程切换到**另一个进程**的线程，通常比在同一进程的两个线程之间切换开销更大。主要的额外开销来自：

- **A.** 需要把被换下进程的脏页全部写回磁盘，为新进程腾出物理内存，等它下次运行时再读回
- **B.** 需要重新加载新进程的可执行文件和共享库，重新完成动态链接时的符号重定位
- **C.** 新进程的套接字在被切出期间处于挂起状态，切回时需要重新建立这些网络连接，并恢复收发缓冲区
- **D.** 要更换页表基址，TLB 里缓存的地址映射不再适用、需重新填充，CPU 缓存命中率也随之下降

<details>
<summary>答案与解析</summary>

**答案：D**

**解析：**

**结论**：上下文切换的开销分两部分：
- **直接开销**：陷入内核、调度器选择下一个任务、保存与恢复寄存器，通常在微秒量级；
- **间接开销**：切换到另一个进程意味着换一套页表，TLB 中的虚拟地址到物理地址的映射需要失效或重新填充，之后的访存会频繁未命中 TLB、触发页表遍历；L1、L2 缓存里也大多是上一个进程的数据。这部分开销往往比直接开销更大，而且难以直接测量。

同一进程内的线程共享地址空间，不需要换页表，TLB 中的映射仍然有效。现代 CPU 用 PCID（x86）或 ASID（ARM）给 TLB 条目打上地址空间标签，可以避免切换时整体刷新 TLB，但缓存污染仍然存在。

- A 错：只有内存不足、发生换页时才会写磁盘，与上下文切换无关。
- B 错：可执行文件和共享库在 exec 时就已映射进地址空间，进程被切换出去只是暂停，切回时不需要重新加载或重定位。
- C 错：被切换的进程只是暂停，套接字和连接都原样保留在内核中，期间到达的数据照常进入接收缓冲区。

<sub>考点：上下文切换、虚拟内存与分页</sub>

</details>

<a name="CS-OS-009"></a>

### CS-OS-009　基础 · 考频 ★★★

某系统规定：任何线程需要同时持有多个账户的锁时，都必须按账户 ID 从小到大的顺序加锁。这条规则能防止死锁，它破坏的是死锁四个必要条件中的哪一个？

- **A.** 互斥
- **B.** 持有并等待
- **C.** 不可抢占
- **D.** 循环等待

<details>
<summary>答案与解析</summary>

**答案：D**

**解析：**

**结论**：所有线程都按同一个全局顺序加锁，等待关系只能从「小号」指向「大号」，不可能形成环，所以破坏的是循环等待。

死锁的四个必要条件（缺一不可）及对应的破坏方法：
- **互斥**：资源一次只能被一个线程使用。改用可共享的资源或无锁数据结构，通常难以做到；
- **持有并等待**：持有资源的同时等待别的资源。一次性申请全部资源，或在申请新资源前先释放已有的；
- **不可抢占**：已分配的资源不能被强行收回。加锁带超时（如 `try_lock`），拿不到就释放已有的锁、退避后重试；
- **循环等待**：存在一个互相等待的环。规定全局加锁顺序，这是工程上最常用的方法。

除了预防，还有**避免**（如银行家算法，分配前检查是否安全）和**检测与恢复**（构建等待图找环，再终止或回滚其中一个线程）。

<sub>考点：锁与死锁</sub>

</details>

<a name="CS-OS-013"></a>

### CS-OS-013　进阶 · 考频 ★★

用条件变量实现消费者，有下面两种写法：

```python
# 写法一
with cond:
    if not queue:
        cond.wait()
    item = queue.popleft()

# 写法二
with cond:
    while not queue:
        cond.wait()
    item = queue.popleft()
```

应当使用写法二，最主要的原因是：

- **A.** 用 while 循环时，wait() 会以轮询方式定期返回检查队列，比 if 写法更快感知到新数据
- **B.** 从 wait() 返回时条件不一定成立：可能是虚假唤醒，也可能数据已被另一个消费者抢先取走
- **C.** 写法一中 wait() 被唤醒后不会自动重新获取锁，随后的 popleft() 在没有锁保护的情况下执行
- **D.** Python 的 Condition 不支持在 if 语句中调用 wait()，会抛出异常

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：条件变量的通知只表示「条件**可能**变了」，被唤醒的线程还要和其他线程竞争锁，拿到锁时条件可能已经不成立，所以必须在循环中重新检查。

两个具体原因：
1. **虚假唤醒**：POSIX 允许 `pthread_cond_wait` 在没有收到通知时返回；
2. **被抢先**：常见的条件变量是 Mesa 语义，`notify` 只是把等待者变为可运行，并不把锁直接交给它。假设队列里只有一个元素，两个消费者先后被唤醒，第一个取走了元素，第二个按写法一会对空队列执行 `popleft()`，抛出异常。

Python 提供了 `cond.wait_for(predicate)`，内部就是这个 while 循环。

- A 错：wait() 是阻塞等待通知（或超时），不是轮询；循环与否不影响它何时返回。
- C 错：`wait()` 总会先释放锁、被唤醒后再重新获取，与外面是 if 还是 while 无关。
- D 错：两种写法语法上都合法，问题在于逻辑。

<sub>考点：信号量与条件变量　｜　出处：Python 文档：threading.Condition</sub>

</details>

<a name="CS-OS-017"></a>

### CS-OS-017　进阶 · 考频 ★★★

关于 select、poll 与 epoll，下列说法正确的是：

- **A.** select、poll 每次调用都要传入并扫描全部 fd；epoll 注册一次即可，epoll_wait 只返回就绪的 fd
- **B.** select 用动态数组传递 fd 集合，数量没有上限；poll 用固定大小的位图，最多只能监视 1024 个 fd
- **C.** epoll 之所以高效，是因为就绪 fd 的数据由网卡经 DMA 直接写入用户缓冲区，省去了从内核拷贝这一步
- **D.** epoll 是 POSIX 标准接口，Linux、macOS、Windows 都直接提供，Python asyncio 在各平台上都基于它实现

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：三者都是 IO 多路复用：一个线程同时监视大量连接，哪个就绪处理哪个。差别在于每次调用的开销。

- **select**：用位图传递 fd 集合，大小受 `FD_SETSIZE` 限制（Linux 上通常为 1024）；每次调用都要把集合拷进内核、线性扫描，返回后用户还要再扫一遍找出就绪的 fd，开销 $O(n)$。
- **poll**：改用数组传递，没有 1024 的限制，但每次仍要传入全部 fd、线性扫描，开销同样是 $O(n)$。
- **epoll**（Linux 专有）：`epoll_ctl` 把 fd 注册到内核维护的集合中（只需一次）；fd 就绪时，内核通过回调把它挂到就绪列表上；`epoll_wait` 只返回就绪的 fd。一万个连接中只有几十个活跃时，开销只与这几十个有关。

- B 错：说反了：select 用固定大小的位图，受 `FD_SETSIZE`（通常为 1024）限制；poll 用数组，没有这个限制。
- C 错：epoll 只负责「通知哪个 fd 就绪」，数据仍要由 read 从内核缓冲区拷贝到用户空间。
- D 错：epoll 是 Linux 特有的；macOS、BSD 上对应 kqueue，Windows 上是 IOCP。Python asyncio、Node.js 的 libuv 都在不同平台上封装了对应的机制。

<sub>考点：IO模型与多路复用　｜　出处：Linux man-pages：epoll(7)、select(2)</sub>

</details>

<a name="CS-OS-024"></a>

### CS-OS-024　挑战 · 考频 ★

在 Linux 上用 PyTorch 训练时，Dataset 用一个很大的 Python 列表保存了几百万条样本的文件路径（字符串对象）。开启 `num_workers=8`，worker 进程以 fork 方式创建（这是 Linux 上 Python 3.13 及更早版本的默认方式）。之后，每个 worker 的物理内存占用随训练逐渐上涨，总内存远超预期，而代码从未修改这个列表。最可能的原因是：

- **A.** fork 后内核会在后台逐步把父进程的物理页完整复制给每个子进程，复制完成前内存持续上涨
- **B.** fork 出的子进程中 Python 的循环垃圾回收器默认被禁用，worker 每轮产生的临时对象无法回收、逐步累积
- **C.** 读取列表元素也会修改对象头部的引用计数，这次写入触发写时复制，相关内存页被逐页复制到各个 worker
- **D.** DataLoader 每个 epoch 都会把整个 Dataset 对象重新序列化，通过管道发给每个 worker，旧副本不会释放

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：这是「读也会触发写时复制」的典型问题，PyTorch 的 issue #13246 详细讨论过。

fork 之后，父子进程共享物理页，页被标记为只读；任何一方**写**某一页时，内核才为它复制一份（写时复制，COW）。CPython 中每个对象的头部都有引用计数，仅仅是读取 `paths[i]`，也会增加、减少这个字符串的引用计数，这就是一次写操作。几百万个小对象散布在大量内存页上，随着训练遍历数据集，几乎每一页都被「写」过一次，每个 worker 最终都拥有了一份副本。内存因此是**逐渐**上涨，而不是 fork 时立刻翻倍。

**解决**：把这类数据存成不带逐元素引用计数的形式，例如 numpy 数组（字符串可以编码成定长字节数组）或 PyArrow 的列式数据（字符串存放在连续的缓冲区里）；也可以把数据放进共享内存或按需从磁盘读取。

- A 错：fork 采用写时复制，只有被写过的页才会复制，内核不会在后台主动复制物理内存。
- B 错：子进程中的垃圾回收照常工作（开关状态随 fork 继承，默认开启）；问题与回收无关，是复制造成的。
- D 错：在 fork 模式下，worker 直接继承父进程的内存，不需要序列化数据集，也不存在每个 epoch 重发一份的情况。

**版本提示**：Python 3.14 起，Linux 上 multiprocessing 的默认启动方式改为 forkserver（Windows 一直是 spawn，macOS 自 Python 3.8 起默认为 spawn）。这些方式下数据集会被序列化后传给每个 worker，每个 worker 一启动就持有一份完整副本，表现不同，但「每个 worker 一份」的内存账同样要提前算清楚。

<sub>考点：虚拟内存与分页、进程与线程　｜　出处：PyTorch issue #13246；PyTorch 文档 torch.utils.data</sub>

</details>

<a name="CS-OS-026"></a>

### CS-OS-026　挑战 · 考频 ★

一个使用 glibc malloc 的服务处理完一批大请求后，释放了大量 64 KiB 左右的内存块，进程的 RSS（常驻物理内存）却几乎没有下降，过一段时间也没有回落。下列解释最合理的是：

- **A.** free() 会立即通过 munmap 把整块内存归还给操作系统，RSS 没降，说明这些块其实没被释放，存在泄漏
- **B.** 这些块小于 mmap 阈值，是从堆或 arena 中切分的；释放后通常留在分配器的空闲链表里复用，难以归还给系统
- **C.** Linux 按进程的历史峰值保留物理页，进程曾经分配过的物理页要等到进程退出才会被系统回收
- **D.** RSS 统计的是进程映射过的虚拟地址空间总大小（含已释放的部分），本来就不会因 free 而下降

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：「free 了但 RSS 不降」多数是分配器的策略与碎片造成的，不一定是泄漏。

glibc malloc（ptmalloc）的行为：
- 小于 mmap 阈值的块从堆（`brk` 扩展的连续区域）或各线程的 arena 中切分。释放后进入空闲链表，等待复用；只有堆顶部连续的空闲空间超过一定阈值时，才会通过收缩堆顶归还给系统。高地址处只要还有一个存活的小对象，下面大片的空闲内存就还不回去。
- 大于等于 mmap 阈值的块单独用 `mmap` 分配，`free` 时直接 `munmap`，RSS 立即下降。这个阈值初值是 128 KiB，而且是动态的：释放过较大的 mmap 块后，阈值会自动调高。
- 多线程程序每个线程可能有自己的 arena，进一步加剧碎片。

**应对**：调用 `malloc_trim` 尝试归还空闲内存；限制 arena 数量（`MALLOC_ARENA_MAX`）；换用 jemalloc 或 tcmalloc；调整分配模式（复用缓冲区、对象池）。确认是否泄漏，要看 RSS 是否随请求数**持续线性增长**，并借助内存分析工具。

- A 错：free 只是把内存还给分配器；只有用 mmap 单独分配的大块才会在 free 时直接 munmap，64 KiB 的块是否还给操作系统由分配器决定。
- C 错：内存归还后，物理页就会被系统回收。
- D 错：RSS 是实际驻留在物理内存中的大小；虚拟地址空间大小是 VSZ。

<sub>考点：内存分配　｜　出处：Linux man-pages：mallopt(3)、malloc_trim(3)</sub>

</details>

<a name="CS-OS-027"></a>

### CS-OS-027　基础 · 考频 ★★

两个进程之间需要频繁交换大块数据（例如数据加载进程把解码好的图像张量交给训练进程）。下列 IPC 方式中，通常吞吐最高、拷贝次数最少的是：

- **A.** 管道（pipe）
- **B.** 本机回环地址上的 TCP 套接字
- **C.** 共享内存，配合信号量等同步机制
- **D.** 信号（signal）

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：共享内存把同一块物理内存同时映射进两个进程的地址空间，写入方写完，读取方直接就能读，数据不经过内核中转。

- A 错：管道要把数据从发送方用户空间拷进内核缓冲区，再拷到接收方用户空间，至少两次拷贝，外加系统调用开销；它使用简单、自带同步，适合中小数据量的消息传递。
- B 错：回环地址上的 TCP 同样要经过内核缓冲区，至少两次拷贝，还要走一遍协议栈；好处是接口统一，还能跨机器。
- D 错：信号只传递一个信号编号，几乎不能携带数据，用于通知，例如让进程优雅退出。

**代价**：共享内存本身不提供同步，读写双方要用信号量、锁或无锁队列协调，否则会读到写了一半的数据。PyTorch 的 DataLoader 正是把 worker 产生的张量放进共享内存，队列里只传递句柄，所以在容器里运行时要保证 `/dev/shm` 足够大。

关于锁与并发问题，下列说法**正确**的有：

- **C.** 活锁：线程没有阻塞、一直在运行，却因为互相「礼让」、反复回退重试而没有任何进展
- **D.** 自旋锁避免了线程挂起和上下文切换，因此即使临界区很长或在单核机器上，也比互斥锁更高效
- **E.** 读写锁允许多个读者同时持有，适合读多写少的场景，但如果读者源源不断，写者可能饥饿

<details>
<summary>答案与解析</summary>

**答案：ACE**

**解析：**

**结论**：A、C、E 正确。

- D 错：自旋锁让等待的线程空转占用 CPU，只适合临界区极短、多核的场景；临界区较长或单核时，自旋纯属浪费，还可能让持锁者得不到 CPU。
- E 对：很多读写锁实现会让新来的读者在有写者等待时也排队，以避免写者饥饿。

<a name="CS-OS-018"></a>

### CS-OS-018　挑战 · 考频 ★★

关于 epoll 的水平触发（LT）与边缘触发（ET），下列说法**正确**的有：

- **A.** 多个线程等待同一个 epoll 实例时，可用 EPOLLONESHOT 让一个 fd 的事件只交给一个线程，处理完要重新启用
- **B.** 边缘触发应当配合阻塞模式的 fd 使用：循环读到没有数据时，线程会在 read 上等待新数据到来，不会空转
- **C.** 水平触发会对同一个就绪事件反复通知、挤占处理时间，更容易漏掉新事件，所以高性能服务器只能使用边缘触发
- **D.** 水平触发下，只要 fd 的接收缓冲区里还有数据没读完，每次调用 epoll_wait 都会再次报告它就绪
- **E.** 边缘触发只在状态变化时通知一次，收到通知后要循环读到 EAGAIN，否则剩余数据可能再也得不到通知

<details>
<summary>答案与解析</summary>

**答案：ADE**

**解析：**

**结论**：A、D、E 正确。

- A 对：否则同一个 fd 的事件可能被多个线程同时取到，并发读写同一个连接。
- B 错：ET 必须配合**非阻塞** fd。循环读到没有数据时，阻塞的 read 会卡住整个事件循环线程，其他连接全部得不到处理；非阻塞的 read 会返回 EAGAIN，循环据此结束。
- C 错：LT 更不容易漏事件；ET 减少了重复通知，但要求更严格的读写纪律。两种模式都被广泛使用，例如 Nginx 使用 ET。
- D 对：LT 是默认模式，语义与 select、poll 相同，「只要还能读，就一直告诉你」。即使这次只读了一部分，下次还会通知，编程最不容易出错。
- E 对：ET 只在「从不可读变为可读」这类变化时通知。如果这次没读完，又没有新数据到来，这个 fd 就不会再被报告，剩下的数据会一直滞留。

man 7 epoll 建议的 ET 用法正是：使用非阻塞 fd，并且只在 read 或 write 返回 EAGAIN 之后才再次等待事件。

**答案：BCD**

**解析：**

**结论**：B、C、D 正确。

<a name="CS-OS-019"></a>

### CS-OS-019　进阶 · 考频 ★★

使用「非阻塞 socket + epoll」的程序，按经典的 IO 模型划分仍然属于同步 IO：epoll 只告诉你哪个 fd 可读，把数据从内核缓冲区拷贝到用户缓冲区的过程，仍然由调用 read 的线程自己完成。

<details>
<summary>答案与解析</summary>

**答案：✅ 正确**

**解析：**

**正确**。一次读操作分两个阶段：① 等待数据就绪（数据到达内核缓冲区）；② 把数据从内核拷贝到用户缓冲区。

- 阻塞 IO、非阻塞 IO、IO 多路复用、信号驱动 IO 的差别都在第 ① 阶段怎么等；第 ② 阶段都由应用线程调用 read 同步完成，所以都属于**同步 IO**。
- **异步 IO**（如 POSIX AIO、Windows 的 IOCP、Linux 的 io_uring）把两个阶段都交给内核，数据已经放进用户缓冲区之后才通知应用。

所以 epoll 的准确说法是「IO 多路复用」或「事件驱动」，而不是「异步 IO」。日常所说的「异步编程」（如 Python asyncio）指的是编程模型：协程在等待时让出、由事件循环调度，它在 Linux 上的底层通常就是 epoll 这类多路复用机制。

</details>

<a name="CS-OS-023"></a>

### CS-OS-023　基础 · 考频 ★★

分页机制把物理内存划分为固定大小的页框，按页分配、不要求连续，因此基本消除了外部碎片；代价是一段内存的最后一页往往用不满，会带来少量内部碎片。

<details>
<summary>答案与解析</summary>

**答案：✅ 正确**

**解析：**

**正确**。

- **外部碎片**：空闲内存总量足够，却被切成许多不连续的小块，凑不出一整块。分段或连续分配会产生外部碎片；分页时任意一个空闲页框都能分给任意一页，不存在「凑不出连续空间」的问题。

vLLM 的 PagedAttention 把同样的思路用在 KV Cache 上：固定大小的块按需分配，浪费只剩每条序列最后一个块中未写满的部分。

## 填空题

<a name="CS-OS-014"></a>

### CS-OS-014　基础 · 考频 ★★

用三个信号量实现容量为 N 的有界缓冲区（生产者消费者问题）：表示空位数的信号量 `empty` 初值为 ____，表示已有数据项数的 `full` 初值为 ____，保护缓冲区的互斥信号量 `mutex` 初值为 ____。生产者必须先 P(empty) 再 P(mutex)；如果把这两个 P 操作的顺序颠倒，缓冲区满时会发生 ____。

<details>
<summary>答案与解析</summary>

**答案：** (1) N；(2) 0；(3) 1；(4) 死锁 / deadlock

**解析：**

**初值**：开始时缓冲区全空，空位为 N、数据项为 0；`mutex` 是二值信号量，初值为 1。

**生产者**：P(empty) → P(mutex) → 放入数据 → V(mutex) → V(full)；**消费者**：P(full) → P(mutex) → 取出数据 → V(mutex) → V(empty)。

**顺序颠倒的后果**：缓冲区满时，生产者先拿到 `mutex`，再在 P(empty) 上阻塞，而且一直持有 `mutex`；消费者要取数据，必须先拿到 `mutex`，于是也阻塞。双方互相等待，形成**死锁**。原则是：先等待「资源是否可用」的同步信号量，再获取保护临界区的互斥信号量；V 操作的顺序则无所谓。

<sub>考点：信号量与条件变量　｜　出处：经典操作系统教材中的生产者消费者问题</sub>

</details>

<a name="CS-OS-022"></a>

### CS-OS-022　进阶 · 考频 ★★

32 位虚拟地址 0x00403ABC，页大小为 4 KiB，采用「10 + 10 + 12」位的两级页表。该地址的页目录索引为 ____（十进制），页表索引为 ____（十进制），页内偏移为 ____（十六进制）。若对应的页表项给出的物理页框号为 0x2A5，则物理地址为 ____（十六进制）。

<details>
<summary>答案与解析</summary>

**答案：** (1) 1；(2) 3；(3) 0xABC / ABC / 0xabc / abc；(4) 0x2A5ABC / 2A5ABC / 0x002A5ABC / 0x2a5abc / 2a5abc

**解析：**

0x00403ABC 的二进制按 10 / 10 / 12 位拆分：
- 页目录索引：最高 10 位，即地址右移 22 位：$\text{0x00403ABC}\gg22=1$（0x00400000 恰好是 4 MiB，即 $2^{22}$）；
- 页表索引：中间 10 位，$(\text{0x00403ABC}\gg12)\ \&\ \text{0x3FF}=\text{0x403}\ \&\ \text{0x3FF}=\text{0x003}=3$；
- 页内偏移：低 12 位，$\text{0x00403ABC}\ \&\ \text{0xFFF}=\text{0xABC}$。

物理地址 = 页框号左移 12 位 + 页内偏移 $=\text{0x2A5000}+\text{0xABC}=\text{0x2A5ABC}$。

页内偏移在翻译前后保持不变，变的只是页号部分。硬件先查 TLB；未命中时，用 CR3 等寄存器中的页目录基址，依次读页目录项、页表项得到页框号，再填入 TLB。如果页表项标记为不存在，就触发缺页异常，由操作系统分配物理页或从磁盘调入。

<sub>考点：虚拟内存与分页</sub>

## 计算题

<a name="CS-OS-011"></a>

### CS-OS-011　挑战 · 考频 ★★

系统有 3 类资源 R1、R2、R3，4 个进程 P0～P3。当前的分配情况、最大需求与可用资源如下：

| 进程 | 已分配 (R1, R2, R3) | 最大需求 (R1, R2, R3) |
|---|---|---|
| P0 | (1, 1, 0) | (4, 3, 2) |
| P1 | (2, 0, 1) | (3, 2, 2) |
| P2 | (1, 2, 1) | (4, 2, 3) |
| P3 | (2, 1, 1) | (2, 2, 2) |

当前可用资源为 (2, 1, 2)。
(1) 计算各进程还需要的资源（Need），判断系统当前是否处于安全状态；若安全，给出一个安全序列（每一轮都从编号最小的进程开始找）。
(2) 此时 P1 请求 (1, 0, 1)，按银行家算法能否立即分配？
(3) 若不是 P1，而是 P0 请求 (2, 1, 1)，能否立即分配？

<details>
<summary>答案与解析</summary>

**答案：(1) 安全，安全序列为 P3, P0, P1, P2；(2) 可以分配，分配后仍安全；(3) 不能立即分配，分配后系统不安全，P0 需要等待**

**解析：**

**(1)** Need = 最大需求 − 已分配：P0 (3, 2, 2)，P1 (1, 2, 1)，P2 (3, 0, 2)，P3 (0, 1, 1)。

安全性检查，Work 初值为可用资源 (2, 1, 2)：
- P0 需要 R1 = 3 > 2，P1 需要 R2 = 2 > 1，P2 需要 R1 = 3 > 2，都不行；P3 的 (0, 1, 1) ≤ (2, 1, 2)，可以完成，释放其已分配资源：Work = (2, 1, 2) + (2, 1, 1) = (4, 2, 3)；
- 从 P0 重新找：(3, 2, 2) ≤ (4, 2, 3)，P0 完成，Work = (5, 3, 3)；
- P1：(1, 2, 1) ≤ (5, 3, 3)，完成，Work = (7, 3, 4)；
- P2：(3, 0, 2) ≤ (7, 3, 4)，完成，Work = (8, 5, 5)，等于资源总量。

所有进程都能完成，系统**安全**，安全序列为 **P3, P0, P1, P2**。

**(2)** P1 请求 (1, 0, 1)：先检查请求 ≤ Need (1, 2, 1)、请求 ≤ 可用 (2, 1, 2)，都满足。假设分配：可用变为 (1, 1, 1)，P1 已分配 (3, 0, 2)，Need 变为 (0, 2, 0)。再做安全性检查：P3 的 (0, 1, 1) ≤ (1, 1, 1)，Work = (3, 2, 2)；P0 的 (3, 2, 2) ≤ (3, 2, 2)，Work = (4, 3, 2)；P1 的 (0, 2, 0) 满足，Work = (7, 3, 4)；P2 满足。仍然安全，**可以分配**。

**(3)** P0 请求 (2, 1, 1)：请求 ≤ Need (3, 2, 2)、请求 ≤ 可用 (2, 1, 2)，资源是够的。假设分配后可用只剩 (0, 0, 1)，Need 为 P0 (1, 1, 1)、P1 (1, 2, 1)、P2 (3, 0, 2)、P3 (0, 1, 1)，没有任何一个进程的需求能被满足，系统**不安全**，所以不能立即分配，P0 需要等待。

**要点**：「当前资源够用」不等于「可以分配」；银行家算法关心的是分配后是否还存在一个让所有进程都能完成的顺序。不安全状态不一定会死锁，但系统已无法保证避免死锁。实际系统很少使用银行家算法，因为它要求事先知道每个进程的最大需求；但它是「死锁避免」思想的标准例子。

<sub>考点：锁与死锁　｜　出处：经典操作系统教材中的银行家算法</sub>

### CS-OS-021　进阶 · 考频 ★★

(1) 32 位虚拟地址空间，页大小 4 KiB，每个页表项 4 字节。若使用单级页表，每个进程的页表要占多少内存？
(2) 改用「10 位页目录索引 + 10 位页表索引 + 12 位页内偏移」的两级页表。某进程只用到了地址空间最低端连续的 12 MiB（代码与数据），以及地址空间顶端的 1 MiB 栈（落在同一个 4 MiB 对齐的区间内）。它的页表一共要占多少内存？
(3) x86-64 使用 48 位虚拟地址、4 KiB 页、每个页表项 8 字节，并要求每一级页表恰好占一个页。需要几级页表？每一级的索引是多少位？

<details>
<summary>答案与解析</summary>

**答案：(1) 4 MiB；(2) 20 KiB（1 个页目录 + 4 个页表）；(3) 4 级，每级 9 位**

**解析：**

**(1)** 页内偏移 12 位，虚拟页号 $32-12=20$ 位，共 $2^{20}$ 个页表项：$2^{20}\times4$ 字节 $=4$ MiB。每个进程都要一份，而且不管用没用到都得全部分配，这正是单级页表的问题。

**(2)** 页目录有 $2^{10}$ 项，每项 4 字节，正好 4 KiB；每个二级页表也是 4 KiB，管理 $2^{10}\times4$ KiB $=4$ MiB 的地址空间。
- 低端 12 MiB：需要 $12\div4=3$ 个二级页表；
- 顶端 1 MiB 栈：落在一个 4 MiB 区间内，需要 1 个二级页表；
- 加上 1 个页目录，共 5 个页，$5\times4$ KiB $=$ **20 KiB**，远小于 4 MiB。没用到的区间，页目录项标记为无效，不分配二级页表。

**(3)** 一页 4 KiB 能放 $4096\div8=512=2^9$ 个页表项，所以每级索引 9 位；需要翻译的位数为 $48-12=36$ 位，$36\div9=$ **4** 级（PML4、PDPT、PD、PT）。

**代价与缓解**：多级页表省内存，但一次 TLB 未命中最多要多访问 4 次内存才能完成地址翻译，所以 TLB 命中率很关键；使用 2 MiB 的大页可以少走一级、扩大 TLB 的覆盖范围，数据库和大内存服务常用。

<sub>考点：虚拟内存与分页</sub>

</details>

<a name="CS-OS-025"></a>

### CS-OS-025　进阶 · 考频 ★

某伙伴系统管理一块 1024 KiB 的连续内存，初始全部空闲。分配时总是取能满足请求的最小的 2 的幂大小的块，需要拆分时从地址最低的空闲块开始，拆出的低地址一半继续使用或分配。依次发生以下操作：A 申请 70 KiB，B 申请 35 KiB，C 申请 80 KiB，然后释放 A。
(1) A、B、C 各分到多大的块？此时三者的内部碎片一共多少？
(2) 释放 A 之后，有哪些空闲块（写出大小与起始地址）？A 的块能否与它的伙伴合并？为什么？
(3) 此时有一个 600 KiB 的申请，能否满足？这说明了什么？

<details>
<summary>答案与解析</summary>

**答案：(1) A 128 KiB、B 64 KiB、C 128 KiB，内部碎片共 135 KiB；(2) 空闲块为 0 起的 128 KiB、192 KiB 起的 64 KiB、384 KiB 起的 128 KiB、512 KiB 起的 512 KiB，A 不能合并；(3) 不能满足**

**解析：**

**(1) 分配过程**（地址单位 KiB）：
- A 申请 70：需要 128 的块。1024 拆成两个 512，[0, 512) 拆成两个 256，[0, 256) 拆成两个 128，A 得到 [0, 128)；空闲：[128, 256)、[256, 512)、[512, 1024)。
- B 申请 35：需要 64 的块。把 [128, 256) 拆成两个 64，B 得到 [128, 192)；空闲多了 [192, 256)。
- C 申请 80：需要 128 的块，但已经没有空闲的 128 块了。把 [256, 512) 拆成两个 128，C 得到 [256, 384)；空闲多了 [384, 512)。

内部碎片：$(128-70)+(64-35)+(128-80)=58+29+48=$ **135 KiB**，接近三者实际申请量（185 KiB）的四分之三。

**(2)** 释放 A 后的空闲块：[0, 128)、[192, 256)、[384, 512)、[512, 1024)，共 $128+64+128+512=832$ KiB。A 的伙伴是 [128, 256)，其中 [128, 192) 仍被 B 占用，伙伴不是一个完整的空闲块，所以**不能合并**。

**(3)** 600 KiB 需要 1024 KiB 的块，而最大的空闲块只有 512 KiB，**无法满足**，尽管空闲总量有 832 KiB。

**说明**：伙伴系统的拆分与合并都很快（地址异或块大小就能算出伙伴），但「向上取整到 2 的幂」带来大量内部碎片，小块又会妨碍伙伴合并，形成碎片化。Linux 内核用伙伴系统按页管理物理内存，小对象再由 slab 类分配器从页中切分；用户态的 malloc（ptmalloc、jemalloc、tcmalloc）按大小分级管理。

<sub>考点：内存分配　｜　出处：经典操作系统教材中的伙伴系统</sub>

## 代码输出题

<a name="CS-OS-003"></a>

### CS-OS-003　基础 · 考频 ★★

下面的代码先用一个线程、再用两个子进程分别执行 `work`。`counter` 是普通的全局列表，`shared` 是放在共享内存中的整数。输出是什么？

```python
import threading
import multiprocessing as mp

counter = [0]


def work(shared):
    counter[0] += 1
    with shared.get_lock():
        shared.value += 1


if __name__ == "__main__":
    shared = mp.Value("i", 0)                  # 放在共享内存中的整数
    t = threading.Thread(target=work, args=(shared,))
    t.start(); t.join()
    ps = [mp.Process(target=work, args=(shared,)) for _ in range(2)]
    for p in ps: p.start()
    for p in ps: p.join()
    print(counter[0], shared.value)
```

<details>
<summary>答案与解析</summary>

**答案（程序输出）：**

```text
1 3
```

**解析：**

- **线程**：与主线程共享地址空间，修改的就是主进程里的 `counter`，`counter[0]` 变为 1；`shared` 也加 1。
- **子进程**：各有独立的地址空间。用 fork 创建时，子进程得到父进程内存的一份写时复制的副本；用 spawn 或 forkserver 创建时，子进程重新导入模块，得到全新的 `counter`（Windows、macOS 默认用 spawn；Linux 上 Python 3.13 及更早默认用 fork，3.14 起默认改为 forkserver）。无论哪种方式，子进程改的都是自己的副本，父进程的 `counter[0]` 仍是 1。
- **共享内存**：`mp.Value` 把整数放在多个进程都映射进来的共享内存里，两个子进程的修改对父进程可见，最终为 $1+2=3$。`get_lock()` 保证「读出、加 1、写回」不被打断。

所以输出 `1 3`。

**要点**：多进程之间要交换数据，必须显式使用 IPC（共享内存、管道、队列等）；在子进程中修改全局变量、期望父进程能看到，是多进程编程中常见的错误。

<sub>考点：进程与线程、进程间通信　｜　出处：Python 文档：multiprocessing</sub>

</details>

## 代码改错题

<a name="CS-OS-012"></a>

### CS-OS-012　进阶 · 考频 ★★★

下面的转账函数在压测中偶尔会让两个线程永久卡住：一个线程执行 `transfer(x, y, ...)` 的同时，另一个线程执行 `transfer(y, x, ...)`。请找出原因并修正（同一账户给自己转账时直接返回 `False`）。

```python
import threading


class Account:
    def __init__(self, aid, balance):
        self.id = aid
        self.balance = balance
        self.lock = threading.Lock()


def transfer(a, b, amount):
    with a.lock:
        with b.lock:
            if a.balance < amount:
                return False
            a.balance -= amount
            b.balance += amount
            return True
```

<details>
<summary>答案与解析</summary>

**答案：**

**原因**：加锁顺序取决于参数顺序。线程 1 执行 `transfer(x, y)`，先锁 x、再等 y；线程 2 执行 `transfer(y, x)`，先锁 y、再等 x。两个线程各持有一把锁、等待对方的锁，满足了循环等待，发生死锁。

另外，`transfer(x, x)` 会对同一把 `threading.Lock` 加锁两次，而它不可重入，线程会自己把自己锁死。

**修正**：按账户 ID 的全局顺序加锁，并单独处理同一账户的情况：

```python
def transfer(a, b, amount):
    if a is b:
        return False
    first, second = (a, b) if a.id < b.id else (b, a)
    with first.lock:
        with second.lock:
            ...   # 余额检查与转账逻辑不变
```

**修正后的代码：**

```python
import threading


class Account:
    def __init__(self, aid, balance):
        self.id = aid
        self.balance = balance
        self.lock = threading.Lock()


def transfer(a, b, amount):
    if a is b:
        return False
    first, second = (a, b) if a.id < b.id else (b, a)
    with first.lock:
        with second.lock:
            if a.balance < amount:
                return False
            a.balance -= amount
            b.balance += amount
            return True
```

**解析：**

**原理**：只要所有线程都按同一个全局顺序获取多把锁，等待关系就只能从小号指向大号，不可能形成环，循环等待被破坏，死锁也就不会发生。注意排序只决定加锁顺序，转账方向（从 a 扣款、给 b 入账）保持不变。

**其他可选方案**：
- 用一把全局锁保护所有转账：简单，但完全失去了并发；
- 用带超时的加锁，拿不到第二把锁就释放第一把、随机退避后重试：能打破死锁，但实现复杂，还可能出现活锁。

**测试技巧**：死锁是概率性的，压测未必能复现；测试中用一个记录加锁顺序的锁替身，直接断言加锁顺序，可以确定性地发现问题。

<sub>考点：锁与死锁</sub>

</details>

## 编程题

<a name="CS-OS-015"></a>

### CS-OS-015　进阶 · 考频 ★★★

用 `threading` 的锁与条件变量实现一个线程安全的有界阻塞队列（不得使用 `queue.Queue`）：

```python
class BoundedQueue:
    def __init__(self, capacity: int): ...
    def put(self, item, timeout=None) -> bool: ...
    def get(self, timeout=None): ...
    def __len__(self) -> int: ...
```

- `capacity <= 0` 时抛出 `ValueError`；队列先进先出；
- `put`：队列满时阻塞，直到有空位后放入并返回 `True`；给定 `timeout`（秒）且超时仍满时，返回 `False`；
- `get`：队列空时阻塞，直到有数据后取出并返回；给定 `timeout` 且超时仍空时，抛出 `TimeoutError`；
- 多个生产者、多个消费者并发调用时，数据不丢不重。

<details>
<summary>答案与解析</summary>

**参考实现：**

```python
import threading
from collections import deque


class BoundedQueue:
    def __init__(self, capacity):
        if capacity <= 0:
            raise ValueError("capacity 必须为正")
        self._items = deque()
        self._cap = capacity
        lock = threading.Lock()
        self._not_full = threading.Condition(lock)    # 两个条件变量共用一把锁
        self._not_empty = threading.Condition(lock)

    def put(self, item, timeout=None):
        with self._not_full:
            if not self._not_full.wait_for(lambda: len(self._items) < self._cap, timeout):
                return False                          # 等到超时仍是满的
            self._items.append(item)
            self._not_empty.notify()                  # 唤醒一个等待取数据的消费者
            return True

    def get(self, timeout=None):
        with self._not_empty:
            if not self._not_empty.wait_for(lambda: len(self._items) > 0, timeout):
                raise TimeoutError
            item = self._items.popleft()
            self._not_full.notify()                   # 腾出一个空位
            return item

    def __len__(self):
        with self._not_full:
            return len(self._items)
```

**测试用例：**

```python
import time

q = BoundedQueue(2)
assert q.put("a") and q.put("b") and len(q) == 2
t0 = time.monotonic()
assert q.put("c", timeout=0.05) is False            # 满了：超时返回 False
assert time.monotonic() - t0 >= 0.04
assert q.get() == "a" and q.get() == "b"            # 先进先出
try:
    q.get(timeout=0.05)
    raise AssertionError("空队列应超时")
except TimeoutError:
    pass

q = BoundedQueue(1)                                 # 阻塞的生产者被消费者唤醒
q.put(0)
res = []
th = threading.Thread(target=lambda: res.append(q.put(1, timeout=5)))
th.start()
time.sleep(0.05)
assert q.get() == 0
th.join()
assert res == [True] and q.get() == 1

q = BoundedQueue(3)                                 # 多生产者、多消费者
N, P, C = 300, 3, 2
got = [[] for _ in range(C)]
def producer(p):
    for i in range(N):
        q.put((p, i))
def consumer(c):
    for _ in range(N * P // C):
        got[c].append(q.get(timeout=5))
        assert len(q) <= 3
ts = [threading.Thread(target=producer, args=(p,)) for p in range(P)]
ts += [threading.Thread(target=consumer, args=(c,)) for c in range(C)]
for t in ts: t.start()
for t in ts: t.join()
assert sorted(got[0] + got[1]) == [(p, i) for p in range(P) for i in range(N)]   # 不丢不重
for c in range(C):                                  # 同一生产者的数据保持先后顺序
    for p in range(P):
        seq = [i for pp, i in got[c] if pp == p]
        assert seq == sorted(seq)
try:
    BoundedQueue(0)
    raise AssertionError
except ValueError:
    pass
```

**解析：**

**思路**：
1. 一把锁保护队列，两个条件变量共用这把锁：`not_full` 让生产者等空位，`not_empty` 让消费者等数据；
2. 等待用 `wait_for(条件, timeout)`：内部在循环里检查条件，能正确处理虚假唤醒和被其他线程抢先的情况，超时返回条件的最终取值；
3. 放入后通知 `not_empty`，取出后通知 `not_full`。每次只改变了一个位置，`notify()` 唤醒一个等待者就够了。

**为什么用两个条件变量**：只用一个条件变量时，生产者和消费者在同一个等待队列里，「放入后通知」可能唤醒的是另一个生产者，它检查条件不满足后又睡回去，真正该醒的消费者没有被唤醒。只用一个条件变量就得改用 `notify_all()`，代价是大量无谓的唤醒。

**易错点**：用 `if` 而不是循环检查条件；忘了在超时分支返回；在锁外修改队列；忘了通知另一类等待者，导致对方永远阻塞。

**与大模型应用的联系**：批处理推理的请求队列、限速的任务队列，本质上都是有界队列：队列满时让上游等待或失败，形成背压，防止请求无限堆积。

<sub>考点：信号量与条件变量　｜　出处：Python 文档：threading.Condition</sub>

</details>

## 简答题

<a name="CS-OS-004"></a>

### CS-OS-004　基础 · 考频 ★★★

请比较进程、线程、协程：它们分别是什么的单位，由谁调度，切换开销有多大，各自适合什么场景？以「同时调用几百个大模型 API 并等待返回」为例，说明你会怎么选。

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **进程**：资源分配的单位，拥有独立的虚拟地址空间、文件描述符表等。由内核抢占式调度；切换要换页表、刷新或失效 TLB，开销最大（微秒量级，加上缓存失效的间接开销）。隔离性最好，一个崩溃不影响别人；通信要靠 IPC。适合 CPU 密集且需要绕开 Python GIL 的计算、需要隔离的任务（代码沙箱、浏览器标签页）。
2. **线程**：CPU 调度的单位，同一进程的线程共享内存。由内核抢占式调度；切换要进入内核、保存恢复寄存器，开销在微秒量级，但不换地址空间。通信方便，但要自己同步，有竞态与死锁风险；每个线程有自己的栈（常见默认为 MB 级），线程数难以上万。适合 IO 密集、或需要调用阻塞库的任务。
3. **协程**：用户态的执行单元，由程序自己（事件循环或语言运行时）在等待点主动让出，协作式调度。切换只需保存少量上下文，不进内核，开销远小于线程；一个线程可以跑成千上万个协程。缺点是一个阻塞调用或长时间的计算会卡住同一线程上的所有协程。适合「连接多、大部分时间在等待」的高并发 IO。
4. **选择**：同时等几百个大模型 API 的响应，CPU 基本空闲，瓶颈在等待网络，首选协程（如 asyncio 加异步 HTTP 客户端），用信号量限制并发；如果只有阻塞的 SDK，可以放进线程池；如果拿到结果后还要做大量 CPU 计算，再把计算交给进程池。

**评分要点（共 10 分）：**

- 说清进程是资源分配单位、线程是调度单位、协程是用户态执行单元（3 分）
- 说清三者的调度方式（抢占式与协作式）与切换开销差异的来源（3 分）
- 说出各自的适用场景与主要风险（2 分）
- 对「并发调用大量 API」给出协程为主、合理配合线程池或进程池的选择（2 分）

**讲解：**

**常见失分点**：说「协程是轻量级线程，由内核调度」；说不出切换开销差在哪里（地址空间、内核态、保存的上下文多少）；只给结论不给场景；忽略协程「一处阻塞、全体卡住」的风险。

<sub>考点：进程与线程、协程、上下文切换</sub>

</details>

<a name="CS-OS-016"></a>

### CS-OS-016　进阶 · 考频 ★★

互斥锁、信号量、条件变量有什么区别？各自适合解决什么问题？请结合一个调用大模型 API 的批处理服务举例说明，并说出使用它们时的常见错误。

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **互斥锁（mutex）**：保证同一时刻只有一个线程进入临界区，保护共享数据。有「所有权」，谁加锁谁解锁。例：多个线程更新同一个 token 用量计数器、写同一个结果字典。
2. **信号量（semaphore）**：一个计数器，P 操作减 1（为 0 时阻塞），V 操作加 1；没有所有权，可以由别的线程释放。计数信号量用于限制同时使用某类资源的数量。例：上游 API 限制最多 20 个并发请求，用初值为 20 的信号量包住每次调用。
3. **条件变量（condition variable）**：配合互斥锁使用，让线程在「某个条件不满足」时睡眠，在其他线程改变状态并通知后醒来重新检查。例：工作线程等待「请求队列非空」或「凑够一个批次」，生产者放入请求后通知。
4. **区别小结**：互斥锁回答「谁能进来」；信号量回答「还能进来几个」；条件变量回答「什么时候该醒来」。二值信号量看起来像互斥锁，但没有所有权，也没有优先级继承等机制，不宜替代互斥锁。
5. **常见错误**：
   - 在持锁期间调用大模型 API 等耗时操作，锁被长时间占用，并发退化为串行；
   - 条件变量用 `if` 检查条件，没有用循环，被虚假唤醒或被抢先时出错；
   - 信号量的 P 与 V 不成对（异常路径漏掉 V），名额逐渐泄漏，最后所有请求都卡住，应该用 `with` 语句保证释放；
   - 多把锁的加锁顺序不一致，导致死锁。

**评分要点（共 10 分）：**

- 说清互斥锁的作用与所有权，并给出例子（2 分）
- 说清信号量的计数语义与限制并发的用途，并给出例子（3 分）
- 说清条件变量要配合互斥锁、等待条件的用途，并给出例子（3 分）
- 说出至少两项常见错误（2 分）

**讲解：**

**常见失分点**：把信号量和互斥锁说成一回事；说不出条件变量为什么必须配合锁使用（检查条件与进入等待必须是原子的，否则会丢失通知）；举例脱离场景；忽略「持锁做 IO」这个最常见的性能问题。

<sub>考点：信号量与条件变量、锁与死锁</sub>

</details>

<a name="CS-OS-020"></a>

### CS-OS-020　进阶 · 考频 ★★

请说明五种 IO 模型（阻塞 IO、非阻塞 IO、IO 多路复用、信号驱动 IO、异步 IO）的区别，以及「同步 IO」与「异步 IO」的划分标准；Python asyncio 和 Nginx 用的是哪种？一个需要同时维持上万条 SSE 长连接的大模型网关，为什么适合用 IO 多路复用？

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **两个阶段**：一次读操作要先等待数据就绪（到达内核缓冲区），再把数据从内核拷贝到用户缓冲区。
2. **五种模型**：
   - 阻塞 IO：read 在两个阶段都阻塞，最简单，一个线程只能服务一个连接；
   - 非阻塞 IO：数据没就绪时 read 立即返回 EAGAIN，应用要反复轮询，浪费 CPU；
   - IO 多路复用（select、poll、epoll、kqueue）：一个线程阻塞在 epoll_wait 上同时等待大量 fd，哪个就绪就去读哪个，拷贝阶段仍由应用同步完成；
   - 信号驱动 IO：数据就绪时内核发 SIGIO 信号通知，拷贝阶段仍同步完成，实际很少使用；
   - 异步 IO（POSIX AIO、Windows IOCP、Linux io_uring）：应用提交请求后立即返回，内核完成等待与拷贝，再通知应用。
3. **划分标准**：看第二阶段（真正的数据拷贝）是否由应用线程同步完成。前四种都是同步 IO，只有最后一种是异步 IO。
4. **实际系统**：Nginx 使用非阻塞 socket 加 epoll 的事件驱动模型；Python asyncio 在 Linux 上默认基于 selectors（epoll）实现事件循环，在 Windows 上默认使用基于 IOCP 的 Proactor 事件循环；协程是建立在事件循环之上的编程模型。
5. **为什么适合网关**：上万条 SSE 长连接中，大部分时间在等上游生成下一个 token。若一个连接一个线程，上万个线程的栈内存和上下文切换开销都很大；多路复用让少数几个线程监视全部连接，只处理就绪的那些，开销与活跃连接数成正比。配合协程，代码仍能写成顺序的风格。要注意的是，事件循环线程里不能有阻塞调用或长时间的计算。

**评分要点（共 10 分）：**

- 说清一次 IO 的两个阶段（1 分）
- 准确区分五种模型（4 分）
- 给出同步与异步的划分标准，并指出 epoll 属于同步 IO（2 分）
- 说出 Nginx、asyncio 的模型，并解释多路复用适合大量长连接的原因（3 分）

**讲解：**

**常见失分点**：把非阻塞 IO 和异步 IO 混为一谈；说「epoll 是异步 IO」；说不出两个阶段，导致无法解释划分标准；只背模型名称，不结合「大量空闲长连接」的场景说明选择理由。

<sub>考点：IO模型与多路复用　｜　出处：W. Richard Stevens《UNIX 网络编程》第 6 章</sub>

</details>

## 场景分析题

<a name="CS-OS-028"></a>

### CS-OS-028　挑战 · 考频 ★★

某训练任务在物理机上运行正常。迁移到 Docker 容器后（只映射了 GPU，其他参数都是默认值），DataLoader 一开多个 worker 就报错：`DataLoader worker (pid ...) is killed by signal: Bus error`，并提示可能是共享内存（shm）不足。该任务的配置为：batch size 64，每张图预处理成 3×224×224 的 float32 张量，`num_workers=8`，`prefetch_factor=2`。请解释报错的原因，估算共享内存的需求，并给出解决方案与注意事项。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 原因**
- DataLoader 的每个 worker 是独立的进程。为了避免在进程间拷贝大张量，worker 把产出的 batch 放进共享内存（`/dev/shm`，一个基于内存的 tmpfs 文件系统），队列里只传递句柄，主进程直接映射读取。
- Docker 容器默认有自己的 IPC 命名空间，`/dev/shm` 默认只有 64 MB。共享内存写满后，进程访问超出容量的映射页时会收到 SIGBUS（总线错误），worker 被杀死。物理机上的 `/dev/shm` 通常是物理内存的一半，所以不会出问题。

**2. 估算**
- 每张图：$3\times224\times224\times4=602{,}112$ 字节，约 0.6 MB；
- 每个 batch：$602{,}112\times64\approx38.5$ MB；
- 同时在途的 batch：`num_workers × prefetch_factor` $=8\times2=16$ 个，约 **616 MB**，再加上标签、固定内存缓冲等，远超 64 MB。

**3. 解决方案**
- 调大共享内存：`docker run --shm-size=2g ...`；Kubernetes 中挂载一个 `medium: Memory` 的 emptyDir 卷到 `/dev/shm`，并设置大小上限；
- 或使用 `--ipc=host` 共享宿主机的 IPC 命名空间：简单，但削弱了隔离，多租户环境不推荐；
- 同时评估是否真的需要这么多在途数据：适当减少 `num_workers`、`prefetch_factor`，或者把预处理的输出改为 uint8，到 GPU 上再转为浮点（体积变为四分之一）。

**4. 注意事项**
- tmpfs 中的页占用的是内存，会计入容器的内存限制（cgroup），调大 shm 时内存 limit 也要留出余量，否则会从总线错误变成 OOM；
- 用 `df -h /dev/shm` 在容器内确认配置是否生效；
- 把共享内存需求写进训练任务的资源模板，避免每次迁移都踩坑。

**评分要点（共 10 分）：**

- 说清 DataLoader 通过共享内存在进程间传递张量（2 分）
- 指出容器有独立的 IPC 命名空间、/dev/shm 默认只有 64 MB，写满后触发 SIGBUS（2 分）
- 正确估算在途 batch 的共享内存需求（约 600 MB 量级）（2 分）
- 给出 --shm-size、K8s 内存型 emptyDir、--ipc=host 等方案并说明取舍（2 分）
- 指出 shm 计入容器内存限制等注意事项（2 分）

**讲解：**

**常见失分点**：把总线错误当成 GPU 或驱动问题；只会说「把 num_workers 设为 0」（能绕过，但数据加载会成为瓶颈）；不会估算需求；不知道 shm 的页同样计入内存 cgroup，调大后又引出 OOM。

<sub>考点：进程间通信、容器隔离　｜　出处：PyTorch 文档与 issue 讨论（DataLoader 共享内存）；Docker 文档：docker run --shm-size</sub>

</details>

<a name="CS-OS-031"></a>

### CS-OS-031　挑战 · 考频 ★★

某大模型推理的前处理服务部署在 Kubernetes 中，CPU limit 为 2 核，所在节点是 64 核的物理机。服务启动时按 `os.cpu_count()` 创建了 64 个工作线程，做分词等 CPU 密集的计算（由 C 扩展实现，计算期间释放 GIL）。监控显示：平均 CPU 使用率不到 limit 的 60%，但 P99 延迟频繁出现 80～100 毫秒的毛刺，同时 cgroup 的 `nr_throttled`（被限流的周期数）持续上涨。请分析原因并给出修复方案。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 原因**
- **CFS 带宽控制**：CPU limit 为 2 核，意味着每个调度周期（默认 100 ms）最多使用 200 ms 的 CPU 时间（cgroup v2 的 `cpu.max` 为 `200000 100000`）。配额按整个 cgroup 计算，不限制同时使用多少个核。
- **线程数按宿主机配置**：`os.cpu_count()` 返回的是节点的 64 个逻辑 CPU，不考虑 cgroup 配额，于是开了 64 个线程。请求一来，64 个线程同时在 64 个核上运行，约 $200\div64\approx3.1$ 毫秒就用完了本周期的全部配额，整个容器随后被限流，直到下一个周期开始，最多要等约 97 毫秒，这正是 80～100 毫秒毛刺的来源。
- **平均值的误导**：按秒平均，CPU 使用率并不高，看起来「还有余量」；但在毫秒尺度上，配额被瞬间耗尽，`nr_throttled` 持续上涨就是证据。过多的线程还带来额外的上下文切换和缓存争用。

**2. 修复**
- 按配额设置并发：从 cgroup 读取配额（cgroup v2 的 `cpu.max`，或 v1 的 `cpu.cfs_quota_us` 与 `cpu.cfs_period_us`），或通过环境变量显式配置，把工作线程数设为 2 左右；Python 3.13 起还可以用 `-X cpu_count=2` 或 `PYTHON_CPU_COUNT=2` 覆盖 `os.cpu_count()` 的返回值。
- 同时约束底层库自己的线程池，例如设置 `OMP_NUM_THREADS`，以及数值计算框架的线程数，避免「每个线程里再开 64 个线程」。
- 对延迟敏感的服务，可以让 requests 等于 limits 并设为整数核，配合 kubelet 的静态 CPU 管理策略获得独占的核；也有团队选择只设 requests、不设 CPU limit 来避免限流，但要承担与其他服务争抢 CPU 的风险，需要按集群的整体策略权衡。
- 如果确实需要更多算力，就提高 limit 或水平扩容，而不是靠超额的线程「抢」配额。

**3. 验证**：观察 `nr_throttled` 与限流总时长（`throttled_usec`）是否趋近于 0，P99 延迟毛刺是否消失；压测不同线程数，找到吞吐与延迟的平衡点。

**评分要点（共 10 分）：**

- 说清 CFS 配额按周期计算、64 个线程约 3 毫秒耗尽配额后整个容器被限流（4 分）
- 指出 os.cpu_count() 返回宿主机 CPU 数、不感知 cgroup 配额（2 分）
- 给出按配额设置线程数、约束底层库线程池等修复（2 分）
- 提到独占核或调整 limit 等部署层面的选择，以及用 nr_throttled 验证（2 分）

**讲解：**

**常见失分点**：看到平均 CPU 使用率不高就判断「CPU 不是瓶颈」；只说「把 limit 调大」，没有找到线程数按宿主机配置这个根因；不知道配额是按周期计算的；忽略底层库各自开线程带来的二次放大。

<sub>考点：容器隔离、上下文切换　｜　出处：Linux 内核文档：CFS Bandwidth Control；Python 文档：os.cpu_count、os.process_cpu_count</sub>

</details>
