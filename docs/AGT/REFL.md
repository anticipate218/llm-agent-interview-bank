## 单选题

<a name="AGT-REFL-001"></a>

### AGT-REFL-001　基础 · 考频 ★★★

Self-Refine（Madaan 等, 2023）的核心做法是：

- **A.** 同一个模型循环「生成初稿 → 给出具体反馈 → 按反馈修改」，直到满足停止条件，不涉及训练
- **B.** 训练一个单独的奖励模型给每版输出打分，再用强化学习更新生成模型，让它学会自我修改
- **C.** 让多个不同的模型分别生成答案并互相点评，再投票选出得票最高的答案
- **D.** 把每次任务失败后总结的经验写入长期记忆，供以后遇到相似任务时检索使用

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：Self-Refine 用**同一个模型**扮演三个角色：生成者、反馈者、修改者，循环到模型认为足够好或达到轮数上限。不需要训练、不需要额外模型，论文在对话回复、代码优化等 7 类任务上报告了平均约 20 个百分点的提升。

- B 错：这是 RLHF 一类的训练方法，Self-Refine 不更新任何参数。
- C 错：这是投票或集成，Self-Refine 只有一个模型、一条不断被修改的输出。
- D 错：跨尝试积累经验是 Reflexion（情景记忆）或 ExpeL 一类方法的做法。

<sub>考点：Self-Refine</sub>

</details>

<a name="AGT-REFL-002"></a>

### AGT-REFL-002　基础 · 考频 ★★★

Reflexion（Shinn 等, 2023）被称为「语言强化学习」（verbal reinforcement learning）。在这个框架里，被「更新」的是：

- **A.** 模型参数：把语言反思转换成策略梯度信号，更新生成模型的权重
- **B.** 奖励模型的参数：根据每次尝试的成败信号微调奖励模型
- **C.** 上下文：把语言形式的反思存入情景记忆，下次尝试时放进提示词
- **D.** 解码温度：每次失败后自动调高温度，以增加下一次尝试的探索

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：Reflexion 不做任何梯度更新。它把环境给出的成败信号（往往只是「失败了」这样稀疏的标量）翻译成具体的语言反思，写进情景记忆；下一次尝试时，记忆作为上下文的一部分影响模型的行为，相当于用语言代替了梯度。

- A、B 错：整个过程不训练任何模型。
- D 错：调温度只是碰运气。手撕实验里温度为 0 的「只重试不反思」会原样复现同一份错误代码；模型需要知道**错在哪**才能改对。

<sub>考点：Reflexion、反思记忆</sub>

</details>

<a name="AGT-REFL-003"></a>

### AGT-REFL-003　基础 · 考频 ★★

CRITIC（Gou 等, 2023）与「让模型自己再检查一遍」相比，根本区别在于：

- **A.** 它让参数量更大的模型充当审稿人，逐条检查并批改小模型给出的输出
- **B.** 它借助外部工具（如搜索引擎、代码解释器）验证输出，再据此修改
- **C.** 它把自我检查能力在训练阶段蒸馏进模型，推理时没有额外的调用开销
- **D.** 它对多个采样结果做多数投票，选出彼此最一致的那个答案作为修正结果

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：CRITIC 把反思的依据从「我觉得」换成了「工具告诉我」：事实性问题用搜索引擎找证据，数学程序题用代码解释器执行验算，毒性检测用打分接口，然后根据验证结果修改，可以迭代多轮。

- A 错：验证者仍是同一个模型，并没有换成更大的模型，关键是它借助了工具获得外部信号。
- C 错：CRITIC 是推理时的提示方法，不需要训练，推理时反而要多调用工具和模型。
- D 错：这是 Self-Consistency 的做法。

<sub>考点：CRITIC</sub>

</details>

<a name="AGT-REFL-004"></a>

### AGT-REFL-004　进阶 · 考频 ★★★

Huang 等（2023）的论文《Large Language Models Cannot Self-Correct Reasoning Yet》的主要发现是：

- **A.** 反思轮数增加到 3 轮以上后，LLM 能纠正大部分推理错误，收益随轮数递增
- **B.** LLM 的内在自我纠错在代码任务上无效，但在数学推理上效果显著，能稳定提升准确率
- **C.** 自我纠错失败的根本原因是反思提示词写得不够详细，换更好的提示词即可解决
- **D.** 没有外部反馈时，内在自我纠错在推理任务上不能稳定提升效果，甚至会把对的答案改错

<details>
<summary>答案与解析</summary>

**答案：D**

**解析：**

**结论**：论文研究的是**内在自我纠错**（intrinsic self-correction），即不借助任何外部反馈，只让模型「检查并修改」自己的答案。在数学与常识推理等基准上，修改后准确率不升反降，原本正确的答案会被改错。论文还指出，此前一些工作报告的提升，用到了标准答案来判断「答对了就停止修改」，这在真实场景中拿不到。

- A 错：轮数越多，越可能在对错之间摇摆，还要多花钱。
- B 错：论文的结论针对推理任务，数学推理正是其中之一。
- C 错：问题出在缺少外部信号，同一个模型很难发现自己的推理盲点，靠改提示词解决不了。

**启示**：反思只有在有外部反馈信号（测试、报错、工具返回、环境状态、人的反馈、独立验证器）时才可靠。

<sub>考点：自我纠错局限、外部反馈与内在反思</sub>

</details>

<a name="AGT-REFL-005"></a>

### AGT-REFL-005　进阶 · 考频 ★★★

关于 Self-Refine 与 Reflexion 的区别，下列说法**正确**的是：

- **A.** Self-Refine 在单次任务内打磨同一份输出；Reflexion 凭评估器的成败信号跨尝试积累反思
- **B.** Self-Refine 依赖单元测试等外部评估器的反馈，Reflexion 则只依赖模型自评
- **C.** 两者都要在每轮迭代后用反思内容更新模型参数：Self-Refine 用 SFT，Reflexion 用强化学习
- **D.** Reflexion 主要用于文本写作类任务，Self-Refine 主要用于代码生成类任务

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：两者的反馈来源和作用范围不同。

| 方法 | 反馈从哪来 | 反思存在哪 | 典型场景 |
|---|---|---|---|
| Self-Refine | 同一模型自评 | 本次生成的上下文 | 文风、格式、约束满足 |
| Reflexion | 评估器（测试、环境奖励、规则或 LLM 打分）+ 语言反思 | 情景记忆，跨尝试保留 | 编码、决策等可多次尝试的任务 |

- B 错：恰好说反了。Self-Refine 的反馈来自同一模型；Reflexion 的成败信号来自评估器。
- C 错：两者都不更新参数，都是推理时的方法；Reflexion 的「强化学习」是语言层面的比喻，反思写进情景记忆，跨尝试积累。
- D 错：Reflexion 论文覆盖了决策（ALFWorld）、推理（HotpotQA）和编程（HumanEval）；Self-Refine 的 7 类任务里既有文本也有代码。

<sub>考点：Self-Refine、Reflexion</sub>

</details>

<a name="AGT-REFL-006"></a>

### AGT-REFL-006　进阶 · 考频 ★★

一个「自然语言转 SQL」的 Agent 想加入反思环节来修正错误的查询。下列反馈信号中，最可靠、最适合作为反思依据的是：

- **A.** 让同一个模型逐行复查 SQL，对照表结构判断它「看起来是否正确」，并给出 0～1 的置信度
- **B.** 在只读测试库上实际执行 SQL，检查报错与结果的列、行数，并与已知答案的样例对比
- **C.** 统计 SQL 的长度与 JOIN 数量，超过阈值就判定过于复杂、要求模型重写
- **D.** 追问模型「你确定吗？」，如果它改口就采用新答案，坚持原答案则视为通过

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：执行结果是外部反馈：语法错误、列名不存在会直接报错；结果集的形状与已知样例的对比能暴露逻辑错误。把这些具体信息回填给模型，反思才有抓手。

- A 错：这是内在自我纠错，模型看不出自己的盲点，容易「自我感觉良好」；它给出的置信度同样是自评。
- C 错：长度、JOIN 数量与正确性没有必然联系，属于无关信号。
- D 错：追问「你确定吗」只会让模型在对错之间摇摆，改口不代表改对，甚至可能把对的改错；坚持原答案也不代表答案正确。

注意：执行要在只读账号、隔离的测试库上进行，并限制执行时间和返回行数。

<sub>考点：验证器、外部反馈与内在反思</sub>

</details>

<a name="AGT-REFL-007"></a>

### AGT-REFL-007　挑战 · 考频 ★★

在 Reflexion 式的编码 Agent 中，团队让模型先为题目自动生成单元测试，再把这些测试作为评估器驱动反思和重写。下列哪种情况最可能出现？

- **A.** 自生成测试由模型批量产出、数量远超人写的测试，覆盖更全面，可以替代隐藏测试来评估最终效果
- **B.** 代码与测试出自同一个模型、理解一致，代码基本能通过自己的测试，反思很少被触发
- **C.** 测试本身可能写错：错误的期望值会诱导模型把正确代码「改错」，遗漏边界的测试又会放过 bug
- **D.** 每条失败的自生成测试会各自产生一条反思，记忆随测试数量快速增长，最终撑爆上下文

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：评估器的质量决定了反思的上限。自生成测试有两类错误：

- **假阴性**（测试写错）：期望值算错，正确代码被判失败，模型被迫去「修」一个不存在的 bug，越改越错；
- **假阳性**（测试太弱）：没覆盖空输入、负数、重复元素等边界，有 bug 的代码也能通过。

Reflexion 论文也讨论了自生成测试的误判问题。对策：测试与代码分开生成（甚至用不同的模型或提示词）；关键用例由人提供或从需求中抽取；用多组测试交叉验证；在隐藏测试或人工抽检上评估最终效果。

- A 错：数量多不等于覆盖全。生成的测试同样依赖模型的理解，它对题意的误解会同时体现在代码和测试里。
- B 错：同一个模型写的代码和测试并不总是一致，代码经常通不过自己写的测试，反思会被频繁触发。
- D 错：记忆条数由实现控制（论文中通常只保留 1～3 条），与测试的来源无关。

<sub>考点：验证器、自我纠错局限</sub>

</details>

<a name="AGT-REFL-008"></a>

### AGT-REFL-008　基础 · 考频 ★★★

下列哪些可以作为反思所依据的**外部反馈信号**？

- **A.** 单元测试的运行结果
- **B.** 同一个模型在同一提示下，对自己的答案「再检查一遍」得出的结论
- **C.** 环境状态，例如网页是否跳转到了订单完成页
- **D.** 用户或人工审核员的反馈
- **E.** 编译器或解释器的报错信息

<details>
<summary>答案与解析</summary>

**答案：ACDE**

**解析：**

**结论**：A、C、D、E 都来自模型之外，是可靠的反思依据。

- A、E 对：测试与报错是编码类任务最常用的信号，Reflexion 在编程任务上就依赖测试结果。
- B 错：这是内在反思，没有引入任何新信息。研究表明它在推理任务上不能稳定纠错，甚至会把对的改错。
- C 对：环境状态是 Agent 的「地面真相」，能直接告诉模型动作是否生效。
- D 对：人的反馈质量高但成本也高，适合高风险环节或作为最终把关。

此外，搜索结果、代码执行结果等工具返回（CRITIC 的做法），以及独立训练的验证器、规则检查，也都属于外部信号。

<sub>考点：外部反馈与内在反思、验证器</sub>

</details>

<a name="AGT-REFL-009"></a>

### AGT-REFL-009　进阶 · 考频 ★★

关于 Reflexion 的组成与机制，下列说法**正确**的有：

- **A.** 情景记忆会保留全部历史反思，以便积累尽可能多的经验
- **B.** 评估器可以是单元测试、环境奖励、规则检查，也可以是 LLM 打分
- **C.** 每次尝试失败后，Reflexion 会用失败轨迹对模型做一次轻量微调
- **D.** 执行者（Actor）生成动作或代码，评估器（Evaluator）给出成败或打分
- **E.** 自我反思模块把稀疏的成败信号翻译成具体的语言反馈：哪里错了、下次怎么做

<details>
<summary>答案与解析</summary>

**答案：BDE**

**解析：**

**结论**：B、D、E 正确。Reflexion 由执行者、评估器、自我反思、情景记忆四部分组成。

- A 错：论文中情景记忆只保留最近的少量反思（通常 1～3 条），否则上下文膨胀，旧的、可能已不相关的教训还会干扰判断。
- B 对：评估器越可靠，效果越好；用 LLM 打分时要警惕它与执行者有相同的盲点。
- C 错：Reflexion 不更新参数，被「更新」的是上下文。
- D 对：执行者负责「做」，评估器负责「判」。
- E 对：这是 Reflexion 的核心。反思要具体到下一步的动作（「先排序再取中位数」），「下次要更仔细」这种反思没有用。

<sub>考点：Reflexion</sub>

</details>

<a name="AGT-REFL-010"></a>

### AGT-REFL-010　进阶 · 考频 ★★

把反思得到的经验写入记忆（无论是单任务内的情景记忆，还是跨任务复用的长期记忆）时，下列哪些是需要防范的风险？

- **A.** 记忆无限增长，挤占上下文、冲淡关键信息
- **B.** 从不可信内容（网页、邮件、工具输出）中提炼出的「经验」夹带恶意指令
- **C.** 错误的教训被写入记忆，污染后续任务
- **D.** 记忆只保存反思、不保存旧版本的完整代码，导致模型无法改进
- **E.** 环境或规则变化后，过时的经验仍在生效

<details>
<summary>答案与解析</summary>

**答案：ABCE**

**解析：**

**结论**：A、B、C、E 是真实风险；D 恰恰是推荐的做法。

- A 对：限制条数，或把多条经验合并成更一般的规则。
- B 对：这是记忆投毒。一次注入被写进长期记忆，就可能在以后的任务中持续生效，要把外部内容当作数据，写入记忆前做过滤与审核。
- C 对：评估器误判（如测试写错）会产生错误教训，写进长期记忆后会在之后的任务中反复误导。写入前最好经过验证，并记录来源以便追溯和删除。
- D 错：记忆里只存精炼的反思而不存整段旧代码，正是为了控制上下文长度；需要时可以另存全文、在上下文里只放指针。
- E 对：经验要带上适用条件和时间，定期清理或在冲突时以最新信息为准。

<sub>考点：反思记忆</sub>

</details>

<a name="AGT-REFL-011"></a>

### AGT-REFL-011　进阶 · 考频 ★★

关于 CRITIC，下列说法**正确**的有：

- **A.** 论文的对比实验表明，去掉工具、只让模型自我批评，也能取得与使用工具相当的提升
- **B.** 只要用了工具，验证结论就一定正确，不需要关心工具的覆盖面和可靠性
- **C.** 对开放式问答，用搜索引擎检索证据来核对答案中的事实
- **D.** 对数学程序类任务，用代码解释器执行程序，根据运行结果和报错来修正
- **E.** CRITIC 需要先用工具交互数据微调模型，才能学会验证

<details>
<summary>答案与解析</summary>

**答案：CD**

**解析：**

**结论**：C、D 正确。CRITIC 的流程是「生成 → 借助工具验证并给出批评 → 依据批评修改」，可迭代多轮。

- A 错：论文的消融结论正好相反：去掉工具、只让模型自我批评（CRITIC w/o Tool）时，提升很有限，在部分任务上还会变差。同样的「批评 - 修改」流程，没有工具提供的新信息就难以奏效，这正说明了**外部反馈**的关键作用。
- B 错：工具也会出错或覆盖不到：搜索可能返回过时或错误的网页，代码执行只能验证能被写成程序的部分。CRITIC 的效果受限于工具的覆盖面和可靠性。
- C、D 对：这是论文中的两类典型任务；此外还用毒性打分接口来降低输出的毒性。
- E 错：CRITIC 不需要训练，靠少样本提示让模型学会调用工具并据此批评。

<sub>考点：CRITIC、外部反馈与内在反思</sub>

</details>

## 判断题

<a name="AGT-REFL-012"></a>

### AGT-REFL-012　基础 · 考频 ★★★

## 填空题

<a name="AGT-REFL-015"></a>

### AGT-REFL-015　进阶 · 考频 ★★

某生成器单次答对的概率为 0.5。用一个验证器把关：对正确答案判「通过」的概率为 0.9，对错误答案误判「通过」的概率为 0.2。系统只生成一次，只交付通过验证的答案（不通过则转人工）。交付率为 ____（保留两位小数）；在被交付的答案中，真正正确的比例约为 ____（保留两位小数）。

<details>
<summary>答案与解析</summary>

**答案：** (1) 0.55 / 55%；(2) 0.82 / 82%

**解析：**

**计算**：

- 交付率：$P(\text{通过})=0.5\times0.9+0.5\times0.2=0.45+0.10=0.55$；
- 交付答案中正确的比例：$P(\text{正确}\mid\text{通过})=\dfrac{0.45}{0.55}\approx0.82$。

**解读**：验证器把交付答案的正确率从 0.5 提升到约 0.82，代价是 45% 的请求要转人工。验证器的**误放行率**（对错误答案判通过的概率）决定了交付质量的上限：若它降到 0.05，正确比例变为 $0.45/0.475\approx0.95$。设计验证器时，要分别评估它对正确答案和错误答案的判别能力，而不是只看一个「准确率」。

<sub>考点：验证器</sub>

</details>

## 计算题

<a name="AGT-REFL-021"></a>

### AGT-REFL-021　挑战 · 考频 ★★

一个编码 Agent 每次独立生成一份代码，正确的概率为 0.4。用验证器把关：正确代码以 0.9 的概率通过，错误代码以 0.1 的概率被误判通过。流程是：生成 → 验证，通过就交付；不通过就重新生成，最多尝试 3 次，3 次都不通过则转人工。

1. 分别求最终「交付了正确代码」「交付了错误代码」「转人工」的概率；
2. 交付的代码中正确的比例是多少？
3. 若验证器是完美的（正确必过、错误必拒），三种结果的概率又是多少？

<details>
<summary>答案与解析</summary>

**答案：交付正确约 0.690，交付错误约 0.115，转人工约 0.195；交付代码的正确率约 0.857；完美验证器下分别为 0.784、0、0.216**

**解析：**

**单次尝试的三种结果**：

- 通过且正确：$a=0.4\times0.9=0.36$；
- 通过但错误：$b=0.6\times0.1=0.06$；
- 未通过：$r=1-a-b=0.58$。

**最多 3 次**：第 $i$ 次才通过的概率是 $r^{i-1}$ 乘以对应结果的概率。

1. 交付正确：$a(1+r+r^2)=0.36\times(1+0.58+0.3364)=0.36\times1.9164\approx0.690$；
   交付错误：$b(1+r+r^2)=0.06\times1.9164\approx0.115$；
   转人工：$r^3=0.58^3\approx0.195$。三者之和为 1。
2. 交付代码的正确率：$\dfrac{a}{a+b}=\dfrac{0.36}{0.42}\approx0.857$，与尝试次数无关。
3. 完美验证器：交付正确 $=1-0.6^3=0.784$，交付错误 $=0$，转人工 $=0.6^3=0.216$。

**启示**：重试让「交付正确」从单次的 0.4 提高到约 0.69，但每多一次尝试，错误代码也多一次「混过去」的机会：交付错误的概率从单次的 0.06 涨到约 0.115。交付质量的上限由验证器的误放行率决定，降低误放行率比增加重试次数更重要。

<sub>考点：验证器、外部反馈与内在反思</sub>

</details>

## 代码输出题

<a name="AGT-REFL-022"></a>

### AGT-REFL-022　进阶 · 考频 ★★

下面用确定性的假模型模拟 Reflexion：`actor` 只有在记忆里看到对应教训时才会修复相应的 bug；每次失败只针对**第一个**失败项写一条反思；`window` 是情景记忆最多保留的条数（0 表示不反思、只重试）。输出是什么？

```python
def actor(memory):
    code = "sorted(xs)" if any("排序" in m for m in memory) else "xs"
    return f"median_even({code})" if any("偶数" in m for m in memory) else f"median_odd({code})"

def evaluate(sol):
    return [msg for ok, msg in [("sorted" in sol, "无序输入失败"),
                                ("even" in sol, "偶数个元素失败")] if not ok]

LESSON = {"无序输入失败": "先排序再取中位数", "偶数个元素失败": "偶数个时取中间两数的平均"}

def run(window, max_trials=4):
    memory = []
    for t in range(1, max_trials + 1):
        sol = actor(memory)
        fails = evaluate(sol)
        if not fails:
            return t, sol
        if window:
            memory = (memory + [LESSON[fails[0]]])[-window:]
    return None, sol

print(run(1))
print(run(3))
print(run(0))
```

<details>
<summary>答案与解析</summary>

**答案（程序输出）：**

```text
(None, 'median_odd(sorted(xs))')
(3, 'median_even(sorted(xs))')
(None, 'median_odd(xs)')
```

**解析：**

**window=1**：记忆只留最新一条。

- 第 1 次 `median_odd(xs)`，两项都失败，记下「先排序」；
- 第 2 次 `median_odd(sorted(xs))`，偶数项失败，记下「偶数……」，「先排序」被挤掉；
- 第 3 次 `median_even(xs)`，又忘了排序；第 4 次又忘了偶数。在两个 bug 之间来回振荡，4 次用完返回 `None`。

**window=3**：第 3 次时记忆里同时有两条教训，生成 `median_even(sorted(xs))`，全部通过。

**window=0**：不反思，温度为 0 的假模型每次给出同一份错误代码。

**启示**：情景记忆太小会「学了新的忘了旧的」，造成振荡；不反思的重试则原样复现错误。Reflexion 论文中记忆通常保留 1～3 条，具体取值要结合任务需要同时满足的约束数量来定，也可以把多条教训合并成一条更完整的经验。

<sub>考点：Reflexion、反思记忆</sub>

</details>

## 代码改错题

<a name="AGT-REFL-023"></a>

### AGT-REFL-023　进阶 · 考频 ★★

下面是一个 Reflexion 循环：`actor(memory)` 根据记忆生成一个函数，`run_tests` 用测试用例评估它，失败时 `reflect` 写一条反思放进记忆再重试。用它修复「求平均值」函数时，第一次生成的代码对空列表会抛出 `ZeroDivisionError`，结果整个循环直接崩溃，根本没有机会反思。请修正。

```python
def run_tests(fn, tests):
    """返回失败用例列表：(参数, 期望, 实际)"""
    fails = []
    for args, want in tests:
        got = fn(*args)
        if got != want:
            fails.append((args, want, got))
    return fails

def reflexion(actor, reflect, tests, max_trials=3):
    memory = []
    for trial in range(1, max_trials + 1):
        fn = actor(memory)
        fails = run_tests(fn, tests)
        if not fails:
            return trial, memory
        memory = (memory + [reflect(fails)])[-3:]
    return None, memory
```

<details>
<summary>答案与解析</summary>

**答案：**

**问题**：`run_tests` 直接调用 `fn(*args)`，被测代码抛出的异常一路传到 `reflexion` 外面，循环崩溃。评估器把「代码运行报错」当成了系统故障，而不是一条反馈。

**修正**：在评估器里捕获被测代码的异常，把「异常类型 + 信息」作为该用例的实际结果记入失败列表：

```python
try:
    got = fn(*args)
except Exception as e:
    got = f"{type(e).__name__}: {e}"
```

这样反思模块就能写出「输入 [] 时抛出 ZeroDivisionError：空列表应返回 0.0」，第二次生成即可修复。

**修正后的代码：**

```python
def run_tests(fn, tests):
    """返回失败用例列表：(参数, 期望, 实际)"""
    fails = []
    for args, want in tests:
        try:
            got = fn(*args)
        except Exception as e:                 # 运行错误也是反馈，转成失败记录
            got = f"{type(e).__name__}: {e}"
        if got != want:
            fails.append((args, want, got))
    return fails

def reflexion(actor, reflect, tests, max_trials=3):
    memory = []
    for trial in range(1, max_trials + 1):
        fn = actor(memory)
        fails = run_tests(fn, tests)
        if not fails:
            return trial, memory
        memory = (memory + [reflect(fails)])[-3:]
    return None, memory
```

**解析：**

在 Agent 与反思系统里，**错误即观察**：工具报错、代码异常、测试失败都应转成结构化的反馈回填，而不是让异常中断循环。报错信息往往是最具体、最可靠的外部信号，正是 Reflexion 这类方法赖以工作的依据。

生产中还要注意：被测代码是模型生成的不可信代码，应在沙箱中执行，并设置超时（防止死循环卡住评估器）和资源限制。

<sub>考点：Reflexion、外部反馈与内在反思</sub>

</details>

## 简答题

<a name="AGT-REFL-017"></a>

### AGT-REFL-017　进阶 · 考频 ★★★

Reflexion 的核心思想是什么？由哪几部分组成？它和 Self-Refine 有什么不同？

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **核心思想**：面向可以反复尝试的任务，把失败翻译成语言形式的反思，存进情景记忆，下次尝试时带上。不更新任何参数，被「更新」的是上下文，所以被称为「语言强化学习」。
2. **四个组成部分**：
   - 执行者（Actor）：生成动作或代码；
   - 评估器（Evaluator）：给出成败或打分，如单元测试、环境奖励、规则或 LLM 打分；
   - 自我反思（Self-Reflection）：把稀疏的成败信号变成具体的语言反馈（哪里错了、下次怎么做）；
   - 情景记忆：只保留最近几条反思（论文中通常 1～3 条），放进下次尝试的提示词。
3. **效果**：论文报告在 HumanEval 上 pass@1 达到 91%，超过当时 GPT-4 的 80%。
4. **与 Self-Refine 的区别**：Self-Refine 在**一次生成内**用同一模型自评自改，适合文风、格式、约束满足；Reflexion **跨多次尝试**积累教训，依赖评估器提供的外部成败信号，适合编码、决策等可重试的任务。
5. **注意**：反思要具体可执行；评估信号的质量决定上限，用模型自己生成的测试当评估器时，测试本身可能写错。

**评分要点（共 10 分）：**

- 说清「失败 → 语言反思 → 情景记忆 → 带着反思重试」的核心机制，指出不更新参数（3 分）
- 列出四个组成部分及职责（3 分）
- 说明与 Self-Refine 在反馈来源、作用范围上的区别（3 分）
- 提到反思要具体或评估信号质量的影响（1 分）

**讲解：**

**常见失分点**：把 Reflexion 说成一种微调方法；说不出评估器的作用，把它和 Self-Refine 混为一谈；不知道记忆条数有限。追问「对照实验说明了什么」时，要能说出：只重试不反思，温度为 0 的模型会原样复现同一个错误；只自评不跑测试，发现不了边界 bug。

<sub>考点：Reflexion、Self-Refine</sub>

</details>

<a name="AGT-REFL-018"></a>

### AGT-REFL-018　进阶 · 考频 ★★★

让大模型自我反思、自我纠错一定有用吗？请说明它在什么情况下可靠、在什么情况下靠不住，以及没有可执行的验证手段时应该怎么办。

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **不一定有用**：Huang 等（2023）发现，没有外部反馈的内在自我纠错在推理任务上不能稳定提升，甚至会把对的答案改错；一些早期工作报告的提升依赖用标准答案决定何时停止修改。
2. **为什么靠不住**：同一个模型有同样的盲点；被要求「检查」时，倾向于要么一律说没问题，要么为了改而改；没有新信息进入，反思只是「再想一遍」。
3. **什么时候可靠**：有外部反馈信号时，例如单元测试、编译和运行报错、工具返回（搜索、代码执行，即 CRITIC 的做法）、环境状态、人的反馈、独立的验证器。Reflexion 依赖评估器的成败信号，评估者-优化者也要求评估标准清晰。
4. **适合内在反思的场景**：文风、格式、是否覆盖要点等约束满足类问题，模型能看出来，风险也低。
5. **没有可执行验证时**：用规则检查格式和硬约束；用不同的提示词或不同的模型做独立评审；对高风险输出交给人审；同时设轮数上限，并离线对比「反思前后」的效果，确认反思真的有收益。

**评分要点（共 10 分）：**

- 明确指出没有外部反馈的自我纠错在推理上不可靠，并给出依据（3 分）
- 解释原因：缺少新信息、同源盲点（2 分）
- 列举可靠的外部信号，并说明适合内在反思的场景（3 分）
- 给出无可执行验证时的替代方案（2 分）

**讲解：**

**常见失分点**：认为「多反思几轮总没坏处」；把 CRITIC 这类借助工具的方法也归为内在反思；只说「不可靠」而给不出替代方案。好的回答能区分三件事：反思的形式（让模型写批评）、反馈的来源（模型自己还是外部）、以及效果如何验证。

<sub>考点：自我纠错局限、外部反馈与内在反思</sub>

</details>

<a name="AGT-REFL-019"></a>

### AGT-REFL-019　挑战 · 考频 ★★

在反思与自我改进的系统里，「验证器」扮演什么角色？常见的验证器有哪些，各自的优缺点是什么？设计验证器时要注意哪些问题？

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **角色**：验证器提供外部反馈信号，决定「要不要改、改哪里、何时停」。它的质量决定了反思的上限：验证器错了，反思只会朝错误的方向努力。
2. **常见类型**：

   | 类型 | 例子 | 优点 | 缺点 |
   |---|---|---|---|
   | 执行类 | 单元测试、编译器、SQL 在测试库执行 | 客观、可复现 | 只覆盖能执行的部分；测试本身可能写错或太弱 |
   | 规则类 | 格式与 Schema 校验、正则、业务约束 | 便宜、确定 | 只能查硬约束，查不了语义 |
   | 工具类 | 搜索核对事实、调用计算器 | 引入新信息 | 受工具覆盖面与来源可靠性限制 |
   | 模型类 | LLM 评审、训练好的验证器或奖励模型 | 能评语义和质量 | 有偏差、可能被「讨好」；与生成者同源时盲点相同 |
   | 人工 | 审核员、用户反馈 | 质量最高 | 慢、贵、难以规模化 |

3. **设计要点**：
   - 分别衡量对正确答案的通过率和对错误答案的误放行率，后者决定交付质量；
   - 利用「验证比生成容易」的任务特性（如代码可以跑测试），优先用可执行的验证；
   - 验证器与生成者尽量独立（不同提示词、不同模型、或由人提供关键用例）；
   - 防止过拟合：反复对着可见的测试修改，可能只是「刷过」测试，要留出隐藏测试或人工抽检；
   - 成本与时延：多层验证时，先跑便宜的规则，再跑昂贵的模型评审。

**评分要点（共 10 分）：**

- 说明验证器决定反思上限的作用（2 分）
- 列出至少四类验证器并给出优缺点（4 分）
- 提到误放行率、独立性、防过拟合等设计要点中的至少两项（3 分）
- 提到成本分层或「验证比生成容易」的利用（1 分）

**讲解：**

**常见失分点**：只说「用 LLM 评审」；忽略验证器自身的错误；不区分误放行与误拒绝；没有意识到反复优化可见测试会过拟合。能结合具体业务（代码、SQL、问答）说明选哪种验证器，是加分项。

<sub>考点：验证器</sub>

</details>

<a name="AGT-REFL-020"></a>

### AGT-REFL-020　挑战 · 考频 ★★

如果要让 Agent 把反思得到的经验保存下来、在后续尝试或后续任务中复用，你会如何设计这套「反思记忆」？请说明存什么、存多少、何时读取、如何更新与清理，以及主要风险。

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **存什么**：精炼、可执行的教训，而不是整段轨迹或旧代码。例如「取中位数前先排序；偶数个元素取中间两数的平均」。每条经验带上元数据：适用的任务类型或条件、来源（哪次失败、哪个评估信号）、时间、被验证有效的次数。
2. **存多少**：单任务内的情景记忆只保留最近几条（Reflexion 通常 1～3 条）；跨任务的长期经验要去重、合并成更一般的规则，并设总量上限。
3. **何时读取**：任务开始时按任务类型或语义检索相关经验，只注入少量最相关的条目；同一任务重试时带上本任务的反思。
4. **如何更新与清理**：新经验与旧经验冲突时以经过验证的、更新的为准；经验被使用后跟踪效果，长期无效或导致失败的予以降权或删除；规则或环境变化时批量失效。跨任务提炼经验的做法可参考 ExpeL 一类方法。
5. **主要风险与对策**：
   - 错误教训（评估器误判导致）：写入前要求有可靠的外部信号支持，保留来源以便追溯和回滚；
   - 记忆投毒：不从不可信内容中直接提炼经验，写入前过滤与审核；
   - 上下文膨胀与干扰：限制条数，只注入相关经验；
   - 隐私：经验中不保存用户敏感数据，按租户隔离。

**评分要点（共 10 分）：**

- 存精炼可执行的教训并附元数据（2 分）
- 限制条数、去重合并（2 分）
- 说明读取时机与相关性检索（2 分）
- 说明冲突处理、效果跟踪与清理（2 分）
- 指出错误教训、记忆投毒等风险及对策（2 分）

**讲解：**

**常见失分点**：把所有轨迹原样塞进记忆；只增不删；不区分单任务的情景记忆与跨任务的长期记忆；忽视错误教训和投毒带来的持续性危害。记忆系统的通用设计（分层、检索、遗忘）属于记忆与上下文工程的话题，这里的重点是「反思产生的经验」如何保证质量。

<sub>考点：反思记忆</sub>

</details>

## 场景分析题

<a name="AGT-REFL-024"></a>

### AGT-REFL-024　挑战 · 考频 ★★

某在线数学辅导产品原本直接用大模型解题，离线评测准确率 82%。为了「更可靠」，团队加了一个自检步骤：模型给出答案后，再提示它「请仔细检查你的解答，如有错误请改正」，以修改后的答案为准。上线后离线准确率反而降到 78%。抽样发现，有不少原本正确的答案在自检后被改错，而原本错误的答案只有少数被改对。请分析原因，并给出改进方案。

<details>
<summary>答案与解析</summary>

**参考答案：**

**原因分析**：

1. **内在自我纠错不可靠**：自检没有引入任何新信息，同一个模型在同一套知识下重新审视，发现不了自己的盲点（Huang 等, 2023 的结论）。
2. **提示带有暗示**：「如有错误请改正」容易被理解为「大概率有错」，模型倾向于做出修改，把对的改错。
3. **以修改结果为准的策略不当**：无论改得对不对都采用新答案，「改对」的收益小于「改错」的损失，准确率自然下降。
4. **评测方式**：上线前没有分别统计「对改错」和「错改对」的比例，只看了直觉。

**改进方案**：

1. **引入外部验证**：让模型把解题过程写成可执行的计算（代码或算式），用解释器验算（CRITIC、程序辅助推理的思路）；把答案代回原题检查是否满足条件；对有标准形式的题目做规则校验（单位、取值范围）。
2. **只在有证据时修改**：验证发现矛盾时，把具体的矛盾（「代入后等式不成立」）回填给模型再修正；验证通过就保留原答案。
3. **用多样性代替自检**：对把握不大的题采样多条解法做 Self-Consistency 投票，或用不同的模型独立求解，结果一致才直接交付。
4. **不确定时降级**：多种方法结论不一致时，向学生说明「这一步还需要确认」，或转人工老师，不要给出不确定的答案。
5. **评测**：按「对改错」「错改对」「不变」三类统计每个策略的效果；监控修改率和修改后的准确率，确认新流程整体有正收益再上线。

**评分要点（共 10 分）：**

- 指出内在自我纠错缺少外部信息、同源盲点这一根因（3 分）
- 指出提示暗示与「一律采用修改结果」的策略问题（2 分）
- 提出引入外部验证（代码验算、代回检验等）并只在有证据时修改（3 分）
- 提出多样化求解、降级或转人工等方案（1 分）
- 提出区分「对改错」与「错改对」的评测方法（1 分）

**讲解：**

**常见失分点**：认为「多检查一遍总比不检查好」；只建议「把自检提示写得更好」；不知道应当分别统计改对和改错。这道题的本质是：反思要依赖外部反馈信号，数学题恰好有天然的外部验证手段（执行计算、代回原题），应当优先利用。

<sub>考点：自我纠错局限、外部反馈与内在反思、验证器</sub>

</details>

<a name="AGT-REFL-025"></a>

### AGT-REFL-025　挑战 · 考频 ★★

团队用 Reflexion 思路做了一个编程题求解 Agent：模型先根据题目自动生成 5 个单元测试，再写代码，跑自己生成的测试，失败就反思重写，最多 4 轮；每次反思还会写入一个跨题目共享的「经验库」，供后续题目参考。上线评测发现：

1. 很多题在自生成测试上全部通过，提交到隐藏测试却失败；
2. 有些题第一版代码其实是对的，却因为自生成测试「失败」被改错了；
3. 经验库里出现了「输出必须按降序排列」这类只适用于个别题目的教训，导致后续不相关的题目也照做。

请分析原因，并提出改进方案。

<details>
<summary>答案与解析</summary>

**参考答案：**

**原因分析**：

1. **评估器太弱（假阳性）**：自生成测试只覆盖模型想到的情况，与代码出自同一个理解，题意误解会同时体现在测试和代码里，边界条件也常被一起遗漏。
2. **评估器出错（假阴性）**：测试的期望值写错时，正确代码被判失败，反思被迫去「修复」不存在的 bug，把对的改错。
3. **经验库污染**：反思是在错误或局部的信号上产生的，又没有标注适用条件、没有经过验证就写入共享记忆，变成了误导后续任务的「错误教训」。

**改进方案**：

1. **提高评估信号质量**：
   - 优先使用题目给出的样例作为必须通过的测试，自生成测试只作补充；
   - 测试与代码分开生成，甚至用不同的提示词或模型；对自生成测试的期望值做交叉验证（例如用暴力解法对拍）；
   - 测试失败时先判断「测试错还是代码错」：多份独立实现都与某个测试期望不符时，优先怀疑测试。
2. **控制修改**：只有在有可靠失败证据时才重写；保留历次版本，按通过的高置信测试数选择最优版本，而不是机械地采用最后一版。
3. **经验库治理**：
   - 写入门槛：只有被最终的隐藏测试或人工确认有效的教训才进入共享经验库；
   - 每条经验标注适用条件（题型、约束）、来源与有效次数，检索时只注入相关经验；
   - 定期评估经验的效果，无效或有害的予以删除。
4. **评测**：在留出的隐藏测试集上衡量最终通过率；单独统计「对改错」比例、自生成测试的误判率，以及经验库注入前后的效果差异。

**评分要点（共 10 分）：**

- 识别自生成测试的假阳性问题（测试太弱、与代码同源）（2 分）
- 识别测试写错导致把对的改错（2 分）
- 识别经验库被错误或局部教训污染（2 分）
- 提出提升评估信号质量与控制修改的措施（2 分）
- 提出经验库的写入门槛、适用条件与清理机制，以及相应评测（2 分）

**讲解：**

**常见失分点**：把问题归咎于「反思轮数不够」而增加轮数；没有意识到评估器本身会出错；只处理当前题目、忽视共享经验库的长期污染。核心结论是：Reflexion 的效果上限由评估信号决定，写进记忆的东西必须比当场的反思经过更严格的验证。

<sub>考点：验证器、Reflexion、反思记忆</sub>

</details>
