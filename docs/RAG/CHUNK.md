## 单选题

<a name="RAG-CHUNK-001"></a>

### RAG-CHUNK-001　基础 · 考频 ★★

双栏排版的论文 PDF，如果用不做版面分析的工具直接抽取文本，**最典型**的问题是：

- **A.** PDF 中的文字全部变成图片，必须经过 OCR 才能读取
- **B.** 左右两栏的文字按行交错拼接，句子被打乱，切出的块语义混乱
- **C.** 抽取出的中文全部变成乱码，必须更换文件编码
- **D.** 公式与参考文献被自动删除，正文信息不完整

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：多栏排版最典型的问题是**阅读顺序错乱**。不少抽取工具（尤其是按坐标从上到下排列文本行的）会把左栏第 1 行和右栏第 1 行拼在一起，句子被拦腰拼接，后续的切块、向量化都建立在错乱的文本上。

对策：先做版面分析（layout analysis），识别栏、标题、段落、表格、图片区域，再按阅读顺序重组；同时去掉页眉页脚和页码。

- A 错：只有扫描件（图片型 PDF）才需要 OCR，论文 PDF 通常带有文本层。
- C 错：个别字体缺少字符映射时可能出现乱码，但这不是双栏排版特有的问题。
- D 错：抽取工具一般不会「自动删除」公式和参考文献；常见的问题反而是公式被抽成一堆零散符号、参考文献混进正文。

<sub>考点：文档解析</sub>

</details>

<a name="RAG-CHUNK-003"></a>

### RAG-CHUNK-003　基础 · 考频 ★★★

一份产品价格表（20 行 × 6 列，列为型号、价格、保修期等）被直接抽成纯文本后入库。用户问「X200 的保修期是多久」时，系统经常答成别的型号的保修期。最可能的原因和改进方法是：

- **A.** 表格块太短、语义信号弱，应把表格与前后三页正文合并成一个大块再入库，补足上下文
- **B.** Embedding 模型不擅长处理数字和型号，应在入库前删除表格中的数字，只保留文字描述
- **C.** 纯文本抽取丢失了行列对应关系，应转成 Markdown 表格，或把每行线性化成带列名的句子
- **D.** 应把表格按每 50 个字符固定切开，让每个单元格更容易被单独命中，提高检索粒度

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：表格的信息藏在「行与列的对应关系」里。纯文本抽取后，单元格变成一串用空格隔开的值，模型看不出「2 年」属于哪一行，于是张冠李戴。

- 改进一：转成 Markdown/HTML 表格，保留结构，小表格整体作为一块；
- 改进二：按行线性化，每行变成一句带列名的完整描述（如「型号：X200；价格：…；保修期：…」），可以单独检索，问某个型号时能精确命中那一行；
- 大表格还可以额外生成一段摘要用于召回，命中后把原表（或相关行加表头）交给模型。

逐项点评：
- A 错：合并更多正文只会稀释表格内容，行列关系依然缺失。
- B 错：数字正是用户要问的内容，删掉就无从回答。
- D 错：固定字符切分会把同一行拆进不同的块，行列关系丢得更彻底。

<sub>考点：文档解析、多模态文档</sub>

</details>

<a name="RAG-CHUNK-005"></a>

### RAG-CHUNK-005　基础 · 考频 ★★★

固定长度切块（每 N 个 token 切一刀）最主要的缺点是：

- **A.** 实现复杂，需要先训练一个切分模型
- **B.** 块的长度不可控，容易超过 Embedding 模型的最大输入长度
- **C.** 每切一块都要调用一次 LLM，离线成本很高
- **D.** 不看语义边界，常把句子、表格或代码拦腰截断

<details>
<summary>答案与解析</summary>

**答案：D**

**解析：**

**结论**：固定长度切块只按长度切，完全不看内容边界。

- A 错：它是最简单的切法，几行代码就能实现，适合作为快速基线。
- B 错：恰恰相反，它的块长度最可控，按 Embedding 模型的上限设置 N 即可。
- C 错：它不需要任何模型调用。需要 LLM 的是 Contextual Retrieval 这类给每块补上下文的方法。
- D 对：一句话可能被切成两半，分别落在两个块里，两块的向量都只表达了半句话的意思；表格的行、代码的函数也会被截断。常见的缓解手段是加重叠，或改用递归切分、按结构切分。

<sub>考点：固定长度切块</sub>

</details>

<a name="RAG-CHUNK-008"></a>

### RAG-CHUNK-008　基础 · 考频 ★★

固定长度切块时，设置相邻块之间的重叠（overlap），主要目的是：

- **A.** 让跨越切分点的句子至少在某一块中完整出现，降低关键信息被切断的风险
- **B.** 增加块的数量，让每个块更短小，从而提升向量检索的速度和精度
- **C.** 让同一段内容在 top-k 中重复出现，从而提高它在生成时的权重
- **D.** 弥补 Embedding 模型最大输入长度不足：超出部分会顺延到下一块，借重叠区接续编码

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：重叠是固定长度切块的「补丁」：切分点附近的内容同时出现在前后两块里，即使一刀切在句子中间，这句话也有机会在某一块中完整出现。

- B 错：重叠不会让块变短，块数增加意味着索引变大、检索变慢，这是重叠的代价而不是目的。
- C 错：同一内容重复占据 top-k 是重叠的副作用，会挤掉其他有用信息，需要用 MMR 等方法去冗余。
- D 错：最大输入长度是块大小必须遵守的约束，与重叠无关；重叠反而让每块的新内容更少。

常见取值是块大小的 10%～20%。递归切分时更好的做法是按完整句子回退来构造重叠，避免块以半句话开头。

<sub>考点：重叠窗口</sub>

</details>

<a name="RAG-CHUNK-012"></a>

### RAG-CHUNK-012　进阶 · 考频 ★★★

递归切块（如 LangChain 的 RecursiveCharacterTextSplitter）使用一组按优先级排列的分隔符（如段落 → 换行 → 句号 → 逗号 → 单个字符）。关于它的切分规则，下列说法正确的是：

- **A.** 先用列表中每一级分隔符把文本一次拆到最细，再按块大小把碎片随机合并
- **B.** 先用最高级分隔符拆分，只有片段仍超过块大小时，才对该片段改用下一级分隔符继续拆
- **C.** 先按单个字符切开，再自底向上合并，遇到段落边界或达到块大小时就结束当前块
- **D.** 文本中出现段落分隔符时就只按段落切，即使某个段落超过块大小也整段保留，以免破坏语义

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：递归切块的原则是「能用高级分隔符解决的，绝不动低级分隔符」。拆分完成后，再把相邻的小片段贪心合并，直到接近块大小。

- A 错：一次性拆到最细会把句子打碎，合并时也没有规则可言。
- C 错：从单个字符开始合并相当于固定长度切分，丢掉了自然边界的优先级。
- D 错：超长段落会递归地降级到换行、句号乃至逗号继续拆，保证每块都不超过块大小。

这样切出来的块尽量在段落或句子边界结束，语义比固定长度切分完整得多，所以它是大多数文本的默认方案。

<sub>考点：递归切块</sub>

</details>

<a name="RAG-CHUNK-013"></a>

### RAG-CHUNK-013　进阶 · 考频 ★★

用 LangChain 的 RecursiveCharacterTextSplitter、默认分隔符 `["\n\n", "\n", " ", ""]` 处理一段很长、中间既没有换行也没有空格的中文段落（远超 chunk_size）。最可能出现的情况是：

- **A.** 切分器检测到中文后会自动启用中文标点，识别句号「。」并在句末切开
- **B.** 默认分隔符都匹配不到，切分器找不到合法的切点，抛出异常提示调整参数
- **C.** 退到空字符串逐字拆开再合并，块在 chunk_size 附近从句子中间断开
- **D.** 找不到换行和空格，整段作为一个块返回，即使它超过了 chunk_size 也不再拆分

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：默认分隔符是为英文这类用空格分词的语言设计的，里面没有中文标点。这段中文既没有 `\n\n`、`\n`，也没有空格，只能退到最后的空字符串：按字符拆开后再合并到 chunk_size。切点与句子边界毫无关系，效果和固定长度切分差不多。

- A 错：默认列表里没有「。」，切分器不会自己识别中文标点。
- B 错：列表最后的空字符串分隔符是兜底，任何文本都能匹配，保证总能切开。
- D 错：正因为有兜底分隔符，超长文本总会被切到 chunk_size 以内。

**改进**：为中文自定义分隔符，例如 `["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""]`，让切点优先落在句末（LangChain 文档中也建议对中文、日文等没有词边界的语言补充标点分隔符）；同时用 tokenizer 计算长度（`length_function`），而不是按字符数。

<sub>考点：递归切块</sub>

</details>

<a name="RAG-CHUNK-017"></a>

### RAG-CHUNK-017　基础 · 考频 ★★★

要为一份 Markdown 格式、有清晰三级标题的《员工手册》建索引，下列切块方式中**最合适**的是：

- **A.** 按固定 512 token 切并设置 20% 重叠，标题作为普通文本留在原处，切分点不受结构影响
- **B.** 先删除标题等格式噪声，再用语义切块按话题相似度切开，让块边界由内容决定
- **C.** 每个三级标题下的内容作为一个块，不论长短都不再拆分，保证小节语义完整
- **D.** 按标题层级切分，每块开头带上标题路径（如「假期 > 年假」），过长的小节再递归细分

<details>
<summary>答案与解析</summary>

**答案：D**

**解析：**

**结论**：结构清晰的文档应该利用结构：按标题切，块的语义天然完整，引用也能精确定位到小节。

- A 错：固定长度切分会把小节拦腰切断，后半块里没有标题，看不出在讲哪个主题。
- B 错：标题是最有价值的结构信息，删掉它等于自废武功。
- C 错：小节长短差异很大，超长小节会超过 Embedding 模型的最大输入长度而被截断，向量也会被稀释；过长时应递归细分，每个子块仍带标题路径。
- D 对：完整的标题路径（如「员工手册 > 假期 > 年假」）拼在块的开头，能让「未休完的可顺延一个季度」这样的块带上「假期 > 年假」的主题信息，向量检索和 BM25 都受益；过短的相邻小节也可以合并。

<sub>考点：结构感知切块</sub>

</details>

<a name="RAG-CHUNK-020"></a>

### RAG-CHUNK-020　基础 · 考频 ★★★

父子块（small-to-big）检索的核心思想是：

- **A.** 用大块计算向量做检索，命中后把大块切成小块送入生成，节省 token
- **B.** 用小块计算向量做检索，命中后把它所属的较大父块（或前后若干句）交给生成模型
- **C.** 同一段文本同时存大、小两种块，检索时把两者的相似度取平均
- **D.** 先检索整篇文档，再在文档内用关键词匹配找出相关段落

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：父子块把「检索用的单元」和「生成用的单元」解耦。

- 小块（如 128 token）语义集中，向量不被稀释，检索更准；
- 大块（如整节 1,024 token）上下文完整，生成时不缺前因后果。

变体是句子窗口检索：按单句检索，命中后把前后各 k 句一起交给模型。

- A 错：方向反了。大块检索不准，正是父子块要解决的问题。
- C 错：父子块不对分数做平均，而是用子块的命中去定位父块。
- D 错：这是「先文档、后段落」的层级检索，是另一种思路。

<sub>考点：父子块</sub>

</details>

<a name="RAG-CHUNK-024"></a>

### RAG-CHUNK-024　进阶 · 考频 ★★

团队用 sentence-transformers 加载了一个 `max_seq_length = 512` 的 BERT 系 Embedding 模型，却把块大小设成了约 1,000 token。最可能的后果是：

- **A.** 只有前 512 个 token 参与编码，后半部分被静默截断，问到后半部分时检索不到
- **B.** 向量库检测到块的文本超过模型上限，拒绝写入，入库阶段直接报错
- **C.** sentence-transformers 会自动把超长的块拆成两段，分别编码、存成两个向量
- **D.** 模型会按输入长度扩展位置编码，输出的向量维度变成原来的两倍，存储量翻倍

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：超过最大长度的输入在分词阶段就被截断了（sentence-transformers 默认截断而不报错），系统看起来一切正常，只是每块的后半部分永远不会被检索到。这是很隐蔽的召回失败原因。

- B 错：向量库并不知道模型的长度上限，它存的是向量，向量长度由模型决定，与块的文本长度无关。
- C 错：模型不会自动拆分，需要在切块时自己控制长度。
- D 错：向量维度是模型固定的输出维度，与输入长度无关；BERT 系模型的绝对位置编码也不会随输入扩展。

**对策**：按目标模型的 tokenizer 计算块长度，把块控制在最大长度以内（还要给查询前缀、特殊 token 留出余量）；需要长块时选择支持长输入的模型（如 BGE-M3 最长支持 8,192 token）；重排模型同样有最大长度，也要匹配。

<sub>考点：块大小权衡</sub>

</details>

<a name="RAG-CHUNK-028"></a>

### RAG-CHUNK-028　基础 · 考频 ★★

一批技术文档中有大量流程图和柱状图，其中的关键信息没有出现在正文里。在仍然使用文本向量检索的前提下，最常见的入库做法是：

- **A.** 直接丢弃图片：文本检索系统处理不了图片，正文已经足以覆盖大部分问题
- **B.** 把图片文件的 base64 编码当作文本切块，用 Embedding 模型建立向量索引，与正文一起检索
- **C.** 用多模态模型为每张图生成文字描述，作为可检索的文本入库，并保留指向原图的链接
- **D.** 只把图片的文件名和图注作为块的内容入库，图片本身另存到对象存储

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：把图片「翻译」成文字，就能复用现有的文本检索链路。

- 描述要具体（可结合图中文字的 OCR 结果）：流程图写清各个步骤及其先后与分支关系，柱状图写清坐标含义、关键数值和趋势；
- 描述块的元数据记录原图位置，命中后可以把原图连同描述一起交给多模态生成模型，或在前端展示原图。

逐项点评：
- A 错：图中的信息没有出现在正文里，丢弃图片就等于丢失这部分知识。
- B 错：base64 只是二进制数据的文本编码，没有任何语义，Embedding 模型无法从中理解图片内容。
- D 错：文件名和图注的信息量太少，回答不了「第三步之后走哪个分支」这类问题。图注可以作为描述的补充，但不能替代描述。

<sub>考点：多模态文档</sub>

</details>

<a name="RAG-CHUNK-002"></a>

### RAG-CHUNK-002　进阶 · 考频 ★★★

对 PDF 做解析时，下列做法中**合理**的有：

- **A.** 把表格整体删除，因为表格内容无法被检索
- **B.** 把跨页断开的段落重新拼接成完整的段落
- **C.** 用版面分析识别标题、段落、表格、图片区域，再按阅读顺序重组文本
- **D.** 为节省索引空间，丢弃所有标题，只保留正文段落
- **E.** 把每页重复出现的页眉、页脚和页码留在正文里，方便引用时定位页数

<details>
<summary>答案与解析</summary>

**答案：BC**

**解析：**

**结论**：B、C 合理。解析的目标是得到「顺序正确、结构完整、没有噪声」的文本，很多团队的经验是：解析质量对最终效果的影响，常常比换 Embedding 模型还大。

- A 错：表格往往集中了价格、参数、规则等关键信息，应转成 Markdown/HTML 或按行线性化保留下来。
- B 对：跨页断句会把一句话拆进两个块，两块都语义不完整。

重叠能缓解切分点把信息截断的问题；但重叠比例过大时，同一段内容会以多个版本同时挤进检索结果的 top-k，反而占掉其他有用信息的位置。

### RAG-CHUNK-006　进阶 · 考频 ★★

## 代码输出题

<a name="RAG-CHUNK-010"></a>

### RAG-CHUNK-010　进阶 · 考频 ★★

下面的代码比较两种固定长度切块的写法（块大小 4、重叠 1），输出是什么？

```python
toks = list(range(10))
size, overlap = 4, 1
step = size - overlap
naive = [toks[i:i + size] for i in range(0, len(toks), step)]
fixed = [toks[i:i + size] for i in range(0, max(len(toks) - overlap, 1), step)]
print(len(naive), naive[-1])
print(len(fixed), fixed[-1])
print(sum(map(len, fixed)) - len(toks))
```

<details>
<summary>答案与解析</summary>

**答案（程序输出）：**

```text
4 [9]
3 [6, 7, 8, 9]
2
```

**解析：**

步长 = 4 − 1 = 3。

- `naive` 的起点是 `range(0, 10, 3)`，即 0、3、6、9，得到 `[0..3]`、`[3..6]`、`[6..9]`、`[9]` 共 4 块。最后一块 `[9]` 完全包含在前一块 `[6, 7, 8, 9]` 里，是一个冗余的「尾巴」：只有 1 个 token，向量质量差，还会和前一块在检索结果中重复出现。
- `fixed` 把循环终点改成 `len - overlap = 9`，起点是 0、3、6，共 3 块，最后一块 `[6, 7, 8, 9]` 恰好到达文末。`max(..., 1)` 保证极短的文本也至少产出一块。
- 第三行：3 块共 12 个 token，比原文多 2 个，正好是 2 处重叠、每处 1 个 token。

结论：固定长度切块的循环终点要写成 `len - overlap`（或在某块到达文末时停止），否则会多出被前一块完全覆盖的冗余小块。

```python
def sliding_chunks(tokens, size, overlap):
    chunks = []
    start = 0
    while start < len(tokens):
        chunks.append(tokens[start:start + size])
        start += size - overlap
    return chunks
```

<details>
<summary>答案与解析</summary>

**答案：**

**问题 1（冗余尾块）**：循环只检查 `start < len(tokens)`。某一块已经覆盖到文末（`start + size >= len(tokens)`）时，循环仍会继续，产出一个完全包含在前一块里的小块。例如 10 个 token、`size=4`、`overlap=1` 时，会多出最后一块 `[9]`。

**问题 2（死循环）**：没有校验参数。`overlap == size` 时步长为 0，`start` 永远不变；`overlap > size` 时步长为负，`start` 越来越小。两种情况都会死循环。

**修正**：

```python
def sliding_chunks(tokens, size, overlap):
    if not 0 <= overlap < size:
        raise ValueError("需要 0 <= overlap < size")
    chunks = []
    start = 0
    while start < len(tokens):
        chunks.append(tokens[start:start + size])
        if start + size >= len(tokens):   # 这一块已到文末，停止
            break
        start += size - overlap
    return chunks
```

**修正后的代码：**

```python
def sliding_chunks(tokens, size, overlap):
    if not 0 <= overlap < size:
        raise ValueError("需要 0 <= overlap < size")
    chunks = []
    start = 0
    while start < len(tokens):
        chunks.append(tokens[start:start + size])
        if start + size >= len(tokens):
            break
        start += size - overlap
    return chunks
```

**解析：**

固定长度切块有两个经典边界：终止条件和步长的合法性。修正后，当文档长度 $L>c$ 时块数为 $\lceil(L-o)/(c-o)\rceil$，最后一块恰好到达文末；空输入不进入循环，直接返回空列表。

工程上还要注意：块大小应按目标 Embedding 模型的 tokenizer 计算，而不是按字符数；重叠最好按完整句子回退，避免块以半句话开头。

<sub>考点：重叠窗口、固定长度切块</sub>

## 编程题

<a name="RAG-CHUNK-014"></a>

### RAG-CHUNK-014　挑战 · 考频 ★★★

实现递归切块：

```python
def recursive_chunk(text: str, size: int, seps=("\n\n", "\n", "。", "，", "")) -> list[str]: ...
```

要求：
- 每块长度（按字符计）不超过 `size`（`size >= 1`），且没有空块；空字符串返回空列表；
- 所有块按顺序拼接后与原文**完全一致**（不重叠、不丢字符，分隔符保留在它前面那一段的末尾）；
- 先用文本中出现的最高级分隔符拆分；拆出的片段仍超过 `size` 时，才对该片段改用下一级分隔符递归拆分；`""` 表示逐字符拆分，作为兜底；
- 拆分完成后从左到右贪心合并相邻片段：当前块加上下一个片段不超过 `size` 就合并，否则先产出当前块。

<details>
<summary>答案与解析</summary>

**参考实现：**

```python
def _split_keep(text, sep):
    """按 sep 拆分，分隔符留在前一段末尾，保证拼接后与原文一致"""
    if sep == "":
        return list(text)
    parts = text.split(sep)
    pieces = [p + sep for p in parts[:-1]] + [parts[-1]]
    return [p for p in pieces if p]


def _atoms(text, size, seps):
    """把 text 拆成长度都不超过 size 的原子片段"""
    if len(text) <= size:
        return [text] if text else []
    sep = next(s for s in seps if s == "" or s in text)   # 出现的最高级分隔符
    rest = seps[seps.index(sep) + 1:]
    out = []
    for piece in _split_keep(text, sep):
        out += [piece] if len(piece) <= size else _atoms(piece, size, rest)
    return out


def recursive_chunk(text, size, seps=("\n\n", "\n", "。", "，", "")):
    chunks, cur = [], ""
    for piece in _atoms(text, size, list(seps)):
        if cur and len(cur) + len(piece) > size:
            chunks.append(cur)
            cur = ""
        cur += piece
    if cur:
        chunks.append(cur)
    return chunks
```

**测试用例：**

```python
import random

doc = ("第一条　员工出差须提前申请。申请须经直属上级审批。\n\n"
       "第二条　住宿标准按城市分级，一线城市每晚不超过 600 元，其他城市每晚不超过 400 元。\n\n"
       "第三条　报销须在 30 天内提交。")
for size in (1, 5, 12, 20, 40, 200):
    chunks = recursive_chunk(doc, size)
    assert "".join(chunks) == doc                       # 无损拼回
    assert all(1 <= len(c) <= size for c in chunks)     # 不超长、无空块
assert recursive_chunk(doc, 200) == [doc]
assert all(c.endswith(("。", "\n\n", "，")) for c in recursive_chunk(doc, 40))
assert recursive_chunk("", 10) == []
assert recursive_chunk("短文本。", 10) == ["短文本。"]
# 段落放得下时，不会为了凑满 size 而跨进下一段的句子中间
assert recursive_chunk("甲乙丙。\n\n丁戊己庚辛壬癸子丑寅。", 12) == ["甲乙丙。\n\n", "丁戊己庚辛壬癸子丑寅。"]
# 没有句号的长句退到逗号处切
line = "，".join(f"城市{i:02d}" for i in range(20))
parts = recursive_chunk(line, 20)
assert "".join(parts) == line and all(p.endswith("，") for p in parts[:-1])
# 没有任何分隔符时逐字兜底
assert recursive_chunk("abcdefg", 3) == ["abc", "def", "g"]
# 随机输入的不变式
rng = random.Random(0)
for _ in range(300):
    s = "".join(rng.choice("ab。，\n") for _ in range(rng.randint(0, 60)))
    size = rng.randint(1, 15)
    cs = recursive_chunk(s, size)
    assert "".join(cs) == s and all(1 <= len(c) <= size for c in cs)
```

**解析：**

**思路**：
1. `_split_keep`：按分隔符拆开，并把分隔符留在前一段末尾（句号跟着句子走），保证拼回去与原文一字不差；过滤掉空片段。
2. `_atoms`：文本不超长就直接返回；否则找到文本中出现的最高级分隔符拆开，仍超长的片段换下一级分隔符递归处理。`""` 兜底逐字符拆，所以递归一定会终止。
3. 贪心合并：逐个加入片段，加不下就产出当前块。只在片段边界上切，所以块尽量落在段落、句子边界。

**复杂度**：拆分 $O(n\cdot S)$（$S$ 为分隔符种数），合并 $O(n)$。

**易错点**：分隔符被 `split` 吃掉导致拼不回原文；`sep` 在文本中不存在时仍然用它拆（应跳到下一级）；忘了 `""` 兜底导致超长片段无法处理；合并时先判断再追加，避免产出空块。生产中长度应按 Embedding 模型的 tokenizer 计算；需要重叠时，可以在新块开头回退若干个完整片段。

<sub>考点：递归切块</sub>

</details>

## 简答题

<a name="RAG-CHUNK-015"></a>

### RAG-CHUNK-015　进阶 · 考频 ★★

语义切块（semantic chunking）是怎么做的？与递归切块相比有哪些优缺点？什么情况下值得用它？

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **做法**：先把文本拆成句子；逐句（或用相邻几句组成的滑动窗口）计算 embedding；计算相邻句之间的余弦相似度；在相似度骤降处（如低于某个百分位阈值）切开，认为那里是话题转换点；最后对过长的块按长度兜底切分，对过短的块与邻居合并。
2. **优点**：切点贴合话题边界，一块只讲一件事，向量更「纯」；对缺少标题、段落结构的文本（访谈记录、会议纪要、长篇叙述）更友好。
3. **缺点**：
   - 成本高：每个句子都要过一次 Embedding 模型，离线计算量远大于递归切分；
   - 阈值难调：不同文档、不同模型的相似度分布不同，阈值需要反复调整；
   - 块长度不稳定：可能产生过长或只有一两句的块，需要设置最大、最小长度；
   - 收益不稳定：公开的对比实验中，它常常并不比调好参数的递归切分更好。
4. **何时用**：话题跳跃频繁、缺乏结构标记的长文本；或者递归切分在评测中暴露出「一块混入多个话题」的问题时。结构清晰的文档（手册、制度、API 文档）应优先按标题结构切。

**评分要点（共 10 分）：**

- 说清逐句向量化、计算相邻相似度、在骤降处切开的流程（3 分）
- 说出至少两个优点（贴合话题边界、适合无结构文本）（2 分）
- 说出成本高、阈值难调、长度不稳定等缺点（3 分）
- 给出合理的适用场景，并指出结构化文档应优先按结构切（2 分）

**讲解：**

**常见失分点**：认为语义切块「一定更好」；不知道每个句子都要做一次向量化；忘了长度兜底；把语义切块和 Contextual Retrieval（给块补上下文说明）混为一谈。

<sub>考点：语义切块</sub>

</details>

### RAG-CHUNK-023　进阶 · 考频 ★★★

块大小如何影响 RAG 的效果？请从检索精度、上下文完整性、成本与延迟、模型长度限制等角度说明，并给出确定块大小的方法。

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **检索精度**：小块（128～256 token）语义集中，向量不被稀释，适合事实型短问答；大块（512～1,024 token）一块混入多个话题，向量被「平均」，检索变钝。
2. **上下文完整性**：小块容易缺上下文，例如块里只有「该条款」而不知道是哪一条；大块上下文完整，适合解释、总结类问题。
3. **成本与延迟**：送入生成模型的 token ≈ 块数 × 块大小，块越大，生成成本和首 token 延迟越高；块越小，块数和向量数越多，索引越大。
4. **长度限制**：块不能超过 Embedding 模型和重排模型的最大输入长度（不少 BERT 系模型只有 512 token），超出部分会被静默截断；长度要按目标模型的 tokenizer 计算，而不是按字符数。
5. **确定方法**：从 256～512 token、重叠 10%～20% 起步；固定其他环节，在评测集上扫块大小和重叠，同时看 Recall@k、端到端正确率与成本；不同类型的文档可以用不同的块大小；两头都想要时用父子块。

**评分要点（共 10 分）：**

- 说明块大小对检索精度的影响（小块精准、大块被稀释）（2 分）
- 说明对上下文完整性的影响（2 分）
- 说明对生成成本、延迟与索引规模的影响（2 分）
- 指出 Embedding 与重排模型的最大长度约束，以及要按 token 计长（2 分）
- 给出经验起点，并强调用评测集扫参决定，或提到父子块折中（2 分）

**讲解：**

**常见失分点**：只说「按 500 字切、重叠 50 字」，讲不出为什么；不知道超长会被静默截断；按字符而不是按 token 计算长度；不提用评测集验证。

<sub>考点：块大小权衡</sub>

某保险公司的条款问答系统采用「每 1,000 字固定切块、无重叠」。线上出现三类问题：

**参考答案：**

1. **规则与例外被切开（问题 1）**：固定长度切分不看条款边界，「等待期 90 天」和它的例外落在两块里；只召回前一块，回答就不完整。
   - 改进：按条款结构切块（每条或每款一块），保证规则与例外在同一块；过长的条款再递归细分，并加 10%～20%、按完整句子回退的重叠；也可以用父子块：子块检索，命中后返回整条条款。
2. **悬空指代（问题 2）**：块里只有「上述情形」，真正的情形列表在前一块，块本身也没有「责任免除」这类主题词，向量与 BM25 都匹配不上。
   - 改进：把标题路径（如「XX 重疾险 > 第 5 条 责任免除」）拼到块的开头；必要时用 Contextual Retrieval 为每块补一句上下文说明；按条款结构切块后，「上述情形」与情形列表通常也会落在同一块。
3. **跨产品串条（问题 3）**：不同产品条款的编号与措辞高度相似，块中没有产品信息，「3.2」这样的编号无法区分。
   - 改进：每块带产品名、条款版本、条款编号等元数据，并拼进块的文本；检索时从问题中识别产品名做过滤，识别不出时先反问用户是哪款产品；条款编号这类精确词项用 BM25 召回。
4. **验证**：用这三类问题构建评测集，比较改进前后的 Recall@k 与回答完整度；抽样检查新的切块是否仍有跨条款截断。

**评分要点（共 10 分）：**

- 指出固定切分把规则与例外切开，并给出按条款切、父子块或重叠等方案（3 分）
- 指出悬空指代与主题词缺失，并给出拼标题路径或补上下文的方案（3 分）
- 指出缺少产品元数据导致串条，并给出元数据过滤或反问澄清的方案（3 分）
- 提到用评测集验证改进效果（1 分）

**讲解：**

**常见失分点**：只建议「调大块」或「加重叠」，不利用条款的天然结构；不知道「上述情形」类块需要补充上下文；忽略多产品场景下的元数据过滤。
