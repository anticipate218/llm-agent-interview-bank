## 单选题

<a name="RAG-BASE-001"></a>

### RAG-BASE-001　基础 · 考频 ★★★

某公司想让大模型回答内部规章制度问题。已知：制度每月都有修订；不同部门的员工能看到的制度范围不同；审计要求每个回答都能指出依据的原文。与「把制度内容微调进模型参数」相比，选择 RAG 的**最主要**理由是：

- **A.** 知识存放在外部索引中：改文档即生效，回答能标注出处，检索时还能按用户权限过滤
- **B.** RAG 把资料与推理过程一起放进上下文，能提升生成模型本身的推理能力，从而减少逻辑错误
- **C.** RAG 的回答只依据检索到的原文，审计时可以逐句核对，因此能保证回答零幻觉
- **D.** RAG 不依赖训练好的模型，只做关键词匹配和拼接，部署后几乎没有额外的在线计算成本

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：题干的三个约束（频繁更新、按人控制可见范围、可溯源）恰好对应 RAG「知识外置」带来的三个好处。

- 更新：知识在索引里，制度修订后重新解析、切块、写入索引即可，分钟级生效；微调要重新训练，周期以天计。
- 权限：每块带部门、密级等元数据，检索时按用户身份过滤；知识一旦进了参数，就没法按人控制。
- 溯源：每块记录来源文档、版本和页码，回答可以逐句标注出处。

逐项点评：
- B 错：RAG 改变的是「模型手里有什么资料」，不改变模型本身的推理能力。
- C 错：检索可能漏召回或召回错误资料，模型也可能不忠实于资料、混入参数里的知识，RAG 只能降低而不能消除幻觉。
- D 错：RAG 依赖 Embedding 模型、（通常还有）重排模型和生成模型，每次请求还多一次检索开销。

<sub>考点：RAG动机</sub>

</details>

<a name="RAG-BASE-002"></a>

### RAG-BASE-002　进阶 · 考频 ★★★

某电商平台的客服机器人有两个需求：① 回复必须使用品牌规定的语气，并稳定输出 `{"intent": ..., "reply": ...}` 格式的 JSON；② 回答要基于最新的商品价格与售后政策，这些信息每天都会变化。下列方案中**最合适**的是：

- **A.** 只做微调：把话术风格和商品知识一起训练进模型，每天用最新数据做一次增量 LoRA 训练
- **B.** 只做 RAG：把话术范例和 JSON 样例也放进知识库，靠检索到的范例让模型模仿语气与格式
- **C.** RAG 提供每天变化的商品知识，微调（或少样本加结构化输出约束）固化语气与 JSON 格式
- **D.** 把商品信息和话术规范整体放进长上下文，每次请求完整输入，配合 Prompt Caching 降低成本

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：需求①是「行为」问题，需求②是「知识」问题，各用最擅长的手段，再组合起来。

- 语气、格式、术语这类「怎么答」的问题，微调能稳定地改变模型行为；轻量方案是少样本示例加结构化输出（如 JSON Schema 约束解码）。
- 每天变化的价格和政策是「答什么」的问题，放在外部索引里，更新文档即可生效。

逐项点评：
- A 错：每天重训（即使是增量 LoRA）成本高、周期长；用微调灌入新知识学得慢、记不牢，还可能诱发幻觉，也无法给出出处。
- B 错：检索到的范例能起一定示范作用，但每次召回的范例不同，语气与格式难以稳定；格式约束更适合交给微调或约束解码。
- D 错：商品信息量大时每次都要处理全部 token，延迟高，中间位置的信息利用率也会下降；Prompt Caching 只能降低重复前缀的计费，解决不了这些问题，也没有解决格式稳定性。

<sub>考点：RAG与微调与长上下文</sub>

</details>

<a name="RAG-BASE-003"></a>

### RAG-BASE-003　进阶 · 考频 ★★

团队有一份约 300 页（约 15 万 token）的产品手册，半年才更新一次；用户的问题经常需要综合多个章节才能回答；日均请求只有几十次，对数据安全没有特殊限制。下列做法中**最合理**的首选是：

- **A.** 立刻搭建完整的混合检索 + 重排 RAG 流水线：15 万 token 的长上下文每次请求都太贵，效果也不如 RAG
- **B.** 先试把整本手册放进长上下文并开启 Prompt Caching，在评测集上验证效果与成本
- **C.** 用手册做继续预训练，把知识写进参数，之后推理时不必再输入手册，单次请求成本最低
- **D.** 用 BM25 检索 3 个最相关的段落放进上下文：成本最低，跨章节的问题也能靠多段拼接回答

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：资料量小、更新少、请求量低、又需要通读全文时，长上下文 + Prompt Caching 往往是更简单的起点。Anthropic 在介绍 Contextual Retrieval 的文章（2024）中给出的经验线是：知识库小于约 20 万 token（约 500 页）时，可以考虑直接整体放进提示词。

- 15 万 token 在不少长上下文模型（20 万 token 及以上窗口）的容量之内；Prompt Caching 让重复的手册前缀按较低价格计费、首 token 也更快；日均几十次请求，总成本可控。
- 问题需要跨章节综合，RAG 只取少数几块，容易漏掉分散在各章的信息。

逐项点评：
- A 错：日均几十次请求、又有 Prompt Caching 时，长上下文的总成本并不高；跨章节综合的问题上它也未必比 RAG 差。规模小、请求少时未必需要 RAG，应该用评测集说话，效果和成本都不达标时再上 RAG。
- C 错：继续预训练成本高，新知识学不牢，也无法给出出处。
- D 错：只取 3 段很难覆盖跨章节的信息，恰恰不适合综合类问题。

延伸：如果资料涨到几千页，或请求量涨到每天几十万次，长上下文的成本和延迟会很快变得不可接受，那时再上 RAG。

<sub>考点：RAG与微调与长上下文　｜　出处：Anthropic: Introducing Contextual Retrieval（2024-09-19，知识库小于约 20 万 token 时可整体放入提示词）https://www.anthropic.com/news/contextual-retrieval</sub>

</details>

<a name="RAG-BASE-007"></a>

### RAG-BASE-007　基础 · 考频 ★★★

下列步骤中，属于 RAG **离线**索引链路（而不是每次请求都要执行的在线链路）的是：

- **A.** 结合对话历史，把用户的追问改写成完整的问题
- **B.** 用 Cross-Encoder 对召回的候选块重新打分排序
- **C.** 把检索到的资料编号后与问题一起拼进提示词
- **D.** 把文档解析、切块，并为每块计算向量写入索引

<details>
<summary>答案与解析</summary>

**答案：D**

**解析：**

**结论**：离线链路负责「把文档变成可检索的索引」：解析 → 切块（附元数据）→ 向量化 → 建索引（向量索引 + 倒排索引）。它在文档入库或更新时运行，与具体问题无关。

- A 错：查询改写依赖用户的问题和对话历史，只能在线做。
- B 错：Cross-Encoder 要把问题和文档拼在一起计算，必须等问题到来，属于在线重排。
- C 错：拼接提示词是在线生成前的最后一步。

记忆方法：凡是需要「问题」作为输入的步骤，都只能在线执行；只依赖文档的步骤，尽量挪到离线提前做，这正是 RAG 在线延迟能做低的关键。

<sub>考点：离线索引与在线检索、标准链路</sub>

</details>

<a name="RAG-BASE-010"></a>

### RAG-BASE-010　进阶 · 考频 ★★

RAG 综述（Gao 等, 2023）把 RAG 的发展分为 Naive、Advanced、Modular 三个阶段。下列改进中，**最能代表**从 Naive RAG 走向 Advanced RAG 的是：

- **A.** 由 Agent 在循环中自主决定是否检索、检索什么、何时停止
- **B.** 在检索前加入查询改写等优化，在检索后加入重排、上下文压缩等优化
- **C.** 把各环节拆成可替换的模块，并支持路由、迭代检索等多种流程编排
- **D.** 用 LLM 抽取实体关系建图，再为社区生成摘要来回答全局问题

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：Advanced RAG 的标志是在 Naive RAG「检索一次 → 拼接 → 生成」的固定流水线上，增加**检索前**（pre-retrieval）和**检索后**（post-retrieval）的优化。

- 检索前：查询改写、扩展、问题分解，以及索引侧的切块优化、补充元数据等；
- 检索后：重排、上下文压缩、去冗余。

逐项点评：
- A 错：这是 Agentic RAG 的特征，检索变成了 Agent 的工具。
- C 错：这是 Modular RAG 的特征，重点在模块化与流程编排。
- D 错：这是 GraphRAG，针对全局性、关系类问题，与 Advanced RAG 是不同的方向。

<sub>考点：Naive与Advanced与Modular RAG</sub>

</details>

<a name="RAG-BASE-013"></a>

### RAG-BASE-013　基础 · 考频 ★★★

排查一条 RAG 的 bad case：包含正确答案的块在重排后排第 2 名，并且已经放进了提示词；但模型的回答依据的是另一块内容，结论是错的。这条 bad case 应归因于哪个环节？

- **A.** 解析：文档解析质量差，正确内容没有被正确抽取
- **B.** 召回：正确的块没有被检索出来
- **C.** 排序：正确的块排名太靠后，被 top-k 截断
- **D.** 生成：资料已在上下文中，但模型没有正确利用

<details>
<summary>答案与解析</summary>

**答案：D**

**解析：**

**结论**：判断依据是「正确资料走到了哪一步」。它已经进入提示词，说明解析、召回、排序都没有挡住它，问题出在生成阶段。

- A 错：正确块的内容完整地出现在了上下文中，说明解析没有丢内容。
- B 错：正确块被召回了。
- C 错：它排第 2 并进入了提示词，没有被截断。

生成阶段常见的原因：多块资料互相干扰，模型选错了依据；新旧版本混用；模型用参数知识覆盖了资料；指代不清导致误读。对应手段有：减少噪声块、把最相关的块放在前面、要求逐句引用并做引用校验。

排查顺序：先看知识库里有没有 → 再看召回里有没有 → 再看进没进上下文 → 最后看模型用没用对。

<sub>考点：失败模式分析</sub>

</details>

<a name="RAG-BASE-027"></a>

### RAG-BASE-027　进阶 · 考频 ★★

在流式输出的 RAG 问答中，下列改动对降低**首字延迟**（用户看到第一个字的时间）**没有**直接帮助的是：

- **A.** 减少送入生成模型的块数，缩短 prefill 的输入长度
- **B.** 稠密检索与 BM25 两路召回改为并行执行
- **C.** 把回答的最大输出长度从 1,000 token 降到 300 token
- **D.** 把 Cross-Encoder 的重排候选从 100 个减到 30 个

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：首字延迟 = 生成之前所有环节的耗时 + 生成模型的首 token 时间（TTFT）。输出长度只影响首字之后的解码阶段，不影响第一个字何时出现。

- A 有帮助：TTFT 主要由 prefill 决定，输入越短，prefill 越快。
- B 有帮助：串行时召回耗时是两路之和，并行后只取较慢的一路。
- C 没有直接帮助：限制最大输出长度只会缩短完整回答的总时长（也能避免长篇大论），对首字没有影响。
- D 有帮助：重排耗时大致与候选数成正比，减少候选能直接缩短生成前的等待；代价是可能漏掉排在后面的正确块。

<sub>考点：端到端延迟</sub>

</details>

<a name="RAG-BASE-029"></a>

### RAG-BASE-029　进阶 · 考频 ★★

用户问「年假有几天」，系统同时召回了 2023 版和 2025 版的《假期制度》，两版规定不同，模型的回答把两版的条款混在了一起。要**从根本上**解决这类问题，最合适的做法是：

- **A.** 索引中为每块记录版本与生效、失效时间，检索时默认只返回现行有效版本
- **B.** 在提示词中加一句「如有多个版本，请以最新版本为准」，并要求模型注明所依据的版本
- **C.** 增大召回的 top-k 并加上重排，让模型看到更多版本的上下文后自行判断哪份有效
- **D.** 换用参数量更大、长上下文能力更强的生成模型，提高它辨别和比对版本的能力

<details>
<summary>答案与解析</summary>

**答案：A**

**解析：**

**结论**：新旧版本混用的根源在索引：已失效的旧版本本来就不应该被检索出来。从数据侧解决，比让模型在生成时「自己分辨」可靠得多。

- A 对：解析入库时记录版本与生效、失效时间（元数据），检索时作为过滤条件，默认只检索现行有效版本；回答时注明依据的版本，也方便溯源。
- B 错：可以作为兜底，但模型不一定能判断哪份更新（块里未必写着日期），不能从根本上解决。
- C 错：召回更多版本只会带来更多干扰，重排按相关性排序，也分不出哪一版现行有效。
- D 错：更大的模型也只能依据上下文中的信息判断，旧版资料仍会干扰回答，而且成本更高。

延伸：如果用户确实在问历史版本（「2023 年时年假几天」），应从问题中识别出时间条件，再按版本过滤，而不是一律只给最新版。

<sub>考点：幻觉与可溯源、离线索引与在线检索　｜　出处：Milvus 文档：Filtered Search（检索时按元数据过滤）https://milvus.io/docs/filtered-search.md</sub>

</details>

<a name="RAG-BASE-031"></a>

### RAG-BASE-031　进阶 · 考频 ★★

团队为内部代码仓库做问答 Agent，在「先为仓库建向量索引做 RAG」与「让 Agent 用 grep、glob、读文件等工具现场搜索（agentic search）」之间选择。下列分析最合理的是：

- **A.** 向量索引能理解语义，查函数名、错误码这类标识符也比 grep 更准；agentic search 的主要好处只是省掉建索引的费用
- **B.** agentic search 不维护索引、读到的是最新代码，标识符能精确命中，可迭代改关键词；代价是多轮调用的时延与 token 开销
- **C.** agentic search 每个问题只发起一次检索、只读取命中的那一行，所以时延低于向量 RAG，也几乎不消耗额外的 token
- **D.** 代码仓库很少变化，向量索引建好后基本不会过期；索引建成后，也不必再考虑同步更新、权限控制和数据安全问题

<details>
<summary>答案与解析</summary>

**答案：B**

**解析：**

**结论**：两种方案各有长短，取决于语料变化的频率、查询里有没有能精确匹配的「钩子」，以及对时延与成本的要求。agentic search 不维护索引，函数名、报错文本能精确命中，还能按上一轮结果改关键词；但对只描述现象、没有可匹配关键词的问题，召回较弱。

- Claude Code 的创建者 Boris Cherny 提到，早期版本用过「RAG + 本地向量库」，但很快发现 agentic search 总体效果更好，也更简单，没有安全、隐私、索引过期与可靠性方面的问题（2026 年初在 X 上的说明）。Anthropic 在《Effective context engineering for AI agents》（2025-09）中把这种做法称为「just in time」检索：只保存文件路径等轻量引用，用 glob、grep 按需取回；同时承认运行时探索比读取预先算好的结果慢。
- 另一方面，Cursor 2025-11 的 A/B 实验发现，给 Agent 增加语义检索、与 grep 组合使用效果最好，在大型代码库上收益更明显。可见这个选择仍在演进，没有放之四海皆准的答案。

- A 错：代码里大量是函数名、错误码等需要逐字匹配的标识符，向量检索并不总是更准；省钱也不是 agentic search 的主要理由。
- C 错：agentic search 往往要多轮「搜索—阅读—再搜索」，每轮结果都会进入上下文，时延和 token 开销通常更高。
- D 错：代码每天都有提交，索引需要持续增量更新；索引是源代码的副本，还要处理权限同步与数据安全。

<sub>考点：Agentic Search与grep　｜　出处：Anthropic: Effective context engineering for AI agents（2025-09-29）https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents；Boris Cherny 在 X 上的说明 https://x.com/bcherny/status/2017824286489383315；Cursor: Improving agent with semantic search（2025-11-06）https://cursor.com/blog/semsearch</sub>

</details>

<a name="RAG-BASE-035"></a>

### RAG-BASE-035　基础 · 考频 ★★

某公司的员工助手要支持三类需求：① 查询 3,000 份、每月都会更新的制度文档中的具体条款；② 按公司模板生成周报 PPT，有固定的步骤、模板文件和校验脚本；③ 汇总上周未关闭的工单，并给超期工单的负责人发催办邮件。关于 RAG、Skill（如 Agent Skills）与 Agent 在其中的分工，下列说法正确的是：

- **A.** Skill 本质上就是把文档切块后按向量相似度检索，与 RAG 没有区别，只是把知识库换成了文件夹的形式
- **B.** Skill 要在模型训练阶段注入参数，相当于一次轻量微调；上线后推理时无法按需增加、删除或修改
- **C.** RAG 从大量常更新的资料中取事实；Skill 封装做事的方法，由模型按描述决定何时加载；Agent 负责多步决策与调用工具
- **D.** 有了 Skill 就不再需要 RAG：把 3,000 份制度文档打包进一个 Skill，模型加载它之后就能随时查到每一条条款

<details>
<summary>答案与解析</summary>

**答案：C**

**解析：**

**结论**：① 用 RAG，② 用 Skill，③ 由 Agent 调用工单系统与邮件工具完成（发邮件这类有副作用的操作最好经过确认）。三者是不同层次的东西，可以组合使用。

Anthropic 的 Agent Skills 是「由说明、脚本和资源组成的文件夹，Agent 可以发现并动态加载」。它采用渐进式加载：启动时只把每个 Skill 的名称和描述放进系统提示词；模型判断某个 Skill 与当前任务相关时，才读入完整的 SKILL.md；其中引用的其他文件在需要时再读取。Skill 擅长沉淀「怎么做」（说明、脚本、模板），RAG 擅长从大规模语料中检索「是什么」，Agent 可以同时使用二者。

- A 错：Skill 由模型根据描述决定是否加载，内容是操作说明与可执行的资源，不是按相似度检索的文本块。
- B 错：Skill 就是文件，随时可以增删改，不涉及训练。
- D 错：3,000 份文档不可能整体放进上下文；按条款精确检索、引用出处、按权限过滤和增量更新，都是 RAG 要做的事。可以写一个「如何查询制度库」的 Skill，让它去调用 RAG 检索工具，但不能用 Skill 代替检索。

<a name="RAG-BASE-004"></a>

### RAG-BASE-004　挑战 · 考频 ★★

关于「用微调给大模型注入新知识」，下列说法**正确**的有：

- **A.** 微调后的模型推理时不需要额外检索，单次请求的输入 token 比 RAG 少
- **B.** 微调进参数的知识难以给出出处，也无法按用户权限控制谁能「看到」哪条知识
- **C.** 只要微调数据足够多，模型就能可靠地记住每一条新知识，且不会影响原有能力
- **D.** 价格、库存这类每天变化的知识特别适合微调，训练一次就能长期使用
- **E.** 有研究发现：用模型预训练中没见过的新知识做微调，这类样本学得明显更慢，而且随着它们被学会，模型更倾向于编造

<details>
<summary>答案与解析</summary>

**答案：ABE**

**解析：**

**结论**：微调擅长改「行为」，不擅长灌「知识」；它在知识场景下最明显的优势只是推理时不多占上下文。

- A 对：RAG 每次要把检索到的块放进提示词，微调后的模型不需要，这是它在成本结构上的优势。
- B 对：知识混在参数里，既说不清出自哪份文档，也没法按人隔离。
- C 错：灌入大量新知识容易过拟合、记不牢，还可能遗忘原有能力（灾难性遗忘）。
- D 错：每天变化的知识要每天重训，成本和周期都不现实，这正是 RAG 的强项。
- E 对：Gekhman 等（2024，*Does Fine-Tuning LLMs on New Knowledge Encourage Hallucinations?*）发现，引入新知识的微调样本比与模型已有知识一致的样本学得慢得多；当这些样本最终被拟合时，模型产生幻觉的倾向随之上升。

延伸：业界常见的组合是「RAG 提供知识 + 微调教模型怎么用资料」，例如 RAFT（Zhang 等, 2024）在训练数据中混入干扰文档，让模型学会忽略无关段落。

<a name="RAG-BASE-009"></a>

### RAG-BASE-009　进阶 · 考频 ★★

关于 RAG 中离线索引与在线检索的分工，下列说法**正确**的有：

- **A.** 离线阶段为每块保留来源、标题路径、版本、权限等元数据，在线的过滤、引用与版本控制都依赖它们
- **B.** Cross-Encoder 重排所需的文档表示也可以离线预计算，所以重排几乎不增加在线延迟
- **C.** 文档频繁变化时，离线链路要支持增量更新与删除，否则在线会检索到过期内容
- **D.** 文档向量在离线阶段算好存入索引，在线只需编码一次问题，这是双塔检索能做到低延迟的前提
- **E.** 更换 Embedding 模型后，只需用新模型编码新增文档，旧文档的向量可以继续使用

<details>
<summary>答案与解析</summary>

**答案：ACD**

**解析：**

**结论**：A、C、D 正确。分工原则是「能提前算的都提前算」，但提前算好的东西必须与在线保持一致、及时更新。

- A 对：元数据要在解析和切块时就保留，事后很难补回。
- B 错：Cross-Encoder 要把问题和文档拼在一起前向计算，无法预计算文档表示，这正是它只能对少量候选重排的原因。
- C 对：增量更新（按内容哈希只重算变化的块）和删除（软删除加定期清理）是离线链路的必备能力。
- D 对：双塔模型的文档编码与问题无关，可以离线完成；在线只编码问题再做近邻搜索，因此千万级文档也能做到毫秒级检索。
- E 错：不同模型（哪怕是同一模型微调前后）的向量空间不同，新旧向量不可比。换模型必须全量重新编码、重建索引，验证后整体切换。

<sub>考点：离线索引与在线检索</sub>

<a name="RAG-BASE-014"></a>

### RAG-BASE-014　进阶 · 考频 ★★★

接入 RAG 后，系统仍然会产生幻觉（回答与事实不符或没有依据）。下列各项中，**可能导致**这种情况的有：

- **A.** 资料不足以回答时，模型用参数中的知识补全或过度推断
- **B.** 知识库中的文档本身过时或有错误
- **C.** 块被切断后缺少上下文，模型误解了「该条款」「上述标准」等指代
- **D.** 提示词中要求「只根据资料回答，资料不足时说不知道」
- **E.** 召回了话题相关但内容不对的片段（如旧版制度），模型照着它回答

<details>
<summary>答案与解析</summary>

**答案：ABCE**

**解析：**

**结论**：A、B、C、E 都会导致幻觉。RAG 把「凭记忆答」变成「凭资料答」，但资料本身、检索、切块、生成任何一环出错，都会让答案出错。

- A 对：资料不够时，模型倾向于用参数知识「补完」答案，这在数字、型号等长尾细节上尤其危险。应设置阈值拒答，并在提示词中明确允许「不知道」。
- B 对：资料错，照着资料答也是错的（garbage in, garbage out）。
- C 对：块里只有「该条款」「上述标准」而没有它们指代的内容，模型可能按自己的理解补全。补救方法是把标题路径拼进块，或为块补充上下文说明。
- D 错：这类约束是治理幻觉的常用手段，会降低而不是增加编造。
- E 对：向量检索按「话题相似」召回，旧版制度与新版高度相似，很容易一起被召回。根本解法是在索引侧做版本管理，只检索有效版本。

<sub>考点：幻觉与可溯源</sub>

</details>

<a name="RAG-BASE-028"></a>

### RAG-BASE-028　进阶 · 考频 ★★

关于 RAG 系统的端到端延迟，下列说法**正确**的有：

- **A.** Cross-Encoder 重排的耗时随候选数近似线性增长，候选数是关键的延迟旋钮
- **B.** 在千万级向量上，HNSW 等 ANN 检索通常只需毫秒级，往往不是主要瓶颈
- **C.** 生成阶段通常占大头，其中首 token 时间随送入的上下文长度增长
- **D.** 多路召回必须串行执行，每增加一路，延迟就增加这一路的全部耗时
- **E.** 查询改写只是字符串层面的处理，不调用模型，几乎不增加端到端延迟

<details>
<summary>答案与解析</summary>

**答案：ABC**

**解析：**

**结论**：A、B、C 正确。

- A 对：每个（问题，块）对都要一次前向计算，总耗时随候选数近似线性增长：候选数从 100 减到 30，重排耗时大约降到三成。块越长单次越慢（自注意力部分随长度平方增长，不是简单的正比），所以块长要与重排模型的最大长度匹配。
- B 对：ANN 索引只访问很小一部分向量，单次查询通常在毫秒级；真正的瓶颈往往在 LLM 调用和重排上。
- C 对：生成包括 prefill 和逐 token 解码，prefill 时间随输入长度增长，解码时间随输出长度增长。「块数 × 块大小」同时影响延迟和成本。
- D 错：各路召回彼此独立，可以并行，总耗时取最慢的一路。
- E 错：查询改写通常要调用一次 LLM，几百毫秒量级，是检索侧最大的额外开销之一。工程上常改用小模型，或只在多轮追问、首次检索分数偏低时触发。

<sub>考点：端到端延迟</sub>

</details>

<a name="RAG-BASE-032"></a>

### RAG-BASE-032　进阶 · 考频 ★★

关于 agentic search（让 Agent 调用 grep、glob、读文件等工具现场检索）与向量 RAG 的比较，下列说法**正确**的有：

- **A.** 函数名、错误码、配置项这类字面明确的查询，grep 能精确命中，往往比向量检索更准
- **B.** agentic search 不需要额外的基础设施，因此在任何规模的语料上，它的总成本都低于向量检索
- **C.** 向量索引是源数据的副本，版本与权限都要额外同步；agentic search 以调用者的身份直接访问源文件或源系统，更容易沿用源系统已有的权限控制
- **D.** agentic search 依赖字面匹配和模型自己想出的关键词，用户说法与文档用词差异很大（同义词、口语、跨语言）时容易漏召回
- **E.** agentic search 没有离线索引，文档或代码一改，下一次搜索就能看到，不存在索引与源数据不同步的问题

<details>
<summary>答案与解析</summary>

**答案：ACDE**

**解析：**

**结论**：A、C、D、E 正确。agentic search 胜在新鲜、精确、权限简单，输在语义召回与多轮探索的开销。

- A 对：这类查询要的是字面一致，grep 按原文精确匹配，不会把 `E1024` 匹配成「语义相近」的 `E2048`；稠密向量对编号、标识符这类词项不敏感。前提是文字可被搜索：扫描件、图片中的文字要先做 OCR，Office、PDF 文件也要先转成文本，grep 才能命中。
- B 错：省的是建索引与维护向量库的成本，付出的是每次查询的多轮调用和读文件的 token。语料很大时，不建任何索引直接扫描也很慢，例如 TB 级日志或上千个仓库，仍需要倒排、trigram 等关键词索引。
- C 对：索引是一份拷贝，权限变更要同步到索引元数据中，否则可能越权；Agent 以用户身份读源文件，权限天然一致。这正是 Claude Code 团队提到「安全、隐私、过期」问题的含义。
- D 对：这是向量检索的强项，用户问「白屏怎么办」，代码和文档里未必有这两个字；混合方案常用语义检索补这一块。
- E 对：没有索引就没有「索引过期」，适合每天大量变动的代码仓库和工作区。

## 判断题

<a name="RAG-BASE-005"></a>

### RAG-BASE-005　基础 · 考频 ★★★

主流模型的上下文窗口扩展到百万 token 之后，企业知识库问答就不再需要 RAG 了，把全部文档放进上下文即可。

<details>
<summary>答案与解析</summary>

**答案：❌ 错误**

**解析：**

**错误**。长上下文是 RAG 的补充，而不是替代：

1. **放不下**：企业知识库动辄几千万到上亿 token，远超百万 token 的窗口。
2. **付不起**：每次请求都要为全部输入 token 付费，首 token 延迟也随输入长度增长；Prompt Caching 只能打折，不能免单。
3. **用不好**：输入越长，模型对中间位置信息的利用率越低（Lost in the Middle、context rot）。
4. **管不住**：权限过滤、版本控制、按块溯源，都需要在拼接前先「选出」该给模型看的资料，这本身就是检索。

正确说法：资料少（如几百页以内）、更新少、需要通读全文时，可以优先考虑长上下文；规模大、更新频繁、需要权限与出处时，RAG 仍是主力。两者也常组合使用，例如检索出较多、较大的块交给长上下文模型。

<sub>考点：RAG与微调与长上下文</sub>

</details>

<a name="RAG-BASE-011"></a>

### RAG-BASE-011　进阶 · 考频 ★★

Modular RAG 与 Advanced RAG 的区别仅在于：Modular RAG 在流水线末端多加了一个重排模块。

<details>
<summary>答案与解析</summary>

**答案：❌ 错误**

**解析：**

**错误**。重排属于 Advanced RAG 的「检索后优化」。Modular RAG 的核心不是多加某一个模块，而是**架构上的模块化与可编排**：

- 检索、改写、重排、记忆、路由等环节都是可替换的组件；
- 流程不再是固定的线性链路，可以按问题类型路由到不同流程，或做迭代检索（检索 → 生成 → 再检索）、递归检索、自适应检索（先判断是否需要检索）。

可以这样理解三者的关系：Naive 是一条固定的链；Advanced 在这条链的前后加了优化环节；Modular 把链拆成积木，可以按需重新搭建。Self-RAG、Agentic RAG 等更灵活的流程，都可以看作模块化思想的延伸。

<sub>考点：Naive与Advanced与Modular RAG</sub>

</details>

<a name="RAG-BASE-015"></a>

### RAG-BASE-015　进阶 · 考频 ★★

即使包含正确答案的资料块排在检索结果第 1 位并放进了提示词，RAG 系统仍可能生成与这份资料相矛盾的回答。

<summary>答案与解析</summary>

**答案：✅ 正确**

**解析：**

**正确**。检索正确只是忠实回答的必要条件，不是充分条件。常见原因：

1. **知识冲突**：资料内容与模型参数中的「记忆」不一致（例如资料是新政策，模型记得的是旧政策），模型可能偏向自己的记忆。
2. **噪声干扰**：上下文中同时有多块相似但不同的资料，模型选错了依据，或把它们混在一起。
3. **理解错误**：资料措辞复杂（例外条款、否定、条件嵌套），模型读错；或者数字、单位抄错。
4. **过度推断**：资料只覆盖了问题的一部分，模型把剩下的部分「脑补」完整。

因此除了保证检索质量，还需要：提示词约束「只依据资料」、逐句标注引用并校验、用忠实度等指标单独评估生成环节。

## 计算题

<a name="RAG-BASE-006"></a>

### RAG-BASE-006　进阶 · 考频 ★★

某知识库共 12 万 token。输入价格按 2.5 美元 / 百万 token 计，Prompt Caching 命中时缓存读取按原价的 1/10 计费；日均 2 万次提问。比较两种方案每天的**输入成本**（忽略问题本身、系统提示词与输出 token，也忽略缓存写入的额外费用）：

- 方案一：每次把整个知识库放进上下文，分别按「不缓存」和「全部命中缓存」两种情况计算；
- 方案二：RAG，每次放入 6 块、每块 400 token。

<details>
<summary>答案与解析</summary>

**答案：方案一不缓存约 6,000 美元/天、全部命中缓存约 600 美元/天；方案二约 120 美元/天；方案一分别是方案二的 50 倍和 5 倍**

**解析：**

**方案一（长上下文）**
- 每次输入：$1.2\times10^5$ token $\times2.5$ 美元 $/10^6=0.30$ 美元；
- 不缓存：$0.30\times20000=6000$ 美元/天；
- 全部命中缓存：$0.30\times\frac{1}{10}\times20000=600$ 美元/天。

**方案二（RAG）**
- 每次输入：$6\times400=2400$ token，$2400\times2.5/10^6=0.006$ 美元；
- 每天：$0.006\times20000=120$ 美元。

**比值**：$6000/120=50$；$600/120=5$。

结论：即使缓存全部命中，长上下文的输入成本仍是 RAG 的 5 倍；而且每次都要处理 12 万 token，首 token 延迟也明显更高（缓存能缓解但不能消除）。反过来，如果日均只有几十次请求，两者每天只差几美元，此时长上下文「不用建索引、不怕漏召回」的简单性可能更有价值。所以选型要把请求量、资料规模和效果放在一起算。

<sub>考点：RAG与微调与长上下文</sub>

</details>

<a name="RAG-BASE-026"></a>

### RAG-BASE-026　挑战 · 考频 ★★

某 RAG 系统一次请求的各环节耗时如下：

- 查询改写（调用一次 LLM）：300 ms；
- 稠密路：问题向量化 20 ms + 向量检索 15 ms；BM25 路：25 ms。两路**并行**执行；
- RRF 融合：1 ms；
- Cross-Encoder 重排 100 个候选：每批 25 个，每批 40 ms，各批**串行**执行；
- 生成：首 token 时间（TTFT）400 ms，之后每个 token 间隔（TPOT）25 ms，回答共 200 个 token，生成总耗时按 $\text{TTFT}+(\text{输出 token 数}-1)\times\text{TPOT}$ 计。

忽略网络与其他开销，求：(1) 流式输出时，用户看到第一个字的时间；(2) 完整回答的时间；(3) 去掉查询改写、并把重排候选减为 50 个后，首字时间是多少？

<details>
<summary>答案与解析</summary>

**答案：(1) 896 ms；(2) 5,871 ms（约 5.9 s）；(3) 516 ms**

**解析：**

**(1) 首字时间** = 改写 + 召回（两路取较慢者）+ 融合 + 重排 + TTFT
- 召回：$\max(20+15,\ 25)=35$ ms；
- 重排：$\lceil100/25\rceil=4$ 批，$4\times40=160$ ms；
- 合计：$300+35+1+160+400=896$ ms。

**(2) 完整回答**：首字之后还有 199 个 token，$199\times25=4975$ ms；$896+4975=5871$ ms。

**(3) 优化后的首字时间**：重排 $\lceil50/25\rceil=2$ 批，共 80 ms；$35+1+80+400=516$ ms，降低约 42%。

**启示**：
- 首字延迟里，LLM 改写（300 ms）和重排（160 ms）占了一半以上，而向量检索本身只有十几毫秒；
- 完整回答的时间由解码（约 5 s）主导，要缩短它，得限制输出长度或选用解码更快的模型；
- 两路召回并行后只取较慢的一路，若改成串行会多出 25 ms；
- 去掉改写、减少重排候选都可能损失效果，要在评测集上确认召回率与正确率不下降（例如只在多轮追问时才触发改写）。

<sub>考点：端到端延迟</sub>

</details>

## 编程题

<a name="RAG-BASE-024"></a>

### RAG-BASE-024　进阶 · 考频 ★★

线上 bad case 归因是 RAG 迭代的起点。实现 `attribute(cases, k)`，对一批样本逐条归因，返回 `collections.Counter`。每个 case 是一个字典：

- `gold`：包含正确答案的块 id 集合（可能是 set 或 list）；知识库里没有答案时为空；
- `ranked`：检索链路（召回 + 融合 + 重排）最终输出的块 id 列表，按相关性降序；
- `answer_ok`：最终回答是否正确（知识库里没有答案时，正确拒答也算正确）。

只有 `ranked` 的前 `k` 块会放进提示词。按以下**顺序**判断，命中第一条即停止：

1. `answer_ok` 为真 → `'ok'`；
2. `gold` 为空（知识库缺失，且没有正确拒答）→ `'missing'`；
3. `gold` 中没有任何块出现在 `ranked` 中 → `'not_retrieved'`；
4. `gold` 中有块出现在 `ranked` 中，但没有任何一块在前 `k` 块里 → `'ranked_out'`；
5. 其余情况（正确块已在前 `k` 块中，回答仍错）→ `'not_used'`。

<details>
<summary>答案与解析</summary>

**参考实现：**

```python
from collections import Counter


def attribute(cases, k):
    counts = Counter()
    for case in cases:
        gold, ranked = set(case["gold"]), list(case["ranked"])
        if case["answer_ok"]:
            label = "ok"
        elif not gold:
            label = "missing"
        elif not gold & set(ranked):
            label = "not_retrieved"
        elif not gold & set(ranked[:k]):
            label = "ranked_out"
        else:
            label = "not_used"
        counts[label] += 1
    return counts
```

**测试用例：**

```python
cases = [
    {"gold": {1}, "ranked": [1, 2, 3], "answer_ok": True},
    {"gold": set(), "ranked": [4, 5], "answer_ok": False},
    {"gold": set(), "ranked": [], "answer_ok": True},           # 正确拒答
    {"gold": {9}, "ranked": [1, 2, 3, 4], "answer_ok": False},
    {"gold": {3}, "ranked": [1, 2, 3, 4], "answer_ok": False},
    {"gold": {2, 7}, "ranked": [5, 2, 6], "answer_ok": False},  # 多个正确块，命中一个即可
    {"gold": [6, 8], "ranked": [1, 2, 6, 8], "answer_ok": False},
]
c = attribute(cases, 2)
assert isinstance(c, Counter)
assert c == Counter({"ok": 2, "missing": 1, "not_retrieved": 1, "ranked_out": 2, "not_used": 1}), c
# 碰巧答对也算 ok：answer_ok 要最先判断
assert attribute([{"gold": {7}, "ranked": [], "answer_ok": True}], 3) == Counter({"ok": 1})
# k 大于 ranked 长度、k 为 0、空输入
one = [{"gold": {5}, "ranked": [5], "answer_ok": False}]
assert attribute(one, 10) == Counter({"not_used": 1})
assert attribute(one, 0) == Counter({"ranked_out": 1})
assert attribute([], 5) == Counter()
```

**解析：**

**思路**：归因顺序就是正确资料在链路中「走了多远」：知识库里有没有 → 召回里有没有 → 进没进上下文 → 模型用没用对。必须按这个顺序判断：如果先判断 `not_used`，一条根本没召回的样本也可能被误归到生成问题上。

**用法**：对抽样的 bad case 跑一遍，就得到各环节的占比，优先修占比高、修复成本低的环节：
- `missing` 多：补充知识，或加强拒答（分数阈值、提示词允许「不知道」）；
- `not_retrieved` 多：查解析与切块、加混合检索、做查询改写或微调 Embedding；
- `ranked_out` 多：查重排模型（领域适配、长块截断），或调整 k 与候选数；
- `not_used` 多：减少噪声块、调整资料顺序、加强引用约束与校验。

**易错点**：`gold` 可能有多个块，只要有一块满足条件即可，所以用集合交集；`k` 大于 `ranked` 长度时切片不会越界；`answer_ok` 要最先判断。

<sub>考点：失败模式分析</sub>

</details>

## 简答题

<a name="RAG-BASE-012"></a>

### RAG-BASE-012　进阶 · 考频 ★★

Naive RAG 有哪些典型缺陷？Advanced RAG 与 Modular RAG 分别是如何改进的？请结合具体技术说明。

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **Naive RAG 的流程**：检索一次 → 拼接 top-k → 生成，没有任何纠错环节。
2. **典型缺陷**：
   - 检索侧：问题与文档用词不一致导致漏召回（词汇鸿沟）；块切得不好导致语义不完整；召回结果噪声多、排序不准，重复内容占满 top-k；
   - 生成侧：资料不相关时仍然硬答，或不忠实于资料；多份资料冲突时混用；
   - 流程侧：一次检索解决不了多跳、比较、汇总类问题。
3. **Advanced RAG**：在固定流水线的前后加优化。
   - 检索前：查询改写、多查询、问题分解、HyDE；索引侧优化切块，补充标题与元数据；
   - 检索后：Cross-Encoder 重排、阈值截断、MMR 去冗余、上下文压缩。
4. **Modular RAG**：把各环节做成可替换、可编排的模块。
   - 新模块：路由（按意图选知识库、SQL 或网页搜索）、记忆、融合等；
   - 新流程：迭代检索、递归检索、自适应检索（先判断要不要检索），可以按问题类型动态组合。
5. **取舍**：链路越复杂，延迟、成本和调试难度越高。实践中先做好 Advanced RAG 基线，用评测证明单次检索不够时，再引入更灵活的编排。

**评分要点（共 10 分）：**

- 说清 Naive RAG 在检索、生成、流程三方面的缺陷（3 分）
- 说明 Advanced RAG 的检索前、检索后优化并举出具体技术（3 分）
- 说明 Modular RAG 的模块化与流程编排特征（如路由、迭代检索）（3 分）
- 提到复杂度与延迟、成本之间的取舍（1 分）

**讲解：**

**常见失分点**：把三者说成「模块越来越多」，讲不出 Modular 的本质是可编排；把 GraphRAG、Agentic RAG 混进 Advanced RAG；只罗列名词，不说明每种改进针对的是 Naive RAG 的哪个缺陷。

<sub>考点：Naive与Advanced与Modular RAG</sub>

</details>

### RAG-BASE-021　基础 · 考频 ★★★

请按顺序说出 RAG 在线链路的主要步骤。如果分别省掉其中的「查询改写」「多路召回与融合」「重排」「引用校验」，各会出现什么典型问题？

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **在线链路**：查询理解（改写、路由、抽取过滤条件）→ 多路召回（稠密 + BM25）→ 融合（如 RRF）→ 重排（Cross-Encoder）→ 带引用的生成（资料编号、阈值拒答）→ 引用校验与日志记录。
2. **省掉查询改写**：多轮对话中的追问（如「那去哪申请？」）缺少主语和上下文，直接检索几乎召回不到正确资料；口语、错别字、缩写也会导致漏召回。
3. **只用单路召回、不做融合**：只用向量检索时，错误码、型号等精确词项容易匹配错；只用 BM25 时，换种说法就搜不到（词汇鸿沟）。
4. **省掉重排**：召回阶段的双塔只比较压缩后的单个向量，排序粗糙；正确的块可能排在第 8 名而被 top-5 截断，噪声块却进了上下文。
5. **省掉引用校验**：模型可能编造引用编号、张冠李戴，或引用的资料并不支持这句话；用户以为有出处就可信，风险反而更大。

**评分要点（共 10 分）：**

- 按正确顺序列出在线链路的主要步骤（3 分）
- 说明省掉查询改写的后果（多轮指代、口语导致漏召回）（2 分）
- 说明不做多路召回与融合的后果（精确匹配或词汇鸿沟）（2 分）
- 说明省掉重排的后果（排序粗、正确块被截断）（2 分）
- 说明省掉引用校验的后果（引用编造、引用不支持结论）（1 分）

**讲解：**

**常见失分点**：把离线步骤（切块、向量化）混进在线链路；只背流程名词，说不出每一步省掉后的具体后果；以为有了重排就不需要多路召回（重排只能调整顺序，找不回漏召回的文档）。

<sub>考点：标准链路、离线索引与在线检索</sub>

</details>

<a name="RAG-BASE-022"></a>

### RAG-BASE-022　进阶 · 考频 ★★

一次 RAG 请求的端到端延迟由哪些部分构成？通常哪些部分是大头？请给出至少 5 种降低延迟的手段，并说明各自的代价。

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **构成**：
   - 查询理解：改写或路由通常要调用一次 LLM，几百毫秒量级；
   - 召回：问题向量化（几到几十毫秒）、ANN 检索与 BM25（通常毫秒到几十毫秒），多路之间可以并行；
   - 融合：RRF 等，耗时可忽略；
   - 重排：Cross-Encoder 对几十到上百个候选打分，耗时与候选数、块长度成正比，常在几十到几百毫秒；
   - 生成：首 token 时间（TTFT，由 prefill 决定，随输入上下文长度增长）+ 逐 token 解码时间（约为 TPOT × 输出长度）；
   - 其他：网络、权限过滤、引用校验等前后处理。
2. **大头**：通常是生成（尤其输出较长时），其次是查询改写这类额外的 LLM 调用和重排。流式输出时，用户感知主要取决于首字延迟。
3. **优化手段与代价**：
   - 多路召回并行执行：实现稍复杂，几乎没有效果损失；
   - 按需触发查询改写（只在多轮追问或首次检索分数偏低时启用），或改用小模型：可能漏掉需要改写的情况；
   - 减少重排候选数、截短块、蒸馏或量化重排模型：可能损失排序质量，需要在评测集上验证；
   - 减少送入生成的块数和块长度（缩短 prefill）：可能丢失证据；
   - 流式输出：不缩短总时长，但大幅改善首字体验；
   - 缓存：对热门问题做精确或语义缓存，用 Prompt Caching 复用固定的系统提示词前缀；要处理权限维度与知识更新后的失效；
   - 限制输出长度、选用更快的生成模型：可能影响回答的完整度和质量。

**评分要点（共 10 分）：**

- 完整列出改写、召回、重排、生成（TTFT 与解码）等构成部分（3 分）
- 指出生成通常是大头，并区分首字延迟与总时长（2 分）
- 给出至少 5 种优化手段（3 分）
- 说明各手段的代价或风险（2 分）

**讲解：**

**常见失分点**：认为向量检索是主要瓶颈（ANN 通常只要毫秒级）；忘了查询改写本身就是一次 LLM 调用；不区分首字延迟和总时长（缩短输出只影响后者）；只说「加机器」「换更快的模型」，不逐个环节分析。

<sub>考点：端到端延迟</sub>

</details>

<a name="RAG-BASE-033"></a>

### RAG-BASE-033　进阶 · 考频 ★★

面试官问：「Claude Code 这类编码 Agent 搜代码为什么用 grep，而不用向量 RAG？是不是向量 RAG 过时了？」请从实时性、精确匹配、语义召回、成本与时延、工程与安全五个方面比较 agentic search 与向量 RAG，并说明两者如何组合。

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **实时性**：agentic search 现场读取源数据，没有索引过期问题；向量 RAG 依赖离线索引，数据一变就要增量更新，有同步延迟。代码仓库每天大量提交，更适合前者。
2. **精确匹配**：函数名、错误码、配置项需要逐字命中，grep 与正则最可靠；向量检索容易把 E1024 与 E1025 当成「相似」。
3. **语义召回**：用户的描述与原文用词不同（「页面白屏」对应「render 抛异常」）时，向量检索更强；agentic search 只能靠模型反复猜关键词，可能漏召回。
4. **成本与时延**：向量 RAG 一次检索几十毫秒、上下文可控，但有建索引和维护向量库的成本；agentic search 不用建索引，却要多轮「搜索—阅读—再搜索」，时延与 token 开销更高，输出不加限制还会把上下文撑满。
5. **工程与安全**：向量索引是数据的副本，要额外同步权限、处理数据外流与索引存储；agentic search 以调用者身份访问源文件，权限沿用源系统，部署简单。Claude Code 团队提到早期用过本地向量库，后来改用 agentic search，理由正是效果更好、更简单，没有安全、隐私、过期与可靠性问题。
6. **组合方式**：
   - 把语义检索也做成 Agent 的一个工具，与 grep、读文件并列，由模型按问题选择；Cursor 2025-11 的 A/B 实验显示，语义检索与 grep 组合效果最好，大型代码库上收益更明显；
   - 按查询路由：含标识符、报错文本的走 grep 或关键词检索，概念性问题走语义检索；
   - 大规模、变化慢的知识库用 RAG 做第一跳召回，Agent 再用 grep、读原文核实细节。
7. **结论**：向量 RAG 没有过时，只是不再是唯一选项。语料小、变化快、标识符多、能现场读取的场景（如单个代码仓库）倾向 agentic search；语料大、口语化查询多、对时延敏感的场景（如企业知识库）仍以混合检索 RAG 为主。

**评分要点（共 10 分）：**

- 实时性与精确匹配两方面的对比正确（2 分）
- 语义召回、成本与时延两方面的对比正确（3 分）
- 说明索引副本带来的权限、安全问题，或引用 Claude Code、Cursor 的实践（2 分）
- 给出至少两种组合方式，并说明按场景如何选择（3 分）

**讲解：**

**常见失分点**：把问题回答成「grep 比向量检索好」或「向量检索比 grep 好」的二选一；忽视 agentic search 的多轮 token 开销与时延；没意识到索引是数据副本带来的同步与权限问题；不知道两者可以作为工具同时提供给 Agent。

注意时效：各家产品的做法仍在变化（本题依据的是 2025-09 至 2026-01 的公开资料），答题时讲清取舍的依据比背具体产品的选择更重要。

<sub>考点：Agentic Search与grep、RAG与微调与长上下文　｜　出处：Anthropic: Effective context engineering for AI agents（2025-09-29）；Boris Cherny 在 X 上的说明 https://x.com/bcherny/status/2017824286489383315；Cursor: Improving agent with semantic search（2025-11-06）https://cursor.com/blog/semsearch</sub>

</details>

## 场景分析题

<a name="RAG-BASE-020"></a>

### RAG-BASE-020　挑战 · 考频 ★★★

请为下列四个需求分别选择方案（RAG、微调、长上下文直接放入，或它们的组合），并说明理由与需要注意的风险：

1. 律所希望模型基于近 20 年、约 3 亿 token 的判例库回答问题，每个结论都要给出判例出处；
2. 某 App 希望客服回复统一成品牌口吻，并稳定输出 `{"intent": ..., "reply": ...}` 格式的 JSON，业务知识很少变化，已经写在系统提示词里；
3. 律师每次上传两份各约 4 万 token 的合同，要求逐条比对差异并给出修改建议；
4. 医院希望模型依据院内诊疗规范（每月更新）回答医生的问题，回答需引用原文，并采用医生习惯的简洁格式。

<details>
<summary>答案与解析</summary>

**参考答案：**

1. **判例库：RAG（混合检索为主）**。
   - 理由：3 亿 token 远超任何上下文窗口；要求给出出处；判例持续新增。
   - 要点：案号、法条编号等精确词项靠 BM25，案情描述靠向量，两路融合后重排；元数据带法院、年份、案由，支持过滤。
   - 风险：判例之间观点可能冲突，生成时要标注出处并提示差异；漏召回会直接导致结论片面。
2. **客服口吻与 JSON：微调（或少样本 + 约束解码）**。
   - 理由：这是行为问题，知识很少变化，不需要检索。
   - 要点：先试少样本提示 + 结构化输出（JSON Schema 约束）；稳定性或成本不达标时，再用几千条高质量对话做 SFT / LoRA。
   - 风险：训练数据风格不一致会学偏；仍要保留格式校验与重试。
3. **合同比对：长上下文直接放入**。
   - 理由：两份合同共约 8 万 token，放得进主流长上下文模型；任务需要逐条通读、对齐，切块检索反而会丢掉条款之间的对应关系；每份合同只用一次，没有建索引的价值。
   - 要点：先按条款结构化解析，再让模型逐条对齐；输出时引用条款编号便于核对。
   - 风险：长输入的中间信息利用率会下降，可以按章节分段比对后再汇总。
4. **诊疗规范：RAG + 微调（或提示词）组合**。
   - 理由：规范每月更新、要求引用，是知识问题，用 RAG；简洁格式是行为问题，用提示词或微调固化。
   - 要点：索引中记录版本与生效时间，默认只检索现行版本；资料不足时拒答。
   - 风险：医疗场景对错误容忍度极低，需要引用校验与人工审核兜底。

**评分要点（共 10 分）：**

- 需求 1 选 RAG，并提到规模、出处、精确匹配或混合检索等理由（2.5 分）
- 需求 2 选微调或少样本加约束解码，并说明这是行为问题（2.5 分）
- 需求 3 选长上下文，并说明数据量放得下、需要通读比对、一次性使用（2.5 分）
- 需求 4 选 RAG 与微调或提示词的组合，并提到版本管理或引用要求（2.5 分）

**讲解：**

**常见失分点**：所有需求都答 RAG；把合同比对也切块检索，丢失条款间的对应关系；需求 4 只答 RAG 而忽略格式要求，或只答微调而忽略每月更新与引用；只给结论不给理由。判断主线：知识问题（新、私、多、要出处）→ RAG；行为问题（格式、风格）→ 微调；资料少、一次性、要通读 → 长上下文。

<sub>考点：RAG与微调与长上下文</sub>

</details>

<a name="RAG-BASE-025"></a>

### RAG-BASE-025　挑战 · 考频 ★★★

某公司的制度问答 RAG 上线一个月，端到端正确率只有 62%。你从答错的样本中随机抽取 200 条做归因，结果如下：

- 40 条：知识库里根本没有相关文档，但模型给出了看似合理的具体答案；
- 50 条：包含答案的块不在召回的 top-100 中。其中约一半来自扫描版 PDF，另一半是用户用口语提问、文档用正式术语表述；
- 60 条：包含答案的块在 top-100 中，但重排后不在送入模型的前 5 块里；
- 50 条：包含答案的块就在前 5 块中，但回答错误，多为新旧两版制度混用或数字抄错。

请分析每类问题的可能原因，给出改进优先级与具体方案，并说明如何验证改进效果。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 归因与原因**
- **知识缺失且未拒答（20%）**：知识库覆盖不全；同时系统缺少拒答机制，模型在没有依据时编造答案。这类错误看起来很可信，对制度问答伤害最大。
- **漏召回（25%）**：
  - 扫描件：没做 OCR 或 OCR 质量差，文本缺失、错字，向量和 BM25 都匹配不上；
  - 口语与术语不一致：词汇鸿沟。只用 BM25 时尤其明显；只用向量时，可能是 Embedding 模型不适配领域。
- **排序截断（30%）**：重排模型可能不适配领域；长块超过重排模型的最大输入长度（如 512 token）被截断，关键内容恰好在后半段；也可能 top-5 偏少。
- **生成问题（25%）**：新旧版本同时被召回，模型混用；提示词缺少「只依据资料、注意版本」的约束；数字抄错说明缺少引用校验。

**2. 优先级（按「占比 × 风险 ÷ 修复成本」）**
1. 先加拒答兜底：重排分数阈值（在评测集上标定）+ 提示词允许「不知道」。成本低、风险收益最大。同时把缺失问题汇总给知识运营团队补文档。
2. 修排序截断（占比最高）：检查块长度与重排模型最大长度是否匹配；在评测集上比较不同重排模型，考虑领域微调；评估 top-5 改为 top-8 的收益与成本。
3. 修漏召回：扫描件重新做版面分析 + OCR，低置信度页人工复核；加入 BM25 与向量的混合检索，对口语问题做查询改写；必要时用业务数据微调 Embedding。
4. 修生成：在索引侧做版本管理，默认只检索现行有效版本（根本解法）；提示词要求逐句引用，并用引用校验拦截数字不一致的句子。

**3. 验证**
- 分段指标：召回段看 Recall@100，排序段看前 5 块的命中率，生成段看忠实度，无答案问题看拒答准确率；
- 把这 200 条连同归因类型加入回归集，每次改动都跑一遍，确认对应类别的错误下降、其他类别不回退；
- 上线后用 A/B 实验观察端到端正确率、点踩率与转人工率。

**评分要点（共 10 分）：**

- 正确解读四类问题分别对应知识缺失、召回、排序、生成四个环节（2 分）
- 对每类给出合理的具体原因（如 OCR、词汇鸿沟、重排截断、版本混用）（2 分）
- 给出有理由的优先级排序（如拒答兜底优先、占比最高的排序问题优先）（2 分）
- 每类都给出可执行的改进方案（2 分）
- 给出分段指标与回归集等验证方法（2 分）

**讲解：**

**常见失分点**：不做归因就直接「换更大的模型」；把四类问题都归到生成上，只改提示词；忽略「知识缺失却不拒答」的风险；给了方案却没有分段指标去验证，无法证明是哪一步带来了提升。

<sub>考点：失败模式分析、幻觉与可溯源</sub>

</details>

<a name="RAG-BASE-034"></a>

### RAG-BASE-034　挑战 · 考频 ★★

公司要做一个「研发助手」，回答三类问题：

1. 代码相关：约 2,000 个仓库，每天几千次提交，问题如「`OrderService` 的超时重试在哪里配置」「这个报错是哪段代码抛的」；
2. 线上排障：日志每天 TB 级，按服务和时间分区、保留 7 天，问题如「昨晚 23 点支付服务 5xx 突增是什么原因」；
3. 研发规范与设计文档：约 5 万篇 Wiki，用户多用口语提问，如「新服务上线要走哪些审批」。

请分别选择检索方案（向量 RAG、agentic search、关键词或结构化检索，或它们的组合），说明理由、关键设计和主要风险。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 代码：以 agentic search 为主，辅以代码搜索服务与语义检索**
- 理由：标识符与报错文本需要精确匹配；提交频繁，向量索引容易过期；仓库权限要与代码托管系统保持一致。
- 设计：2,000 个仓库不可能都 clone 到本地逐个 grep，需要一个随提交增量更新的代码搜索服务（支持正则或 trigram 的关键词索引），作为 Agent 的 search_code 工具；配合符号跳转（定义、引用）、读文件（按行号分段）和仓库地图；对只描述现象、没有关键词的问题，增加语义检索工具作为补充。
- 风险：检索结果过多撑爆上下文（限制返回条数、要求先缩小范围）；按用户身份做仓库级权限过滤；多轮探索的时延与成本需要设上限。

**2. 日志：结构化检索与聚合，由 Agent 生成查询**
- 理由：TB 级、快速滚动、单行语义价值低，做向量化成本高、意义小；直接 grep 全量日志太慢。
- 设计：使用已有的日志平台（按服务、时间、级别、trace id 建索引的检索或列式分析系统），把「按条件查询」「按字段聚合统计」「按 trace id 拉调用链」做成工具；Agent 先确定时间窗与服务，看错误码分布与突变点，再取少量样例日志，结合发布记录、监控指标归因。
- 风险：工具要返回聚合结果和少量样例，而不是原始日志全文；日志中的个人信息与密钥要脱敏；要防止查询范围过大拖垮日志集群；归因结论要附上证据（具体查询与样例）。

**3. Wiki：混合检索 RAG**
- 理由：问题口语化，文档用词规范，需要语义召回；语料规模中等、变化不频繁，适合离线索引；回答需要引用出处。
- 设计：按标题层级切块，向量 + BM25 混合召回，RRF 融合后用 Cross-Encoder 重排；文档更新时增量重建；块的元数据带上权限、版本与更新时间，检索时按用户权限过滤；生成时附带引用。复杂问题可以让 Agent 多轮检索。
- 风险：过期文档与新文档冲突（标注版本、优先新版）；权限同步延迟导致越权；缺少评测集，需要从真实提问中构建。

**4. 统一入口**：先做意图路由（代码 / 日志 / 文档），一个问题涉及多类时由 Agent 依次调用；为每类问题分别建立评测集，跟踪命中率、正确率、时延与成本。

**评分要点（共 10 分）：**

- 代码场景选 agentic search（或代码搜索服务 + 语义检索补充），理由涉及精确匹配、实时性、权限（2 分）
- 指出大规模代码仍需随提交更新的关键词或代码搜索索引，而不是逐仓库 grep（1 分）
- 日志场景选结构化检索与聚合，说明不适合向量化或全量 grep 的原因（2 分）
- Wiki 场景选混合检索 RAG，含重排、增量更新、权限过滤与引用（2 分）
- 对各场景给出风险控制，如输出截断、脱敏、查询范围限制、版本冲突（2 分）
- 提到统一路由与分场景评测（1 分）

**讲解：**

**常见失分点**：一刀切地全部用向量 RAG，或全部用 grep；以为 agentic search 等于「完全不需要索引」，忽视了大规模代码与日志仍需关键词或结构化索引；日志场景让模型直接读原始日志全文；忽视权限与脱敏。

## 系统设计题

<a name="RAG-BASE-030"></a>

### RAG-BASE-030　挑战 · 考频 ★★★

你负责为一家 2 万名员工的公司设计「IT 与 HR 知识库问答助手」。已知：

- 文档约 5 万份（PDF、Word、Wiki 页面，其中部分为扫描件），平均每份约 5,000 token，每天约有 500 份新增或修改；
- 部分文档仅限特定部门查看；
- 日均约 3 万次提问，要求流式输出且 P95 首字延迟 < 2 s；回答必须标注出处，资料不足时拒答。

请给出整体方案：为什么选 RAG（而不是微调或长上下文）、离线与在线链路设计、关键参数与容量估算、首字延迟预算，以及主要风险。

<details>
<summary>答案与解析</summary>

**参考答案：**

**1. 选型**：知识量约 2.5 亿 token，远超上下文窗口；每天 500 份变更；要求出处和部门权限。这些都是知识问题，选 RAG。生成模型如需固定话术或格式，再考虑轻量微调。

**2. 离线链路**
- 解析：版面分析恢复阅读顺序，去掉页眉页脚；表格转 Markdown 或按行线性化；扫描件做 OCR，低置信度页标记复核；
- 切块：递归切分 + 按标题结构，256～512 token、10%～20% 重叠，块开头拼上标题路径；
- 元数据：来源、标题路径、页码、版本、生效时间、部门 ACL、内容哈希；
- 索引：稠密向量（HNSW）+ BM25 倒排；按内容哈希增量更新，删除走软删除。

**3. 在线链路**：多轮追问时用小模型改写 → 带 ACL 前过滤的稠密 + BM25 并行召回（各 top-50）→ RRF 融合 → Cross-Encoder 重排保留 top-5 → 分数低于阈值则拒答 → 资料编号、逐句引用生成 → 引用校验、记录日志与反馈。

**4. 容量估算**
- 语料 $5\times10^4\times5000=2.5\times10^8$ token；块 512、重叠 64（步长 448），约 $2.5\times10^8/448\approx5.6\times10^5$ 块；
- 1,024 维 float32 向量每个 4 KB，共约 2.3 GB；HNSW 邻接表（M = 32，底层 64 个 4 字节 id）约 0.14 GB；单机内存即可容纳；
- 每天 500 份变更，约 5,600 块需要重新向量化，离线开销很小；
- 日均 3 万次，按 8 小时工作时间集中、高峰系数 3 估算，峰值约 3 QPS，规模不大。

**5. 首字延迟预算（P95 < 2 s）**
- 改写（按需触发，小模型）约 200 ms；向量化 + ANN 与 BM25 并行，约 50 ms；RRF 约 1 ms；重排 50 个候选约 150 ms；
- 生成 TTFT：5 块 × 约 500 token ≈ 2.5K token 输入，约 300～500 ms；
- 合计约 0.7～0.9 s，为网络与排队留出余量。

**6. 风险与对策**
- 解析质量（扫描件、表格）决定下限：抽样检查解析结果，建立解析质量监控；
- 权限泄露：ACL 在检索阶段前过滤，缓存键也要包含权限维度；
- 新旧版本混用：版本元数据 + 默认只检索有效版本；
- 幻觉：阈值拒答 + 引用校验；
- 效果评估：建立分类型评测集（事实、多跳、无答案、权限），分段看 Recall@k、忠实度、拒答准确率，配合线上点踩与转人工的反馈闭环。

**评分要点（共 10 分）：**

- 给出选 RAG 的理由，并与微调、长上下文对比（1 分）
- 离线链路完整：解析（含扫描件与表格）、切块、元数据、混合索引、增量更新（2 分）
- 在线链路完整：改写、带权限过滤的混合召回、融合、重排、拒答、引用生成与校验（2 分）
- 给出语料规模、块数、向量存储与 QPS 等量级估算（2 分）
- 给出合理的首字延迟预算，并说明并行、按需触发等手段（2 分）
- 指出权限、版本、解析质量、评测等主要风险与对策（1 分）

**讲解：**

**常见失分点**：只画「切块 → 向量库 → LLM」三个框；不做任何量级估算；权限靠提示词控制或检索后再过滤；忽略扫描件与表格的解析；延迟预算只算生成、不算改写和重排；没有评测与反馈闭环，无法证明系统可用。

<sub>考点：标准链路、离线索引与在线检索、端到端延迟、RAG与微调与长上下文</sub>
